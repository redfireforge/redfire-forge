WebSocket Workflow Nodes

The Workflow Runner's node palette includes four WebSocket-specific nodes. In the palette, search for WS to filter them.

NodePalette testidPurpose
WS Connectwf-palette-block-wsConnectOpen a WebSocket connection and assign it a named connection ID for later nodes to reference
WS Sendwf-palette-block-wsSendSend a message over a named connection
WS Receivewf-palette-block-wsReceiveWait for a message matching a pattern; capture it into a variable
WS Triggerwf-palette-block-wsTriggerTrigger the workflow when a specific WS message arrives (event-driven entry point)

WS Trigger Configuration

WS Trigger is an event-driven start node — the workflow begins when a message arrives on the monitored connection matching the trigger condition. It replaces the standard Start node when building reactive workflows.

FieldDescription
Connection IDConnection to monitor for trigger messages

Capture AsVariable name for the triggering message payload

Walkthrough: Request–Response Workflow

Build a workflow that connects to an echo server, sends a JSON request, waits for the echoed response, and asserts the payload is correct.

1
Open the Workflow Runner. Create a new workflow. On the canvas, drag from the palette:
  • Start node (auto-added)
  • WS Connect node
  • WS Send node
  • WS Receive node
  • Assert node
  • End node (auto-added)
2
Wire them in sequence: Start → WS Connect → WS Send → WS Receive → Assert → End.
3
Configure WS Connect:
  • URL: ws://localhost:9876
  • Connection ID: echo
4
Configure WS Send:
  • Connection ID: echo
  • Payload: {"action":"ping","timestamp":"{{$timestamp}}"}
5
Configure WS Receive:
  • Connection ID: echo
  • Match: jsonPath: $.action === "ping"
  • Capture As: response
  • Timeout: 5000
6
Configure Assert:
  • Expression: {{response.action}} === "ping"
  • Message: Echo action mismatch
7
Click Run Workflow. The workflow opens a WS connection, sends the ping, receives the echoed response, and asserts. All steps turn green if successful.

Event-Driven Workflow (WS Trigger)

1
Replace the Start node with a WS Trigger node. Configure it:
  • Connection ID: listener (connect a separate WS Connect node first, or use an already-open connection)
  • Match: jsonPath: $.type === "alert"
  • Capture As: alertMessage
2
Wire downstream nodes: WS Trigger → Assert → HTTP Post (notify team) → End.
3
Run the workflow. It sits in Waiting for trigger state until a message matching $.type === "alert" arrives on the listener connection. When it does, the workflow continues automatically.

CI Usage with Mock Server

For automated test pipelines, combine the mock server with WS workflow tests:

# 1. Start mock server (headless CLI)
npx redfire ws-mock --port 9880 --rules ./mock-rules.json

# 2. Run workflow tests
npx redfire run-workflow ./workflows/ws-ping-assert.json --env ci

Both commands exit cleanly after completion, making them suitable for CI scripts.

Practice Exercises

  1. Build the request–response workflow from the walkthrough above. Run it. Confirm all steps pass.
  2. Modify the WS Receive step to use Timeout: 500 ms. Run again but ensure the mock server is stopped so no response arrives. Confirm the step times out and the workflow fails with a clear error.
  3. Add a second WS Connect → WS Send → WS Receive chain to the same workflow (using connection ID echo2). Wire both chains in parallel (join them with a Merge node before Assert). Run the workflow and confirm both connections operate concurrently.
  4. Build an event-driven workflow using WS Trigger. Use the mock server's broadcast button to trigger it. Confirm the workflow fires when the broadcast message matches the trigger condition.
