How WebSocket Auth Works

Unlike HTTP requests, WebSocket frames do not carry per-frame headers. Authentication is injected during the initial HTTP Upgrade handshake — the one-time HTTP request that promotes the connection to a WebSocket. Any headers or query parameters you configure in the Auth and Headers tabs are sent on this upgrade request and never again.

⚠️ Browser limitation Standard browser WebSocket APIs (new WebSocket(url)) cannot set custom HTTP headers. RedfireForge routes connections through its Express proxy backend, which adds the headers server-side. This transparent proxying applies to all auth types.

The Auth Tab

Click the Auth left-tab (left-tab-auth) to configure authentication. The type selector (ws-auth-type-trigger) shows the current auth type. Click it to open the dropdown.

Auth Types

None (default)

No authentication headers are added. Select this when the server has no auth requirement, or when you are providing auth as a query parameter instead.

Bearer Token

1
Click the auth type trigger → select Bearer (ws-auth-type-opt-bearer).
2
A Token input field appears. Enter your JWT or opaque token, e.g.:
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...
3
On connect, the studio adds the header:
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...
4
To use an environment variable, type the variable name in double braces: {{AUTH_TOKEN}}. The variable is resolved at connection time from the active environment.

API Key

1
Click the auth type trigger → select API Key (ws-auth-type-opt-api-key).
2
Two fields appear: Header Name and Header Value. Common combinations:
Header NameHeader Value
X-API-Keymy-secret-key
x-api-key{{API_KEY}}
3
The specified header is added to the upgrade request exactly as entered.

Basic Auth

1
Click the auth type trigger → select Basic (ws-auth-type-opt-basic).
2
Enter Username and Password fields.
3
RedfireForge encodes these as base64(username:password) and adds:
Authorization: Basic dXNlcjpwYXNzd29yZA==
⚠️ Basic auth security Basic auth sends credentials in every connection upgrade. Always pair with wss:// TLS to prevent credential exposure in transit.

Custom Headers

The Headers left-tab (left-tab-headers) lets you add arbitrary key-value header pairs to the upgrade request, independently of the auth type. This is useful for:

  • Tenant or workspace identifiers (X-Tenant-ID: org-42)
  • Correlation IDs (X-Correlation-ID: {{$guid}})
  • Protocol sub-negotiation (Sec-WebSocket-Protocol: chat)

Adding a Header

1
Click the Headers tab. Click + Add Header.
2
Enter a key, e.g. X-Tenant-ID, and a value, e.g. tenant-001.
3
Add as many rows as needed. Click the trash icon to remove a row. Headers are sent in addition to the Auth tab headers.

Using Environment Variables in Auth

All auth and header value fields support {{variable}} interpolation from the active RedfireForge environment. This lets you keep credentials out of saved connection files and rotate them by updating the environment.

SyntaxMeaning
{{AUTH_TOKEN}}Resolved from environment key AUTH_TOKEN
{{$guid}}Auto-generated UUID per connection
{{$timestamp}}Unix timestamp at connection time

Practice Exercises

  1. Configure Bearer auth with a static token. Connect to ws://localhost:9876 (local mock). Observe the auth header in the console log at connection time.
  2. Switch to API Key auth. Set X-API-Key: test-key. Reconnect. Confirm the header appears in the console.
  3. Add a custom header X-Test-ID: run-001 in the Headers tab. Connect and verify it is visible in the request headers.
  4. Create an environment variable MY_TOKEN=secret. Set Bearer token to {{MY_TOKEN}}. Confirm the resolved value is used on connect.
