WebSocket: Load Testing

Advanced   Concurrent connections · Message rate · Latency percentiles

What You Will Learn

  • Navigate to the Load Test panel and understand prerequisites

  • Start and stop a load test
  • Interpret throughput and latency results

Prerequisites

Before running a load test you must have an active connection open in the current tab. The load test inherits the URL, protocol, auth, and TLS settings from the active connection — configure those first using the Connect and Auth tabs.

⚠️ Do not load test public servers Load testing sends high-volume traffic. Never run a load test against a public or third-party server (wss://echo.websocket.org, a production API, etc.) without explicit permission. Always test against a local server or a dedicated test environment.

Opening the Load Test Panel

1
Connect to your test server (e.g., start the mock server on port 9881 — use a non-default port to avoid conflicts with the test suite).
2
In the right panel, click the Load Test tab (right-tab-loadtest). The load test configuration panel appears.

Load Test Configuration

SettingDescriptionRecommended range
Concurrent ConnectionsNumber of WebSocket connections opened simultaneously. Each runs on a worker in the background.1 – 500
Message RateMessages sent per second, per connection. Total throughput = rate × connections.1 – 1000 msg/s per connection
DurationHow long the test runs before automatically stopping (seconds).10 – 300 s
Message PayloadThe payload template sent by each worker. Supports {{$index}} (worker index) and {{$seq}} (sequence number) placeholders.Any valid text or JSON
Ramp-upSeconds over which to gradually open all connections (avoids a thundering herd at start).0 – 30 s

Running a Load Test

3
Set your configuration. A sensible first test: 10 connections, 10 msg/s, 30 s duration, payload {"seq":"{{$seq}}"}.
4
Click Start Load Test (lt-start-btn). The lt-running indicator appears, showing the test is active. The configuration fields are disabled while the test runs.
5
While running, live metrics update in the results area:
  • Connections established — how many workers connected successfully
  • Messages sent — running total across all workers
  • Messages received — running total responses received
  • Errors — connection failures or send errors
  • Throughput (msg/s) — rolling aggregate message rate
6
The test stops automatically when the duration elapses. To stop early, click Stop.

Results Panel

After the test completes, a results summary appears:

MetricDescription
Total messages sentSum across all workers for the full duration
Total messages receivedSum of responses/echoes received
Error ratePercentage of sends that resulted in an error (failed connections or send failures)
Throughput (avg)Average messages/second over the test duration
Latency P50Median round-trip time (send → receive echo) in milliseconds
Latency P9595th percentile round-trip time — the "tail latency"
Latency P9999th percentile — the worst 1% of round trips
💡 Latency measurement Latency is measured as the time between sending a message and receiving the first response from the server. For accurate latency, use an echo server (the mock server's default echo behaviour is ideal). Non-echo servers may have different response counts or no response at all.

Using Mock Server as Load Test Target

The recommended pattern for local load testing:

1
Open Tab 1. Switch to Mock mode. Set port to 9881 (avoids conflicts with the default 9876 port used by test suites). Start the mock server.
2
Open Tab 2. Set URL to ws://localhost:9881. Connect. Verify the connection.
3
Open the Load Test panel in Tab 2. Configure 50 connections, 50 msg/s, 30 s.
4
Start the test. Tab 1 shows the connected client count rising to 50. The mock server echoes all messages. Tab 2's results show latency and throughput for the local echo server.

Interpreting Results

  • Error rate > 0% — the server is refusing connections or dropping messages under load; investigate server logs
  • P99 latency > 200ms on localhost — the Node.js proxy or the server event loop is saturated; reduce concurrency
  • Messages received < messages sent — the server is dropping frames; common at very high rates without flow control
  • Throughput plateau — the server has hit its concurrency limit; this is the measured capacity ceiling

Practice Exercises

  1. Start the mock server on port 9881. Run a 10-connection, 10 msg/s, 30 s load test. Record P50 and P99 latency.
  2. Double the concurrency to 20 connections. Re-run. Compare latency results. Did P99 change significantly?
  3. Increase message rate to 100 msg/s with 10 connections. Observe whether error rate remains 0% or begins to rise.
  4. Open the Stats panel alongside the Load Test. Confirm stats-msg-rate reflects the aggregate throughput during the test.
