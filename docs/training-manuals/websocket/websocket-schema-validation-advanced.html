WebSocket: Schema Validation

Advanced   Define schemas · Generate from traffic · Validate live frames

What You Will Learn

  • Open the Schema panel and understand its purpose
  • Generate a JSON Schema automatically from received messages
  • Define schemas manually for inbound and outbound messages
  • Enable live validation and interpret schema violations

Why Schema Validation?

WebSocket APIs are often undocumented or loosely typed. Schema validation in RedfireForge lets you:

  • Catch unexpected payload structure changes introduced by server updates
  • Enforce a contract on outgoing messages before they're sent
  • Surface violations inline in the message log without writing custom assertions
  • Infer a schema from live traffic and export it as documentation

Opening the Schema Panel

1
Connect to your WebSocket server. In the right panel, click the Schema tab (right-tab-schema). The schema panel (ws-schema-panel) appears.
2
At the top is a Validate toggle (ws-validation-toggle). When off (default), schemas are stored but not applied to messages. When on, every message is validated against its matching schema.

Generating a Schema from Traffic

3
Connect to your server and let it send several messages with your expected structure (e.g., 20+ messages to cover variations).
4
Click Generate Schema (ws-schema-generate-btn). The studio analyses all received messages in the current session and infers a JSON Schema that covers the observed types and required fields.
5
A new schema card appears in the list (ws-schema-card) named Generated with direction set to inbound. Click the card to expand and review the generated schema.
6
Edit the schema if needed (click the edit icon on the card), then save. You can rename it from "Generated" to something meaningful like ServerEvent.
💡 Generate with coverage The more varied the observed traffic, the more accurate the generated schema. If your server sends multiple message types, expose all of them before clicking Generate — the inferred schema will use oneOf or a union to cover all variants.

Adding a Schema Manually

1
Click + Add Schema (ws-schema-add-btn). An inline form opens with:
  • Name (ws-schema-name-input) — e.g., OrderUpdate
  • Direction (ws-schema-direction-select) — inbound (received) or outbound (sent)
  • Schema textarea (ws-schema-textarea) — paste or type your JSON Schema
2
Enter a name and direction. In the schema textarea, paste a JSON Schema, e.g.:
{
  "type": "object",
  "required": ["type", "orderId", "status"],
  "properties": {
    "type": { "type": "string", "const": "OrderUpdate" },
    "orderId": { "type": "string" },
    "status": { "type": "string", "enum": ["pending", "filled", "cancelled"] },
    "price": { "type": "number" }
  },
  "additionalProperties": false
}
3
Click Save (ws-schema-save-btn). The schema appears as a card (ws-schema-card) in the list.

Schema Card Actions

ActionDescription
Edit (pencil icon)Open the schema in the editor for changes
Delete (trash icon)Remove the schema; messages will no longer be validated against it
Export (↓ icon)Download the schema as a .json file for sharing or documentation
Direction badgeShows Inbound (↓) or Outbound (↑) at a glance

Enabling Live Validation

1
After defining schemas, enable the Validate toggle (ws-validation-toggle). It turns green.
2
As messages arrive or are sent, the studio runs each payload against the matching schema (matched by direction and, if multiple schemas exist, by a type discriminator or the first matching schema).
3
A message that passes validation shows a green check mark on its row in the Events log.
4
A message that fails validation shows a red ! on its row. Click the row to expand it and see the validation error details (e.g., required property "orderId" missing).
⚠️ Non-JSON messages Schema validation only applies to messages that parse as valid JSON. Plain text or binary frames are skipped and shown with a grey neutral indicator.

Multiple Schemas

You can define multiple schemas per direction. The studio applies schemas in list order. If a message matches the first schema's type discriminator (or passes the first schema's required check), that schema is used. Define a permissive catch-all schema at the bottom if you want all messages validated regardless of type.

Practice Exercises

  1. Connect to an echo server. Send 10 JSON messages with the same structure. Click Generate. Review the inferred schema.
  2. Manually add an inbound schema that requires a type field (string, required). Enable validation. Send a message missing the type field. Confirm the violation appears in the Events log.
  3. Add an outbound schema. Enable validation. Try to send a message that violates it. Observe whether the studio blocks the send or shows a warning.
  4. Export the generated schema to a JSON file and share it with a teammate as API documentation.
