Environment Manager: Variables & Overrides

Medium   Global Vars · Env Overrides · {{varName}} Interpolation · Derived Vars

What You Will Learn

  • Open the Protocol Vars modal and define a global variable for a microservice
  • Use {{varName}} in a request URL, header, and body
  • Open the Env Vars modal and override a global variable for a specific environment
  • Understand the "overridden" tag and resolution order
  • Identify derived variables like {{host}} in the Derived Vars panel

Prerequisite

Complete Environment Manager: Basics first. You should have at least one microservice (user-api) deployed in dev and staging with base URLs set.

Step-by-Step Walkthrough

Part A — Define a Global Variable

1
Open the Environment Manager and expand the user-api card (click Configure).
2
Locate the Protocol vars badge in the panel header (test ID protocol-vars-badge). It shows a count badge — click it to open the Protocol Vars modal (protocol-vars-modal).
3
The modal has two inputs: Key (protocol-vars-key-input) and Value (protocol-vars-val-input). Enter:
Key:   apiVersion
Value: v2
4
Click Add (protocol-vars-add-btn). A row appears showing {{apiVersion}} = v2.
5
Add a second variable:
Key:   timeout
Value: 30
6
Click Save changes (protocol-vars-save-btn). The modal closes. The Protocol vars badge count updates to 2.
💡 Global means "all environments" {{apiVersion}} now resolves to v2 in dev, staging, and prod — unless overridden per environment (shown in Part B).

Part B — Use {{varName}} in a Request

7
Navigate to the Requests tab and open a request targeting user-api.
8
In the URL field, use both built-in and custom variables:
{{baseUrl}}/api/{{apiVersion}}/users
9
With the header env selector set to dev, the resolved URL preview shows http://localhost:3000/api/v2/users.
10
In a request header, add:
X-Request-Timeout: {{timeout}}
11
The header value resolves to 30 at runtime.

Part C — Add an Env-Var Override

12
Return to the Environment Manager and open the user-api configuration panel.
13
In the staging row (which must be deployed), click the Env vars badge (test ID env-vars-badge-{stagingEnvId}). The Environment Variables modal opens (env-vars-modal).
14
The top section shows Global variables (read-only) — you can see {{apiVersion}} = v2 and {{timeout}} = 30 listed as references.
15
In the staging overrides section, type in the add row:
Key:   apiVersion
Value: v3
16
Click Add (env-vars-add-btn). The row appears in the override list. Notice the global apiVersion row now shows an overridden tag — confirming the staging value will shadow the global one.
17
Click Save changes (env-vars-save-btn). The modal closes. The Env vars badge for staging now shows count 1 (highlighted).

Part D — Verify Override Resolution

18
In the app header, switch to staging.
19
Return to the request from Part B. The resolved URL preview is now http://staging.internal:3000/api/v3/users — the env override for apiVersion took effect.
20
Switch back to dev. The resolved URL reverts to http://localhost:3000/api/v2/users.

Part E — Explore Derived Variables

21
In the protocol panel, locate the Derived Vars panel at the bottom (test ID derived-vars-http). It is read-only.
22
The panel shows {{host}} computed as localhost (for dev) — derived by stripping the protocol and port from baseUrl. You can use {{host}} in gRPC or WebSocket URLs where only the hostname is needed.
Derived vars are protocol-specific There is a separate derived vars panel for each protocol tab (HTTP, gRPC, GraphQL, etc.). Each derives contextual variables from that protocol's endpoint configuration.

Self-Practice Exercises

  1. Add a global variable clientId = webapp to user-api and use it in a request header X-Client-ID: {{clientId}}.
  2. Override clientId to webapp-staging for the staging environment only.
  3. Create a second microservice order-api with its own apiVersion variable set to v1. Confirm that changing user-api's version does not affect order-api.
  4. Delete an env-var override from staging and verify the global value is restored.
