Prerequisite

Complete Environment Manager: Basics and Variables & Overrides. You should have user-api deployed to dev, staging, and prod with base URLs and at least one global variable set.

How Test Environments Work

Feature Group Scoping

In the Scenarios tab, each Feature Group has two properties:

  • Microservice — which service this group tests (e.g. user-api)
  • Environment — which environment this group's scenarios target by default

When you run a feature group, RedfireForge resolves {{baseUrl}} and all custom variables from that combination. This is the static assignment — useful when a group is permanently pinned to an environment (e.g. a smoke-test group always running against staging).

Cascade Environment Override

When you send tests to the harness via Send to Harness, a field labelled Cascade environment (send-harness-cascade-environment) lets you override the feature group's static environment for this run. All scenarios in the promoted batch use the cascaded environment — without modifying the feature group itself.

Step-by-Step Walkthrough

Part A — Assign an Environment to a Feature Group

1
Navigate to the Scenarios tab. Select or create a Feature Group named user-api smoke tests.
2
In the Feature Group settings panel on the right, locate the Microservice dropdown and select user-api.
3
Locate the Environment dropdown and select dev. This group's scenarios will now resolve variables from the user-api + dev configuration by default.

Part B — Send to Harness with Cascade Override

4
Click Send to Harness (or equivalent promote action) from the feature group. The Send to Harness modal opens.
5
Locate the Cascade environment dropdown (send-harness-cascade-environment). It defaults to the feature group's static environment (dev).
6
Change it to staging. This means the promoted tests will run against staging — even though the feature group is statically assigned to dev.
7
Click Promote. The harness receives the scenarios with the staging environment context injected.
💡 Promoting to multiple environments To run the same scenarios against dev, staging, and prod, repeat the Send to Harness flow three times — once per environment — changing the cascade dropdown each time. The feature group itself remains unchanged.

Part C — Run via the Parameterized Runner

8
Navigate to the Parameterized Runner tab. This runner executes a test definition multiple times with different data rows — and optionally different environments.
9
In the Environment column of the parameter matrix, assign a different environment to each row. For example:
  • Row 1: dev
  • Row 2: staging
  • Row 3: prod
10
Start the run. Each iteration resolves {{baseUrl}} and all vars from its assigned environment independently. Row 1 hits dev, row 2 hits staging, row 3 hits prod — in a single runner pass.
11
In the Results Dashboard, each iteration shows its environment label alongside the status. Failed assertions on one environment do not affect the others.

Part D — Diagnose an Unresolved Variable Warning

12
If a test run uses {{baseUrl}} but the microservice is not deployed for the selected environment, a yellow warning bar (env-unresolved-warning) appears in the run detail view.
13
The warning reads: "Variable 'baseUrl' could not be resolved for environment X". The request will be sent with an empty base URL, likely causing a connection error.
14
To fix: go to the Environment Manager, open the microservice panel, and tick the deploy checkbox for the missing environment, then set a base URL.
⚠️ Always verify deploy + base URL before a multi-env run A common mistake is adding a new environment to the environment list but forgetting to deploy all microservices to it. Check that every service used in your test has a base URL for every environment you plan to target.

Part E — Monitor the Active Environment During a Run

15
While a test is executing, the header env selector (header-env-select) still reflects the global active environment. If you are running a parameterized test that rotates environments, the selector does not change — each iteration uses its own context internally.
16
To manually trace a specific iteration's variable resolution, click into the Results panel for that iteration and look at the Variables or Resolved URL detail.

Self-Practice Exercises

  1. Create a feature group pinned to staging. Promote it to the harness twice — once with cascade env = staging and once with cascade env = prod. Observe that different base URLs are used.
  2. Run a parameterized test with 3 rows, each targeting a different environment. Confirm in the results that each row hit a different server.
  3. Intentionally leave prod undeployed for user-api and trigger a run that targets prod. Observe and resolve the env-unresolved-warning.
