Environment Manager: Basics

Easy   Create Environments · Add a Microservice · Deploy · Set Base URL

What You Will Learn

  • Open the Environment Manager
  • Create three environments: dev, staging, and prod
  • Add a microservice called user-api
  • Enable (deploy) the microservice for dev
  • Set a base URL and verify that {{baseUrl}} resolves in a request
  • Switch the active environment using the app header selector

Before You Begin

Open RedfireForge. You will work in the Environments tab only for the first half of this tutorial, then briefly switch to Requests to verify variable resolution.

Step-by-Step Walkthrough

1 — Open the Environment Manager

1
Click Environments in the left sidebar tab bar. The Environment Manager panel opens, showing two empty sections: Environments and Microservices.

2 — Create Three Environments

2
In the Environments section, locate the text input (em-new-env-input). Type dev and press Enter (or click Add). A green chip labelled dev appears below the input.
3
Type staging and press Enter. A second chip appears.
4
Type prod and press Enter. You now have three environment chips. You can drag the ⠿ grip on any chip to reorder them — for example, place prod last.
💡 What are these environments? These are not actual servers. They are labels. The real URLs will be set later in the microservice configuration. Think of them as named columns in a configuration spreadsheet.

3 — Add a Microservice

5
Scroll to the Microservices section. In the name input (em-new-svc-input), type user-api and press Enter. A service card labelled user-api appears.
6
The card shows: name, a protocol badge summary, a fraction 0/3 envs (none deployed yet), a Configure button, and a red × delete button.

4 — Open the Configuration Panel

7
Click Configure on the user-api card (test ID em-svc-configure-{id}). The card expands to reveal a protocol panel (microservice-protocol-panel).
8
The panel defaults to the HTTP tab. You see a table with one row per environment (dev, staging, prod) plus columns: checkbox, Environment, Base URL, Env vars, and Auth profile.

5 — Deploy to dev

9
In the dev row, tick the checkbox in the leftmost column. The row activates — the Base URL, Env vars, and Auth profile cells become interactive.
10
The card header now shows 1/3 envs — confirming that user-api is deployed to one environment.
Why a deploy toggle? Not every microservice is available in every environment. The deploy checkbox prevents accidental cross-environment requests — only checked environments participate in test runs that target this service.

6 — Set the Base URL

11
In the dev row, click the pencil / edit icon in the Base URL cell (test ID em-endpoint-edit-btn). An input field (em-endpoint-edit-input) appears.
12
Type the base URL for your dev environment, for example:
http://localhost:3000
13
Click Save (em-endpoint-save-btn). The URL is saved. The cell now shows http://localhost:3000 as a read-only label.
14
Optionally, deploy staging and set its URL to http://staging.internal:3000.

7 — Activate dev in the App Header

15
Look at the top-right of the app. There is a dropdown labelled with the current environment (or No environment if none is selected). This is the header env selector (header-env-select).
16
Click the dropdown and select dev. The app is now running in dev context — all variable references resolve against dev's configuration.

8 — Verify {{baseUrl}} in a Request

17
Navigate to the Requests tab and open any existing request, or create a new one.
18
In the URL field, type:
{{baseUrl}}/users
19
The request editor shows the resolved preview: http://localhost:3000/users. This confirms that {{baseUrl}} is being sourced from the user-api dev configuration.
💡 Switch without editing Now change the header env selector to staging. The resolved URL instantly updates to http://staging.internal:3000/users — without changing the request definition. This is the core power of the Environment Manager.

Deleting an Environment

Click the × on an environment chip. A confirmation dialog appears listing all affected microservices and feature groups. Deleting an environment does not delete microservices or test scenarios — it only removes the environment association (deployed flag and stored base URL for that env).

Self-Practice Exercises

  1. Add a fourth environment called perf. Drag it to sit between staging and prod.
  2. Deploy user-api to prod and set its URL to https://api.example.com.
  3. Add a second microservice order-api. Deploy it to all three environments and set different base URLs for each.
  4. Switch the header env selector to each environment and confirm that {{baseUrl}} resolves to the correct URL in a test request.
