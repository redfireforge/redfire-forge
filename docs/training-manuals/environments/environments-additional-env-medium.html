Environment Manager: Additional Environments

Medium   Microservice-Specific Envs · Drag Reorder · Impact-Safe Deletion

What You Will Learn

  • Understand the difference between global environments and microservice-specific additional environments
  • Add a custom environment to a single microservice (e.g. a canary or blue/green slot)
  • Set a base URL and env-var overrides for the additional environment
  • Reorder environments and microservices by drag-and-drop
  • Safely delete an environment — understand the impact warning dialog

Global Environments vs Additional Environments

The Environments section at the top of the Environment Manager defines global environments — labels visible to every microservice. All services share the same global list.

Some services have deployment slots that don't map to any global environment. For example, a canary deployment URL that exists only for payment-api and no other service. For these cases, additional environments let you add service-scoped deployment targets.

Step-by-Step Walkthrough

Part A — Add a Microservice-Specific Additional Environment

1
Open the Environment Manager and expand user-api (click Configure).
2
In the HTTP tab's deploy table, scroll past the global environment rows. At the very bottom of the table (in the tfoot area) there is a text input with placeholder "+ Add additional environment (e.g. staging-2)".
3
Click the input and type canary. Press Enter. A new row appears in the table under a separator row labelled Additional environments. The row shows the name canary with a distinct tag style.
4
Tick the deploy checkbox for the canary row to enable it.
5
Click the edit icon in the Base URL cell for canary and enter:
http://canary.user-api.internal:3000
6
Click Save. The canary environment is now configured for user-api. It does not appear in any other microservice's table.
💡 When to use additional environments Use global environments for standard deployment tiers (dev / staging / prod) that all services share. Use additional environments for one-off deployment slots: canary releases, blue/green switches, hotfix branches, tenant-specific URLs.

Part B — Set Variables for the Additional Environment

7
In the canary row, click the Env vars badge (test ID env-vars-badge-{canaryEnvId}). The Env Vars modal opens for this additional environment.
8
The modal behaves identically to any other environment: global vars appear as read-only references at the top; you can add key/value overrides specific to canary.
9
Add an override:
Key:   featureFlags
Value: canary-v2
10
Click Save changes. The canary env vars badge now shows count 1.

Part C — Remove an Additional Environment

11
In the canary row, locate the red × button at the far right of the row (class svc-env-additional-del). This button is only shown for additional environments, not global ones.
12
Click × to remove the canary additional environment. The row disappears immediately. No confirmation dialog — additional environments are scoped to one service and have no cross-feature impact.
⚠️ Additional environment removal is immediate Unlike deleting a global environment (which shows an impact dialog), removing an additional environment from a service's table is instant. There is no undo. Any feature groups or scenarios bound to that additional env ID will lose their environment association.

Part D — Reorder Environments (Drag and Drop)

13
In the Environments section, identify the ⠿ grip on the left side of each environment chip.
14
Drag the prod chip upward to place it before staging. Release. The chips reorder immediately. The order in this list controls the column order in each service's deploy table.
💡 Order affects usability, not function Reordering environments changes visual presentation only. Variable resolution and test execution are not affected by the display order.

Part E — Reorder Microservices (Drag and Drop)

15
In the Microservices section, each service card has a ⠿ grip on the left edge of its header bar (class svc-drag-grip).
16
Drag order-api above user-api. The card list reorders. Note: dragging is disabled while a card is expanded — collapse it first.

Part F — Delete a Global Environment Safely

17
Click the × on the prod environment chip. If any microservices have base URLs set for prod, or if any feature groups are scoped to prod, a confirmation dialog appears.
18
The dialog message lists:
  • How many microservices will lose their prod base URL
  • How many feature groups (and their scenarios/tests) will become unassociated
19
The dialog explicitly notes: "They will NOT be deleted but will lose their environment association." Confirm if you want to proceed. The environment chip is removed and all prod base URLs are cleared from every service.

Self-Practice Exercises

  1. Add two additional environments to order-api: blue and green. Deploy both and set different base URLs. Add a distinct slot env-var override for each.
  2. Reorder the global environments so that prod is last. Verify that the deploy table column order updates in all expanded service panels.
  3. Delete the staging global environment. Review the impact dialog. Then recreate it and redeploy all services to it.
  4. Attempt to drag a microservice card while it is expanded. Confirm that dragging is blocked, then collapse and try again.
