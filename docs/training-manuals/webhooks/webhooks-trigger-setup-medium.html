Webhook Trigger Node Setup

Medium   URL format · HTTP method config · JSONPath variable extraction · Error codes · Testing your endpoint

Overview

A Webhook Trigger node in the Workflow Runner turns your workflow into an HTTP endpoint. When an external system sends a request to that URL, your workflow executes and the request payload becomes available as variables for downstream nodes.

When to use a Webhook Trigger Use a Webhook Trigger when you want to react to events: CI/CD pipelines posting build results, payment gateways posting transaction events, IoT devices reporting sensor data, or any system that can make an outbound HTTP request.

Endpoint URL Format

Every Webhook Trigger node produces a unique URL derived from the workflow ID and the node ID:

METHOD /webhooks/{workflowId}/{triggerId}

Example:
POST http://localhost:3001/webhooks/order-processing/wh-new-order
PartSourceExample
workflowIdWorkflow name/ID set when savingorder-processing
triggerIdNode ID of the Webhook Trigger node on the canvaswh-new-order
HTTP methodConfigured in the node panel (POST, PUT, or PATCH)POST

Configuring a Webhook Trigger Node

1
Add the node In the Workflow Runner canvas, click + Add Node and choose Webhook Trigger. A node card appears on the canvas with a hook icon.
2
Set the HTTP method Click the node to open its config panel. Choose POST, PUT, or PATCH from the Method dropdown. This locks the endpoint to that method — calls with a different method receive a 405 Method Not Allowed response.
3
Add a sample payload In the Sample Payload field, paste an example JSON body. This documents the expected shape of incoming requests and can be used for test runs.
4
Define variable extractions (optional) Use the Extract Variables section to pull values from the request into named variables. These variables are then available to all downstream nodes in the workflow.
5
Save the workflow Click Save Workflow. The endpoint is now live — the server immediately starts accepting requests at the generated URL.

JSONPath Variable Extraction

Variable extractions let you pull data out of the incoming request and pass it to downstream nodes as named variables. Each extraction has a name (the variable name) and a JSONPath expression (where to find the value).

JSONPath Syntax

JSONPath ExampleExtracts FromDescription
$.body.orderIdRequest bodyThe orderId field from the JSON body
$.body.customer.emailRequest bodyNested field — email inside customer
$.headers.x-user-idRequest headersThe x-user-id custom header
$.headers.authorizationRequest headersThe Authorization header value
$.query.pageURL query stringThe ?page= query parameter
$.orderIdRequest body (default)Shorthand — no prefix defaults to body extraction
Body is the default source If your JSONPath does not start with body, headers, or query, the engine automatically prefixes body.. So $.orderId is equivalent to $.body.orderId.

Example: Order Webhook Extraction

Incoming request body:

{
  "orderId": "ORD-5521",
  "amount": 99.99,
  "customer": { "email": "alice@example.com" }
}

Variable extractions configured in the node:

Variable NameJSONPathExtracted Value
orderId$.body.orderIdORD-5521
amount$.body.amount99.99
customerEmail$.body.customer.emailalice@example.com

Downstream HTTP nodes can reference these as {{orderId}}, {{amount}}, {{customerEmail}}.

HTTP Response Codes

CodeCause
200Webhook received and workflow executed (includes status, duration, step results)
404Workflow not found — check the workflowId in the URL matches a saved workflow
404Trigger node not found — check the triggerId matches a Webhook Trigger node in the workflow
405Wrong HTTP method — the node is configured for a different method
500Workflow execution error — see the response body's message and check the delivery detail panel

Testing Your Webhook Endpoint

You can test a webhook endpoint with any HTTP client. Using curl:

# Basic POST webhook call
curl -X POST http://localhost:3001/webhooks/order-processing/wh-new-order \
  -H "Content-Type: application/json" \
  -d '{"orderId":"ORD-5521","amount":99.99}'

# With a custom header extracted by the trigger
curl -X POST http://localhost:3001/webhooks/order-processing/wh-new-order \
  -H "Content-Type: application/json" \
  -H "x-user-id: user-42" \
  -d '{"orderId":"ORD-5521"}'

# Enable full execution trace in the response
curl -X POST "http://localhost:3001/webhooks/order-processing/wh-new-order?_trace=true" \
  -H "Content-Type: application/json" \
  -d '{"orderId":"ORD-5521"}'
The _trace=true query parameter Adding ?_trace=true to the webhook URL causes the server to return a full execution trace in the response body under the key iterationTrace. This includes every step's input, output, and timing — useful for debugging extraction logic and workflow step failures.

Viewing Results in Delivery Logs

After calling a webhook endpoint, open Workflow → Webhook Deliveries. The new delivery appears at the top of the list (newest-first). Click it to see:

  • The Trigger ID — matches the triggerId segment of the URL you called
  • The Method — the HTTP method used
  • The Status — SUCCESS, FAILED, or ERROR
  • The Payload — the request body that was received
  • The Error block — present only if the delivery has status ERROR

Smoke-Test Checklist

  1. Create a workflow with a Webhook Trigger node; configure it for POST method
  2. Save the workflow and note the workflowId and triggerId
  3. Send a POST to http://localhost:3001/webhooks/{workflowId}/{triggerId} — verify 200 response
  4. Send the same call with PUT method — verify 405 response
  5. Call a non-existent workflowId — verify 404 response
  6. Configure a variable extraction: name orderId, path $.body.orderId; send payload {"orderId":"TEST-1"} and verify downstream nodes receive {{orderId}} = TEST-1
  7. Open Webhook Deliveries and verify the new delivery appears with the correct status and payload
