Environment Audit Log

Easy — Training Manual

Learn to browse audit entries, filter by entity type and action, and inspect field-level change tracking for environments, microservices, and auth profiles.

1. Purpose & Use Case

Environments, microservices, and auth profiles are shared configuration entities — they affect every test, request, and workflow in your workspace. A stray deletion or a wrong base URL can break dozens of tests silently.

The Audit Log gives you a chronological record of every create, update, delete, and rename operation on these entities. It answers questions like:

  • "Who changed the Staging base URL?" — filter by entity type microservice, action updated.
  • "When was the OAuth profile deleted?" — filter by authProfile + deleted.
  • "What was the old value before this rename?" — expand the field-level change details.

Real-world scenario: "Debugging a Broken Test Suite"

Your team's API regression suite suddenly fails across 12 tests — all returning 404. You suspect someone changed the Staging environment's base URL. Instead of asking around, you open the Audit Log, filter to microservice + updated, and immediately see the entry: baseUrls[staging] changed from https://api.staging.example.com to https://api.staging.example.com/v2 — two hours ago. Mystery solved in seconds.

💡 Tip The Audit Log does not require importing any gallery sample. It tracks changes you make in the Settings → Environments panel during normal app usage.

2. Concepts You'll Learn

  • Audit entry — a timestamped record of a single CRUD operation on an environment, microservice, or auth profile.
  • Entity types — three categories are tracked: environment, microservice, and authProfile.
  • Actions — four action types: created, updated, deleted, and renamed.
  • Field-level changes — for updated and renamed actions, the log records exactly which fields changed, with old and new values.
  • Filtering & search — combine entity type, action type, and free-text search to narrow results.
  • Timeline view — entries displayed newest-first with action icons (+, ~, ×, →) and color-coded badges.
  • 500-entry FIFO cap — the log holds up to 500 entries; oldest entries are evicted automatically.
  • Persistence — entries survive browser refreshes and app restarts (localStorage / Tauri store).

3. Key Data Model

Each audit entry follows this structure:

type AuditEntityType = 'environment' | 'microservice' | 'authProfile';
type AuditAction = 'created' | 'updated' | 'deleted' | 'renamed';

interface AuditChange {
  field: string;       // Which field changed (e.g., "name", "baseUrls[staging]")
  oldValue: unknown;   // Previous value
  newValue: unknown;   // New value
}

interface AuditEntry {
  id: string;             // UUID — unique entry identifier
  timestamp: number;      // Epoch ms — when the action occurred
  entityType: AuditEntityType;
  entityId: string;       // UUID of the affected entity
  entityName: string;     // Human-readable name at time of action
  action: AuditAction;
  changes?: AuditChange[];  // Field-level diffs (for update/rename)
}

const DEFAULT_MAX_ENTRIES = 500;

Key points about the data model:

  • changes is only present for updated and renamed actions. created and deleted entries have no changes array.
  • entityName captures the name at the time of the action — if the entity is later renamed, old entries still show the original name.
  • Each entry has a UUID id independent of the entity's own ID, so you can have many entries for the same entity.
📋 Note The computeChanges() utility automatically diffs two objects field-by-field using JSON.stringify comparison. This means nested object differences (like a changed JSON body) are detected as a single field change with the full old/new objects.

4. Where to Find the Audit Log

The Audit Log panel lives inside the Settings modal:

  1. Click the ⚙️ Settings button in the top toolbar.
  2. The Settings modal opens with tabs: Global Auth, Export / Import, Storage, Audit Log.
  3. Click the Audit Log tab.

The panel shows a toolbar (search + filters), action buttons (Export, Refresh, Clear), and the timeline of entries.

5. Step-by-Step Walkthrough

Step 1 — Generate Audit Entries

Before exploring the log, you need some entries. Go to Settings → Global Auth or close the modal and use the Environments section in the left sidebar. Perform these actions:

  1. Create an environment — name it Staging. This logs a created entry for entity type environment.
  2. Create a microservice — name it User API with base URL https://api.staging.example.com/users. This logs a created entry for microservice.
  3. Update the microservice — change the base URL to https://api.staging.example.com/v2/users. This logs an updated entry with a field-level change on baseUrls.
  4. Create an auth profile — name it OAuth Dev in Settings → Global Auth. This logs a created entry for authProfile.
  5. Rename the auth profile — change it to OAuth Staging. This logs a renamed entry with a change on the name field.

You should now have at least 5 audit entries covering all three entity types and multiple action types.

Step 2 — Open the Audit Log

Navigate to Settings → Audit Log. The panel header shows the total entry count: "5 entries recorded".

Step 3 — Read the Timeline

Entries are displayed newest-first. Each entry shows:

ElementDescription
Action icon+ (green) for created, ~ (blue) for updated, × (red) for deleted, → (orange) for renamed
Entity typeBadge showing "Environment", "Microservice", or "Auth Profile"
Entity nameBold text — the entity's name at the time of the action
Action badgeColor-coded pill: Created / Updated / Deleted / Renamed
TimestampFormatted date and time (e.g., "May 1, 2:30 PM")
ChangesExpandable field-level diffs (only for updated/renamed actions)

Step 4 — Inspect Field-Level Changes

Find the "User API — Updated" entry. Below the header, you'll see the changes section:

baseUrls[staging]: "https://api.staging.example.com/users" → "https://api.staging.example.com/v2/users"

This tells you exactly which field changed, what the old value was, and what the new value is. For the "OAuth Staging — Renamed" entry, you'll see:

name: "OAuth Dev" → "OAuth Staging"
💡 Tip Field-level changes use JSON.stringify comparison internally. For complex values (like nested objects), the full old and new objects are shown. Simple string values are displayed directly.

Step 5 — Filter by Entity Type

Use the entity type dropdown in the toolbar. Select "Microservice". The timeline now shows only microservice-related entries (created + updated). The counter updates to reflect the filtered count.

Try selecting "Auth Profile" — you should see the created and renamed entries.

Step 6 — Filter by Action

Reset the entity type filter to "All Types". Now use the action dropdown and select "Updated". Only entries where something was modified appear — the microservice URL change.

You can combine both filters: set entity type to "Auth Profile" and action to "Renamed" to see only auth profile rename operations.

Step 7 — Free-Text Search

Clear both dropdown filters. Type OAuth in the search box. The timeline filters to entries where the entity name, entity type, or action label contains "OAuth" — you should see the auth profile entries.

Search is case-insensitive and matches against:

  • entityName — e.g., "OAuth Staging"
  • formatEntityType() — e.g., "Auth Profile"
  • formatAction() — e.g., "Renamed"

Step 8 — Combine Filters with Search

Try this combination: entity type = microservice, action = updated, search = User. This narrows the timeline to only microservice updates where the name contains "User" — a very precise query.

Step 9 — Refresh the Log

Click the Refresh button. This reloads entries from storage (localStorage or Tauri store). Use this if you've made changes in another tab or if you want to confirm the latest state.

Step 10 — Delete an Entity and Check the Log

Go back to the Environments panel and delete the Staging environment. Return to Settings → Audit Log and click Refresh. A new entry appears at the top: Environment — Staging — Deleted with a red × icon.

6. How Entries Are Recorded

Audit entries are created automatically by convenience logger functions called from the CRUD operations in the EnvironmentManager and SettingsModal:

User ActionLogger FunctionEntity TypeAction
Create environmentlogEnvironmentCreated(name, id)environmentcreated
Delete environmentlogEnvironmentDeleted(name, id)environmentdeleted
Rename environmentlogEnvironmentRenamed(id, old, new)environmentrenamed
Create microservicelogMicroserviceCreated(name, id)microservicecreated
Delete microservicelogMicroserviceDeleted(name, id)microservicedeleted
Update microservice URLlogMicroserviceUpdated(name, id, changes)microserviceupdated
Create auth profilelogAuthProfileCreated(name, id)authProfilecreated
Delete auth profilelogAuthProfileDeleted(name, id)authProfiledeleted
Update auth profilelogAuthProfileUpdated(name, id, changes)authProfileupdated
Rename auth profilelogAuthProfileRenamed(id, old, new)authProfilerenamed

All loggers call addAuditEntry() which assigns a UUID and timestamp, appends to the log, and enforces the 500-entry FIFO cap.

📋 Note The logMicroserviceUpdated() and logAuthProfileUpdated() functions have a guard: if changes.length === 0, no entry is created. This prevents noise from save operations where nothing actually changed.

7. The computeChanges() Utility

When an entity is updated, the calling code uses computeChanges() to diff the old and new objects:

function computeChanges(
  oldObj: Record<string, unknown>,
  newObj: Record<string, unknown>,
  fields?: string[],   // Optional — restrict to specific fields
): AuditChange[]

How it works:

  1. If fields is provided, only those keys are compared. Otherwise, the union of all keys from both objects is used.
  2. For each key, JSON.stringify(oldVal) is compared with JSON.stringify(newVal).
  3. If they differ, an AuditChange is added with the field name, old value, and new value.

Example:

const old = { name: 'User API', baseUrls: { prod: 'https://prod.api.com' } };
const updated = { name: 'User API', baseUrls: { prod: 'https://prod.api.com/v2' } };

computeChanges(old, updated);
// → [{ field: 'baseUrls', oldValue: { prod: '...' }, newValue: { prod: '.../v2' } }]

9. Persistence & Storage

Audit entries are stored under the key perf-test-audit-log in:

  • Web mode — localStorage
  • Desktop mode (Tauri) — Tauri store via getItem / setItem

The storage layer is abstracted by internal readKey() / writeKey() helpers that auto-detect the platform. Entries survive browser tab closes and app restarts.

10. Try It Yourself

Exercise 1 — Build an Audit Trail

Create 3 environments (Dev, Staging, Production) and 2 microservices (User API, Order API). Update one microservice's base URL. Delete the Dev environment. Open the Audit Log and verify you see 6 entries with correct entity types, actions, and field-level changes.

Exercise 2 — Master Filtering

Using the entries from Exercise 1, practice these filter combinations:

  • Show only environment entries → expect 4 (3 created + 1 deleted).
  • Show only deleted actions → expect 1 (the Dev environment).
  • Combine: microservice + updated → expect 1.
  • Search for "Order" → expect entries related to Order API.

Exercise 3 — Persistence Check

Create several audit entries. Close the browser tab entirely. Reopen RedfireForge and navigate to Settings → Audit Log. Verify all entries are intact — including field-level changes and timestamps.

💡 Tip Use the Refresh button after generating entries in a different part of the app to ensure the Audit Log panel shows the latest data.
