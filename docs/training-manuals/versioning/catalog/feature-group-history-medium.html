1. Purpose & Use Case

The Easy manual taught you to read structure logs. This manual teaches you to analyze them — reconstructing the evolution of a feature group, understanding move patterns across groups, managing logs during export/import, and using the display helpers programmatically.

Real-world scenario: "Pre-Release Structure Audit"

Before releasing a test suite to your team, you want to verify the final structure matches the planned design. Open the Structure History for each feature group. By reading the log chronologically (bottom to top), you reconstruct the evolution:

  1. Started with 3 scenarios from gallery import.
  2. Added 2 custom scenarios for edge cases.
  3. Moved "Auth Validation" from "User API" to the new "Auth API" group.
  4. Renamed "Error Cases" to "Edge Cases" for consistency.
  5. Copied "Health Check" test from "Infrastructure" group.

This gives you confidence the structure is intentional, not accidental.

📋 Prerequisite Complete the Feature Group History (Easy) manual first. This manual assumes you understand the 12 action types, filters, and basic panel operations.

3. Move Patterns: Dual-Entry Design

When a scenario or test is moved between feature groups, two entries are created — one in each group:

GroupEntryDetail
Source (User API)− Scenario moved outto Auth API
Target (Auth API)+ Scenario moved infrom User API

This dual-entry design has several benefits:

  • Self-contained — each group's log is complete without cross-referencing.
  • Traceable — you can follow the trail from either direction.
  • Audit-friendly — the detail field names the other group.

3.1 Move vs. Copy

OperationSource Group EntryTarget Group Entry
Move scenarioscenario-moved-outscenario-moved-in
Move testtest-moved-outtest-moved-in
Copy test(none)test-copied

Copies only create an entry in the target group because the source is unchanged. Moves create entries in both groups because both are structurally modified.

4. Export & Import Behavior

The structure log interacts with test suite export/import in specific ways:

4.1 Exporting with Logs

By default, exporting a test suite includes the structure log. This preserves the full history for the recipient:

// Export includes structureLog
{
  "id": "fg1",
  "name": "User API",
  "scenarios": [...],
  "structureLog": [
    { "id": "...", "action": "scenario-added", "entityName": "Login", ... },
    ...
  ]
}

4.2 Stripping Logs for Clean Export

If you want a "clean" export without history, use stripStructureLog():

function stripStructureLog(fg: FeatureGroup): FeatureGroup {
  const { structureLog: _, ...rest } = fg;
  return rest as FeatureGroup;
}

Use cases for stripping:

  • Sharing a template — recipients don't need your development history.
  • Reducing file size — 50 entries × multiple groups adds up.
  • Privacy — log entries may reveal internal project names.

4.3 Importing with Logs

Importing a test suite with structure logs preserves the imported history. The imported logs merge with any existing logs if the feature group already exists, or appear as-is if it's a new group.

⚠️ Important Imported structure logs retain their original timestamps. This means imported entries may appear chronologically mixed with local entries. Use the filter buttons to isolate entry types if the log becomes confusing after import.

6. Step-by-Step Walkthrough

Step 1 — Import and Set Up Two Feature Groups

Import "Country Search Tests" from the Gallery. Create a second feature group called "Regional API". You now have two groups: "Country API" (with scenarios) and "Regional API" (empty).

Step 2 — Build a Rich History

Perform these structural changes to build a realistic log:

  1. Add scenario "Population Filter" to "Country API".
  2. Add test "Countries > 1M" inside "Population Filter".
  3. Add test "Countries < 100K" inside "Population Filter".
  4. Rename "Filter by Region" scenario to "Region Queries".
  5. Move "Region Queries" scenario from "Country API" to "Regional API" (drag & drop).
  6. Copy a test from "Country API" to "Regional API".
  7. Rename the feature group "Country API" to "Country Search API".

Step 3 — Analyze the Source Group Log

Open the Structure History for "Country Search API". You should see ~6 entries. Read bottom to top to reconstruct the evolution:

  • Added "Population Filter" scenario
  • Added 2 tests
  • Renamed a scenario
  • Moved "Region Queries" out to "Regional API"
  • Renamed the group itself

Step 4 — Analyze the Target Group Log

Open the Structure History for "Regional API". You should see 2 entries:

  • + Scenario moved in — Region Queries — from Country Search API
  • + Test copied — [test name] — in [scenario]

Notice the detail field shows the source group name. Cross-reference with the source group's "moved out" entry to verify consistency.

Step 5 — Filter to Isolate Patterns

In "Country Search API", use the filter buttons:

  • Scenario filter: Shows 3 entries (added, renamed, moved out). This reveals the scenario lifecycle.
  • Test filter: Shows 2 entries (both added). This isolates test-level changes.
  • Group filter: Shows 1 entry (renamed). This isolates group-level changes.

The footer shows filtered vs. total: "3 of 6 entries".

Step 6 — Understand the Display Helpers

The three display helper functions control how entries render in the UI:

// Human-readable label for each action
actionLabel('scenario-moved-in')  // → "Scenario moved in"
actionLabel('test-renamed')       // → "Test renamed"
actionLabel('fg-renamed')         // → "Group renamed"

// Badge icon character
actionIcon('scenario-added')     // → "+"  (addition)
actionIcon('test-removed')       // → "−"  (removal)
actionIcon('scenario-renamed')   // → "~"  (modification)

// CSS class for color coding
actionClass('test-moved-in')    // → "added"    (green)
actionClass('scenario-removed') // → "removed"  (red)
actionClass('fg-renamed')       // → "modified"  (amber)

The logic uses string matching:

  • Actions containing added, moved-in, or copied → green (+)
  • Actions containing removed or moved-out → red (−)
  • Actions containing renamed → amber (~)

Step 7 — Selective Entry Deletion

Delete specific "noise" entries — for example, if you added a scenario by mistake and immediately removed it, delete both entries to keep the log clean. Use the × button on each entry.

💡 Tip Think of entry deletion as "curating" the log. In a clean log, every entry represents an intentional structural decision. Accidental add/remove pairs just add noise.

Step 8 — Test the 50-Entry Cap

The cap is generous — 50 entries covers weeks of normal usage. But you can test it:

  1. Rapidly add and remove tests (each creates 2 entries: add + remove).
  2. After 25 add/remove cycles (50 entries), the next action evicts the oldest entry.
  3. Verify the footer never shows more than 50.

Step 9 — Prepare for Export

Before exporting, decide whether to include or strip the log:

Include LogStrip Log
Team sharing — recipients benefit from historyTemplate sharing — history is irrelevant
Audit trail neededSmaller file size desired
Import into same project (continuation)Import into different project (clean start)

Step 10 — Correlate Logs Across Groups

Open Structure History in both feature groups side by side. For each "moved out" entry in the source, find the matching "moved in" entry in the target. Verify:

  • Same entity name appears in both.
  • Source detail says to [target name].
  • Target detail says from [source name].
  • Timestamps are within seconds of each other.

7. Common Structure Change Patterns

Learn to recognize these patterns in your logs:

PatternLog SignatureMeaning
Initial build-out Cluster of + entries (added) Feature group was populated from scratch
Reorganization Alternating − moved-out and + moved-in entries Scenarios/tests were redistributed across groups
Cleanup Cluster of − removed entries Unused scenarios/tests were pruned
Standardization Multiple ~ renamed entries Naming convention was applied
Duplication + test-copied entries Tests were shared across groups via copy
Accidental churn Paired add + remove for same entity Item was added then immediately removed (noise)

9. Advanced Filtering Strategies

The built-in filters cover the three main categories (Scenario, Test, Group). For more advanced analysis, combine filtering with manual reading:

9.1 Finding All Moves

Filter to Scenario, then scan for entries with detail containing "from" or "to". These are move operations. The detail field names the other group.

9.2 Finding All Renames

Filter to any category. Renamed entries always have a ~ badge and a detail field showing Old → New.

9.3 Correlating Test Changes with Scenarios

Filter to Test. Each test entry includes scenarioName (shown as "in [scenario]"). This tells you which scenario the test belongs to, even if you've renamed or moved the scenario since.

💡 Tip The scenarioName on test entries captures the name at the time the entry was created. If the scenario was later renamed, the log entry still shows the old name. Cross-reference with scenario-renamed entries to resolve name changes.

10. Try It Yourself

Exercise 1 — Reconstruct a History

Import "Country Search Tests". Perform 8 structural changes (mix of adds, removes, renames, and moves). Then close the Structure History panel. Reopen it and, reading bottom to top, write down the chronological story of the feature group's evolution. Verify each step matches what you did.

Exercise 2 — Cross-Group Move Audit

Create 3 feature groups. Move a scenario from Group A → Group B, then from Group B → Group C. Open the Structure History for all 3 groups. Verify:

  • Group A: 1 "moved out" entry (to Group B)
  • Group B: 1 "moved in" entry (from A) + 1 "moved out" entry (to C)
  • Group C: 1 "moved in" entry (from B)

The full migration path is traceable by following the chain: A → B → C.

Exercise 3 — Log Curation

Build a log with 10+ entries, including some "noise" (accidental add/remove pairs). Use selective deletion to curate the log — remove noise entries while preserving meaningful ones. Aim for a clean log where every entry represents an intentional change.

💡 Tip In production workflows, curate your structure logs before sharing test suites. A clean log is documentation — it communicates your structural decisions to teammates who import the suite.
