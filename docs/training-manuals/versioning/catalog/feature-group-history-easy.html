1. What Is the Structure Change Log?

Every feature group maintains its own structure change log — a chronological record of every scenario and test added, removed, renamed, moved, or copied within that group. Think of it as a local Git log for your test organization.

Real-world scenario: "Who Moved My Scenario?"

Your team shares a test suite with 5 feature groups. On Monday you had 3 scenarios in "User API." On Wednesday you notice only 2 remain. Instead of guessing, open the Structure History panel — it shows: "Scenario moved out — Profile Tests → to Auth API" with a timestamp. Mystery solved in seconds.

How It Differs from Other Versioning

FeatureStructure Change LogDefinition Versioning
What it tracksStructural changes (add, remove, move, rename)Content changes (URL, body, headers, etc.)
ScopePer feature groupPer request / per test definition
TriggerImmediate — logged when action occursNavigation — logged when you switch items
Snapshots?No — event log only (action + entity name)Yes — full content snapshots
Restore?No — informational onlyYes — full restore from snapshot
Max entries50 per feature group15–20 per item
📋 Key Difference The structure log is an event log, not a snapshot system. It records what happened but doesn't store full copies. You can't "restore" a previous structure — but you can see exactly what changed and when.

2. The StructureChangeEntry Data Model

interface StructureChangeEntry {
  id: string;                    // UUID
  timestamp: number;             // Date.now() when logged
  action: StructureChangeAction; // One of 12 action types
  entityName: string;            // Name of the changed entity
  scenarioName?: string;         // Parent scenario (for test-level changes)
  detail?: string;               // Additional context
}

3. How Entries Are Created

Unlike definition versioning (which auto-saves on navigation), structure log entries are created immediately when you perform an action. There are 12 convenience functions — one per action type:

// Adding a scenario
function logScenarioAdded(fg: FeatureGroup, scenarioName: string): FeatureGroup {
  return appendToLog(fg, createEntry('scenario-added', scenarioName));
}

// Moving a scenario between feature groups
function logScenarioMovedIn(fg: FeatureGroup, scenarioName: string, fromFgName: string): FeatureGroup {
  return appendToLog(fg, createEntry('scenario-moved-in', scenarioName, undefined, `from ${fromFgName}`));
}

// Renaming a test
function logTestRenamed(fg: FeatureGroup, oldName: string, newName: string, scenarioName: string): FeatureGroup {
  return appendToLog(fg, createEntry('test-renamed', newName, scenarioName, `${oldName} → ${newName}`));
}

Each function calls appendToLog() which prepends the entry and caps at 50:

function appendToLog(
  fg: FeatureGroup,
  entry: StructureChangeEntry,
  maxEntries: number = MAX_LOG_ENTRIES,  // 50
): FeatureGroup {
  const log = [entry, ...(fg.structureLog ?? [])].slice(0, maxEntries);
  return { ...fg, structureLog: log };
}
💡 Immutable Updates Every function returns a new FeatureGroup object — it never mutates the original. This is essential for React state management and undo/redo compatibility.

4. The 50-Entry Cap

Each feature group stores up to 50 structure log entries (vs. 15 for request versions, 20 for test versions, 500 for audit log).

const MAX_LOG_ENTRIES = 50;

Why 50?

  • Structure changes are less frequent than definition edits — 50 covers weeks of normal activity.
  • Entries are lightweight (no snapshots) — 50 entries use minimal memory.
  • FIFO eviction: oldest entry silently dropped when exceeding 50.

6. Step-by-Step Walkthrough

Step 1 — Import the Sample

Open the Gallery → Tests → find "User API Smoke Tests" (test-user-api-smoke). Click Load Test. You should see a feature group named "User API" with 2–3 scenarios.

Step 2 — Open the Structure History Panel

Click the clock/history icon (🕒) on the feature group header bar. The StructureChangeLogPanel opens below the header. Initially it shows: "No structure changes recorded".

📋 Note Gallery imports don't create structure log entries. The log only records changes you make after importing.

Step 3 — Add a Scenario

Click "+ Scenario" on the feature group. Name it "Delete User". Check the Structure History panel — you should see:

BadgeActionEntityTime
+Scenario addedDelete Userjust now

Step 4 — Add a Test to the New Scenario

Inside "Delete User", click "+ Test". Name it "Delete User by ID". The structure log now shows 2 entries (newest first):

BadgeActionEntityContext
+Test addedDelete User by IDin Delete User
+Scenario addedDelete User—

Notice the scenarioName field: test-level entries show "in [scenario name]" so you know which scenario the test belongs to.

Step 5 — Rename a Scenario

Double-click the "Delete User" scenario name and rename it to "User Deletion". The log now shows:

BadgeActionEntityDetail
~Scenario renamedUser DeletionDelete User → User Deletion

The detail field shows the old → new name transition.

Step 6 — Use Filters

The toolbar has 4 filter buttons: All, Scenario, Test, Group.

  • Click Scenario — shows only scenario-level entries (added, removed, renamed, moved).
  • Click Test — shows only test-level entries.
  • Click Group — shows only feature group rename entries.
  • Click All — shows everything.

The footer updates to show filtered vs. total count: "2 of 3 entries".

Step 7 — Rename the Feature Group

Double-click the feature group name "User API" and rename it to "User Management API". A fg-renamed entry appears. Filter to Group to see it isolated.

Step 8 — Move a Scenario

If you have a second feature group, drag a scenario from "User Management API" to the other group. Two entries are created:

  • In the source group: − "Scenario moved out — [name] → to [target FG]"
  • In the target group: + "Scenario moved in — [name] → from [source FG]"

This dual-entry design means each feature group has a complete local history — you don't need to check other groups to understand what happened.

Step 9 — Delete an Entry

Click the × button on any log entry. It's immediately removed from the list. This is useful for cleaning up noise (e.g., accidental adds followed by removes).

function deleteLogEntry(fg: FeatureGroup, entryId: string): FeatureGroup {
  return {
    ...fg,
    structureLog: (fg.structureLog ?? []).filter(e => e.id !== entryId),
  };
}

Step 10 — Clear All Entries

Click Clear in the toolbar. A confirmation appears: "Clear all? [Yes] [No]". Click Yes to wipe the entire log. Click No to cancel.

The confirmation prevents accidental clearing — especially important since clearing is irreversible.

7. Where the Log Lives

The structure log is stored directly on the FeatureGroup object:

interface FeatureGroup {
  id: string;
  name: string;
  scenarios: TestScenario[];
  structureLog?: StructureChangeEntry[];  // ← here
  // ... other fields
}

This means:

  • The log persists with the feature group — saved to IndexedDB alongside scenarios and tests.
  • Exporting a test suite includes the structure log (unless stripped with stripStructureLog()).
  • Each feature group has its own independent log — no cross-group log.

10. Try It Yourself

Exercise 1 — Build a Change History

Import "User API Smoke Tests" from the Gallery. Perform these actions:

  1. Add a scenario "Error Handling".
  2. Add a test "404 Not Found" inside "Error Handling".
  3. Rename "Error Handling" to "Edge Cases".
  4. Remove the test "404 Not Found".

Verify: 4 entries in the Structure History. Use filters to isolate scenario vs. test entries.

Exercise 2 — Cross-Group Moves

Create a second feature group "Auth API". Drag a scenario from "User API" to "Auth API". Open the Structure History in both groups. Verify that the source shows "moved out" and the target shows "moved in" with the correct group names in the detail field.

Exercise 3 — Cap & Clear

Rapidly add and remove scenarios to generate 10+ entries. Delete individual entries using the × button. Then use Clear to wipe the log. Verify the confirmation dialog works correctly.

💡 Tip The structure log is especially valuable in team workflows. When you import a shared test suite and notice structural changes, the log tells you exactly what your teammates modified — even without Git history.
