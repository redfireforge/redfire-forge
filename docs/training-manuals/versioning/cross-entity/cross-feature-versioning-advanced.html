1. The Big Picture

RedfireForge versions 7 entity types independently. Each has its own storage, caps, and auto-save triggers. This capstone manual ties them all together into a cohesive release workflow.

📐 Workflow
Nodes, edges, variables, services
Cap: 30 · Trigger: explicit save
🧪 Test Definition
Scenarios, expectations, assertions
Cap: 20 · Trigger: save with changes
📨 Request Definition
URL, method, headers, body, auth
Cap: 15 · Trigger: navigation
📜 Script Library
Name, description, code
Cap: 15 · Trigger: edit save
📋 Audit Log
Environment, service, auth CRUD
Cap: 500 entries · Trigger: any mutation
📊 Run Baselines
P50, P95, P99, error rate, throughput
Cap: 10 · Trigger: manual mark
📁 Feature Group Structure
Scenario/test/FG mutations
Cap: 50 · Trigger: any mutation
📦 Export/Import
4 version checkboxes + structure log
Selective inclusion per type

4. Phase 1 — Pre-Release Snapshot

Before making any changes, capture the current state across all entity types.

4.1 Save All Workflows

Open each workflow and click Save. This creates the first workflow version for each. Since there are no prior versions, each gets the summary "initial version".

4.2 Save Test Definitions

Open the test editor. Make sure all test definitions are saved. The first version of each test definition is auto-created with the current scenario structure and expectations.

4.3 Mark a Run Baseline

Run the full test suite. When results appear, click Mark as Baseline. Name it [2026-05-01] Pre-Release v3.0. This captures P50, P95, P99, error rate, and throughput as your reference point.

4.4 Note the Audit Log State

Open the Audit Log panel. Note how many entries exist. After the development phase, you'll filter by date to see only the new changes.

📋 Snapshot Checklist At this point you should have: workflow versions (1 each), test definition versions (1 each), a named run baseline, and an audit log starting point. No request versions yet (they're created on navigation), and no script library versions yet (they're created on edit).

5. Phase 2 — Development Sprint

Simulate a development sprint by making changes across all entity types. Each change auto-creates version history.

5.1 Modify Workflow: Add Retry Logic

  1. Open the "Webhook Trigger" workflow.
  2. Add a new node: a retry wrapper around the HTTP request node.
  3. Connect the retry node to the existing flow.
  4. Click Save.

A new workflow version is created. The change summary will show something like "1 node added, 2 edges added".

5.2 Update Test Definition: Change Expected Status

  1. Open the "Create Order" test (or equivalent scenario in the E-Commerce suite).
  2. Change the expected HTTP status from 200 to 201.
  3. Save the test.

A new test definition version is created. The Overview tab in the diff shows the expectation change.

5.3 Update Request Definition: Add Header

  1. Open the "Get All Users" request.
  2. Add a new header: X-Idempotency-Key: abc-123.
  3. Navigate to another request (or collection) to trigger auto-save.

A request definition version is created on navigation. The Headers tab in the diff shows 1 header added.

5.4 Modify Script Library: Add Validation Rule

  1. Open the Script Library Manager from any workflow.
  2. Create (or edit) a "Response Validator" library.
  3. Add a new validation function.
  4. Click Save.

A script library version is created. Click History to see the "Used by" section — this shows which workflows will be affected by your change.

5.5 Change Environment Config

  1. Go to Settings → Environments.
  2. Change the staging environment base URL (e.g., from https://staging-v2.example.com to https://staging-v3.example.com).

The audit log automatically records this change with timestamp, old value, new value, and the action type (environment-update).

5.6 Rearrange Feature Groups

  1. In the scenario builder, move a test from one feature group to another.
  2. Rename a feature group to reflect the sprint's focus.

The structure change log captures both mutations with action types (test-move, fg-rename).

6. Phase 3 — Change Audit Trail

Now review what changed during the sprint using each versioning tool.

6.1 Audit Log Review

  1. Open the Audit Log panel.
  2. Filter by date: set the range to cover your sprint (e.g., last 7 days).
  3. You should see entries for every environment, service, and auth change.
  4. Click Export CSV to save a copy for your team's sprint retrospective.

6.2 Workflow Version Comparison

  1. Open the "Webhook Trigger" workflow version panel.
  2. Select the pre-release version and the post-change version.
  3. Click Compare. The 4-tab diff shows:
    • Overview — summary of changes.
    • Nodes — the new retry node highlighted.
    • Edges — new connections.
    • Variables/Services — any config changes.

6.3 Script Library Impact Check

  1. Open the "Response Validator" library's History panel.
  2. Check the "Used by" section — lists all affected workflows.
  3. Compare the two versions to see exactly what code changed (Code tab).

7. Phase 4 — Regression Detection

Run your tests and compare against the pre-release baseline.

  1. Run the full E-Commerce test suite.
  2. When results appear, click Compare with Baseline.
  3. Select the [2026-05-01] Pre-Release v3.0 baseline.
  4. Review the comparison:
    • P50 latency — did it increase by more than 15%? If yes, RegressionAlert fires.
    • Error rate — did it increase by more than 1 percentage point?
    • Throughput — did it drop significantly?
🚨 Regression Alert Thresholds RedfireForge flags regressions at: P50 latency > 15% increase, Error Rate > 1pp increase, P95/P99 > 20% increase. These alerts help you catch performance degradation before deploying.

7.1 Investigating a Regression

Suppose P50 latency increased 25% and one test is failing. Use cross-entity traceability to find the root cause:

CheckToolFinding
Was the request URL changed?Request version diff → URL tab✅ URL unchanged
Were test expectations changed?Test definition diff → Overview tab✅ Expectations unchanged
Was the workflow modified?Workflow version diff → Nodes tab✅ Only retry node added (expected)
Was the environment changed?Audit Log → filter by environment❌ Base URL changed 2 days ago!

Root cause: The staging environment base URL was updated to a new server that has higher latency. The version diff for the request is clean, the test expectations are correct, but the infrastructure changed. Without the audit log, this would have been much harder to diagnose.

Before deploying, create a full backup with all version history.

8.1 Export with Version Checkboxes

Open the Export dialog. You'll see checkboxes for each version type:

8.2 Verify Before Export

Use countVersions() to check what's included:

// countVersions() returns:
{
  workflowVersionCount: 4,      // 2 workflows × 2 versions each
  definitionVersionCount: 3,     // 3 test defs with versions
  requestVersionCount: 2,        // 2 request defs with versions
  scriptLibraryVersionCount: 1,  // 1 script library with versions
  structureLogCount: 2           // 2 structure change entries
}

8.3 Import on Another Machine

When importing, the same checkboxes appear. You can selectively import version data — useful when you want the latest test definitions but don't need historical versions from another team member's export.

💡 Export as Safety Net Before major refactors, export with ALL version checkboxes checked. If the refactor goes wrong, you can import the backup and restore to the pre-refactor state — complete with all version history.

9. Version Hygiene Best Practices

9.1 Naming Conventions

EntityConventionExample
Workflow versions[Sprint-XX] Description[Sprint-42] Added retry logic
Test definitions[Sprint-XX] Description[Sprint-42] Updated status assertions
Run baselines[YYYY-MM-DD] Context[2026-05-01] Pre-Release v3.0
Script librariesvN Descriptionv3 Added retry with backoff

9.2 Regular Cleanup

  • Workflows (30 cap): Delete unnamed versions periodically. Keep labeled milestones (sprint boundaries, releases).
  • Test definitions (20 cap): Label versions that correspond to spec changes. Let minor iterations be auto-evicted.
  • Script libraries (15 cap): Always rename versions with meaningful descriptions. Code changes without labels are hard to identify later.
  • Audit log (500 cap): Export to CSV before clearing. Use exports in sprint retrospectives.
  • Run baselines (10 cap): Keep one baseline per release. Delete intermediate benchmarks after the release ships.
  • FG structure log (50 cap): Review after major reorganizations. Clear once the new structure is stable.

9.3 Cap Awareness

All version arrays use FIFO eviction — the oldest entry is silently dropped when the cap is reached. This means:

  • You can never lose the most recent version (it's always index 0).
  • Important historical versions (release milestones) should be labeled so you notice if they're about to be evicted.
  • If a cap feels too low, export the entity before it's evicted — the export preserves all versions at the time of export.

10. Cross-Entity Traceability Map

When debugging a failure, use this decision tree to trace the root cause across entity types:

Test is failing
├── Check request version diff
│   ├── URL changed? → Request was modified
│   ├── Headers changed? → Auth or config issue
│   └── Body changed? → Payload was updated
├── Check test definition diff
│   ├── Expectations changed? → Test was updated
│   └── Assertions changed? → Validation rules modified
├── Check workflow version diff (if workflow-driven)
│   ├── Nodes added/removed? → Flow logic changed
│   └── Variables changed? → Runtime config modified
├── Check script library impact (if scripts involved)
│   ├── Which workflows affected? → Check "Used by"
│   └── What code changed? → Review Code tab diff
├── Check audit log
│   ├── Environment URL changed? → Infrastructure issue
│   ├── Service config changed? → Backend change
│   └── Auth credentials rotated? → Auth issue
└── Compare run baseline
    ├── P50 regressed? → Performance degradation
    └── Error rate increased? → Reliability issue
📋 The Power of Cross-Entity Debugging No single versioning feature tells the whole story. A test failure might be caused by a request change (request versioning), a test update (test versioning), a workflow modification (workflow versioning), a shared script change (script impact analysis), or an infrastructure change (audit log). Cross-entity traceability lets you check all of these systematically.

11. Team Collaboration Patterns

11.1 Sprint Boundary Workflow

  1. Sprint start: Export current state with all versions → archive as sprint-41-start.json.
  2. During sprint: Make changes freely. Versions auto-accumulate.
  3. Sprint end: Run full test suite. Compare with sprint-start baseline. Export → sprint-41-end.json.
  4. Retrospective: Export audit log CSV. Review infrastructure changes as a team.

11.2 Release Checklist

1Label all workflow versions with release tagWorkflow versioning
2Label script library versionsScript library versioning
3Run tests and mark baselineRun baselines
4Compare with previous release baselineBaseline comparison
5Export audit log for the release periodAudit log
6Full export with all version dataExport/import
7Clean up unlabeled versionsAll version panels

11.3 Shared Library Governance

For teams sharing script libraries across workflows:

  • Before editing: Always check "Used by" in the impact analysis panel.
  • Blast radius > 5 workflows: Consider creating a new library version instead of modifying in place. Migrate workflows one at a time.
  • After editing: Re-run all affected workflows (use "Used by" as your checklist).
  • Document changes: Rename the version with a meaningful label immediately after saving.

12. Try It Yourself

Exercise 1 — Full Release Simulation

Import the three gallery samples. Follow the complete flow:

  1. Pre-release snapshot (save everything, mark baseline).
  2. Make 5+ changes across different entity types.
  3. Review all changes using version diffs and audit log.
  4. Run tests and compare with baseline.
  5. Export with all version checkboxes.

Verify you can trace every change back to its source using cross-entity traceability.

Exercise 2 — Root Cause Analysis

Intentionally break a test by changing the environment base URL (not the request URL). Run tests. Use the traceability map from Section 10 to systematically find the root cause. Verify the audit log is the tool that reveals the issue.

Exercise 3 — Version Cap Management

Pick one entity type (e.g., script library with cap 15). Make 16+ changes. Verify the oldest version is evicted. Label a mid-range version, then continue making changes. Is your labeled version still there after the cap is reached, or was it evicted? (It will be evicted — FIFO doesn't preserve labels. This is why exports are your safety net.)

Exercise 4 — Export/Import Round-Trip

Export with all version checkboxes. Clear all data (Settings → Data Management). Import the export file. Verify all version histories are restored. Verify the audit log is restored. Verify baselines are accessible.
