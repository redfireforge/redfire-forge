Workflow Version History

Easy — Training Manual

Learn to create, browse, rename, and restore workflow version snapshots. Every time you save a workflow, RedfireForge captures a fingerprinted snapshot you can revisit at any time.

RedfireForge v0.8.0
Difficulty: ★☆☆
Gallery Sample: sample-workflow-001 · jsonplaceholder.typicode.com

1. Purpose & Use Case

When developing and refining workflows, changes accumulate quickly — adding nodes, rewiring edges, tuning variables. Without version history, a bad change can mean starting over. Workflow versioning solves this by automatically capturing a snapshot every time you save.

Real-world scenario: "Evolving an Order Processing Workflow"

You've imported a "Create → Extract → Verify" workflow from the Gallery. It works perfectly — creates a post on JSONPlaceholder, checks the response, waits, fetches the post, and verifies the user. Now you want to add a notification step. With versioning, you can evolve the workflow confidently, knowing every milestone is saved and restorable.

💡 Tip This manual uses the Gallery sample sample-workflow-001 ("Create → Extract → Verify") as its starting point. Import it from the Gallery before beginning the walkthrough.

2. Concepts You'll Learn

  • Automatic snapshots — how saving a workflow triggers a version snapshot (if the fingerprint changed).
  • Fingerprint deduplication — the cyrb53 hash prevents duplicate snapshots when nothing changed.
  • Version panel — browsing the version list (newest-first) with timestamps, labels, and node/edge counts.
  • Inline rename — double-click a version label to give it a meaningful name.
  • Restore with undo safety — reverting to an older version with an automatic undo snapshot.
  • 30-version FIFO cap — the oldest version is evicted when the cap is reached.
  • Persistence — versions survive browser tab closes and app restarts via localStorage / Tauri store.

3. Key Data Model

Understanding the underlying data helps you reason about what's captured in each snapshot:

interface WorkflowVersion {
  id: string;             // Unique version ID (UUID)
  timestamp: number;      // When the snapshot was taken (epoch ms)
  label?: string;         // Optional user-assigned label
  fingerprint: string;    // cyrb53 hash of nodes + edges + variables + services
  nodes: WorkflowNode[];  // Full snapshot of all nodes
  edges: WorkflowEdge[];  // Full snapshot of all edges
  variables: Record<string, string>;  // Workflow variables
  services: WorkflowService[];        // Service configurations
}

const MAX_WORKFLOW_VERSIONS = 30;

The fingerprint is computed from a normalized representation of nodes, edges, variables, and services. Node positions are included, so moving a node counts as a change. Node data (configuration) is included, so changing a URL or body also counts.

// Fingerprint computation
computeWorkflowFingerprint(nodes, edges, variables, services): string
// → normalizes all arrays → JSON.stringify → cyrb53 hash → hex string
📋 Note The fingerprint includes node position, type, id, and data — but excludes transient UI state like selection or animation. Edge fingerprints include source, target, and sourceHandle/targetHandle.

5. Step-by-Step Walkthrough

Step 1 — Import the Sample

Open the Gallery from the sidebar. Navigate to the Workflows tab. Find "Create → Extract → Verify" (sample-workflow-001). Click Import.

The workflow loads into the editor with 6 nodes connected by edges. You should see the full flow laid out on the canvas.

Step 2 — Verify It Works

Click Run in the toolbar. The workflow executes:

  1. Creates a post on JSONPlaceholder (POST /posts) — returns 201 Created.
  2. Checks the status code equals 201 (Condition node).
  3. Waits 1 second (Delay node).
  4. Fetches the created post (GET /posts/1).
  5. Verifies the userId field is correct.

All nodes should show green checkmarks when complete.

Step 3 — Save the Workflow

Click Save in the toolbar. This triggers the versioning system:

  1. The current state (nodes, edges, variables, services) is normalized.
  2. computeWorkflowFingerprint() produces a cyrb53 hash.
  3. Since there are no existing versions, the fingerprint is unique.
  4. createWorkflowVersion() creates a snapshot with all node/edge/variable/service data.
  5. addVersionToList() prepends it to the versions[] array.
  6. The toolbar badge updates to show "1".

Step 4 — Make Changes

Add a 7th node to the workflow — an HTTP Request node for sending a notification:

PropertyValue
LabelSend Notification
MethodPOST
URLhttps://jsonplaceholder.typicode.com/posts
Body{"title": "Order Complete", "body": "Post verified", "userId": 1}

Connect it after the Verify node. The workflow now has 7 nodes and one additional edge.

Step 5 — Save Again

Click Save. The fingerprint differs from Version 1 (new node + new edge), so a new snapshot is created. The toolbar badge updates to "2".

Step 6 — Open Version History

Click the clock/history icon (🕰️) in the toolbar. The WorkflowVersionPanel slides open, showing 2 entries:

  • Version 2 (newest) — timestamp, "7 nodes, N edges"
  • Version 1 — timestamp, "6 nodes, N edges"

Versions are always listed newest-first.

Step 7 — Browse Versions

Each version entry displays:

  • Timestamp — formatted date and time (e.g., "May 1, 2026, 2:30 PM").
  • Label — initially empty (auto-generated placeholder). Editable via double-click.
  • Change summary — auto-generated by generateChangeSummary(). Example: "1 node added, 1 edge added".
  • Fingerprint — hover to see the full hash string.

Step 8 — Restore Version 1

Click Restore on Version 1. The workflow reverts to the original 6-node state:

  1. The system first takes an undo snapshot of the current state (safety net).
  2. The canvas updates — the "Send Notification" node and its edge disappear.
  3. The workflow is now identical to the imported Gallery sample.
📋 Note Restoring does NOT delete Version 2. Both versions remain in the history. A restore simply replaces the current editor state with the snapshot's data.

Step 9 — Verify Undo Safety

Press Ctrl+Z (or ⌘Z on macOS). The workflow reverts to the 7-node state (before the restore). This works because the system took an automatic undo snapshot before restoring.

The undo stack persists in localStorage (debounced at 500ms), so it survives page refreshes.

Step 10 — Rename a Version

In the Version Panel, double-click the label area of Version 1. A text input appears. Type "Original Gallery Sample" and press Enter. The version is now labeled for easy identification.

💡 Tip Use descriptive labels for milestone versions: "Before refactor", "Sprint 42 release", "Pre-deploy v2.1". This makes it easier to find the right version when you need to restore.

6. How the 30-Version Cap Works

Workflows can hold up to 30 versions. When a 31st version is created, the oldest (first) version is automatically evicted — this is FIFO (First-In, First-Out).

export function addVersionToList(
  versions: WorkflowVersion[],
  newVersion: WorkflowVersion,
  max = MAX_WORKFLOW_VERSIONS  // 30
): WorkflowVersion[] {
  const updated = [newVersion, ...versions];
  return updated.slice(0, max);
  // If versions.length was 30, the 30th (oldest) entry is dropped
}

Key points about FIFO eviction:

  • Named/renamed versions are NOT exempt from eviction. If the oldest version has a label, it's still removed.
  • Eviction is silent — no confirmation dialog. The version simply disappears from the list.
  • To preserve important versions beyond the cap, export the workflow with "Include Version History" before the version is evicted.

7. Fingerprint Deduplication in Action

Try this experiment: open a workflow, make NO changes, and click Save. Does a new version appear?

No. The fingerprint of the current state matches the latest version's fingerprint, so createWorkflowVersion() detects the duplicate and skips creating a new snapshot. This prevents the version list from filling up with identical entries.

8. Persistence Across Sessions

Version data is stored in localStorage (web mode) or the Tauri store (desktop mode). This means:

  • Close the browser tab → reopen → versions are still there.
  • Restart the app → versions survive.
  • The undo stack also persists (key: perf-test-wf-undo-{workflowId}, debounced 500ms).

You can verify persistence by closing the browser, reopening RedfireForge, navigating to the workflow, and opening the Version Panel — all versions and labels should be intact.

9. Try It Yourself

Exercise 1 — Build Version History

Starting from the imported Gallery sample, make 5 distinct changes and save after each one. Verify the version list grows to 6 entries (1 initial + 5 changes). Check that each entry shows the correct node/edge count.

Exercise 2 — Test Fingerprint Dedup

Make a change to the workflow and save (creating a new version). Then press Ctrl+Z to undo the change, restoring the previous state. Save again. Does a new version appear? (It should not — the fingerprint matches the version before your change.)

Exercise 3 — Persistence Check

Create several labeled versions. Close the browser tab entirely. Reopen RedfireForge and navigate to the same workflow. Open the Version Panel. Verify all versions — including labels — are intact.

💡 Tip These exercises build on each other. Complete them in order to develop a full understanding of how workflow versioning behaves in different scenarios.
