Workflow Version Advanced

Advanced — Training Manual

Master bulk version operations, export/import with version history, FIFO cap rotation strategies, and undo persistence across sessions. This manual covers the power-user workflows for managing long-lived workflow version histories.

1. Purpose & Use Case

As workflows grow in complexity and undergo dozens of iterations, your version history becomes a valuable record of every design decision. But with a 30-version cap and no automatic archival, you need strategies for managing version lifecycle — knowing when to name, when to export, and how the FIFO cap affects your history.

Real-world scenario: "Complex Orchestrator — Long-lived Version Management"

You've imported the "Sub-Workflow Orchestrator" — a 9-node workflow that fetches users, sets variables, delegates to a sub-workflow, logs results, and handles success/failure branching. Over the next sprint, you'll evolve it through 10+ iterations: adding retry logic, tuning variables, swapping API endpoints, and inserting error handlers. This manual teaches you to manage that growing version history like a pro.

💡 Prerequisites Complete workflow-version-history-easy and workflow-version-diff-medium before starting this manual. You should be comfortable with creating snapshots, browsing history, restoring versions, and reading the 4-tab diff modal.

2. Concepts You'll Learn

  • Bulk version selection & deletion — select multiple checkboxes and delete old versions in one operation.
  • Export with version history — save a workflow JSON that includes the full versions[] array.
  • Import with version history — load an exported workflow and choose whether to bring versions along.
  • 30-version FIFO cap rotation — what happens when you exceed the cap and how to prepare.
  • Version naming as documentation — naming conventions that make version history useful months later.
  • Undo persistence across sessions — how the undo stack survives page refreshes via localStorage.
  • Cross-session restore — restoring versions from previous development sessions.
  • Strip & count helpers — using stripWorkflowVersions() and countWorkflowVersions() for clean exports.

3. Key Data Model

The advanced operations work with the same WorkflowVersion interface, but now you need to understand the export/import helpers:

// Export helpers
export function stripWorkflowVersions(
  workflow: WorkflowDefinition
): WorkflowDefinition {
  // Returns a copy with versions[] removed — clean export
  const { versions, ...rest } = workflow;
  return rest;
}

export function countWorkflowVersions(
  workflow: WorkflowDefinition
): number {
  // Returns the number of versions (used for export UI badge)
  return workflow.versions?.length ?? 0;
}

// FIFO cap enforcement
export function addVersionToList(
  versions: WorkflowVersion[],
  newVersion: WorkflowVersion,
  max = MAX_WORKFLOW_VERSIONS  // 30
): WorkflowVersion[] {
  const updated = [newVersion, ...versions];
  return updated.slice(0, max);
  // oldest entry silently evicted when list exceeds max
}

3.1 Undo Persistence

The undo/redo stack is separate from version history. It stores the last 10 state snapshots and persists to localStorage:

// Undo stack storage key
const UNDO_KEY = `perf-test-wf-undo-${workflowId}`;

// Persistence is debounced at 500ms to prevent excessive writes
// during rapid edits. The stack survives:
//   - Page refresh (F5)
//   - Browser tab close + reopen
//   - App restart (Tauri)
//
// The undo stack does NOT survive:
//   - localStorage.clear()
//   - Incognito/private browsing (no persistence)
📋 Note The undo stack and version history serve different purposes. Undo captures every micro-change (move a node 10px, type one character) for immediate Ctrl+Z. Versions capture full-state snapshots on explicit save — they're your named milestones.

5. Step-by-Step Walkthrough

Step 1 — Import & Build Initial History

Open the Gallery → Workflows. Find "Sub-Workflow Orchestrator" (sample-workflow-sub-workflow). Click Import.

The workflow loads with 9 nodes. Click Save to create Version 1. This is your baseline — the unmodified Gallery sample.

Immediately rename this version: open the Version Panel (🕰️ icon), double-click the label, type "Original Gallery Import", press Enter.

Step 2 — Simulate Iterative Development

Over the next steps, you'll make a series of changes that simulate real sprint work. Save after each change to accumulate versions:

Save #ChangeExpected Summary
V2Add a Delay node (2s) between Fetch Users and Set Variables"1 node added, 2 edges modified"
V3Add variable {{retryCount}} = 3"1 variable added"
V4Change the Fetch Users URL from /users to /users?_limit=5"1 node modified"
V5Add an HTTP Request node: POST /posts (notification). Wire it after the Success node."1 node added, 1 edge added"
V6Add variable {{notifyEmail}} = admin@example.com"1 variable added"
V7Remove the Delay node (revert V2's change). Rewire edges."1 node removed, 2 edges modified"
V8Change the Condition node's expression from status === 200 to status < 300"1 node modified"

After 8 saves, your Version Panel should show 8 entries, newest first.

Step 3 — Rename Key Milestones

Open the Version Panel. Double-click labels to name the important milestones:

  • V1 → "Original Gallery Import" (already done)
  • V5 → "Added Notification"
  • V7 → "Removed Delay (cleanup)"
  • V8 → "Relaxed Status Check"

Leave V2–V4 and V6 unnamed — they're intermediate steps. Named versions are easier to find when the list grows long, but remember: named versions are NOT exempt from FIFO eviction.

⚠️ Important Naming a version does NOT protect it from eviction. When the 30-version cap is reached, the oldest version is removed regardless of whether it has a label. To preserve important versions permanently, export the workflow with version history included.

Step 4 — Bulk Delete Old Versions

Sometimes you want to clean up intermediate versions that clutter the history. In the Version Panel:

  1. Check the checkboxes on V2, V3, V4, and V6 (the unnamed intermediate versions).
  2. The "Delete Selected" button activates, showing the count (4).
  3. Click "Delete Selected".
  4. A confirmation dialog appears: "Delete 4 versions? This cannot be undone."
  5. Confirm. The version list now shows 4 entries: V1, V5, V7, V8 — all named milestones.
📋 Note Bulk deletion is permanent and cannot be undone with Ctrl+Z. The undo stack tracks workflow state changes (nodes, edges, variables), not version panel operations. If you accidentally delete a version, your only recovery option is importing from a previously exported file.

Step 5 — Export with Version History

Now let's export the workflow including all remaining version snapshots:

  1. Click Export in the toolbar (or Version Panel).
  2. The Export dialog shows a checkbox: "Include Version History". Check it.
  3. A badge shows "4 versions" (from countWorkflowVersions()).
  4. Click Export. A .json file is saved.

Open the exported JSON in a text editor. You'll see the versions array containing 4 full snapshots, each with its own nodes[], edges[], variables, services[], timestamp, label, and fingerprint.

// Exported JSON structure (simplified)
{
  "name": "Sub-Workflow Orchestrator",
  "nodes": [ ... ],    // Current state
  "edges": [ ... ],
  "variables": { "retryCount": "3", "notifyEmail": "admin@example.com" },
  "versions": [
    {
      "id": "v8-uuid",
      "timestamp": 1746100800000,
      "label": "Relaxed Status Check",
      "fingerprint": "a3f2c1...",
      "nodes": [ ... ],   // Full snapshot at V8
      "edges": [ ... ],
      "variables": { ... },
      "services": [ ... ]
    },
    // ... V7, V5, V1
  ]
}

Step 6 — Import with Version History

Test the import path to verify version portability:

  1. Create a new empty workflow (or use a different workspace).
  2. Click Import → select the exported JSON file.
  3. The Import dialog shows: "Include Version History" checkbox. Toggle it ON.
  4. Click Import. The workflow loads with the current state (V8's nodes/edges/variables).
  5. Open the Version Panel — all 4 named versions appear with their original timestamps and labels.
💡 Tip To share a workflow without its history, either uncheck "Include Version History" during export, or use the stripWorkflowVersions() helper programmatically. This produces a clean JSON with only the current state — smaller file size and no historical data exposed.

Step 7 — Import WITHOUT Version History

Repeat Step 6 but with the checkbox OFF:

  1. Import the same exported JSON into another new workflow.
  2. Leave "Include Version History" unchecked.
  3. Click Import. The workflow loads with the current state.
  4. Open the Version Panel — it's empty. Zero versions. A clean slate.
  5. Save once → Version 1 is created from scratch with a new fingerprint.

6. The 30-Version FIFO Cap in Practice

Let's observe what happens when the version list hits the 30-version ceiling.

6.1 Building to the Cap

Starting from a workflow with 4 versions (after bulk deletion), make 26 more changes and saves to reach exactly 30 versions. A quick way to do this:

  1. Add a new variable → Save (V5)
  2. Rename the variable → Save (V6)
  3. Change the variable value → Save (V7)
  4. Repeat with different variables, node positions, or URL tweaks until you reach 30.

The Version Panel now shows 30 entries. Your original "Original Gallery Import" (V1) is at the very bottom — the oldest entry.

6.2 Triggering Eviction

Make one more change and save. This creates Version 31, but the cap is 30:

// What happens internally
const updated = [newVersion, ...versions]; // 31 entries
return updated.slice(0, 30);              // drops entry at index 30 (oldest)
  • Version 31 (newest) appears at the top of the list.
  • "Original Gallery Import" (the oldest) silently disappears from the bottom.
  • No confirmation dialog. No warning. It's gone.
  • The version count stays at 30.

6.3 Rotation Strategy

To avoid losing important versions to FIFO eviction:

StrategyHowWhen
Export before cap Export with "Include Version History" when approaching 25+ versions Before a major refactor or sprint boundary
Bulk delete intermediates Delete unnamed intermediate versions to free slots for meaningful saves Weekly cleanup during active development
Name-then-export Name the milestone versions, export, then continue — the export preserves them even if evicted later At release milestones

7. Undo Persistence Across Sessions

The undo/redo stack is independent of version history but equally important for day-to-day work.

7.1 How It Persists

  • Every workflow state change (add node, move node, edit config, etc.) pushes to the undo stack.
  • The stack is written to localStorage under key perf-test-wf-undo-{workflowId}.
  • Writes are debounced at 500ms — rapid changes batch into a single write.
  • The stack holds the last 10 snapshots.

7.2 Cross-Session Undo

Try this experiment:

  1. Make 3 changes to the workflow (add a node, move it, change its URL).
  2. Close the browser tab entirely.
  3. Reopen RedfireForge. Navigate to the same workflow.
  4. Press Ctrl+Z three times.
  5. Each undo reverts one change — the URL change, the position, and finally the node addition.

This works because the undo stack was written to localStorage before the tab closed (debounced within 500ms of your last change).

7.3 Undo vs Version Restore

FeatureUndo (Ctrl+Z)Version Restore
GranularityEvery micro-changeFull-state snapshots on save
Stack size10 entries30 entries
Triggered byAny edit (automatic)Explicit save
Survives refreshYes (localStorage)Yes (localStorage)
Can be redoneYes (Ctrl+Y)No (but undo snapshot taken first)
NamingNoYes (inline rename)

8. Cross-Session Restore

Version history and undo stacks both survive browser restarts. Here's a comprehensive persistence test:

  1. Create a workflow with 5 named versions spanning multiple editing sessions.
  2. Close the browser completely (not just the tab — quit the browser).
  3. Reopen RedfireForge. Navigate to the workflow.
  4. Open the Version Panel — all 5 versions should be present with their labels and timestamps.
  5. Click Restore on the oldest version.
  6. The workflow reverts. An undo snapshot is created automatically.
  7. Press Ctrl+Z — the restore is undone. The current state is back.

Everything works exactly as if you had never left the page.

📋 Note In desktop mode (Tauri), persistence uses the Tauri store instead of localStorage. The behavior is identical — versions and undo stacks survive app restarts. The Tauri store also supports larger data sizes than localStorage's ~5MB limit.

9. Try It Yourself

Exercise 1 — Export with and without History

Create a workflow with 10 versions. Export it twice:

  • Export A — with "Include Version History" checked.
  • Export B — with the checkbox unchecked.

Open both JSON files. Compare their sizes. Export A should be significantly larger (contains 10 full snapshots). Verify that Export B has no versions array.

Import Export A into a new workflow with history toggled ON. Verify all 10 versions appear. Import Export B — verify zero versions and a fresh start.

Exercise 2 — FIFO Cap Rotation

Starting from a clean workflow, rapidly create 32 versions by making small changes and saving:

  1. Name Version 1 as "Do Not Delete".
  2. Make 31 more saves.
  3. Open the Version Panel. Is "Do Not Delete" still there? (No — it was evicted at Version 31.)
  4. Reflect: how would you prevent this? (Answer: export before reaching the cap.)

Exercise 3 — Undo Persistence

  1. Open a workflow. Make 5 changes (do NOT save).
  2. Close the browser tab.
  3. Reopen the workflow.
  4. Press Ctrl+Z five times. Do all 5 changes undo correctly?
  5. Now press Ctrl+Y five times. Do all 5 changes redo?

This confirms that the undo stack persists independently of version history.

💡 Tip These exercises cover the most common advanced scenarios. After completing them, you'll have a strong mental model of how version history, undo stacks, export/import, and FIFO eviction interact in real workflows.
