Workflow Version Diff

Medium — Training Manual

Compare two workflow versions side-by-side using the 4-tab diff modal. Understand exactly what changed — which nodes were added, edges rewired, variables modified, and services updated — with color-coded change indicators.

RedfireForge v0.8.0
Difficulty: ★★☆
Gallery Sample: sample-workflow-webhook · jsonplaceholder.typicode.com

1. Purpose & Use Case

Version history tells you when changes happened. The version diff tells you what changed. When a workflow has 10+ versions, being able to compare any two versions side-by-side is essential for understanding evolution, debugging regressions, and documenting changes for your team.

Real-world scenario: "Webhook Order Processing — Adding Fraud Detection"

You've imported a webhook-triggered order processing workflow from the Gallery. It handles incoming orders by checking inventory and routing to either "Process Order" or "Out of Stock Alert". Your task is to add a fraud detection step between the inventory check and the routing condition. After making these changes, you want to compare the before and after to verify exactly what was added, removed, and modified.

2. Prerequisites

  • Completed the workflow-version-history-easy manual (understand snapshots, restore, version panel).
  • Basic familiarity with the workflow editor (nodes, edges, variables).

3. Concepts You'll Learn

  • Multi-select comparison — checking two version checkboxes to activate the Compare button.
  • 4-tab diff modal — Nodes, Edges, Variables, and Services tabs showing categorized changes.
  • Change indicators — color coding: Added Removed Modified Unchanged
  • Property-level diff — expanding a modified node to see exactly which properties changed (via json-diff-kit).
  • VersionDiffResult — the data structure driving the diff display.

4. Key Data Model

The computeVersionDiff() function compares two WorkflowVersion objects and returns a structured result:

interface VersionDiffResult {
  addedNodes: WorkflowNode[];
  removedNodes: WorkflowNode[];
  modifiedNodes: Array<{
    id: string;
    label: string;
    old: WorkflowNode;
    new: WorkflowNode;
  }>;
  addedEdges: WorkflowEdge[];
  removedEdges: WorkflowEdge[];
  variableChanges: {
    added: Array<{ key: string; value: string }>;
    removed: Array<{ key: string; value: string }>;
    modified: Array<{ key: string; oldValue: string; newValue: string }>;
  };
  serviceChanges: {
    added: WorkflowService[];
    removed: WorkflowService[];
    modified: Array<{
      id: string;
      name: string;
      old: WorkflowService;
      new: WorkflowService;
    }>;
  };
}

The diff algorithm works by matching entities by id:

  • A node in the newer version but not in the older → Added
  • A node in the older version but not in the newer → Removed
  • A node in both but with different data → Modified (property-level diff available)
  • A node in both with identical data → Unchanged

6. Step-by-Step Walkthrough

Step 1 — Import and Save as Version 1

Open the Gallery → Workflows tab. Find "Webhook Trigger" (sample-workflow-webhook). Click Import.

The workflow loads with 6 nodes. Click Save immediately to create Version 1 — this captures the original Gallery state as your baseline.

Step 2 — Evolve the Workflow

Now add fraud detection between the inventory check and the routing condition:

  1. Add a Script Node — Label: "Fraud Score Check". Position it between "Check Inventory" and the Condition node.
  2. Add a variable — Name: fraudThreshold, Value: 85.
  3. Rewire edges:
    • Remove the direct edge from "Check Inventory" → Condition.
    • Add edge: "Check Inventory" → "Fraud Score Check".
    • Add edge: "Fraud Score Check" → Condition.

Click Save to create Version 2.

Step 3 — Open Version History

Click the clock/history icon in the toolbar. The Version Panel shows two entries: Version 2 (newest) and Version 1.

Step 4 — Select Two Versions

Check the checkbox on both Version 1 and Version 2. When exactly 2 versions are selected, the "Compare" button activates in the panel toolbar.

📋 Note You can only compare exactly 2 versions at a time. Checking a 3rd checkbox will deselect the oldest selection. The older version is always treated as the "baseline" and the newer as the "current" state.

Step 5 — Open the Diff Modal

Click Compare. The WorkflowVersionDiff modal opens with 4 tabs across the top: Nodes, Edges, Variables, Services.

Step 6 — Nodes Tab

The Nodes tab shows all nodes from both versions, categorized by change type:

The Services tab shows service configuration changes. In this case, no services were added, removed, or modified — all HTTP requests still target jsonplaceholder.typicode.com.

Step 10 — Interpret the Full Picture

Across all 4 tabs, the diff tells a clear story:

  • 1 node added (Fraud Score Check) — new capability.
  • 1 edge removed, 2 edges added — the flow was rerouted through the new node.
  • 1 variable added (fraudThreshold) — new configuration for the fraud check.
  • 0 service changes — no infrastructure impact.
💡 Tip The diff summary at the top of the modal shows aggregate counts: "1 node added, 1 edge removed, 2 edges added, 1 variable added". Use this for a quick overview before diving into individual tabs.

7. Understanding Modified Nodes

In the walkthrough above, all existing nodes were unchanged. But when you modify a node (change its URL, method, body, script, or any configuration), the Nodes tab shows it as Modified with an expandable property-level diff.

Example: Changing a node's URL

If you changed "Check Inventory" from GET /posts to GET /posts/1, the Nodes tab would show:

NodeStatusChanged Properties
Check Inventory Modified data.url: "/posts" → "/posts/1"

Click the modified node to expand the full property diff. RedfireForge uses json-diff-kit to display a structured side-by-side comparison of the old vs. new node data, highlighting exactly which JSON properties changed.

// How modified nodes are detected
const modifiedNodes = [];
for (const [id, olderNode] of olderNodeMap) {
  const newerNode = newerNodeMap.get(id);
  if (newerNode && JSON.stringify(olderNode.data) !== JSON.stringify(newerNode.data)) {
    modifiedNodes.push({ id, label: newerNode.data?.label, old: olderNode, new: newerNode });
  }
}

8. Variable & Service Change Details

Variable Changes

The variableChanges section of VersionDiffResult categorizes variable changes into three groups:

  • Added — variable exists in the newer version but not the older. Shows key + value.
  • Removed — variable exists in the older version but not the newer. Shows key + last known value.
  • Modified — variable exists in both but the value changed. Shows key + old value → new value.

Service Changes

Services are compared by id. A modified service shows the old and new WorkflowService objects side-by-side, highlighting changes to name, baseUrl, headers, or auth configuration.

9. Try It Yourself

Exercise 1 — Modify Without Adding/Removing

Starting from a saved version, change an existing node's URL (don't add or remove any nodes). Save. Compare the two versions. Verify the Nodes tab shows exactly 1 Modified node with a property-level diff showing the old URL → new URL. The Edges, Variables, and Services tabs should show zero changes.

Exercise 2 — Variable Value Change

Change a variable's value (e.g., fraudThreshold from 85 to 70) without changing its name. Save and compare. Verify the Variables tab shows it as Modified with oldValue: "85" → newValue: "70".

Exercise 3 — Identity Comparison

Select the same version twice (check its checkbox, uncheck, check again — or compare version 1 with version 1). The diff should show zero changes across all 4 tabs. This confirms the diff algorithm is working correctly — identical inputs produce an empty diff.

💡 Tip Use the diff modal when reviewing changes before deploying a workflow update. It serves as a visual "code review" for workflow modifications — you can verify that only intended changes were made.
