1. What Is Request Definition Versioning?

Every time you modify an API request (URL, method, headers, body, auth) and then navigate away, RedfireForge automatically saves a snapshot of the request definition. This creates a version history you can browse, compare, and restore — like "undo" for your API requests.

Real-world scenario: "Accidental Header Deletion"

You're testing a REST API that requires a custom X-Api-Key header. While experimenting, you accidentally remove it and add a Bearer token instead. You switch to another request, come back, and realize the API key is gone. Without versioning, you'd have to remember the exact header value. With request definition versioning, you open the History tab, find the version that had the header, and click Restore.

2. The RequestDefinitionVersion Data Model

Each version entry stores:

interface RequestDefinitionVersion {
  id: string;           // UUID — unique identifier
  timestamp: number;    // Date.now() when saved
  changeSummary: string; // Human-readable: "URL changed, 1 header added"
  label?: string;       // Optional user-assigned label
  snapshot: RequestDefinitionSnapshot;
}

The snapshot captures the request's editable fields:

interface RequestDefinitionSnapshot {
  name: string;
  url: string;
  method: HttpMethod;       // GET, POST, PUT, PATCH, DELETE
  headers: KeyValue[];      // Filtered — only non-empty keys
  body: string;
  bodyType?: string;        // 'json', 'form-data', 'raw', etc.
  bodyForm?: KeyValue[];    // Form data entries (filtered)
  auth: AuthConfig;         // Type + credentials
}
📋 What's Excluded The snapshot deliberately excludes: id (internal), savedQueryParams (ephemeral UI state), catalogMeta (immutable API reference data), and any runtime fields like response data or history.

3. How Auto-Save Works

Versions are created automatically — you don't click "Save Version." The trigger is navigation:

  1. You edit Request A (change URL, add a header).
  2. You click on Request B to switch.
  3. The selectRequest() hook detects the switch.
  4. It calls autoSaveVersion(requestA) on the previous request.
  5. autoSaveVersion() checks if Request A has changed since the last version.
  6. If changed → creates a new version. If identical → skips (deduplication).

3.1 Fingerprint-Based Deduplication

To determine "has it changed?", RedfireForge computes a canonical JSON fingerprint:

function computeSnapshotFingerprint(snapshot: RequestDefinitionSnapshot): string {
  return JSON.stringify(canonicalize(snapshot));
}

function hasChanged(request: RequestItem, versions: RequestDefinitionVersion[]): boolean {
  if (versions.length === 0) return true;  // Always save first version
  const latest = versions[0];              // Newest first
  const current = createSnapshot(request);
  return computeSnapshotFingerprint(current)
      !== computeSnapshotFingerprint(latest.snapshot);
}

The canonicalize() function sorts object keys alphabetically and recursively normalizes nested objects. This means:

  • {"b": 1, "a": 2} and {"a": 2, "b": 1} produce the same fingerprint.
  • Only genuine content changes trigger a new version — reordering JSON keys doesn't.
  • Empty headers (key = "") are filtered out before snapshotting, so adding/removing empty rows doesn't create versions.

3.2 The autoSaveVersion() Function

function autoSaveVersion(
  request: RequestItem,
  maxVersions: number = MAX_VERSIONS,  // 15
): RequestDefinitionVersion[] | null {
  const versions = request.definitionVersions ?? [];
  if (!hasChanged(request, versions)) return null;  // No change → no save
  const version = createRequestDefinitionVersion(request, versions);
  return addVersionToList(versions, version, maxVersions);
}

Returns null if no changes detected — the caller checks this and skips the update.

💡 Tip Switching to another request and switching back without making changes will NOT create a duplicate version. The fingerprint comparison prevents this.

4. The 15-Version Cap

Request definitions are capped at 15 versions per request (vs. 20 for test definitions). When you exceed the limit, the oldest version is evicted:

const MAX_VERSIONS = 15;

function addVersionToList(
  versions: RequestDefinitionVersion[],
  version: RequestDefinitionVersion,
  maxVersions: number = MAX_VERSIONS,
): RequestDefinitionVersion[] {
  return [version, ...versions].slice(0, maxVersions);
  //       ^-- newest first         ^-- trim oldest
}

This is a FIFO (First-In-First-Out) strategy:

  • New versions are prepended to the array (index 0 = newest).
  • .slice(0, 15) trims the array to the cap.
  • The oldest version (index 15+) is silently discarded.
  • No warning is shown — this is by design to keep the UX simple.
⚠️ Important If you have a version you want to keep permanently, give it a label (e.g., "Working v1.0"). Labeled versions aren't automatically preserved — they're evicted like any other — but the label makes them easy to identify before they rotate out. Consider exporting critical requests to preserve their full history.

5. Change Summaries

Each version includes a human-readable changeSummary generated by generateChangeSummary():

function generateChangeSummary(
  oldSnap: RequestDefinitionSnapshot,
  newSnap: RequestDefinitionSnapshot,
): string {
  const changes: string[] = [];

  if (oldSnap.name !== newSnap.name) changes.push('name changed');
  if (oldSnap.url !== newSnap.url) changes.push('URL changed');
  if (oldSnap.method !== newSnap.method)
    changes.push(`method → ${newSnap.method}`);

  // Header diff — counts added/removed, detects modifications
  const headerDiff = newHeaders.length - oldHeaders.length;
  if (headerDiff > 0) changes.push(`${headerDiff} header added`);
  else if (headerDiff < 0) changes.push(`${-headerDiff} header removed`);
  else if (headersModified) changes.push('headers modified');

  if (oldSnap.body !== newSnap.body) changes.push('body modified');
  if (oldSnap.bodyType !== newSnap.bodyType)
    changes.push(`body type → ${newSnap.bodyType ?? 'none'}`);
  if (formDataChanged) changes.push('form data modified');
  if (authChanged)
    changes.push(`auth ${oldSnap.auth.type} → ${newSnap.auth.type}`);

  return changes.join(', ') || 'no changes detected';
}

7. Step-by-Step Walkthrough

Step 1 — Import the Sample

Open the Gallery → Requests → find "Get All Users" (req-get-all-users). Click Load Request. The request appears in your collection.

Step 2 — Verify Initial State

Click the History tab in the request editor. You should see: "No definition history yet". This is because no versions have been saved — versions are created on navigation, not on load.

Step 3 — Make Your First Change

Change the URL from https://dummyjson.com/users to https://dummyjson.com/users?limit=10.

Now switch to another request in your collection (any request). Switch back to "Get All Users." Open the History tab — you should now see 1 version with summary initial version.

💡 Why "initial version"? The first version always shows initial version because there's no previous snapshot to compare against. Subsequent versions show specific change summaries.

Step 4 — Create Multiple Versions

Make the following changes, switching to another request after each one:

  1. Add header: Accept: application/json → switch away → switch back.
  2. Change method to POST and add body: {"limit": 10} → switch away → switch back.
  3. Add header: X-Request-ID: test-123 → switch away → switch back.
  4. Change auth from None to Bearer Token with value test-token-abc → switch away → switch back.

After all changes, the History tab should show 5 versions, newest first:

#TimestampChange Summary
1(most recent)auth none → bearer
21 header added
3method → POST, body modified
41 header added
5(oldest)initial version

Step 5 — Rename a Version

Double-click the label of version #5 ("initial version" timestamp). A text field appears. Type Original GET and press Enter. The version now shows your custom label instead of the timestamp.

You can also click the ✏ Rename button on any version row.

Under the hood, this calls:

function renameVersion(
  versions: RequestDefinitionVersion[],
  versionId: string,
  label: string,
): RequestDefinitionVersion[] {
  return versions.map(v =>
    v.id === versionId ? { ...v, label } : v
  );
}

Step 6 — Restore a Previous Version

Click ↩ Restore on the "Original GET" version (#5). The request editor immediately reverts to:

  • Method: GET
  • URL: https://dummyjson.com/users
  • Headers: empty
  • Body: empty
  • Auth: None

The restore applies a partial patch to the request:

function restoreFromVersion(version: RequestDefinitionVersion): Partial<RequestItem> {
  const s = version.snapshot;
  return {
    name: s.name,
    url: s.url,
    method: s.method,
    headers: s.headers.length > 0 ? s.headers : [{ key: '', value: '' }],
    body: s.body,
    bodyType: s.bodyType,
    bodyForm: s.bodyForm,
    auth: s.auth,
  };
}
⚠️ Important Restoring does not create a new version automatically. The version is only created when you navigate away. If you restore and immediately navigate, the restored state becomes the latest version.

Step 7 — Delete a Version

Click ✕ Delete on version #3 (the POST change). Confirm if prompted. The version is removed from the list. Version count drops to 4.

function deleteVersion(
  versions: RequestDefinitionVersion[],
  versionId: string,
): RequestDefinitionVersion[] {
  return versions.filter(v => v.id !== versionId);
}

Step 8 — Test Deduplication

Without making any changes, switch to another request and back. Check the History tab — the version count should remain the same. The fingerprint comparison detected no changes and skipped saving.

Now make a purely cosmetic change: reorder JSON body keys (if present). Switch away and back. The version count should still remain the same — the canonical fingerprint normalizes key order.

Step 9 — Test the 15-Version Cap

Create versions rapidly by making small changes (append /1, /2, ... to the URL) and switching between requests each time. When you reach 15 versions, the next save will evict the oldest version from the list.

Check that the footer shows 15 versions (never more).

Step 10 — Select Versions for Comparison

Click the checkbox on two different versions. A "Compare" button appears in the toolbar. Click it to open the diff view (covered in the Request Definition Diff manual).

You can select at most 2 versions. Selecting a third deselects nothing — the UI limits selection to 2.

10. Try It Yourself

Exercise 1 — Build a 5-Version History

Import "Get All Users" from the Gallery. Create 5 versions by making these changes (switch away after each):

  1. Add ?limit=5 to the URL.
  2. Add header Accept: application/json.
  3. Change method to POST.
  4. Add a JSON body: {"skip": 0, "limit": 5}.
  5. Change auth to Bearer Token with value my-token.

Verify: 5 versions in History tab. Label version #5 (oldest) as "Original GET". Restore it and verify the request reverts to a simple GET with no headers/body/auth.

Exercise 2 — Deduplication Test

Without changing anything, switch away 3 times and back. Verify the version count stays at 5 — no duplicates created.

Exercise 3 — Cap Eviction

Create 12 more versions (total 17 attempts). Verify the History tab shows exactly 15 versions. Check that the 2 oldest versions were evicted. Was your "Original GET" label preserved if it was within the newest 15?

💡 Tip If your labeled version was evicted (it was the oldest), this demonstrates why periodic exports are important for preserving critical request configurations. Consider using collection export to save the full request with its version history.
