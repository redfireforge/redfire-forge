1. Why Impact Analysis Matters

A script library is shared code — multiple workflow script nodes can include the same library. When you modify a library, every workflow that references it is affected. Without impact analysis, you're making changes blind.

Real-world scenario: "The Shared Auth Token Refresher"

Your team has an "Auth Token Refresher" library with OAuth token refresh logic. It's used by 4 workflows: User Registration, Payment Processing, Order Management, and Admin Health Check. You need to change the token expiry logic. Before touching the code, you check the "Used by" section in the version panel — it lists all 4 workflows and the specific script nodes that reference this library. You now have a retesting checklist before you even make the change.

⚠️ The Blast Radius Problem Script libraries are the only versioned entity in RedfireForge with built-in cross-entity dependency tracking. Unlike workflow versioning (self-contained) or request versioning (per-request), script changes ripple across workflows. Impact analysis is your safety net.

2. The LibraryUsage Data Model

2.1 LibraryUsage Interface

interface LibraryUsage {
  workflowId: string;     // ID of the workflow containing the reference
  workflowName: string;   // Human-readable workflow name
  nodeId: string;         // ID of the specific script node
  nodeLabel: string;      // Display label of the node (falls back to "Script")
}

2.2 How References Work

Each workflow script node has a data.libraryIds array listing the IDs of included libraries:

// Inside a workflow node:
{
  id: "node-5",
  type: "script",
  data: {
    label: "Refresh Token",
    libraryIds: ["lib-auth-001", "lib-utils-002"],
    code: "// Node-specific code that uses library functions..."
  }
}

When you include a library via checkbox in the Script Library Manager, its ID is added to libraryIds. When unchecked, it's removed.

3. How findLibraryUsages() Works

The core impact analysis function scans all workflows for nodes that reference a specific library:

function findLibraryUsages(
  workflows: Array<{
    id: string;
    name: string;
    nodes: Array<{
      id: string;
      type: string;
      data: Record<string, unknown>
    }>
  }>,
  libraryId: string,
): LibraryUsage[] {
  const usages: LibraryUsage[] = [];
  for (const wf of workflows) {
    for (const node of wf.nodes) {
      if (node.type === 'script') {
        const data = node.data as {
          libraryIds?: string[];
          label?: string;
        };
        if (data.libraryIds?.includes(libraryId)) {
          usages.push({
            workflowId: wf.id,
            workflowName: wf.name,
            nodeId: node.id,
            nodeLabel: data.label || 'Script',
          });
        }
      }
    }
  }
  return usages;
}

Key Implementation Details

  • Only nodes with type === 'script' are scanned — other node types are skipped.
  • If a node has no label, it falls back to "Script".
  • The function runs dynamically — it scans current workflows each time the version panel opens.
  • If a node references the library in libraryIds but isn't type 'script', it won't be found (by design).
  • A single workflow can produce multiple usages if it has multiple script nodes referencing the same library.

5. The 2-Tab Diff Viewer

When you select two versions and click Compare, the ScriptLibraryVersionDiff component shows a diff view with two tabs:

5.1 Overview Tab

Shows field-level changes for metadata fields:

  • Name — old → new (only shown if changed).
  • Description — old → new (shows "(empty)" for blank values).
  • If neither name nor description changed: displays "No metadata changes — code may differ."
// ScriptLibraryDiffResult structure
{
  nameChanged: true,
  oldName: "Auth Helper",
  newName: "Auth Token Refresher",
  descriptionChanged: false,
  codeChanged: true,
  oldCode: "function refresh() { ... }",
  newCode: "function refreshToken() { ... }"
}

5.2 Code Tab

Shows a full code diff using json-diff-kit:

  • Line numbers on both sides.
  • Inline highlighting — added characters in green, removed in red.
  • Monokai theme for dark code background.
  • Falls back to side-by-side <pre> blocks if json-diff-kit encounters an error.

Tab Badges

Each tab shows a badge count indicating how many changes it contains:

TabBadge Logic

Code1 if code changed, 0 otherwise

6. How the Manager Wires It Together

The ScriptLibraryManager orchestrates the full flow:

  1. History button — Each library row shows a "History" button. If versions exist, a badge shows the count.
  2. Click History → sets historyLibId state, which triggers rendering ScriptLibraryVersionPanel.
  3. Usage computation — findLibraryUsages(workflows, historyLibId) runs as a useMemo, recalculating only when the selected library or workflow list changes.
  4. Auto-save on edit — handleSaveEdit() calls autoSaveVersion(lib) before applying changes, capturing the pre-edit state.
// In ScriptLibraryManager.tsx
const historyUsages = useMemo<LibraryUsage[]>(() => {
  if (!historyLibId || workflows.length === 0) return [];
  return findLibraryUsages(workflows, historyLibId);
}, [historyLibId, workflows]);

const handleSaveEdit = (id, name, description, code) => {
  const lib = libraries.find(l => l.id === id);
  let updatedLibs = libraries;
  if (lib) {
    const versioned = autoSaveVersion(lib);
    if (versioned !== lib) {
      updatedLibs = libraries.map(l =>
        l.id === id ? versioned : l
      );
    }
  }
  onLibrariesChange(
    updateScriptLibrary(updatedLibs, id, { name, description, code })
  );
};
📋 Note The workflows prop is optional (defaults to []). If no workflows are provided, impact analysis simply returns an empty usages list and the "Used by" section is hidden.

7. Step-by-Step Walkthrough

Step 1 — Create a Shared Script Library

Create a library called "Auth Token Refresher" with this code:

async function refreshAuthToken(currentToken) {
  const response = await fetch('/api/auth/refresh', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${currentToken}`
    },
    body: JSON.stringify({ token: currentToken })
  });
  if (!response.ok) {
    throw new Error(`Token refresh failed: ${response.status}`);
  }
  const data = await response.json();
  return data.accessToken;
}

Step 2 — Reference in Multiple Workflows

Create (or open) 3 workflows. In each, add a Script node. Open the Script Library Manager and check the "Auth Token Refresher" library. This adds the library's ID to the node's data.libraryIds array.

  • Workflow 1: "Payment Processing" — Script node labeled "Refresh Token"
  • Workflow 2: "Order Management" — Script node labeled "Auth Check"
  • Workflow 3: "Admin Health Check" — Script node labeled "Get Token"

Step 3 — Check Impact Analysis

Go back to the Script Library Manager. Click History on "Auth Token Refresher". At the top of the version panel, you see:

Used by: Payment Processing › Refresh Token · Order Management › Auth Check · Admin Health Check › Get Token

This is your blast radius — 3 workflows will be affected by any change to this library.

Step 4 — Make a Change

Click the back button to return to the library list. Edit "Auth Token Refresher" — add retry logic:

async function refreshAuthToken(currentToken, retries = 3) {
  for (let attempt = 1; attempt <= retries; attempt++) {
    try {
      const response = await fetch('/api/auth/refresh', {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          'Authorization': `Bearer ${currentToken}`
        },
        body: JSON.stringify({ token: currentToken })
      });
      if (!response.ok) {
        throw new Error(`Token refresh failed: ${response.status}`);
      }
      const data = await response.json();
      return data.accessToken;
    } catch (err) {
      if (attempt === retries) throw err;
      await new Promise(r => setTimeout(r, 1000 * attempt));
    }
  }
}

Click Save. A new version is auto-created capturing the pre-edit state.

Step 5 — Compare Versions

Click History. You now see 1 version (the pre-change state). Check both the current-state awareness and the version entry. Select the version and the current state (if available) or make another edit to have 2 versions. Select both checkboxes and click Compare.

Overview Tab

Shows: name unchanged, description unchanged. Message: "No metadata changes — code may differ."

Code Tab

Shows the full side-by-side diff:

  • Red lines — removed code (the old simple version)
  • Green lines — added code (the retry wrapper, try/catch, delay)
  • Inline highlighting shows exact character changes within modified lines.

Step 6 — Document Impact

Before closing the version panel, note the "Used by" tags. These are your retesting checklist:

  1. Payment Processing → Run the workflow, verify token refresh works with retry.
  2. Order Management → Run, verify auth check passes.
  3. Admin Health Check → Run, verify token retrieval succeeds.

Step 7 — Safe Restore

If the retry logic introduces issues (e.g., too many retries slowing down workflows), click ↩ Restore on the original version. All 3 workflows immediately get the simpler version. Re-run them to confirm.

8. Edge Cases and Gotchas

8.1 Multiple Nodes in Same Workflow

If "Payment Processing" has two script nodes both referencing "Auth Token Refresher", findLibraryUsages() returns two entries for that workflow — one per node. Each node is tracked individually.

8.2 Dynamic Scanning

The usage list is computed live from the current workflow state. If you delete a workflow or remove a library reference, the "Used by" list updates the next time you open the version panel.

8.3 No Workflows Provided

If the workflows prop is empty (e.g., no workflows exist), the "Used by" section is hidden entirely. The function returns an empty array.

8.4 Non-Script Nodes Ignored

Only type === 'script' nodes are scanned. If another node type somehow has libraryIds in its data, it won't appear in the usage list.

8.5 Diff Fallback

If json-diff-kit throws an error (e.g., the code is not valid for diffing), the Code tab falls back to plain side-by-side <pre> blocks. You still see the old and new code — just without line-level highlighting.

9. Impact Analysis as a Team Practice

9.1 Pre-Change Review

Before modifying any shared library:

  1. Open the version panel.
  2. Check "Used by" to understand the blast radius.
  3. If the list is long (5+ workflows), consider whether the change is backward-compatible.
  4. If it's a breaking change, plan to test all listed workflows.

9.2 Post-Change Verification

After modifying a library:

  1. Run each workflow listed in "Used by".
  2. If any workflow fails, compare the version diff to understand what changed.
  3. Restore if needed — the previous version is one click away.

9.3 When to Split Libraries

If a library has 10+ usages and frequent changes, consider splitting it into smaller, focused libraries. This reduces the blast radius of each change.

10. Try It Yourself

Exercise 1 — Remove a Workflow

Delete one of the workflows that uses your shared library. Open the version panel again. Verify the "Used by" list now shows one fewer entry. This confirms findLibraryUsages() dynamically scans current workflows.

Exercise 2 — Duplicate References

In a single workflow, add two script nodes that both reference the same library. Open the version panel. Count the usage tags — you should see two entries for the same workflow (one per node). This is correct: each node is an independent consumer.

Exercise 3 — Empty Usages

Remove all library references (uncheck the library in all script nodes across all workflows). Open the version panel. The "Used by" section should be completely hidden — no tags, no label. This is the safest state: the library has no dependents, so you can freely modify or delete it.

💡 Pro Tip Use impact analysis as a pre-change safety check, not just a post-change audit. Before modifying a shared library, always check "Used by" first. If the blast radius is large, consider creating a new version of the library instead of modifying the existing one — then migrate workflows one at a time.
