1. What Are Script Libraries?

Script libraries are reusable JavaScript functions that workflow script nodes can import. Instead of duplicating utility code in every script node, you write it once as a library and include it by checking a box.

Each library has three editable fields:

  • Name — identifier displayed in the library manager (e.g., "Response Helpers").
  • Description — optional documentation (e.g., "Shared parsing and validation functions").
  • Code — the JavaScript source that gets prepended to script nodes that include it.

Real-world scenario: "The Evolving JSON Flattener"

You create a "JSON Flatten" library with a recursive function. Over time you add error handling, optimize for performance, then realize the optimized version has a bug. With script library versioning, you open the History panel, find the "v2 Error Handling" version, and restore it — keeping the improvements while reverting the broken optimization.

2. The Data Model

2.1 ScriptLibrarySnapshot

A snapshot captures only the editable content — no metadata:

interface ScriptLibrarySnapshot {
  name: string;
  description: string;
  code: string;
}

Excluded from snapshots: id, createdAt, updatedAt, versions array itself.

2.2 ScriptLibraryVersion

interface ScriptLibraryVersion {
  id: string;             // UUID
  timestamp: number;      // Date.now() when saved
  changeSummary: string;  // "code changed (+5 lines), name changed"
  label?: string;         // Optional user-assigned label
  snapshot: ScriptLibrarySnapshot;
}

2.3 Storage

Versions are stored directly on the ScriptLibrary object in its versions array:

interface ScriptLibrary {
  id: string;
  name: string;
  description: string;
  code: string;
  createdAt: string;      // ISO timestamp
  updatedAt: string;      // ISO timestamp
  versions?: ScriptLibraryVersion[];  // ← version history
}

3. How Auto-Save Works

Script library versions are created when you save edits — not on navigation like request definitions. The flow:

  1. You open a library in the Script Library Manager and click Edit.
  2. You modify the name, description, or code.
  3. You click Save.
  4. Before applying your edits, the manager calls autoSaveVersion() on the current state.
  5. If the current state differs from the latest version → a new version is created.
  6. Then your edits are applied.
function autoSaveVersion(
  lib: ScriptLibrary,
  maxVersions: number = MAX_VERSIONS,  // 15
): ScriptLibrary {
  if (!hasChanged(lib)) return lib;    // No change → return as-is

  const snapshot = createSnapshot(lib);
  const versions = lib.versions ?? [];
  const changeSummary = versions.length > 0
    ? generateChangeSummary(versions[0].snapshot, snapshot)
    : 'initial version';

  const version: ScriptLibraryVersion = {
    id: uuidv4(),
    timestamp: Date.now(),
    changeSummary,
    snapshot,
  };

  const updated = [version, ...versions].slice(0, maxVersions);
  return { ...lib, versions: updated };
}
💡 Key Difference Unlike request/test definitions which return null when nothing changed, autoSaveVersion() for scripts returns the original library object unchanged. The caller can check referential equality (versioned !== lib) to know if a version was created.

4. Change Summaries with Line Counts

Script change summaries are special — they include line count diffs for code changes:

function generateChangeSummary(
  oldSnap: ScriptLibrarySnapshot,
  newSnap: ScriptLibrarySnapshot,
): string {
  const parts: string[] = [];
  if (oldSnap.name !== newSnap.name) parts.push('name changed');
  if (oldSnap.description !== newSnap.description) parts.push('description changed');
  if (oldSnap.code !== newSnap.code) {
    const oldLines = oldSnap.code.split('\n').length;
    const newLines = newSnap.code.split('\n').length;
    const diff = newLines - oldLines;
    if (diff > 0) parts.push(`code changed (+${diff} lines)`);
    else if (diff < 0) parts.push(`code changed (${diff} lines)`);
    else parts.push('code changed');
  }
  return parts.length ? parts.join(', ') : 'no changes';
}

5. The 15-Version Cap

Script libraries use the same 15-version cap as request definitions:

const MAX_VERSIONS = 15;

// In autoSaveVersion():
const updated = [version, ...versions].slice(0, maxVersions);
return { ...lib, versions: updated };

FIFO eviction: oldest version silently dropped when cap is reached. Versions are stored newest-first (index 0 = most recent).

⚠️ Important Script code can be significantly longer than request definitions. 15 versions of a 200-line library = 3,000+ lines stored. If you have many libraries with large codebases, consider periodically deleting old versions to manage storage.

6. Fingerprint-Based Deduplication

Like all RedfireForge versioning, scripts use canonical JSON fingerprinting to prevent duplicate versions:

function hasChanged(lib: ScriptLibrary): boolean {
  const versions = lib.versions ?? [];
  if (versions.length === 0) return true;  // Always save first version
  const latest = versions[0];
  const current = createSnapshot(lib);
  return computeSnapshotFingerprint(current)
      !== computeSnapshotFingerprint(latest.snapshot);
}

The fingerprint covers all three snapshot fields (name, description, code). If any of them differ from the latest version, a new version is created. If all three are identical, no version is saved.

7. Step-by-Step Walkthrough

Step 1 — Create a Script Library

Open a workflow editor. Click the Script Libraries button (or the equivalent in the toolbar). Click "+ New Library". Fill in:

  • Name: JSON Flatten
  • Description: Recursively flatten nested JSON objects
  • Code:
function flatten(obj, prefix = '') {
  const result = {};
  for (const key in obj) {
    const fullKey = prefix ? `${prefix}.${key}` : key;
    if (typeof obj[key] === 'object' && obj[key] !== null) {
      Object.assign(result, flatten(obj[key], fullKey));
    } else {
      result[fullKey] = obj[key];
    }
  }
  return result;
}

Click Create.

Step 2 — Verify Initial State

Click History on the library. You should see: "No version history yet". The first version is created when you edit the library, not when you create it.

Step 3 — Make Your First Edit

Click Edit. Add error handling:

function flatten(obj, prefix = '') {
  if (obj === null || obj === undefined) return {};
  if (typeof obj !== 'object') return { [prefix || 'value']: obj };
  const result = {};
  for (const key in obj) {
    const fullKey = prefix ? `${prefix}.${key}` : key;
    if (Array.isArray(obj[key])) {
      obj[key].forEach((item, i) => {
        Object.assign(result, flatten(item, `${fullKey}[${i}]`));
      });
    } else if (typeof obj[key] === 'object' && obj[key] !== null) {
      Object.assign(result, flatten(obj[key], fullKey));
    } else {
      result[fullKey] = obj[key];
    }
  }
  return result;
}

Click Save. The auto-save captures the pre-edit state as a version.

Step 4 — Check Version History

Click History. You should see 1 version:

#TimestampSummary
1(just now)initial version

Step 5 — Create More Versions

Edit the library again — add a try/catch wrapper around the whole function. Save. Edit again — change the function name to flattenJSON. Save. You now have 3 versions:

Step 6 — Rename Versions

Double-click the label of version #3 (oldest). Type v1 Basic and press Enter. Rename #2 to v2 Error Handling and #1 to v3 Renamed.

function renameVersion(
  lib: ScriptLibrary,
  versionId: string,
  label: string,
): ScriptLibrary {
  return {
    ...lib,
    versions: versions.map(v =>
      v.id === versionId ? { ...v, label: label.trim() || undefined } : v,
    ),
  };
}

Note: setting an empty label ("") removes the label (reverts to timestamp display).

Step 7 — Restore a Previous Version

Click ↩ Restore on "v1 Basic". The library immediately reverts to the original simple recursive flatten — name, description, and code all restored:

function restoreFromVersion(
  lib: ScriptLibrary,
  versionId: string,
): ScriptLibrary {
  const version = versions.find(v => v.id === versionId);
  if (!version) return lib;
  return {
    ...lib,
    name: version.snapshot.name,
    description: version.snapshot.description,
    code: version.snapshot.code,
    updatedAt: new Date().toISOString(),
  };
}
📋 Note Restoring updates updatedAt but does NOT auto-create a new version. The version is only created on the next edit save.

Step 8 — Delete a Version

Click ✕ Delete on version #2. It's removed from the list. The version count drops to 2.

Step 9 — Test Deduplication

Click Edit, make no changes, click Save. Check History — the version count should remain the same. The fingerprint detected no changes.

Step 10 — Compare Two Versions

Check the boxes on two versions. Click Compare. The diff view opens (covered in detail in the Script Impact Analysis manual).

10. Try It Yourself

Exercise 1 — Build a 5-Version History

Create a "JSON Flatten" library. Edit it 5 times, making progressively more sophisticated changes:

  1. Basic recursive flatten (initial).
  2. Add null/undefined checks.
  3. Add array handling.
  4. Add try/catch error handling.
  5. Change description to document the new features.

Verify 5 versions in History. Check that code-related summaries include line count diffs.

Exercise 2 — Description-Only Change

Edit the library and change only the description (not the code or name). Save. Verify a new version is created with summary description changed. This confirms description is part of the fingerprint.

Exercise 3 — Restore and Dedup

Restore version #5 (the oldest). The library reverts to the simple version. Now click Edit → Save without making any changes. Does a new version appear? (It depends — if the restored state matches the latest version's fingerprint, no. If it doesn't, yes.) Explore why.

💡 Tip Script libraries are particularly valuable for shared utility code (date formatting, response parsing, auth token handling). Version each library independently so you can trace exactly when a shared function changed — and which workflows it might affect.
