Test Definition Diff

Medium — Training Manual

Master the 5-tab diff modal for comparing test definition versions. See exactly what changed — URL, headers, body, auth, and extractions — with color-coded indicators and property-level detail via json-diff-kit.

RedfireForge v0.5.6
Difficulty: ★★☆
Gallery Sample: test-ecommerce-full · dummyjson.com

1. Purpose & Use Case

Knowing that a test changed isn't enough — you need to know what changed and how. The 5-tab diff modal breaks down version differences into logical categories so you can review changes with surgical precision before deciding to keep or revert them.

Real-world scenario: "E-Commerce Test Suite — Comprehensive Configuration Evolution"

You've imported the "E-Commerce Full Suite" — 6 scenarios testing DummyJSON's product, search, cart, and user APIs. Over a sprint, you evolve one scenario from a simple GET to a POST with JSON body, authentication, and response extractions. The diff modal lets you compare the original and evolved versions across all 5 dimensions.

💡 Prerequisites Complete test-definition-history-easy before starting this manual. You should be comfortable with creating snapshots, browsing history, and restoring versions.

2. Concepts You'll Learn

  • 5-tab diff modal — Overview, Headers, Body, Auth, and Extractions tabs for structured comparison.
  • Tab badges — each tab displays a change count (e.g., "Headers (2)") showing how many items changed.
  • Color-coded indicators — green (added), red (removed), yellow (modified), gray (unchanged).
  • Property-level diff — json-diff-kit shows exact old→new values for modified fields.
  • SnapshotDiffResult — the data structure powering the diff modal.
  • Multi-select comparison — select any two versions for side-by-side comparison.
  • Export with definition versions — include version history when sharing tests.

3. Key Data Model

The diff modal is powered by SnapshotDiffResult, which provides field-level granularity:

interface SnapshotDiffResult {
  // Overview tab
  nameChanged: boolean;
  urlChanged: boolean;
  methodChanged: boolean;

  // Headers tab
  headersAdded: Header[];
  headersRemoved: Header[];
  headersModified: Array<{
    key: string;
    oldValue: string;
    newValue: string;
  }>;

  // Body tab
  bodyChanged: boolean;
  bodyOld?: RequestBody;
  bodyNew?: RequestBody;

  // Auth tab
  authChanged: boolean;
  authOld?: AuthConfig;
  authNew?: AuthConfig;

  // Extractions tab
  extractionsAdded: Extraction[];
  extractionsRemoved: Extraction[];
  extractionsModified: Array<{
    jsonPath: string;
    oldVariable: string;
    newVariable: string;
  }>;
}

// Computed by:
function computeSnapshotDiff(
  older: TestDefinitionSnapshot,
  newer: TestDefinitionSnapshot
): SnapshotDiffResult;

5. Step-by-Step Walkthrough

Step 1 — Import the Sample

Open the Gallery → Tests. Find "E-Commerce Full Suite" (test-ecommerce-full). Click Import.

A FeatureGroup with 6 scenarios loads into your workspace. All scenarios target dummyjson.com — a free JSON API that returns realistic e-commerce data.

Step 2 — Open & Save Version A

Open the "Search Products" scenario. This is a simple GET request:

  • URL: https://dummyjson.com/products/search?q=phone
  • Method: GET
  • Headers: none
  • Body: none
  • Auth: none
  • Extractions: none

Save to create Version A (the baseline).

Step 3 — Evolve to Version B

Now transform this scenario from a simple GET search to a comprehensive POST-based product filter. Make these changes:

3a — Change Method & URL

  • Method: GET → POST
  • URL: https://dummyjson.com/products/search?q=phone → https://dummyjson.com/products/add

3b — Add Headers

KeyValue
Content-Typeapplication/json
Acceptapplication/json

3c — Add Body

{
  "title": "Test Phone",
  "description": "A test product for automation",
  "price": 549,
  "category": "smartphones"
}

3d — Add Auth

Set auth type to Bearer Token with value test-bearer-token-123.

3e — Add Extractions

JSONPathVariable Name
$.idnewProductId

Save to create Version B.

Step 4 — Open History & Select Versions

Click the History tab. Two versions visible. Check the checkbox on both Version A and Version B. The "Compare" button activates.

Step 5 — Open the Diff Modal

Click "Compare". The TestDefinitionVersionDiff modal opens with 5 tabs across the top. Each tab shows a badge with the number of changes in that category.

Step 6 — Overview Tab

The Overview tab shows high-level configuration changes:

FieldVersion AVersion BStatus
NameSearch ProductsSearch ProductsUnchanged
URL/products/search?q=phone/products/addModified
MethodGETPOSTModified

The tab badge shows "Overview (2)" — two fields changed (URL and Method).

Step 7 — Headers Tab

The Headers tab shows header-level diff:

  • + Content-Type: application/json (added)
  • + Accept: application/json (added)

Tab badge: "Headers (2)" — 2 headers added, 0 removed, 0 modified.

Step 8 — Body Tab

The Body tab shows the most dramatic change:

  • Version A: No body (GET request)
  • Version B: Full JSON body with 4 fields

The entire body appears as added (green). For structured JSON, json-diff-kit renders a tree view showing each property. Since there was no body before, every field is "added".

Tab badge: "Body (1)" — body changed from empty to populated.

Step 9 — Auth Tab

The Auth tab shows the authentication transition:

FieldVersion AVersion B
Auth TypeNoneBearer Token
Token—test-bearer-token-123

The type transition is displayed as "None → Bearer Token". The token value appears as added.

Tab badge: "Auth (1)" — auth configuration changed.

Step 10 — Extractions Tab

The Extractions tab lists response data extractions:

  • + $.id → newProductId (added)

Each extraction shows its JSONPath expression and target variable name. Added extractions appear in green, removed in red.

Tab badge: "Extractions (1)" — 1 extraction added.

💡 Tip Tab badges give you an at-a-glance summary of where changes occurred. If you see "Headers (0)" you can skip that tab entirely — nothing changed there. Focus on tabs with non-zero badges.

6. Understanding Modified Items

The walkthrough above showed mostly "added" items (since Version A was minimal). Let's explore what modified items look like.

6.1 Modified Headers

If you change a header's value (not its key), it appears as modified:

  • ~ Accept: application/json → text/plain

The key is unchanged, but the value shows old→new with the yellow modified indicator.

6.2 Modified Body (json-diff-kit)

When both versions have JSON bodies, json-diff-kit provides a structured comparison:

// Version A body                    // Version B body
{                                    {
  "title": "Test Phone",               "title": "Test Phone",      // unchanged
  "price": 549,              →         "price": 599,               // modified
  "category": "smartphones"             "category": "smartphones",  // unchanged
                                        "stock": 25                 // added
}

Each property is individually categorized: unchanged (gray), modified (yellow with old→new), added (green), or removed (red).

6.3 Modified Auth

Changing just the token value (keeping Bearer Token type) shows:

  • Auth Type: Bearer Token (unchanged)
  • Token: test-bearer-token-123 → production-token-456 (modified)

7. Export with Definition Versions

When exporting a test, you can include version history so it travels with the test:

  1. Open the test's export dialog.
  2. Check "Include Definition Versions".
  3. The badge shows the version count (e.g., "5 versions").
  4. Export. The JSON includes a definitionVersions[] array with all snapshots.

When importing, toggle "Include Definition Versions" to bring history along. Without it, the imported test starts with zero definition versions.

📋 Note Definition versions are separate from response versions and rules versions. The export dialog has 3 checkboxes via VersionExportOptions:
  • Include Response Versions — saved response body snapshots
  • Include Rules Versions — validation rule snapshots
  • Include Definition Versions — the configuration snapshots covered in this manual

8. Workflow Diff vs Test Diff

If you've completed the workflow diff manual, here's how the two compare:

AspectWorkflow Diff (4 tabs)Test Definition Diff (5 tabs)
Tab 1Nodes (structural)Overview (URL, method, name)
Tab 2Edges (connections)Headers (key-value pairs)
Tab 3Variables (key-value)Body (JSON/form data)
Tab 4Services (configs)Auth (type + credentials)
Tab 5—Extractions (JSONPath + variable)
Diff enginejson-diff-kit for node datajson-diff-kit for body
Color schemeGreen/Red/Yellow/GrayGreen/Red/Yellow/Gray (same)
Tab badgesChange count per tabChange count per tab

The mental model is the same — select two versions, compare, read tab badges, drill into changes. The tabs just reflect different structural aspects of the entity being compared.

9. Try It Yourself

Exercise 1 — Header Modifications

Add 3 headers to a test, then in a new version remove 2 and modify 1. Compare versions. Verify the Headers tab shows:

  • 2 removed (red)
  • 1 modified (yellow) with old→new value
  • 0 added (no green items)
  • Tab badge: "Headers (3)"

Exercise 2 — Auth Token Change

Change only the auth token value (keep the type as Bearer). Compare versions. The Auth tab should show:

  • Auth Type: unchanged (gray)
  • Token: modified (yellow) with old→new values
  • Tab badge: "Auth (1)"

Exercise 3 — Export with Versions

Export a test with "Include Definition Versions" checked. Import into another scenario with the checkbox ON. Open the History tab on the imported test — verify all version history traveled with it. Then import the same file with the checkbox OFF — verify zero versions.

💡 Tip Exercise 3 is especially important for team workflows. Sharing tests with version history means reviewers can see the evolution of test configuration, not just the final state.
