Test Definition History

Easy — Training Manual

Learn to track, browse, and restore test definition versions. Every time you modify a scenario's configuration — URL, headers, body, auth, or extractions — RedfireForge captures a fingerprinted snapshot you can revisit at any time.

1. Purpose & Use Case

Test definitions evolve constantly — you tweak URLs, add headers, change authentication, refine assertions, and add extractions. Without version history, a misconfigured change can leave you guessing what the original setup looked like. Test definition versioning solves this by automatically capturing a snapshot whenever a meaningful change is saved.

Real-world scenario: "User API Smoke Test — Iterative Refinement"

You've imported the "User API Smoke Test" from the Gallery — 3 scenarios that validate JSONPlaceholder's user endpoints. The tests pass, but now you want to refine them: add request headers, change URL paths to target specific users, and add extractions for downstream use. With versioning, every refinement is captured so you can compare or roll back at any point.

💡 Tip This manual uses the Gallery sample test-user-api-smoke ("User API Smoke Test") as its starting point. Import it from the Gallery before beginning the walkthrough.

2. Concepts You'll Learn

  • Automatic snapshots — how saving a test definition triggers a version snapshot (if the fingerprint changed).
  • Canonical JSON fingerprinting — keys are sorted alphabetically before hashing, so {"a":1,"b":2} and {"b":2,"a":1} produce the same fingerprint.
  • History tab — browsing the version list (newest-first) with timestamps, labels, and change summaries.
  • Change summaries — auto-generated descriptions like "URL changed, 1 header added".
  • Inline rename — double-click a version label to give it a meaningful name.
  • Restore with undo safety — reverting to an older version with an automatic undo snapshot.
  • 20-version FIFO cap — the oldest version is evicted when the cap is reached.
  • Persistence — versions survive browser tab closes and app restarts via localStorage / Tauri store.

3. Key Data Model

Understanding the underlying data helps you reason about what's captured in each snapshot:

interface TestDefinitionVersion {
  id: string;             // Unique version ID (UUID)
  timestamp: number;      // When the snapshot was taken (epoch ms)
  label?: string;         // Optional user-assigned label
  changeSummary?: string; // Auto-generated: "URL changed, 2 headers added"
  snapshot: {
    name: string;         // Scenario name
    url: string;          // Request URL
    method: string;       // HTTP method
    headers: Header[];    // Request headers
    body?: RequestBody;   // Request body (if applicable)
    auth?: AuthConfig;    // Auth configuration
    extractions: Extraction[]; // Response extractions
  };
}

const MAX_TEST_DEFINITION_VERSIONS = 20;

3.1 Canonical JSON Fingerprinting

Unlike workflows (which use cyrb53), test definitions use canonical JSON for fingerprinting. This means object keys are sorted alphabetically before hashing:

// Canonical JSON fingerprinting
function computeSnapshotFingerprint(snapshot: TestDefinitionSnapshot): string {
  // 1. Deep-sort all object keys alphabetically
  // 2. JSON.stringify the sorted object
  // 3. Hash the resulting string
  //
  // This ensures {"url":"...", "method":"GET"}
  // and {"method":"GET", "url":"..."}
  // produce the SAME fingerprint
  return hash(JSON.stringify(sortKeys(snapshot)));
}
📋 Note Canonical JSON fingerprinting guarantees that key ordering differences don't create false-positive "changes". The snapshot content must actually differ for a new version to be created.

5. Step-by-Step Walkthrough

Step 1 — Import the Sample

Open the Gallery from the sidebar. Navigate to the Tests tab. Find "User API Smoke Test" (test-user-api-smoke). Click Import.

The test suite loads as a FeatureGroup with 3 scenarios. Each scenario is pre-configured with URL, method, and assertions.

Step 2 — Open a Test Scenario

Open the "Get All Users" scenario (GET https://jsonplaceholder.typicode.com/users). This is the simplest scenario — a plain GET with status 200 and arrayLength assertions.

Step 3 — Save the Test

Save the test definition. This triggers the versioning system:

  1. The current configuration (URL, method, headers, body, auth, extractions) is captured.
  2. computeSnapshotFingerprint() produces a canonical JSON hash.
  3. Since there are no existing versions, the fingerprint is unique.
  4. A TestDefinitionVersion is created with the full snapshot.
  5. The definitionVersions[] array now has 1 entry.
  6. The History tab badge shows "1".

Step 4 — Add a Header

In the Headers tab, add a new header:

KeyValue
Acceptapplication/json

Save. Version 2 is created. The auto-generated change summary reads: "1 header added".

Step 5 — Change the URL

Change the URL from https://jsonplaceholder.typicode.com/users to https://jsonplaceholder.typicode.com/users/1 (targeting a single user instead of the full list).

Save. Version 3. Change summary: "URL changed".

Step 6 — Add an Extraction

In the Extractions tab, add:

JSONPathVariable Name
$.emailuserEmail

Save. Version 4. Change summary: "1 extraction added".

Step 7 — Open the History Tab

In the Test Editor, click the History tab. The badge shows "4". The list shows all versions newest-first:

  • Version 4 — "1 extraction added" — shows extraction count changed
  • Version 3 — "URL changed" — shows URL diff
  • Version 2 — "1 header added" — shows header count changed
  • Version 1 — initial snapshot — no change summary

Each entry displays a timestamp, optional label, and the auto-generated change summary.

Step 8 — Restore Version 1

Click Restore on Version 1 (the initial snapshot). The test reverts to its original configuration:

  1. The system first takes an undo snapshot of the current state (safety net).
  2. Headers tab: empty (the Accept header disappears).
  3. URL: back to /users (not /users/1).
  4. Extractions: empty (the userEmail extraction disappears).
  5. Auth: unchanged (was empty throughout).
📋 Note Restoring does NOT delete versions 2, 3, or 4. All versions remain in the history. A restore simply replaces the current editor state with the snapshot's data. You can restore any version at any time.

Step 9 — Rename Versions

In the History tab, double-click the label area of key versions:

  • Version 1 → "Initial bare test"
  • Version 4 → "Final with extractions"

Named versions are easier to identify in a long history list. Use descriptive labels at milestone points.

💡 Tip Use labels like "Before auth change", "Sprint 5 config", or "Pre-refactor" to document why a snapshot matters. When your history grows to 15+ versions, labels save time scrolling and reading change summaries.

6. How the 20-Version Cap Works

Test definitions can hold up to 20 versions. When a 21st version is created, the oldest version is automatically evicted — FIFO (First-In, First-Out), identical to workflows but with a lower cap.

// FIFO enforcement for test definition versions
function addDefinitionVersion(
  versions: TestDefinitionVersion[],
  newVersion: TestDefinitionVersion,
  max = MAX_TEST_DEFINITION_VERSIONS  // 20
): TestDefinitionVersion[] {
  const updated = [newVersion, ...versions];
  return updated.slice(0, max);
}

Key points:

  • Named versions are NOT exempt from eviction — same as workflows.
  • Eviction is silent — no confirmation dialog.
  • To preserve important versions, export the test with "Include Definition Versions" checked.
  • The 20-version cap is lower than workflows (30) because test definition snapshots are typically smaller.

7. Fingerprint Deduplication in Action

Try this experiment: open a test, make NO changes, and save. Does a new version appear?

No. The canonical JSON fingerprint of the current state matches the latest version's fingerprint, so no new snapshot is created. This prevents the version list from filling up with identical entries.

What counts as a "change" for fingerprinting?

Change TypeCreates New Version?
Change URLYes
Change HTTP methodYes
Add, remove, or modify a headerYes
Change request bodyYes
Change auth type or credentialsYes
Add, remove, or modify an extractionYes
Change scenario nameYes
Change assertions/validation rulesNo (tracked separately)
Reorder headers without changing valuesNo (canonical JSON sorts keys)
📋 Note Assertions and validation rules are tracked by a separate versioning system (Rules Versions), not by definition versions. This manual covers only definition versioning — the configuration of the HTTP request itself.

8. Change Summaries

Every version (except the first) includes an auto-generated change summary. The system compares the new snapshot against the previous one and produces a human-readable description:

What ChangedSummary Example
URL modified"URL changed"
Method changed"Method changed (GET → POST)"
1 header added"1 header added"
2 headers removed, 1 modified"2 headers removed, 1 header modified"
Body added"Body added"
Auth type changed"Auth changed (None → Bearer Token)"
1 extraction added"1 extraction added"
Multiple changes"URL changed, 1 header added, body modified"

Summaries are generated by comparing the snapshot's fields against the previous version's snapshot. Multiple changes are combined into a comma-separated list.

9. Try It Yourself

Exercise 1 — Fingerprint Dedup Test

Open a test scenario. Save it without making any changes. Check the History tab — no new version should appear. The badge count stays the same. This confirms canonical JSON fingerprint deduplication is working.

Exercise 2 — Change Summary Verification

Change only the URL path from /users/1 to /users/2. Save. Open the History tab. What does the change summary say? It should read "URL changed". Now change the URL back to /users/1. Save again. The change summary should again read "URL changed" — even though you're reverting to an earlier value, the fingerprint differs from the immediate previous version.

Exercise 3 — 20-Version Cap

Starting from a test with 1 version, make 20 distinct changes (tweak the URL path each time: /users/1, /users/2, ..., /users/20). Save after each change. Verify the History tab shows 20 versions. Make one more change and save. Check the History tab — the oldest version should have been evicted. The count stays at 20.

💡 Tip These exercises build on each other. Complete them in order to develop a full understanding of how test definition versioning differs from — and mirrors — workflow versioning.
