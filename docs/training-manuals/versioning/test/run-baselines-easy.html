1. Purpose & Use Case

Every time you run a test suite, RedfireForge records full metrics — response times, TPS, error rates, percentiles. But which run represents your "known-good" performance? Without baselines, you're comparing against nothing.

Baselines let you pin specific runs as reference points. They answer: "Is today's performance better or worse than when we last deployed?"

Real-world scenario: "API Performance Baseline — Pre-Release Benchmark"

Your team is about to deploy API v2.0. You want to capture the current performance as a benchmark. You import the "Product Listing Check" from the Gallery, run it, and mark the result as baseline "Pre-v2.0 Release". After deployment, you run the same test and compare — instantly seeing whether response times improved, regressed, or stayed flat.

💡 Tip This manual uses the Gallery sample test-product-listing ("Product Listing Check") as its starting point. Import it from the Gallery before beginning the walkthrough.

2. Concepts You'll Learn

  • BaselineMark — a lightweight index entry that references a run by ID, with an optional label and timestamp.
  • Marking & unmarking — pin or unpin any completed run as a baseline.
  • Labeling — give baselines descriptive names for identification ("Pre-v2.0", "Morning Peak", "Post-Hotfix").
  • 10-baseline cap — FIFO eviction when the cap is reached.
  • Deduplication — marking the same run twice has no effect.
  • Persistence — baselines survive browser refreshes and app restarts (localStorage / Tauri store).
  • Separation of concerns — baselines are stored separately from run data. Runs live in IndexedDB; baselines are a lightweight JSON array in localStorage.

3. Key Data Model

Baselines are intentionally simple — they don't duplicate run data:

interface BaselineMark {
  runId: string;     // References the TestRun stored in IndexedDB
  label?: string;    // Optional user-assigned label
  markedAt: number;  // Epoch ms — when the baseline was marked
}

const BASELINES_KEY = 'perf-test-baselines';
const MAX_BASELINES = 10;

Key design decisions:

  • BaselineMark is a pointer, not a copy. It references a run by ID. The actual run data (response times, metrics, scenarios) lives in IndexedDB.
  • This means deleting a run leaves a dangling baseline mark. The mark still exists, but the referenced run data is gone.
  • The label is optional — unmarked baselines show the run timestamp as their identifier.
  • The cap is 10, much smaller than the audit log's 500 — because baselines are high-value reference points, not a comprehensive history.
📋 Note Baselines are stored under the key perf-test-baselines in localStorage (web) or Tauri store (desktop). They are global — not scoped per test. All tests share the same 10-baseline pool.

Step 10 — Observe the 10-Baseline Cap

Create baselines until you have 10. Mark one more run as baseline. The oldest baseline (the one at the end of the array) is automatically evicted — FIFO, just like version history.

const next = [entry, ...baselines];  // Prepend new entry
const capped = next.length > MAX_BASELINES
  ? next.slice(0, MAX_BASELINES)      // Drop oldest if over 10
  : next;
⚠️ Warning Eviction is silent — no confirmation dialog. If you need to preserve more than 10 baselines, export the run data before the oldest baseline is evicted.

6. Storage Architecture

Baselines and runs use different storage layers — this is important to understand:

DataStorageKey/DatabaseCapacity
Baseline markslocalStorage / Tauri storeperf-test-baselines10 entries
Run data (metrics, results)IndexedDBTest run databaseLimited by browser quota

The readKey() / writeKey() storage helpers auto-detect the platform:

  • Web mode: Uses localStorage for baselines.
  • Desktop mode (Tauri): Uses the Tauri store via getItem / setItem.

This separation means:

  • Baselines are cheap to store (just run IDs and labels — a few KB).
  • Run data can be large (thousands of request results with response times).
  • Deleting a run from IndexedDB does NOT remove its baseline mark — the mark becomes a dangling reference.
  • Clearing localStorage removes baseline marks but NOT run data.

7. Baselines vs. Other Versioning Features

Baselines are different from workflow/test/request versioning:

FeatureWhat's VersionedMaxStorageRestore?
Workflow VersionsNode/edge/variable snapshots30localStorageYes — full restore
Test Definition VersionsScenario configuration20localStorageYes — full restore
Request VersionsRequest configuration15localStorageYes — partial patch
Audit LogConfig change events500localStorageNo
Run BaselinesTest run references10localStorageNo — read-only comparison

Baselines don't "restore" anything — they're reference points for comparison. You compare a current run's metrics against a baseline to detect regressions or improvements.

9. Try It Yourself

Exercise 1 — Build a Baseline History

Import "Product Listing Check" from the Gallery. Run it 5 times. Mark runs #1, #3, and #5 as baselines with labels: "Initial", "Mid-Sprint", "End-of-Sprint". Verify the baseline list shows 3 entries in newest-first order.

Exercise 2 — Test the 10-Baseline Cap

Run the test 10 times and mark each as a baseline. Mark an 11th run. Verify the oldest baseline (your first mark) was evicted. Check: does the evicted baseline's run data still exist in the results? (Yes — only the mark was removed.)

Exercise 3 — Dangling References

Mark a run as baseline. Then delete that run from the results history. Open the baseline list — the mark should still exist, but it references a missing run. What happens when you try to compare against it?
