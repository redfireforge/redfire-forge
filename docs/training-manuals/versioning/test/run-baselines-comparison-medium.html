1. Purpose & Use Case

Marking baselines is just the first step. The real power lies in comparison — quantifying how a current run differs from the baseline across every metric and every scenario.

Real-world scenario: "Post-Deployment Regression Detection — Auth API"

Your team deploys Auth API v2.0. Login endpoint was refactored for security. Before deployment, you ran the "Auth Flow Validation" test and marked it as baseline. After deployment, you run the same test. The comparison reveals:

  • Login success: response time +87% (145ms → 275ms) — critical regression.
  • Login failure: response time +12% — within threshold, no alert.
  • Profile fetch: response time −5% — improved.
  • Error rate: 0.5% → 2.3% (+1.8 percentage points) — exceeds 1pp threshold, regression alert.

Without baseline comparison, you'd see raw numbers but have no context. With it, you immediately know what regressed, by how much, and whether it's critical.

📋 Prerequisite Complete the Run Baselines (Easy) manual first. This manual assumes you can mark, unmark, and label baselines.

2. Concepts You'll Learn

  • RunComparison — the top-level comparison result containing metric deltas, scenario deltas, and regression alerts.
  • MetricDelta — per-metric comparison (baseline vs. current) with absolute and percentage change, plus improved/regressed flags.
  • ScenarioDelta — per-scenario breakdown showing response time, request count, and error rate changes.
  • RegressionAlert — triggered when a metric exceeds its configured threshold, with warning or critical severity.
  • RegressionThresholds — configurable limits for each metric (P50 ±15%, P95 ±10%, etc.).
  • TrendPoint — data point for trend visualization across multiple runs.
  • Histogram overlay — response time distribution comparison between baseline and current run.

3. Key Data Models

3.1 MetricDelta

interface MetricDelta {
  metric: string;        // e.g., "Avg Response Time", "P95 Response Time", "TPS", "Error Rate"
  baselineValue: number; // Value from the baseline run
  currentValue: number;  // Value from the current run
  delta: number;         // Absolute difference (current - baseline)
  deltaPercent: number;  // Percentage change ((delta / baseline) * 100)
  improved: boolean;     // True if change is favorable
  regressed: boolean;    // True if change exceeds regression threshold
}

Direction of "improved" depends on the metric:

MetricImproved WhenRegressed When
Response times (Avg, P50, P95, P99, Min, Max)delta < 0 (faster)deltaPercent > threshold
TPS (transactions per second)delta > 0 (higher throughput)deltaPercent < −threshold
Error Ratedelta < 0 (fewer errors)delta > threshold (absolute pp)

3.2 ScenarioDelta

interface ScenarioDelta {
  scenarioName: string;
  featureGroupName?: string;
  baselineAvgTime: number;    // Avg response time from baseline
  currentAvgTime: number;     // Avg response time from current
  baselineCount: number;      // Number of requests in baseline
  currentCount: number;       // Number of requests in current
  baselineErrorRate: number;  // Error % in baseline
  currentErrorRate: number;   // Error % in current
  timeDelta: number;          // Absolute time difference
  timeDeltaPercent: number;   // Percentage time change
  regressed: boolean;         // True if timeDeltaPercent > P95 threshold
}

3.3 RegressionAlert

interface RegressionAlert {
  metric: string;
  threshold: number;    // The threshold that was exceeded
  actual: number;       // The actual deviation
  severity: 'warning' | 'critical';
  // warning: deviation 1x–2x threshold
  // critical: deviation > 2x threshold
}

3.4 RunComparison

interface RunComparison {
  baselineRun: TestRun;
  currentRun: TestRun;
  metricDeltas: MetricDelta[];      // 8 metrics compared
  scenarioDeltas: ScenarioDelta[];  // Per-scenario breakdown
  regressions: RegressionAlert[];   // Only triggered alerts
}

4. Default Regression Thresholds

RedfireForge ships with sensible defaults that balance sensitivity with noise reduction:

const DEFAULT_THRESHOLDS: RegressionThresholds = {
  p50Percent: 15,           // P50 response time ± 15%
  p95Percent: 10,           // P95 response time ± 10% (stricter — tail latency matters)
  p99Percent: 15,           // P99 response time ± 15%
  avgPercent: 10,           // Average response time ± 10%
  errorRateAbsolute: 1,     // Error rate ± 1 percentage point (absolute, not relative)
  tpsPercent: 10,           // Transactions per second ± 10%
};

Why these values?

ThresholdValueRationale
P50 ±15%15%Median is stable — 15% allows for natural network variance
P95 ±10%10%Tail latency is critical for user experience — tighter threshold
P99 ±15%15%P99 is inherently noisy — slightly relaxed to reduce false positives
Avg ±10%10%Average is the most common metric — 10% is a standard benchmark
Error Rate ±1pp1ppAbsolute percentage points — even 1% more errors is significant
TPS ±10%10%Throughput drop of 10% indicates capacity regression
💡 Tip Error rate uses absolute percentage points, not relative change. A jump from 0.5% to 1.5% is +1pp (triggers alert), even though the relative change is +200%. This avoids false alarms on very low base rates.

Run the test 5 more times to build trend data. Response times will naturally vary due to network conditions. Don't mark these as baselines — they're regular comparison runs.

Step 3 — Open Comparison View

Select the baseline run and a recent run. Click "Compare". The compareRuns() function executes:

function compareRuns(
  baseline: TestRun,
  current: TestRun,
  thresholds: RegressionThresholds = DEFAULT_THRESHOLDS,
): RunComparison {
  const metricDeltas = computeMetricDeltas(baseline.summary, current.summary, thresholds);
  const scenarioDeltas = computeScenarioDeltas(baseline, current, thresholds);
  const regressions = detectRegressions(metricDeltas, baseline.summary, current.summary, thresholds);
  return { baselineRun: baseline, currentRun: current, metricDeltas, scenarioDeltas, regressions };
}

Step 6 — Review Regression Alerts

If any metric exceeds its threshold, detectRegressions() generates alerts:

// Example regression alert
{
  metric: "P95 Response Time",
  threshold: 12.5,    // The actual percentage deviation
  actual: 12.5,       // deltaPercent that triggered the alert
  severity: "warning"  // 10% < 12.5% < 20% (1x–2x threshold)
}

Severity classification:

SeverityConditionExample (P95 threshold = 10%)
warningDeviation 1×–2× threshold10%–20% regression
criticalDeviation > 2× threshold>20% regression

For Error Rate, severity is based on absolute percentage points: >1pp = warning, >2pp = critical.

Step 7 — Understand Threshold Logic

Not all metrics use the same comparison direction:

// Response times: lower is better
improved: delta < 0          // Faster = improved
regressed: deltaPercent > threshold  // Slower beyond threshold = regressed

// TPS: higher is better
improved: delta > 0          // More throughput = improved
regressed: deltaPercent < -threshold  // Lower throughput = regressed

// Error Rate: lower is better, uses ABSOLUTE threshold
improved: delta < 0          // Fewer errors = improved
regressed: delta > errorRateAbsolute  // More errors (pp) = regressed

Step 8 — View Trend Data

With multiple runs completed, view the trend chart. The computeTrend() function extracts data points:

function computeTrend(runs: TestRun[], baselines: BaselineMark[]): TrendPoint[] {
  return [...runs].reverse().map((r) => {
    const bl = baselines.find((b) => b.runId === r.id);
    return {
      runId: r.id,
      timestamp: r.timestamp,
      label: bl?.label,       // Baseline label (if marked)
      tps: r.summary.tps,
      avgResponseTime: r.summary.avgResponseTime,
      p50ResponseTime: r.summary.p50ResponseTime ?? 0,
      p95ResponseTime: r.summary.p95ResponseTime,
      p99ResponseTime: r.summary.p99ResponseTime,
      errorRate: r.summary.errorRate,
      totalRequests: r.summary.totalRequests,
    };
  });
}

Trend points are sorted chronologically (oldest first, reversing the newest-first run list). Baseline runs are annotated with their label in the trend chart for easy identification.

Step 9 — Response Time Histogram Overlay

For deeper analysis, the histogram overlay compares the distribution of response times between baseline and current:

interface OverlayHistogram {
  bins: { min: number; max: number }[];  // Shared bin boundaries
  baseline: number[];       // Baseline request counts per bin
  current: number[];        // Current request counts per bin
  baselinePercent: number[];  // Baseline distribution (%)
  currentPercent: number[];   // Current distribution (%)
}

This reveals distribution shifts that averages hide. For example, a bimodal distribution (some fast, some slow) would show the same average as a unimodal one, but the histogram makes the difference visually obvious.

Step 10 — Interpret the Full Picture

Combine all three analysis layers for a complete assessment:

  1. Metric Deltas — "What changed at the aggregate level?"
  2. Scenario Deltas — "Which specific endpoint caused the regression?"
  3. Regression Alerts — "How severe is it? Warning or critical?"
  4. Trend — "Is this a one-time spike or a persistent degradation?"
  5. Histogram — "Did the distribution shift, or is it outlier-driven?"

7. How compareRuns() Works Internally

The comparison pipeline has three stages:

7.1 Stage 1 — computeMetricDeltas()

Iterates over 8 metrics from TestSummary:

  • 6 time metrics: Avg, P50, P95, P99, Min, Max (lower is better)
  • 1 throughput metric: TPS (higher is better)
  • 1 error metric: Error Rate (lower is better, absolute threshold)

For each metric, computes delta = current - baseline and deltaPercent = (delta / baseline) * 100. Sets improved and regressed flags based on direction and threshold.

7.2 Stage 2 — computeScenarioDeltas()

Groups request results by scenarioName using groupByScenario(). For each scenario:

  • Computes average response time from individual request times
  • Counts total requests and error count (status ≥ 400 or status 0)
  • Calculates error rate: (errorCount / totalCount) * 100

Handles scenarios present in only one run (new scenarios or removed scenarios).

7.3 Stage 3 — detectRegressions()

Iterates MetricDelta[] and creates RegressionAlert for any delta where regressed: true. Severity is determined by comparing the actual deviation against 2× the threshold.

8. Practical Threshold Tuning

The default thresholds work for most cases, but you may need to adjust them:

ScenarioRecommended Adjustment
High-traffic production APITighten P95 to ±5%, Error Rate to ±0.5pp
Internal/batch APIsRelax all thresholds by 2× (less latency-sensitive)
APIs with high natural varianceWiden P99 to ±25% to reduce false positives
Zero-tolerance error policySet errorRateAbsolute to 0.1 (any error increase triggers alert)
Migration/rewrite validationUse strict thresholds: all ±5%, errorRate ±0.5pp
💡 Tip When running tests over the public internet, response time variance of ±10-15% is normal. If you see frequent false positive regressions on P95/P99, consider widening those thresholds or running tests against a local/staging environment for more consistent results.

9. Common Regression Patterns

Learn to recognize these patterns in your comparison results:

PatternMetric SignalsLikely Cause
Uniform slowdownAll response times ↑ proportionally, TPS ↓Infrastructure issue (CPU, memory, network)
Tail latency spikeP95/P99 ↑↑, P50/Avg ↑ slightlyContention (lock, queue, connection pool)
Error rate jumpError Rate ↑, response times may ↓ (fast failures)Bug in deployment (config, dependency)
Single scenario regressionOne ScenarioDelta regressed, others stableEndpoint-specific change (query, index, logic)
TPS drop with stable latencyTPS ↓, response times unchangedRate limiting, throttling, or reduced concurrency
Improved + regressed mixSome metrics ↑, some ↓Trade-off (e.g., caching improves reads, slows writes)

10. Try It Yourself

Exercise 1 — Full Comparison Workflow

Import "Auth Flow Validation" from the Gallery. Run it, mark as baseline "v1.0". Run 5 more times. Compare the baseline against the run with the highest P95. Identify which scenario contributed most to the P95 regression using the scenario deltas.

Exercise 2 — Threshold Sensitivity

Using the same runs from Exercise 1, mentally calculate: would a P50 threshold of 5% (instead of 15%) trigger a regression alert? What about 25%? This helps you understand how threshold tuning affects alert sensitivity.

Hint: Find the P50 deltaPercent in your comparison. If it's 8%, then a 5% threshold would alert (8% > 5%) but a 25% threshold would not (8% < 25%).

Exercise 3 — Trend Analysis

Run the test 8 times total. Mark runs #1, #4, and #8 as baselines with labels "Sprint Start", "Mid-Sprint", "Sprint End". View the trend chart. Can you identify any performance drift over the 8 runs? Do baseline labels help you correlate performance with deployment events?

💡 Tip In real projects, label baselines with deployment versions and timestamps. A trend chart with labeled baselines becomes a visual deployment impact timeline — invaluable during incident investigations.
