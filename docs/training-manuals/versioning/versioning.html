1. What Gets Versioned?

RedfireForge automatically tracks change history for 6 entity types across 7 implementation phases. Every time you save a workflow, modify a test, or change an environment setting, the system captures a snapshot so you can browse history, compare changes, and restore previous states.

Test Definition V-Phase 2 20 Canonical JSON On change Overview, Headers, Body, Auth, Extractions Full
Audit Log V-Phase 3 500 — Automatic Inline old→new N/A

2. How Versioning Works

2.1 Fingerprinting & Deduplication

Before creating a new version snapshot, the system computes a fingerprint of the current state. If the fingerprint matches the most recent version, no new snapshot is created — this prevents duplicate entries from "save without changes" operations.

  • Workflows use the cyrb53 hash function applied to a normalized representation of nodes, edges, variables, and services.
  • Tests, Requests, and Scripts use canonical JSON — keys are sorted alphabetically, then the JSON string is hashed. This ensures that {"a":1,"b":2} and {"b":2,"a":1} produce the same fingerprint.
// Workflow fingerprinting (cyrb53)
export function computeWorkflowFingerprint(
  nodes: WorkflowNode[],
  edges: WorkflowEdge[],
  variables: Record<string, string>,
  services: WorkflowService[]
): string {
  const normalized = {
    nodes: nodes.map(n => ({ id: n.id, type: n.type, position: n.position, data: n.data })),
    edges: edges.map(e => ({ id: e.id, source: e.source, target: e.target, ... })),
    variables,
    services,
  };
  return cyrb53(JSON.stringify(normalized));
}

2.2 Auto-Save vs Manual Save

  • Workflows: A version snapshot is taken when you click Save. The fingerprint is checked first — if nothing changed, no snapshot is created.
  • Tests & Requests: Snapshots are created automatically when you modify and save a scenario definition (URL, headers, body, auth, extractions).
  • Audit Log: Entries are created automatically whenever an environment, microservice, or auth profile is created, updated, deleted, or renamed.
  • Baselines: You manually mark a test run as a baseline — no auto-save.
  • Scripts: Snapshots are created when you save a script library entry.

2.3 FIFO Eviction

Each entity type has a maximum number of versions (shown in the table above). When the cap is reached, the oldest version is automatically removed to make room for the new one — this is First-In, First-Out (FIFO) eviction. Named/renamed versions are NOT exempt from eviction.

// Adding a version with FIFO cap
export function addVersionToList(
  versions: WorkflowVersion[],
  newVersion: WorkflowVersion,
  max = MAX_WORKFLOW_VERSIONS  // 30
): WorkflowVersion[] {
  const updated = [newVersion, ...versions];
  return updated.slice(0, max); // FIFO: drop oldest if over cap
}

3. The Version Lifecycle

Every versioned entity follows the same high-level workflow:

User Action → Fingerprint Check → Snapshot Created → Version List Updated → FIFO Eviction (if needed)

Browse History → Select & Compare → Diff Modal (tab-based) → Restore / Export

3.1 Version Panel

Each entity has a Version Panel accessible from the editor toolbar (clock/history icon). The panel shows all versions newest-first, with:

  • Timestamp — when the snapshot was taken.
  • Label — optional, user-editable via double-click (inline rename).
  • Change Summary — auto-generated description of what changed (e.g., "2 nodes added, 1 variable changed").
  • Checkbox — select up to 2 versions for comparison.
  • Restore button — revert to this version (with undo snapshot taken first).

3.2 Diff Modal

When two versions are selected and compared, a tab-based diff modal opens. Each tab shows changes for a specific aspect of the entity:

  • Green = added items
  • Red = removed items
  • Yellow = modified items (with property-level detail via json-diff-kit)
  • Gray = unchanged items

3.3 Restore

Restoring a version replaces the current state with the snapshot's data. Before restoring, the system automatically takes an undo snapshot so you can press Ctrl+Z to revert the restore if needed.

3.4 Data Persistence

Version data is stored in localStorage (web mode) or the Tauri store (desktop mode). This means versions persist across browser tab closes and app restarts. Undo history is also persisted (debounced at 500ms to prevent excessive writes).

4. Export & Import with Versions

When exporting scenarios, requests, or workflows, you can optionally include version history. The export dialog provides 4 checkboxes via VersionExportOptions:

Checkbox What It Includes Applicable To
Include Response Versions Saved response body snapshots Requests
Include Rules Versions Validation rule snapshots Requests
Include Definition Versions Entity configuration snapshots (URL, headers, body, auth, etc.) Tests, Requests
Include Structure Log Feature group structural change history Feature Groups

Helper functions for managing version data during export/import:

stripWorkflowVersions(workflow)   // Remove version data for clean export
countWorkflowVersions(workflow)   // Count versions before export
stripDefinitionVersions(scenario) // Remove test/request definition versions
stripStructureLog(featureGroup)   // Remove FG structure changelog
countVersions(scenario)           // Count all version types
📋 Note When importing, toggle "Include Version History" to bring version data along. Without it, the imported entity starts with zero versions — a clean slate.

  1. Start with workflows — Read workflow-version-history-easy. Import the Gallery sample sample-workflow-001 and follow the 10-step walkthrough to create, browse, and restore versions.
  2. Learn diffing — Read workflow-version-diff-medium. Import sample-workflow-webhook and explore the 4-tab diff modal to understand change visualization.
  3. Apply to tests — Read test-definition-history-easy. Import test-user-api-smoke and see how test versioning mirrors workflow versioning with a 5-tab diff.
  4. Explore audit & baselines — Read the audit log and baselines manuals for infrastructure-level tracking.
  5. Capstone — When comfortable with all features, read cross-feature-versioning-advanced for holistic release-management strategies.
