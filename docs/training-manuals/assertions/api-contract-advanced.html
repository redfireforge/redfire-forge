1. Purpose & Use Case

The Full API Contract preset provides comprehensive contract testing for a single API resource. It validates five properties of the response: the exact status code, the resource ID, the title format, the body content length, and the user association. Together, these assertions ensure the API returns exactly the expected response shape and values.

Use this preset when you need to guarantee that an API hasn't changed its contract — the exact fields, types, and value constraints it returns. Contract tests are essential for detecting breaking changes introduced by API updates, backend refactors, or deployment issues.

📋 Note Contract testing is stricter than smoke testing. While a health check just verifies "the API is up," a contract test verifies "the API returns exactly what we expect." Use contract tests for critical endpoints where any deviation could break downstream consumers.

2. Concepts You'll Learn

  • Exact Status Code Matching — Asserting a specific status (200) rather than a range (2xx)
  • Numeric Range Assertions — Validating IDs and values fall within expected bounds
  • Regex Pattern Matching — Using regular expressions to validate string format and content
  • String Length Checks — Ensuring text fields contain meaningful content
  • Contract Testing — The practice of validating exact API response shapes to catch breaking changes

3. Assertion Rules

Type Field / Path Operator Expected Value Description
status response.status == 200 HTTP status code is exactly 200 OK
numeric response.body.id > 0 Resource ID is a positive integer
regex response.body.title matches ^.+$ Title is a non-empty string (at least one character)
numeric response.body.body.length > 10 Body content is longer than 10 characters
numeric response.body.userId between 1–10 UserId is within the valid range (1 to 10)

4. How It Works

Assertion 1 — Status Exactly 200

Unlike the health check preset which accepts any 2xx status, this contract test requires exactly 200 OK. A 201 Created or 204 No Content would fail — because for a GET request on an existing resource, the only correct status is 200. This strictness is intentional: contract tests catch subtle behavioral changes that looser checks would miss.

Assertion 2 — ID Is Numeric > 0

The numeric assertion verifies that the id field is a positive integer. This catches several contract violations: IDs returned as strings instead of numbers, IDs that are 0 or negative (invalid in most systems), and responses where the id field is missing entirely.

Assertion 3 — Title Matches Non-Empty Pattern

The regex assertion with pattern ^.+$ validates that the title field is a non-empty string containing at least one character. While simple, this catches a common API bug: returning empty strings "" or null values for required text fields. The regex approach is extensible — you could tighten the pattern to require specific formats.

Assertion 4 — Body Length > 10

The numeric assertion on body.length checks that the post's body text is longer than 10 characters. This ensures the content field contains meaningful text rather than a placeholder like "..." or "TBD". A body with fewer than 10 characters is almost certainly incomplete or corrupted data.

Assertion 5 — UserId in Range 1–10

The final assertion validates that userId falls within the known valid range of 1 to 10 (JSONPlaceholder has exactly 10 users). This is a referential integrity check — it ensures the post references a valid user. A userId of 0, 11, or null would indicate a data relationship problem.

💡 Tip Contract tests are most valuable in CI/CD pipelines. Run them automatically on every deployment to catch breaking API changes before they reach production.

5. Step-by-Step Guide

Step 1 — Import the Preset

  1. Open the Gallery → Assertions tab in RedfireForge.
  2. Find 📝 Full API Contract and click Import Preset.
  3. The preset is added to your workspace's assertion library.

Step 2 — Attach to a Post Request

  1. Create a request node: GET https://jsonplaceholder.typicode.com/posts/1.
  2. In the request's Assertions panel, click Add Preset.
  3. Select Full API Contract — all 5 assertions appear.

Step 3 — Run and Review

  1. Click Run to execute the request.
  2. Verify all 5 assertions pass: status 200, id > 0, title non-empty, body > 10 chars, userId 1–10.
  3. Inspect each assertion result to understand what was checked and what value was evaluated.

6. Try It Yourself

Exercise 1 — Full Coverage Test

Apply the contract test across multiple resources:

  1. Test posts 1, 50, and 100: GET /posts/1, /posts/50, /posts/100.
  2. Verify all 5 assertions pass for each post (15 assertions total).
  3. Check if the userId distribution is reasonable across the dataset.

Exercise 2 — Break the Contract

Test what happens when assertions fail:

  1. Request a non-existent post: GET /posts/999 — observe which assertions fail.
  2. Tighten the regex pattern to require a specific word — watch it fail on posts without that word.
  3. Change the userId range to 1–5 — find posts assigned to users 6–10 that now fail.

Exercise 3 — Build Your Own Contract

Create a custom contract test for the /users/{id} endpoint:

  1. Clone this preset and modify the assertions for user fields.
  2. Add assertions for: name (non-empty), email (regex for email format), id (1–10).
  3. Consider what other fields (phone, website, company.name) should be validated.
