E-commerce Price Guard

Assertion Preset — Training Manual

Medium ★★☆   data-quality   3 assertions   fakestoreapi.com

RedfireForge · April 2026

1. Purpose & Use Case

The E-commerce Price Guard preset ensures product data integrity in e-commerce APIs. It validates that product prices are within reasonable bounds and that each product has at least one image or variant — essential checks for any storefront that displays product data from an API.

Use this preset when testing e-commerce endpoints, product catalogs, or any API that returns pricing data. Catching a $0 price or a $999,999 price in testing prevents embarrassing — and potentially costly — production incidents.

📋 Note Price validation is one of the most impactful data quality checks you can run. A single incorrect price displayed to customers can result in financial losses, legal issues, or reputational damage.

2. Concepts You'll Learn

  • Numeric Range Assertions — Validating that values fall within an acceptable minimum and maximum range
  • Array Length Assertions — Ensuring required collections (images, variants) are not empty
  • Data Quality Testing — Catching data integrity issues before they reach production
  • Business Rule Validation — Encoding business constraints (price > 0, price < 10000) as automated checks

3. Assertion Rules

Type Field / Path Operator Expected Value Description
numeric response.body.price > 0 Product price is a positive number (not free or negative)
numeric response.body.price < 10000 Product price is below the maximum threshold
arrayLength response.body.image >= 1 Product has at least one image

4. How It Works

Assertion 1 — Price > 0

The first numeric assertion reads the price field from the response body and verifies it is greater than zero. This catches several common data issues: products with a price of 0 (usually a data entry error), products with negative prices (a bug in discount calculations), and products where the price field is null or missing (the assertion fails because null is not > 0).

Assertion 2 — Price < 10000

The second numeric assertion sets an upper bound on the price. While the threshold of 10,000 is configurable, the principle is important: absurdly high prices are almost always data errors. A product priced at $50,000 in a store that sells $10–$200 items is a red flag. This upper-bound check catches data corruption, currency conversion errors, and prices stored in cents instead of dollars.

Assertion 3 — At Least 1 Image

The arrayLength assertion checks that the product's image field contains at least one entry. A product without images is a poor customer experience and usually indicates incomplete data. In e-commerce, images are essential — products without them have significantly lower conversion rates and may indicate the product listing was created incorrectly.

💡 Tip Adjust the price thresholds to match your specific domain. A luxury goods API might set the upper bound to 100,000 while a grocery API might cap at 500.

5. Step-by-Step Guide

Step 1 — Import the Preset

  1. Open the Gallery → Assertions tab in RedfireForge.
  2. Find 💰 E-commerce Price Guard and click Import Preset.
  3. The preset is added to your workspace's assertion library.

Step 2 — Attach to a Product Request

  1. Create a request node: GET https://fakestoreapi.com/products/1.
  2. In the request's Assertions panel, click Add Preset.
  3. Select E-commerce Price Guard — all 3 assertions appear.

Step 3 — Run and Review

  1. Click Run to execute the request.
  2. Verify all 3 assertions pass: price is positive, under 10000, and image exists.
  3. Inspect the actual price value and image URL in the response to confirm they're reasonable.

6. Try It Yourself

Exercise 1 — Scan Multiple Products

Test several products to find any data quality issues:

  1. Create requests for products 1 through 5: GET /products/1, /products/2, etc.
  2. Attach the Price Guard preset to each request.
  3. Run all 5 and check if any fail — this simulates a data quality scan.

Exercise 2 — Customize Thresholds

Clone the preset and adjust the price bounds:

  1. Change the upper limit from 10000 to 500 for a budget store scenario.
  2. Run against the same products — do any now fail the stricter check?
  3. Consider what the right thresholds are for your own use case.

Exercise 3 — Bulk Product Validation

Apply data quality checks at scale:

  1. Send GET https://fakestoreapi.com/products to get all products.
  2. For each product in the array, verify price and image assertions.
  3. Report how many products pass vs. fail across the entire catalog.
