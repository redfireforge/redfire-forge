Token Expiry Guard

1. Purpose & Use Case

The Token Expiry Guard preset validates authentication tokens before they're used in subsequent API requests. It checks three properties: the token matches a JWT format, the token hasn't expired, and the token is long enough to be cryptographically meaningful.

Use this preset in workflows that authenticate against an API and then reuse the token for subsequent requests. By validating the token immediately after receiving it, you catch auth issues early instead of getting mysterious 401 errors later in the workflow.

📋 Note This preset validates token format and metadata, not token signature or permissions. Full cryptographic verification requires server-side validation.

3. Assertion Rules

Type Field / Path Operator Expected Value Description
regex response.body.token matches ^[A-Za-z0-9-_]+\.[A-Za-z0-9-_]+\.[A-Za-z0-9-_]+$ Token matches the JWT three-part format (header.payload.signature)
date response.body.expires_at > now Token expiry date is in the future (not expired)
numeric response.body.token.length > 20 Token is at least 20 characters long

4. How It Works

Assertion 1 — JWT Regex Pattern

The regex assertion applies a regular expression pattern to the token field in the response body. The pattern ^[A-Za-z0-9-_]+\.[A-Za-z0-9-_]+\.[A-Za-z0-9-_]+$ matches the standard JWT format: three Base64url-encoded segments separated by dots.

A valid JWT has three parts: the header (algorithm and type), the payload (claims like user ID and expiry), and the signature (cryptographic proof). If the token doesn't match this pattern, it's either malformed or not a JWT at all.

Assertion 2 — Token Not Expired

The date assertion compares the expires_at field against the current time (now). If expires_at is in the past, the assertion fails — the token has expired and would be rejected by any properly configured API. This catches issues like clock skew, tokens with very short TTLs, or auth servers returning pre-expired tokens.

Assertion 3 — Minimum Token Length

The numeric assertion checks that the token string is at least 20 characters long. While JWTs are typically much longer (hundreds of characters), this is a sanity check. A token shorter than 20 characters is almost certainly invalid — it might be a truncated token, an error message, or an empty string that slipped through.

💡 Tip In real-world workflows, extract the token from the auth response and pass it as a variable to subsequent request headers: Authorization: Bearer {{token}}.

5. Step-by-Step Guide

Step 1 — Import the Preset

  1. Open the Gallery → Assertions tab in RedfireForge.
  2. Find 🔐 Token Expiry Guard and click Import Preset.
  3. The preset is added to your workspace's assertion library.

Step 2 — Attach to an Auth Request

  1. Create a request node that authenticates against your API (e.g., POST https://httpbin.org/post with credentials in the body).
  2. In the request's Assertions panel, click Add Preset.
  3. Select Token Expiry Guard — all 3 assertions appear.

Step 3 — Run and Review

  1. Click Run to execute the auth request.
  2. Check the assertion results: regex format, expiry date, and token length.
  3. If all pass, the token is safe to use in subsequent requests.

6. Try It Yourself

Exercise 1 — Inspect a JWT

Decode a JWT token to understand its structure:

  1. Take a JWT token and split it by the . character into three parts.
  2. Base64-decode the header and payload segments to see the claims.
  3. Find the exp claim in the payload — this is the Unix timestamp of when the token expires.

Exercise 2 — Test with Expired Token

Simulate a token expiry scenario:

  1. Modify the assertion's expected value for the date check to use a future date instead of now.
  2. Observe how the assertion result changes based on the comparison target.
  3. Reset it back to now when done.

Exercise 3 — Build an Auth Workflow

Create a two-step workflow:

  1. Step 1: Auth request with Token Expiry Guard assertions.
  2. Step 2: A protected API call using the token from step 1.
  3. If step 1 assertions fail, the workflow should stop before step 2.
