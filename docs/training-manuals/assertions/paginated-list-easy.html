Paginated List Validation

1. Purpose & Use Case

The Paginated List Validation preset verifies that a paginated API endpoint returns data correctly. It checks three essential properties of any paginated response: the items array is not empty, the total count is reported, and the number of items returned doesn't exceed the requested limit.

Use this preset whenever you're testing APIs that return paginated lists — product catalogs, search results, user listings, or any endpoint with limit and skip parameters. These are among the most common API patterns and are easy to get wrong.

💡 Tip Pagination bugs are a frequent source of production issues. Off-by-one errors, missing totals, and over-fetching are all caught by this preset.

2. Concepts You'll Learn

  • Array Length Assertions — Validating that arrays contain the expected number of elements
  • Numeric Assertions — Comparing numeric response values against expected thresholds
  • Pagination Patterns — Understanding limit, skip, total in paginated APIs
  • Data Consistency — Ensuring returned item counts are consistent with reported totals

3. Assertion Rules

Type Field / Path Operator Expected Value Description
arrayLength response.body.products > 0 Products array contains at least one item
numeric response.body.total > 0 Total count is a positive number
numeric response.body.products.length <= limit Returned items do not exceed the requested limit

4. How It Works

Assertion 1 — Array Items Exist

The first assertion checks that the products array in the response body has a length greater than 0. This ensures the API actually returned data and didn't silently return an empty list. A common bug in pagination implementations is returning 200 OK with {"products": [], "total": 100} — technically valid HTTP but clearly wrong.

Assertion 2 — Total Count > 0

The numeric assertion reads the total field from the response body and verifies it's greater than zero. This field tells the client how many total items exist across all pages. If the total is 0 or missing, the pagination metadata is broken even if items were returned in the current page.

Assertion 3 — Items Count ≤ Limit

The final assertion verifies that the number of items in the products array does not exceed the limit query parameter. If you request ?limit=10 and receive 15 items, the API's pagination logic is broken. This catches over-fetching bugs that can cause performance issues and UI rendering problems.

📋 Note The DummyJSON API uses products as the items key and total for the count. Other APIs may use items, data, results, or count. Adjust the field paths when adapting this preset to other endpoints.

5. Step-by-Step Guide

Step 1 — Import the Preset

  1. Open the Gallery → Assertions tab in RedfireForge.
  2. Find 📄 Paginated List Validation and click Import Preset.
  3. The preset is added to your workspace's assertion library.

Step 2 — Attach to a Request

  1. Create a request node: GET https://dummyjson.com/products?limit=10&skip=0.
  2. In the request's Assertions panel, click Add Preset.
  3. Select Paginated List Validation — all 3 assertions appear.

Step 3 — Run and Review

  1. Click Run to execute the request.
  2. Verify all 3 assertions pass: items exist, total > 0, and item count ≤ 10.
  3. Inspect the response body to confirm the pagination metadata looks correct.

6. Try It Yourself

Exercise 1 — Page Through Results

Test multiple pages to verify pagination consistency:

  1. Send GET https://dummyjson.com/products?limit=10&skip=0 — page 1.
  2. Send GET https://dummyjson.com/products?limit=10&skip=10 — page 2.
  3. Verify both pass all assertions and the total is the same across pages.

Exercise 2 — Edge Cases

Test boundary conditions:

  1. Set limit=0 — what happens to the assertions?
  2. Set skip=99999 — a skip beyond total items. Does the array come back empty?
  3. Omit both parameters entirely — does the API use sensible defaults?

Exercise 3 — Adapt to Another API

Clone the preset and modify the field paths to work with a different paginated API. Try GET https://dummyjson.com/users?limit=5 — you'll need to change products to users in the assertion paths.
