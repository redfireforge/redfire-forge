1. The Mapper in Workflow Context

When you open the Data Mapper from a workflow node, it operates differently from the standalone (request/test) mode:

AspectStandalone ModeWorkflow Mode
SourceSingle response (body/headers/status)All upstream node variables, grouped by origin node
TargetRequest body / extraction rulesThis node's input fields or body builder
Source groupsTabs (Body / Headers / Status)Collapsible groups — one per upstream node
Variable scopeSingle requestFull upstream chain via graph traversal

2. Opening the Mapper from a Node

  1. Double-click a workflow node to open the Node Config Modal.
  2. In the body builder or variable assignment section, click Open Mapper.
  3. The Data Mapper opens with the source panel pre-populated with all upstream variables.

3. Source Panel: Upstream Variables

The source panel groups variables by their origin node. Each group is a collapsible section with the node name and icon.

3.1 Linear Chain

Get User → Get Orders → Create Report ← you are here

Source panel shows:

▸ From: Get User (HTTP)
   userId        num    42
   userEmail     str    "john@example.com"
   userName      str    "John Doe"

▸ From: Get Orders (HTTP)
   orders        arr[5]
   totalAmount   num    1250.00

All fields from both upstream nodes are available. Drag any field to this node's target.

3.2 Fork Pattern (Multiple Parallel Upstream Branches)

Start → Fork ↗ Get User
Start → Fork ↘ Get Products
Start → Fork → → ↘ ↗
Start → Fork → → Join → Build Report

After a Join node, the source panel shows variables from all converging branches:

▸ From: Start (HTTP)
   initialToken   str    "abc123"

▸ From: Get User (HTTP)   [Branch A]
   userId          num    42
   userName        str    "John"

▸ From: Get Products (HTTP)   [Branch B]
   products        arr[10]
   totalProducts   num    10
💡 Branch labels When variables come from parallel branches, the source panel adds branch labels (e.g., [Branch A], [Branch B]) to help you identify which branch each variable came from.

3.3 Variable Collisions

When two upstream branches produce variables with the same name, the mapper detects this and shows a collision warning:

▸ From: Service A (HTTP)
   ⚠ status      str    "active"

▸ From: Service B (HTTP)
   ⚠ status      str    "pending"
⚠ Variable Collision Detected Two upstream nodes produce a variable named status. To avoid ambiguity, use node-scoped references:
  • serviceA.status — from Service A node
  • serviceB.status — from Service B node
The mapper automatically creates scoped references when you drag from a collision group. You can also rename variables in the node config to eliminate collisions.

4. Diamond Topology: Fork → Work → Join

4.1 Simple Diamond

A → Fork → B & C → Join → D

At node D, the source panel contains variables from A, B, and C. Variables from A pass through the fork unchanged. Variables from B and C arrive after the join.

4.2 Chained Diamonds

A → Fork₁ → B & C → Join₁ → Fork₂ → D & E → Join₂ → F

At node F, all ancestor variables (A, B, C, D, E) are available. The mapper groups them by origin and shows collision warnings for any duplicates.

4.3 Nested Diamonds (Fork within Fork)

A → Fork₁ → B → Fork₂ → D & E → Join₂ → Join₁ → G

The mapper resolves the full ancestor graph recursively. At G, you see variables from A, B, D, E, and any other branches. The grouping hierarchy reflects the nesting:

▸ From: A (HTTP)
   ...

▸ From: B (HTTP)
   ...

▸ From: D (HTTP)   [Fork₂ → Branch 1]
   ...

▸ From: E (HTTP)   [Fork₂ → Branch 2]
   ...

6. Working with Workflow Variables

6.1 Referencing Upstream Variables

In expressions, upstream variables use node-scoped notation:

// Reference specific node's output
getUser.userId
getOrders.orders[0].total

// Unscoped reference (works if unique across all upstream nodes)
userId

7. Best Practices

7.1 Avoid Variable Naming Collisions

  • Use descriptive, node-specific variable names: userEmail not email.
  • When parallel branches extract similar data, prefix with the branch context: serviceA_status, serviceB_status.

7.2 Keep Mappings Simple

  • Prefer multiple simple mappings over one complex expression.
  • If a mapping requires more than 3 chained functions, consider using a Script node instead.

7.3 Verify with Quick Test

After setting up mappings, use Quick Test (debug mode) to step through the workflow and verify that each node receives the expected mapped values. The debugger shows the actual runtime values at each step.

💡 Schema Drift Detection When an upstream API changes its response shape, the Data Mapper detects the drift and shows a warning banner: "Source schema changed — review affected mappings." This helps catch breaking changes before they cause test failures.

8. Troubleshooting

SymptomCauseFix
Source panel is emptyNo upstream nodes or no extractions configuredAdd extraction rules to upstream HTTP nodes
Variable shows undefinedUpstream node hasn't been executed (no sample data)Run Quick Test or Fetch Sample on the upstream node
Collision warning won't go awayTwo nodes produce same variable nameRename one variable or use node-scoped references
Mapping line is redSource field was removed (schema drift)Re-fetch source sample, check drift report, re-map
Expression error in loopUsing source.field instead of item.field inside loopInside a loop, reference the loop variable (item), not the root source

9. Practice Exercises

  1. Create a 3-node linear workflow (Get User → Get Orders → Build Report). Open the mapper at Build Report and map userName and orders[] into a report JSON.
  2. Create a fork/join diamond where Branch A fetches users and Branch B fetches products. At the join target, map fields from both branches and handle any naming collisions.
  3. In a loop workflow (paginated fetcher), open the mapper inside the loop body and map the current page's items to the accumulator array using a flatten pattern.
  4. Set up a Script node after two HTTP nodes. Use the mapper to feed both HTTP responses as inputs to the script.
