Array Assertions & DSL Rules

ADVANCED   Sample: dm-array-assertions-dsl

Master array-level assertions (LENGTH, EACH, CONTAINS, SUBSET), the DSL code editor, ASSERT custom predicates with lambda syntax, and universal negation — all using real product data from DummyJSON.

Prerequisites Import the dm-array-assertions-dsl sample from Gallery → Data Mapper. Familiarity with basic field operators is recommended — see Validation Operators — Products first.

Part 1 — Array Assertions in the Test Editor

The sample test includes array-level assertions at the Test Editor level. Open the test and check the Assertions section:

1
Array Length

The assertion $.products LENGTH >= 3 verifies the products array has at least 3 items. Since dummyjson.com/products?limit=3 returns exactly 3 products, this passes.

In DSL syntax:

$.products                    length >=       3
2
EACH — every item must match

Two EACH assertions are configured:

  • $.products EACH price > 0 — every product's price must be positive
  • $.products EACH rating BETWEEN 0, 5 — every product's rating must be 0–5

In DSL syntax:

$.products[*].price           each >          0
$.products[*].rating          each between     0, 5
All 3 products pass: prices are 9.99, 19.99, 14.99 (all > 0) and ratings are 4.94, 3.28, 3.82 (all 0–5).
3
SUBSET — partial object match

The assertion $.products SUBSET {"category": "beauty"} checks that at least one product contains a category field equal to "beauty". SUBSET uses deep recursive partial matching — extra fields are ignored.

SUBSET vs CONTAINS

CONTAINS does exact match on every specified field. SUBSET is more lenient — it only checks the fields you specify and ignores the rest. Use SUBSET when you don't want to specify every field in a complex object.

Part 2 — ASSERT Custom Predicates

4
ASSERT with $count

The first custom assertion:

ASSERT $gt($count($.body.products), 0) // Products array is non-empty

This uses $count() to get the array length and $gt() for a "greater than 0" check. The $.body prefix gives access to the full response body within ASSERT expressions.

5
ASSERT with $all and lambda

Two lambda-based assertions:

ASSERT $all($.body.products, x => $gte(x.price, 0))   // All prices are non-negative
ASSERT $all($.body.products, x => $gte(x.rating, 1))  // All ratings >= 1

$all(array, predicate) returns true only when every element passes the predicate. The lambda x => $gte(x.price, 0) binds each product to x and checks x.price >= 0.

Try it: Change $gte(x.rating, 1) to $gte(x.rating, 4). Products with rating 3.28 and 3.82 fail — the assertion turns red.

Part 3 — Universal Negation (NOT)

6
Open the Data Mapper

Go to Validation tab → Data Mapper. The Target panel shows 7 rules, including two with NOT badges.

7
NOT is_empty

Find $.products[0].title with NOT is_empty. This asserts the title is NOT empty — the logical inverse of is_empty. "Essence Mascara Lash Princess" is not empty — passes.

In DSL syntax:

$.products[0].title           NOT is_empty
8
NOT equals

Find $.products[0].availabilityStatus with NOT equals "Discontinued". This asserts the status is anything except "Discontinued". The actual value is "Low Stock" — passes.

In DSL syntax:

$.products[0].availabilityStatus NOT equals     "Discontinued"
NOT vs not_equals

NOT equals and not_equals are semantically identical. Use whichever reads better in your team's conventions. NOT is a universal modifier that works with any operator — including NOT contains, NOT exists, NOT between.

Part 4 — DSL Code Editor

9
Open the Rules modal

Click Rules in the toolbar to open the Validation Rules Modal. The Monaco editor shows the DSL representation of all rules.

Your DSL should look like:

# Field operators
$.total                       >               0
$.products[0].title           is_not_empty
$.products[0].price           >               0
$.products[0].category        equals          "beauty"
$.products[0].brand           exists

# Negation
$.products[0].title           NOT is_empty
$.products[0].availabilityStatus NOT equals   "Discontinued"
10
Add a new rule via DSL

Type a new line at the end:

$.products[0].sku             regex           "^[A-Z0-9]+$"

After the debounce (~300ms), the Data Mapper updates: a new target node appears with a purple regex pill.

You should see: The visual mapper and DSL editor stay synchronized. Adding a rule in either location updates the other.
11
Add an ASSERT via DSL

Append:

ASSERT $eq($sum($map($.body.products, x => x.price)), 44.97) // Total price check

This sums all product prices (9.99 + 19.99 + 14.99 = 44.97) and asserts the total. Click Verify in the modal to confirm.

12
DSL Reference Panel

Click Reference in the modal header to open the DSL Reference Panel. Browse 8 categories of operators, assertion types, and ASSERT syntax. Click any entry to insert it at the cursor position.

Part 5 — Verify & Review

13
Verify All

Close the Rules modal. Click Verify All in the toolbar. All rules — field operators, negated rules, and ASSERT predicates — are evaluated together.

Open Mapping View → Table to see the complete results:

  • Field rules show "✓ pass" / "✗ fail" in the Status column
  • Assertion rows (STATUS, ARRAYLENGTH, EACH, SUBSET, CUSTOM) show "✓ pass" / "✗ fail"
  • NOT-negated rules show the NOT badge in the operator column
14
Pivot view for array data

Switch the Table view to Pivot (if available). The pivot table shows array indices as rows and fields as columns — useful for comparing products[0], products[1], products[2] side by side.
