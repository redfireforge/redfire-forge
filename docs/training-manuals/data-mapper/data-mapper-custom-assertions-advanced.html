Custom Assertions & ASSERT Keyword

ADVANCED   Sample: dm-validation-mapping

Write custom predicate assertions using the ASSERT keyword and the shared 125-function expression engine. This manual assumes you already know how validation rules are edited visually and as DSL.

Prerequisites Import the dm-validation-mapping sample from the Gallery. Work through Validation Operators & DSL Editor first so terms like Rules dock, validation-dsl, and Verify are familiar.

Part 1 — The ASSERT Keyword

1
Open DSL editor in the validation mapper

Navigate to your validation-capable step, open Visual Mapper as needed, then focus the Rules tab in the bottom dock so Monaco shows the validation DSL buffer.

You should see: Existing field rules mixed with optional ASSERT lines if the sample shipped with custom checks.
2
Basic ASSERT

Append a line such as:

ASSERT $gt($.price, 0) // Price must be positive
  • ASSERT marks the remainder of the line as an expression-backed predicate wired into the validation engine.
  • The expression $gt($.price, 0) runs against the resolved response JSON (see Part 2 for other roots).
  • Everything after // is treated as the human-readable description surfaced beside pass/fail rows in verification output.
You should see: Syntax highlighting separates ASSERT, the expression, and the trailing comment trail.
3
How ASSERT works

When Verify runs:

  1. The parser extracts the predicate expression following ASSERT.
  2. The 125-function expression engine evaluates that expression.
  3. Dollar-sign paths such as $.price resolve against the response body (and related roots described below).
  4. The engine coerces the outcome to a boolean truth test: truthy ⇒ pass, falsy ⇒ fail with your // description as context.
Runtime clarity

Keep comments short and outcome-oriented (“Price must remain positive”) so failed runs remain scannable in large suites.

Part 2 — Expression Context

4
Available variables

ASSERT expressions share the mapper's familiarity with dollar paths. Typical roots include:

Symbol / pathRole
$.body or root $The primary response body object (often you write $.field directly).
$.statusNumeric HTTP status code of the captured response.
$.responseTimeElapsed latency in milliseconds end-to-end for the HTTP call.
$.headersMap-like response headers for header-level ASSERTs ($contains($.headers.X-Trace-Id, "-"), etc.).
$.rawBodyRaw string payload before JSON parsing — useful when the body is not JSON.
You should see: Autocomplete proposing matching segments when typing $.; invalid paths underline in Monaco.
5
Combining functions

Assertions become powerful when composing numeric, string, and collection helpers:

ASSERT $gt($count($.products), 0) // Response has products

ASSERT $contains($lower($.brand), "essence") // Brand contains essence

ASSERT $all($.reviews, x => $gte(x.rating, 1)) // All ratings >= 1

ASSERT $eq($type($.price), "number") // Price is a number

Each line remains a single validation rule with an independent pass/fail channel and description.

6
Lambda support

Higher-order helpers accept inline lambdas using arrow syntax:

  • Single parameter — x => body
  • Multiple parameters — (a, b) => body

Typical consumers include $map, $filter, $all, $any, and $reduce. Inside the lambda, use dotted paths on the parameter (for example x.rating) exactly as with outer $. paths.

You should see: Parsing errors when arrow syntax is malformed; successful checks highlight whichever collection items caused failure when the debugger surfaces iteration detail.

Part 3 — Verification

7
Verify custom assertions

Click Verify All (or the equivalent validation run control). Field rules and ASSERT lines evaluate together.

  • Custom ASSERT rows show the trailing comment text as the assertion title or subtitle in result panes.
  • Failures bubble with the evaluated expression snippet when diagnostics are expanded.
You should see: Assertions interleaved with mapper-driven rules in summaries; PASS rows stay green while FAIL rows show red cues consistent with pill rules.
8
Negation

Prefix with NOT when you want inverted truth:

NOT ASSERT $isEmpty($.products) // Products should NOT be empty

Here the assertion passes when $isEmpty($.products) evaluates to falsy — that is, when the collection has one or more items.

You should see: NOT ASSERT lines flagged distinctly in tooling so operators can differentiate negated custom checks from plain NOT field operators.

The expression engine organizes helpers into thematic groups. Approximate catalogue sizes:

Top 10 shortcuts for assertions

  1. $gt — strict greater-than numeric guard
  2. $gte — inclusive lower bound
  3. $lt — strict less-than numeric guard
  4. $lte — inclusive upper bound
  5. $eq — exact equality without field-operator sugar
  6. $contains — substring / membership-style checks inside expressions
  7. $isEmpty — collections or strings devoid of meaningful content
  8. $count — length-aware ASSERT chains
  9. $type — dynamic schema guards when is_type field rules need composition
  10. $all — “every element satisfies…” predicates with lambdas

Expand beyond these by exploring the searchable function catalog embedded in Expression tooling elsewhere in the app.
