1. Why Header Assertions?

HTTP headers carry critical metadata: content type, caching policy, security headers, rate limits, and CORS configuration. A correct response body with wrong headers can cause:

  • Browser parsing failures — wrong Content-Type causes JSON not parsed
  • Stale data — missing or wrong Cache-Control serves outdated content
  • CORS blocks — missing Access-Control-Allow-Origin breaks frontends
  • Security gaps — missing X-Frame-Options or Strict-Transport-Security

Header assertions let you verify these headers automatically on every test run.

2. The Header Assertion Data Model

// Assertion type for response headers
{
  type: 'header',
  name: string,               // header name (case-insensitive)
  operator: AssertionOperator, // 'exists' | 'equals' | 'contains' | 'regex'
  value?: string              // expected value (not needed for 'exists')
}

type AssertionOperator = 'equals' | 'contains' | 'regex' | 'exists';

Four Operators

OperatorDescriptionvalue Required?
existsHeader is present (any value)No
equalsExact string matchYes
containsSubstring matchYes
regexRegular expression matchYes (pattern)

Examples

// Does the Content-Type header exist?
{ type: 'header', name: 'Content-Type', operator: 'exists' }

// Is Content-Type exactly "application/json"?
{ type: 'header', name: 'Content-Type', operator: 'equals',
  value: 'application/json' }

// Does Content-Type contain "json"?
{ type: 'header', name: 'Content-Type', operator: 'contains',
  value: 'json' }

// Does X-Request-Id match a UUID pattern?
{ type: 'header', name: 'X-Request-Id', operator: 'regex',
  value: '^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$' }

3. How Header Assertions Are Evaluated

The evaluation uses two helper functions: findHeader() for case-insensitive lookup and evaluateHeaderOp() for operator logic.

Case-Insensitive Header Lookup

// src/engine/validator.ts

function findHeader(
  headers: Record<string, string>,
  name: string
): string | undefined {
  const lower = name.toLowerCase();
  for (const [k, v] of Object.entries(headers)) {
    if (k.toLowerCase() === lower) return v;
  }
  return undefined;
}
💡 Case-Insensitive Matching HTTP header names are case-insensitive by spec (RFC 7230). findHeader() normalizes both the assertion name and the response header keys to lowercase, so 'content-type', 'Content-Type', and 'CONTENT-TYPE' all match the same header.

Operator Evaluation

function evaluateHeaderOp(
  headerVal: string | undefined,
  operator: string,
  expected?: string,
): { pass: boolean; expected: string; actual: string } {
  const actual = headerVal ?? '(not present)';
  switch (operator) {
    case 'exists':
      return {
        pass: headerVal !== undefined,
        expected: 'header exists',
        actual,
      };
    case 'equals':
      return {
        pass: headerVal === expected,
        expected: expected ?? '',
        actual,
      };
    case 'contains':
      return {
        pass: headerVal !== undefined
           && headerVal.includes(expected ?? ''),
        expected: `contains "${expected ?? ''}"`,
        actual,
      };
    case 'regex': {
      try {
        const re = new RegExp(expected ?? '');
        return {
          pass: headerVal !== undefined && re.test(headerVal),
          expected: `matches /${expected}/`,
          actual,
        };
      } catch {
        return {
          pass: false,
          expected: `valid regex /${expected}/`,
          actual: 'invalid regex pattern',
        };
      }
    }
    default:
      return {
        pass: false,
        expected: `operator "${operator}"`,
        actual: 'unknown operator',
      };
  }
}

4. Evaluation in evaluateAssertions()

// Inside evaluateAssertions() switch statement
case 'header': {
  const headerVal = findHeader(ctx.responseHeaders, a.name);
  const opResult = evaluateHeaderOp(headerVal, a.operator, a.value);
  if (!opResult.pass) {
    failures.push({
      path: `(header:${a.name})`,
      expected: opResult.expected,
      actual: opResult.actual,
    });
  }
  break;
}

5. Common Header Assertions

Content-Type Validation

// Exact match — strict
{ type: 'header', name: 'Content-Type', operator: 'equals',
  value: 'application/json; charset=utf-8' }

// Contains — flexible (ignores charset)
{ type: 'header', name: 'Content-Type', operator: 'contains',
  value: 'application/json' }

// Regex — accept JSON or XML
{ type: 'header', name: 'Content-Type', operator: 'regex',
  value: 'application/(json|xml)' }

Cache Control

// Verify caching is disabled for sensitive data
{ type: 'header', name: 'Cache-Control', operator: 'contains',
  value: 'no-store' }

// Verify public cache with max-age
{ type: 'header', name: 'Cache-Control', operator: 'regex',
  value: 'public.*max-age=\\d+' }

CORS Headers

// Verify CORS allows any origin
{ type: 'header', name: 'Access-Control-Allow-Origin',
  operator: 'equals', value: '*' }

// Verify CORS allows specific origin
{ type: 'header', name: 'Access-Control-Allow-Origin',
  operator: 'equals', value: 'https://app.example.com' }

// Verify allowed methods include POST
{ type: 'header', name: 'Access-Control-Allow-Methods',
  operator: 'contains', value: 'POST' }

Security Headers

// HSTS is present
{ type: 'header', name: 'Strict-Transport-Security',
  operator: 'exists' }

// X-Frame-Options prevents clickjacking
{ type: 'header', name: 'X-Frame-Options', operator: 'equals',
  value: 'DENY' }

// CSP is configured
{ type: 'header', name: 'Content-Security-Policy',
  operator: 'exists' }

Rate Limiting

// Rate limit header exists
{ type: 'header', name: 'X-RateLimit-Remaining',
  operator: 'exists' }

// Rate limit is a number
{ type: 'header', name: 'X-RateLimit-Remaining',
  operator: 'regex', value: '^\\d+$' }

6. Combining Header + Body Assertions

Header assertions complement body assertions. A complete API contract test might check both:

assertions: [
  // Status
  { type: 'status', expected: '200' },
  { type: 'responseTime', maxMs: 500 },

  // Headers
  { type: 'header', name: 'Content-Type', operator: 'contains',
    value: 'json' },
  { type: 'header', name: 'X-Request-Id', operator: 'regex',
    value: '^[0-9a-f-]{36}$' },
  { type: 'header', name: 'Cache-Control', operator: 'contains',
    value: 'no-store' },

  // Body
  { type: 'numeric', jsonPath: '$.id', operator: '>', value: 0 },
  { type: 'regex', jsonPath: '$.email',
    pattern: '^[^@]+@[^@]+\\.[^@]+$' },
]
📘 Independent Evaluation Each assertion is evaluated independently. A header assertion failure doesn't prevent body assertions from running — you see all failures at once, making debugging faster.

7. Exercises

Exercise 1: Assert Content-Type Contains "json"

Goal: Verify an API returns JSON content.

  1. Create a test: GET https://jsonplaceholder.typicode.com/users/1.
  2. Add assertion: header Content-Type, operator contains, value json.
  3. Run — should pass (application/json; charset=utf-8 contains "json").
  4. Change value to xml — should fail.

Exercise 2: Assert a Custom Header Exists

Goal: Check for the presence of a specific header.

  1. Create a test: GET https://httpbin.org/response-headers?X-Custom-Header=hello.
  2. Add assertion: header X-Custom-Header, operator exists.
  3. Run — should pass.
  4. Change header name to X-Missing-Header — should fail with (not present).

Exercise 3: Regex Validate a Request ID Header

Goal: Use regex to validate header format.

  1. Create a test to any API that returns a request/trace ID header.
  2. Add assertion: header X-Request-Id, operator regex, value ^[0-9a-f-]{36}$.
  3. Run and observe — if the header matches UUID format, it passes.
  4. Try an invalid regex pattern (e.g., [invalid) — observe the graceful error message.
