1. Why Response Time Assertions?

A 200 OK means the API works — but what if it takes 15 seconds? A response time assertion catches performance regressions that status checks alone cannot detect.

Real-World Scenarios

  • SLA enforcement — "All user-facing APIs must respond within 500ms"
  • Performance baselines — "This endpoint was 120ms last week, now it's 2.3s — something changed"
  • Load testing gates — "Under 100 concurrent users, p95 latency must stay below 1s"
  • Timeout detection — "If the API takes longer than 5s, we have a database issue"

2. The Response Time Assertion Data Model

// Assertion type for response time
{ type: 'responseTime', maxMs: number }

Simple threshold check: pass if responseTimeMs <= maxMs, fail otherwise.

How It's Evaluated

// Inside evaluateAssertions()
case 'responseTime':
  if (ctx.responseTimeMs > a.maxMs) {
    failures.push({
      path: '(responseTime)',
      expected: `≤ ${a.maxMs}ms`,
      actual: `${ctx.responseTimeMs}ms`,
      message: `expected ≤ ${a.maxMs}ms, actual ${ctx.responseTimeMs}ms`,
    });
  }
  break;

Where responseTimeMs Comes From

The responseTimeMs is populated by the request execution engine. It measures the time from request sent to full response received (includes network latency, server processing, and response body transfer).

// In AssertionContext — passed to evaluateAssertions()
interface AssertionContext {
  httpStatus: number;
  responseTimeMs: number;     // ← measured by the engine
  responseHeaders: Record<string, string>;
  responseBody: unknown;
}
📘 What's Included in Response Time The measurement includes: DNS resolution, TCP connection, TLS handshake, request send, server processing, and response download. It does not include RedfireForge's own JSON parsing or assertion evaluation time.

3. Choosing Appropriate Thresholds

Setting the right maxMs value depends on the API type and your performance requirements:

API TypeTypical RangeSuggested maxMs
Health check / ping10–50ms200
Simple CRUD (read)50–200ms500
Search / filter100–500ms1000
Report generation500–3000ms5000
File upload / export1000–10000ms15000
Third-party APIVaries3000 (generous)
💡 Start Generous, Then Tighten Begin with a generous threshold (e.g., 2000ms) that you know the API should meet. Once you have baseline data, tighten the threshold to catch real regressions. A threshold that's too tight causes flaky tests from normal network variance.

Accounting for Network Variance

Response times vary due to network conditions, cold starts, and server load. Best practices:

  • Set maxMs at 2–3× your expected p50 latency
  • For CI/CD pipelines, use more generous thresholds than local development
  • For load tests, use the p95 target from your SLA, not the average

5. Combining with Status Assertions

The most common assertion pair is status + response time:

assertions: [
  { type: 'status', expected: '200' },
  { type: 'responseTime', maxMs: 500 }
]

This ensures the API returns the right status code and does it fast enough. If either fails, the test fails.

6. Response Time in Load Testing

Response time assertions are especially valuable in load test profiles where you run the same test under increasing concurrency:

ConcurrencyAvg Response TimemaxMs: 1000
1 user120msPass ✅
10 users340msPass ✅
50 users780msPass ✅
100 users1450msFail ❌

The assertion catches the exact point where the API degrades under load — telling you the capacity limit.

⚠ Individual vs. Average The response time assertion checks each individual request, not the average. In a load test, even if the average is 300ms, a single request at 1200ms will fail the 1000ms threshold. This is intentional — it catches tail latency issues that averages hide.

7. Exercises

Exercise 1: Basic Threshold

Goal: Add a response time assertion and observe pass/fail behavior.

  1. Create a test: GET https://jsonplaceholder.typicode.com/posts.
  2. Add assertion: response time ≤ 2000ms.
  3. Run — should pass easily (JSONPlaceholder is typically < 500ms).
  4. Tighten to 50ms — likely fails due to network latency.
  5. Find a threshold that reliably passes for your connection.

Exercise 2: Status + Response Time

Goal: Combine the two most common assertion types.

  1. Create a test: GET https://jsonplaceholder.typicode.com/users/1.
  2. Add two assertions: status = 200, response time ≤ 1000ms.
  3. Run and verify both pass.
  4. Change URL to /users/99999 — status fails (404), response time likely still passes.

Exercise 3: Find the Baseline

Goal: Establish a performance baseline for an endpoint.

  1. Create a test: GET https://jsonplaceholder.typicode.com/posts.
  2. Run 5 times without any response time assertion. Note the latency each time.
  3. Calculate: average × 2.5 = your threshold.
  4. Add a response time assertion with that threshold.
  5. Run 5 more times — should pass reliably without being too generous.
