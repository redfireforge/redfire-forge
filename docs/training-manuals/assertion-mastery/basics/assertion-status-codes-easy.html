1. Why Status Code Assertions Matter

By default, RedfireForge uses a simple heuristic: any status < 400 is a pass. This means a 301 redirect or a 204 No Content both pass — even if you expected a 200 OK.

A status assertion gives you precise control:

Without AssertionWith Assertion
200 → Pass ✅200 → expected: '200' → Pass ✅
301 → Pass ✅ (wrong!)301 → expected: '200' → Fail ❌
204 → Pass ✅ (maybe wrong)204 → expected: '200' → Fail ❌
404 → Fail ❌404 → expected: '404' → Pass ✅ (intentional)
💡 The statusAsserted Flag When you add a status assertion, the engine sets statusAsserted = true. This tells buildValidationResult() to use your assertion result instead of the default < 400 heuristic. This is how you can make a 404 test pass — the assertion says "404 is expected."

2. The Status Assertion Data Model

// Assertion type for status codes
{ type: 'status', expected: string }

The expected field is a pattern string — not just a number. It supports four matching modes:

Four Matching Patterns

PatternExampleMatches
Exact'200'Only 200
Range'200-299'200, 201, 204, ..., 299
Class wildcard'2xx'Any 2xx status (200–299)
Comma-separated'200,201,204'200 or 201 or 204

Examples

// Exact — only 200 passes
{ type: 'status', expected: '200' }

// Range — any success status
{ type: 'status', expected: '200-299' }

// Class — any 2xx
{ type: 'status', expected: '2xx' }

// Comma — specific success codes
{ type: 'status', expected: '200,201,204' }

// Negative test — expect 404
{ type: 'status', expected: '404' }

// Accept 4xx or 5xx (error testing)
{ type: 'status', expected: '4xx,5xx' }

3. How matchesStatusPattern Works

The matchesStatusPattern(httpStatus, pattern) function handles all four pattern types:

function matchesStatusPattern(httpStatus: number, pattern: string): boolean {
  // Comma-separated: split and recursively check each part
  if (pattern.includes(',')) {
    return pattern.split(',').some(p =>
      matchesStatusPattern(httpStatus, p.trim())
    );
  }

  // Range: "200-299"
  if (pattern.includes('-')) {
    const [lo, hi] = pattern.split('-').map(Number);
    return httpStatus >= lo && httpStatus <= hi;
  }

  // Class wildcard: "2xx"
  if (pattern.endsWith('xx')) {
    const classDigit = parseInt(pattern[0], 10);
    return Math.floor(httpStatus / 100) === classDigit;
  }

  // Exact match
  return httpStatus === Number(pattern);
}

Evaluation in evaluateAssertions()

// Inside evaluateAssertions()
case 'status':
  statusAsserted = true;
  if (!matchesStatusPattern(ctx.httpStatus, a.expected)) {
    failures.push({
      path: '(status)',
      expected: a.expected,
      actual: String(ctx.httpStatus),
      message: `Status ${ctx.httpStatus} does not match pattern "${a.expected}"`,
    });
  }
  break;
📘 Failure Detail Format When a status assertion fails, it produces a FailureDetail with path: '(status)'. This special path distinguishes status failures from JSON body failures, which use JSONPath strings like $.items.

4. Configuring Status Assertions in the UI

Step 1: Open the Validation Tab

  1. Open the test in the Test Editor.
  2. Click the Validation tab.
  3. In the Assertions section, click + Add Assertion.

Step 2: Select Status Type

  1. From the type dropdown, select Status Code.
  2. Enter the expected pattern in the Expected field.

Step 3: Use Pattern Syntax

6. Common Patterns

Pattern: REST CRUD Status Checks

OperationExpected StatusPattern
GET (read)200 OK200
POST (create)201 Created201
PUT (update)200 or 204200,204
DELETE200 or 204200,204
GET (not found)404404
POST (bad input)400 or 422400,422
Any unauthorized401 or 403401,403

Pattern: Negative Testing

Status assertions let you write tests that expect errors:

// Test: verify 404 for missing resource
{ type: 'status', expected: '404' }

// Test: verify 401 without auth
{ type: 'status', expected: '401' }

// Test: verify 400 with invalid payload
{ type: 'status', expected: '400' }
⚠ Only One Status Assertion You can add multiple assertions to a test, but only one should be of type status. Multiple status assertions would both set statusAsserted = true and potentially conflict. Use comma-separated patterns if you need to accept multiple codes.

7. Exercises

Exercise 1: Exact Status Match

Goal: Add a status assertion and see it pass and fail.

  1. Create a test: GET https://jsonplaceholder.typicode.com/posts/1.
  2. Add assertion: status = 200.
  3. Run — verify it passes.
  4. Change URL to /posts/99999 — JSONPlaceholder returns 404. Verify the assertion fails.
  5. Change expected to 404 — verify it now passes (negative test).

Exercise 2: Class Wildcard

Goal: Use 2xx to accept any success status.

  1. Create a test: POST https://jsonplaceholder.typicode.com/posts with a JSON body.
  2. Add assertion: status = 2xx.
  3. Run — JSONPlaceholder returns 201 Created. Verify the assertion passes.
  4. Change to 200 — it should fail (201 ≠ 200).

Exercise 3: Comma-Separated Pattern

Goal: Accept multiple specific status codes.

  1. Create a test: PUT https://jsonplaceholder.typicode.com/posts/1 with a JSON body.
  2. Add assertion: status = 200,204.
  3. Run and verify — either 200 or 204 should pass.
  4. Add another test for DELETE with the same pattern.
