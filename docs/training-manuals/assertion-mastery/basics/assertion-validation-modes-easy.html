1. Two Validation Layers

RedfireForge has two independent validation systems that run in parallel and merge their results:

Layer 1: Assertions (status, responseTime, regex, numeric, …)
↓
failureDetails[]

Layer 2: Validation Mode (none, full, selective)
↓
failureDetails[]

→ buildValidationResult() → merged failureDetails[] → pass/fail

Both layers feed into failureDetails[]. If either layer produces failures, the test fails. They are complementary — you can use assertions alone, validation mode alone, or both together.

💡 Key Insight Assertions check specific properties of the response (status, timing, individual fields). Validation modes check the entire response body structure. Together they provide both pinpoint and broad coverage.

2. The ValidationConfig Interface

type ValidationMode = 'none' | 'full' | 'selective';
type SelectiveMode = 'include' | 'exclude';

interface ValidationConfig {
  mode: ValidationMode;

  // Full mode
  expectedJson?: string;          // entire expected JSON body

  // Selective mode
  expectedFields?: ExpectedField[];
  selectiveMode?: SelectiveMode;  // 'include' | 'exclude'

  // Shared options
  sampleJson?: string;            // reference sample for UI
  excludedPaths?: string[];       // paths to ignore in full mode
  unorderedArrays?: boolean;      // ignore array order

  // Assertions (independent layer)
  assertions?: Assertion[];
}

interface ExpectedField {
  jsonPath: string;       // e.g., "$.user.name"
  expectedValue: string;  // e.g., "John Doe"
}

3. Mode: None ("No Body Validation")

mode: 'none' disables JSON body validation entirely. Only assertions (if any) are evaluated. In the UI, this is labeled "No Body Validation".

{
  mode: 'none',
  assertions: [
    { type: 'status', expected: '200' },
    { type: 'responseTime', maxMs: 500 }
  ]
}

When to Use

  • You only care about status + response time, not body content
  • The response body is unpredictable (timestamps, random IDs)
  • You're doing basic connectivity or smoke testing
  • You have specific assertions that check individual fields already
📘 "No Body Validation" ≠ No Validation At All mode: 'none' only disables the body validation layer. Assertions still run! If you have a status assertion, it will still be checked. "No Body Validation" refers to JSON body comparison, not to all validation.

4. Mode: Full

mode: 'full' performs a deep comparison of the entire response body against an expected JSON snapshot.

{
  mode: 'full',
  expectedJson: '{"id": 1, "name": "Leanne Graham", "email": "Sincere@april.biz"}',
  assertions: [
    { type: 'status', expected: '200' }
  ]
}

How It Works

  1. The engine parses expectedJson and the actual response body.
  2. It performs a deep recursive comparison of every key and value.
  3. Any difference produces a FailureDetail with the JSONPath of the mismatch.

Failure Example

// Expected:  {"name": "Leanne Graham", "email": "Sincere@april.biz"}
// Actual:    {"name": "Leanne Graham", "email": "new@email.com"}

FailureDetail {
  path: '$.email',
  expected: '"Sincere@april.biz"',
  actual: '"new@email.com"',
  message: 'Value mismatch at $.email'
}

Options That Modify Full Mode

OptionEffect
excludedPathsSkip specific JSONPaths from comparison (e.g., ["$.timestamp", "$.requestId"])
unorderedArraysWhen true, arrays are compared as sets — order doesn't matter

When to Use

  • API responses are deterministic (no timestamps, random IDs)
  • You want to catch any change to the response shape
  • Contract testing — "this endpoint must return exactly this structure"
  • Snapshot testing — capture a known-good response, compare on every run
⚠ Dynamic Fields Full mode will fail on dynamic fields like timestamps, UUIDs, or request IDs. Use excludedPaths to skip these, or switch to selective mode where you only check the stable fields.
⚠ Empty Expected JSON If you select "Full JSON Match" but leave the expected JSON textarea empty, the UI will show a warning banner. On save, the mode is automatically switched to "No Body Validation" to prevent a silent no-op. Always paste the expected response before saving with Full JSON Match.

5. Mode: Selective

mode: 'selective' validates only specific fields by JSONPath, leaving everything else unchecked.

{
  mode: 'selective',
  selectiveMode: 'include',
  expectedFields: [
    { jsonPath: '$.name', expectedValue: 'Leanne Graham' },
    { jsonPath: '$.email', expectedValue: 'Sincere@april.biz' },
    { jsonPath: '$.address.city', expectedValue: 'Gwenborough' }
  ]
}

selectiveMode: Include vs. Exclude

ModeMeaningUse When
include Only check the listed fields; ignore everything else You know exactly which fields matter
exclude Check everything except the listed fields Most fields matter, but a few are dynamic

Include Mode Example

// Only these 2 fields are checked — the rest can change freely
{
  mode: 'selective',
  selectiveMode: 'include',
  expectedFields: [
    { jsonPath: '$.status', expectedValue: 'active' },
    { jsonPath: '$.role', expectedValue: 'admin' }
  ]
}

Exclude Mode Example

// Check everything in expectedJson EXCEPT these dynamic paths
{
  mode: 'selective',
  selectiveMode: 'exclude',
  expectedFields: [
    { jsonPath: '$.updatedAt', expectedValue: '' },
    { jsonPath: '$.requestId', expectedValue: '' }
  ],
  expectedJson: '{ ... full expected body ... }'
}

When to Use

  • Responses have a mix of stable and dynamic fields
  • You want to validate business-critical fields without snapshot rigidity
  • Testing partial updates — "after PUT, verify only the changed fields"
  • API returns extra metadata you don't care about

6. Choosing the Right Mode

QuestionAnswer → Mode
Do I only care about status/timing?Yes → none
Must the response be exactly this shape?Yes → full
Are there dynamic/unpredictable fields?Some → full + excludedPaths
Many → selective (include)
Do I care about specific fields only?Yes → selective (include)
I want full check minus a few fields?→ selective (exclude)

↓ Yes

↓ No

7. Combining Validation Mode + Assertions

The two layers complement each other. Here's a complete validation config using both:

{
  mode: 'selective',
  selectiveMode: 'include',
  expectedFields: [
    { jsonPath: '$.name', expectedValue: 'Leanne Graham' },
    { jsonPath: '$.company.name', expectedValue: 'Romaguera-Crona' }
  ],
  assertions: [
    { type: 'status', expected: '200' },
    { type: 'responseTime', maxMs: 500 },
    { type: 'regex', jsonPath: '$.email', pattern: '^[^@]+@[^@]+\\.[^@]+$' }
  ]
}

In this example:

  • Validation mode checks that name and company.name match expected values
  • Status assertion checks HTTP 200
  • Response time checks latency ≤ 500ms
  • Regex assertion checks email format without pinning the exact value

All four checks are independent — each can pass or fail on its own.

8. Exercises

Exercise 1: Compare None vs. Full

Goal: See how validation mode affects test results.

  1. Create a test: GET https://jsonplaceholder.typicode.com/users/1.
  2. Set mode to none. Run — passes (only default heuristic).
  3. Switch to full. Paste the response body as expectedJson.
  4. Run — should pass (exact match).
  5. Edit one value in expectedJson. Run — fails with a path-specific error.

Exercise 2: Selective Include

Goal: Validate only the fields you care about.

  1. Same test as above. Switch to selective, include mode.
  2. Add expected fields: $.name = Leanne Graham, $.email = Sincere@april.biz.
  3. Run — passes. Only those 2 fields are checked.
  4. Change $.name expected to Wrong Name — fails on that field only.

Exercise 3: Full Mode with excludedPaths

Goal: Handle dynamic fields in full mode.

  1. Create a test: POST https://jsonplaceholder.typicode.com/posts with a JSON body.
  2. Run once, copy the response as expectedJson.
  3. Set mode to full. Run again — the id field changes each time → failure.
  4. Add "$.id" to excludedPaths. Run — passes now.

Exercise 4: Both Layers Together

Goal: Use assertions + validation mode in one test.

  1. Create a test: GET https://jsonplaceholder.typicode.com/users/1.
  2. Set mode to selective with $.name = Leanne Graham.
  3. Add assertions: status = 200, response time ≤ 1000ms.
  4. Run — all three checks should pass independently.
  5. Change status to 201 — status fails, but selective validation still passes.
