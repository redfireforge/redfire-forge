1. The JsonPathBuilder Component

The JsonPathBuilder provides an interactive tree view for selecting which JSON paths to validate. Instead of typing paths manually, you navigate a visual tree built from an actual API response.

JsonPathBuilder Workflow

1. Fetch sample response (or paste JSON)
→ 2. buildTree() parses JSON into JsonNode tree
→ 3. Tree renders with expandable nodes
→ 4. Check/uncheck paths to validate
→ 5. Selected paths become ExpectedField[] rules

Key Functions

FunctionPurpose
buildTree(json)Parses JSON into a navigable JsonNode tree with paths
getAllLeafPaths(tree)Returns all selectable leaf paths from the tree
Checkbox selectionToggle individual paths on/off for validation
Search filterFilter nodes by name to find paths in large responses

Include vs. Exclude Mode

ModeBehaviorUse When
Include Only checked paths are validated You want to validate specific fields only
Exclude All paths validated except unchecked ones You want to validate everything except dynamic fields (timestamps, IDs)
💡 Exclude Mode for Volatile Fields Use exclude mode and uncheck $.createdAt, $.updatedAt, and $.id — these change between runs. Everything else is validated automatically.

2. Selective Validation Modes

RedfireForge supports four validation modes that determine how the response body is checked:

ModeComparesBest For
noneNothing (assertions only)When assertions are sufficient
exactEntire response body as JSON stringSnapshot testing
selectiveSpecific fields via ExpectedField[]Partial validation
regexResponse body against a regex patternLoose format checks

ExpectedField Interface

export interface ExpectedField {
  jsonPath: string;         // e.g. "$.data[0].name"
  operator: string;         // '=', '!=', 'contains', 'exists', etc.
  expectedValue: string;    // expected value to compare
}

When using selective mode, the JsonPathBuilder helps you select which paths become ExpectedField entries.

3. Unordered Array Validation

By default, validation is ordered: $.items[0].name = "A" checks index 0 specifically. But many APIs return arrays in unpredictable order. The unorderedArrays flag enables row-based matching.

The Problem

// Expected (from when you recorded the test):
{
  "products": [
    { "name": "Widget A", "code": "WA" },   // index 0
    { "name": "Widget B", "code": "WB" },   // index 1
  ]
}

// Actual response (different order):
{
  "products": [
    { "name": "Widget B", "code": "WB" },   // index 0 — was index 1!
    { "name": "Widget A", "code": "WA" },   // index 1 — was index 0!
  ]
}

// With ordered validation:
// ❌ $.products[0].name: expected "Widget A" got "Widget B"

// With unorderedArrays: true:
// ✅ Found matching row for {"name": "Widget A", "code": "WA"} at index 1

4. How validateFieldsUnordered() Works

Row-Based Matching Algorithm

1. Group fields by array prefix (e.g., products[0])
→ 2. For each row group, extract field suffixes (.name, .code)
→ 3. Scan ALL array indices for a row where ALL fields match
→ 4. If found → pass. If not → report best partial match. 
function validateFieldsUnordered(
  fields: ExpectedField[],
  responseBody: unknown
): FailureDetail[] {
  // 1. Separate array fields from non-array fields
  //    Array fields: path contains [N] like "products[0].name"
  //    Non-array: simple paths like "$.total"

  // 2. Validate non-array fields normally (exact path)

  // 3. Group array fields by row prefix:
  //    "products[0].name" → group "products[0]"
  //    "products[0].code" → group "products[0]"
  //    "products[1].name" → group "products[1]"

  // 4. Group rows by array pattern:
  //    "products[0]" and "products[1]" → array "products[*]"

  // 5. For each expected row, search all indices:
  //    Try products[0], products[1], ... products[N]
  //    Check if ALL fields in the row match at that index
  //    Track "used" indices to prevent double-matching
}

Key Behaviors

  • Row grouping: Fields with the same array prefix (e.g., products[0].name and products[0].code) are treated as one row.
  • All-or-nothing: A row matches only if ALL fields in the row match at the same index.
  • No reuse: Once an index is matched, it can't be used by another expected row.
  • Best partial: If no exact match is found, the error reports the closest partial match.
⚠️ Non-Array Fields Are Always Ordered unorderedArrays only affects paths containing array indices like [0]. Fields without array indices (e.g., $.total, $.status) are always validated by exact path.

5. The RulesTable Component

The RulesTable provides a tabular view of your validation rules. Each row shows:

ColumnShows
PathJSONPath expression (e.g., $.products[0].name)
OperatorComparison: =, !=, contains, exists, etc.
ExpectedExpected value
ActualActual value from last response (live preview)
Status✅ Pass / ❌ Fail indicator

The RulesTable updates in real-time when you run a test, showing pass/fail for each rule.

6. Response and Rules Versioning

For regression testing, you can save snapshots of responses and rule sets:

Response Versions

export interface ResponseVersion {
  id: string;
  label: string;       // e.g., "v1.2 baseline"
  timestamp: string;
  body: string;        // saved response body (JSON)
}
  • Save a "known good" response as a baseline.
  • Compare current responses against the baseline.
  • Detect regressions when the API changes.

Rules Versions

export interface RulesVersion {
  id: string;
  label: string;
  timestamp: string;
  fields: ExpectedField[];     // saved validation rules
  excludedPaths?: string[];    // paths excluded from validation
}
  • Save a set of validation rules as a named version.
  • Switch between rule versions to test different contracts.
  • Compare rule sets to see what changed.
📘 Version Workflow 1. Run test → save response as "v1 baseline" → save rules as "v1 contract".
2. API changes → run again → compare new response against v1 baseline.
3. Update rules if needed → save as "v2 contract".

7. Putting It All Together

A complete advanced validation setup for an e-commerce products endpoint:

validation: {
  mode: 'selective',
  unorderedArrays: true,       // products can arrive in any order
  sampleJson: '...',           // stored for JsonPathBuilder tree

  // Assertions (run always):
  assertions: [
    { type: 'status', expected: '200' },
    { type: 'responseTime', maxMs: 500 },
    { type: 'arrayLength', jsonPath: '$.products', operator: '>=', value: 2 },
  ],

  // Selective fields (run because mode = 'selective'):
  expectedFields: [
    { jsonPath: '$.products[0].name', operator: '=', expectedValue: 'Widget A' },
    { jsonPath: '$.products[0].price', operator: '=', expectedValue: '29.99' },
    { jsonPath: '$.products[1].name', operator: '=', expectedValue: 'Widget B' },
    { jsonPath: '$.products[1].price', operator: '=', expectedValue: '39.99' },
  ],

  // Exclude volatile paths:
  excludedPaths: ['$.products[*].updatedAt', '$.requestId'],

  // Saved versions for regression:
  responseVersions: [{ id: 'v1', label: 'Baseline', ... }],
  rulesVersions: [{ id: 'v1', label: 'Contract v1', ... }],
}

This setup: checks status + timing + array size via assertions, validates product fields unordered via selective mode, excludes volatile timestamps, and has version history for regression comparison.

8. Exercises

Exercise 1: Use the JSON Tree

Goal: Select validation paths from a complex nested response.

  1. Create a test targeting https://dummyjson.com/products/1.
  2. Run the test once to populate the response.
  3. Switch to Selective validation mode.
  4. Open the JsonPathBuilder — the response tree appears.
  5. Check $.title, $.price, $.category.
  6. Uncheck $.meta.updatedAt (volatile).
  7. Run again — only selected paths are validated.

Exercise 2: Unordered Array Validation

Goal: Validate products that arrive in any order.

  1. Create a test targeting https://dummyjson.com/products?limit=3.
  2. Enable unorderedArrays in validation settings.
  3. Add expected fields for $.products[0].title and $.products[1].title.
  4. Run the test — even if the API returns products in different order, validation passes because unordered matching finds the row at any index.

Exercise 3: Response Versioning

Goal: Save a baseline and detect regressions.

  1. Run a test and save the response as "v1 baseline".
  2. Save the current rules as "v1 contract".
  3. Modify an expected field value to simulate an API change.
  4. Run again — observe the failure against the new expectation.
  5. Restore the "v1 contract" rules version — test passes again.
