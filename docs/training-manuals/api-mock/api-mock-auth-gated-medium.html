API Mock: Auth-Gated Routes

Medium   Bearer Token · API Key Header · mTLS · 401 Fallback Variant

What You Will Learn

  • Use the security predicate source to gate on Bearer tokens
  • Require an API Key header using the header predicate source
  • Return a 401 Unauthorized variant when auth is absent
  • Configure mTLS certificate matching using the transport predicate source
  • Verify auth-gated routes with the Simulate modal

Predicate Sources for Auth

SourceWhat it reads from the request
securityParsed authentication token: scheme (Bearer/Basic/ApiKey), credential, claims
headerAny HTTP request header by name
transportTLS connection metadata: client cert subject DN, cert fingerprint

Part A — Bearer Token Gate

1
Create (or select) a route, e.g. GET /profile. Open the Match tab.
2
Click + Add Predicate. Set:
  • Source: security
  • Selector: scheme
  • Operator: exact
  • Expected value: Bearer
This predicate passes when the request has an Authorization: Bearer <token> header — any token value is accepted. To also validate the token value, add a second predicate with selector credential.

Add the 401 Fallback Variant

3
Go to the Response tab. Click + Add Variant. Name it 401 Unauthorized and set:
  • Status: 401
  • Content-Type: application/json
  • Body: {"error": "Unauthorized", "message": "Bearer token required"}
4
Switch to the Behavior tab → Selection panel. Set mode to Condition. Configure:
  • Default variant (200 OK) — condition: security scheme exact Bearer
  • Variant "401 Unauthorized" — condition: security scheme absent

Part B — API Key Header Gate

5
Create route GET /data. Add a predicate:
  • Source: header
  • Selector: X-Api-Key
  • Operator: present
This matches any request that supplies the X-Api-Key header, regardless of its value.
6
To validate a specific key value, change the operator to exact and set the expected value to your key string (e.g. sk-test-12345).

Part C — mTLS Client Certificate Gate

7
Open Server Settings (⚙ in title bar). Under the mTLS section, enable mTLS and supply the CA certificate PEM to use for client verification.
8
In a route, add a predicate:
  • Source: transport
  • Selector: clientCert.subject
  • Operator: contains
  • Expected value: CN=my-service
Only connections whose client certificate subject contains CN=my-service will match.

Part D — Verify with Simulate

9
Open the ⚗ Simulate modal for the GET /profile route.
10
First run: in the headers field, type: 
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.test.token
Click ▶ Run. The Trace tab should show ✅ for the security predicate and the 200 variant selected.
11
Second run: clear the Authorization header. Click ▶ Run. The Trace tab should show ❌ for security scheme predicate (absent) and the 401 variant selected.
💡 Don't hardcode tokens in predicates Use the present operator to gate on whether a token is supplied (structural auth gate), not the token's actual value. Actual token validation belongs in your real service. The mock is for functional testing, not security enforcement.

Security Predicate Selector Reference

SelectorMatches
schemeAuth scheme: Bearer, Basic, ApiKey
credentialRaw token/credential string after the scheme
claims.subJWT sub claim (decoded without verification)
claims.scopeJWT scope claim

Self-Practice Exercises

  1. Create a route with two variants: 200 OK for requests with a valid Bearer token, and 403 Forbidden for requests with a Bearer token whose claims.scope does NOT contain read:users.
  2. Gate GET /admin on an X-Admin-Token header with an exact value. Test both with the correct and incorrect token values using Simulate.
  3. Gate a route on the combination of a Bearer token AND an X-Tenant-Id header (use "All" predicate combinator). Verify that both must be present for a match.
