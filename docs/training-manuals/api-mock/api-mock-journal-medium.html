API Mock: Journal, Conflicts & Runtime Dock

Medium   Transactions Log · Conflict Inspector · State Tab · Variables · Console

What You Will Learn

  • Read the Transactions log: matched vs unmatched vs ambiguous outcomes
  • Inspect a transaction's full request and response detail
  • Create a new route directly from a captured transaction
  • Use the Conflict Inspector to find overlapping rules and adjust priority
  • Monitor scenario state and reset it
  • Add server variables used by template expressions

The Runtime Dock

The dock panel at the bottom of the studio activates when a server is running. Tabs: Transactions · Conflicts · State · Variables · Diagnostics · Console. You can resize the dock by dragging its top edge, or maximise it.

Part A — Transactions Tab

1
Start your mock server. With the server running, click the Transactions tab in the dock.
2
Each incoming request appears as a row. The row shows:
  • Outcome badge: matched (green), unmatched (grey), or ambiguous (yellow)
  • Method + path of the request
  • Matched Route name (if matched)
  • Duration in ms
  • Generation counter (how many times this route has been matched)
3
Click any row to open Transaction Detail below the list. It shows:
  • Full request: method, path, headers, body
  • Full response: status, headers, body sent
  • Policy decision: which selection policy applied
4
In Transaction Detail, use the action buttons:
  • Create route from transaction — opens a new route pre-filled with the request's method, path, and inferred body predicates. Edit and save.
  • Open in Requests — sends this transaction as a new item in your Requests workspace for further testing.
  • Copy — copies the full transaction as JSON to clipboard.
5
To clear the log, click the 🗑 Clear button in the Transactions tab header.

Part B — Conflicts Tab

6
The dock's Conflicts tab shows findings from the overlap analyser. Conflicts appear when two or more routes have match conditions that could both satisfy the same request.
7
Each conflict finding shows:
  • The two (or more) overlapping route names
  • Which predicates create the overlap
  • The current priority order between them
8
To resolve, click ↑ or ↓ on a route in the Conflict Inspector to raise or lower its priority. The higher-priority route wins when both match.
9
If the overlap is intentional (e.g. a broad catch-all plus a specific override), click Acknowledge on the finding. It is silenced until the routes change again.

Match Policies

PolicyBehaviour
highest_priorityWhen multiple routes match, the one with highest priority wins (default)
reject_multipleWhen multiple routes match, the request is rejected as ambiguous — no response is sent
specificity_then_idAmong equal-priority matches, the more specific predicate set wins

Part C — State Tab

10
The State tab shows, for each route using sequence or state selection mode:
  • The current scenario state (state mode) or next step index (sequence mode)
  • Match counters
11
Click Reset State to return all routes to step 0 / initial state. Useful after manually testing a lifecycle scenario and wanting to restart.

Part D — Variables Tab

12
Click the Variables tab. Add server-level variables using + Add:
  • Key: environment
  • Value: staging
This variable is now accessible in all route bodies as {{variables.environment}}.
13
Modify a variable value while the server is running — the new value takes effect on the very next request without a restart.
💡 Using "Create route from transaction" Send any real request to the mock server (even if unmatched), then click "Create route from transaction" in the detail panel. The studio pre-fills a new route with the method, path, and any headers it could infer as predicates. This is the fastest way to build a mock library from real traffic.

Self-Practice Exercises

  1. Send two identical requests to a running mock. In the Transactions log, click each row. Verify the generation counter increments.
  2. Create two routes that overlap (same method, same path, different header predicates). Check the Conflicts tab — a finding appears. Adjust their priority.
  3. Add a route in sequence mode with 3 variants. Check the State tab after each request. Click Reset State and verify the sequence restarts from step 1.
  4. Add a variable version = 1.0 in the Variables tab. Add a body template {"version": "{{variables.version}}"}. Update the variable to 2.0 at runtime and verify the response changes.
