API Mock: Library & Server Settings

Advanced   Library Landing · Tab Management · Server Settings · Native Export · Variables

What You Will Learn

  • Navigate the Library Landing to see all saved servers
  • Open, park, and delete servers; understand tab limits
  • Configure all Server Settings options (host, port, match policies, fallback, mTLS)
  • Export a server to a native JSON file and re-import it
  • Manage server-level variables used in template expressions

Part A — Library Landing

1
In the title bar, click the ≡ Library icon. The Library Landing modal opens showing a card for every saved server.
2
Each server card shows:
  • Server name and host:port
  • Route count and Example count
  • Status badge: open (currently in a tab), parked (saved but no open tab), or running
3
Click Open on any server card to load it into a new tab. API Mock Studio supports up to 8 simultaneous open tabs. If you are at the limit, close or park a tab first.

Part B — Tab Management

ActionHowEffect
Open serverLibrary → Open cardLoads server into a new tab
Park serverClose a tab (× button)Saves and removes the tab; server still exists in the library
Delete serverLibrary → Delete card (with confirmation)Permanently removes server and all its routes
Undo deleteToast notification → Undo (5 s window)Restores the server fully
4
To park the current server, click the × tab close button. If the server is running, you are prompted to stop it first. After closing, it appears in the Library as parked.
⚠️ Tab limit The maximum is 8 open server tabs. When you try to open a 9th, you get an error — park at least one tab first.

Part C — Server Settings

5
Click the ⚙ Settings icon in the title bar. The Server Settings modal opens.

Network Settings

SettingOptionsUse when
Host127.0.0.1 / localhost / 0.0.0.0Use 127.0.0.1 for local-only; 0.0.0.0 to accept connections from other devices on your LAN
PortAny integer 1–65535Change if the default port conflicts with another service

Match Policies

PolicyOptionsMeaning
Multiple-match policyhighest_priority (default) / reject_multipleWhen multiple routes match: highest_priority wins silently; reject_multiple returns an ambiguous error
Equal-priority policyreject / specificity_then_idAmong equal-priority matches: reject = ambiguous error; specificity_then_id = more specific predicate set wins

Fallback Behaviour

Fallback modeBehaviour when no route matches
Default responseReturns a generic 404 JSON body
Closest-match debugReturns a 404 JSON body that includes the near-miss trace — which route almost matched and which predicate failed
Proxy to upstreamForwards the request to a configured upstream URL; the upstream's response is returned to the client

Advanced Settings

Part D — Native Export

6
In the title bar, click ⬇ Export. The Export Confirmation dialog opens showing a summary (server name, route count, example count).
7
Click Download. A JSON file is downloaded (filename: <server-name>-mock-config.json). The file contains:
  • Server settings (name, host, port, policies)
  • All routes with predicates, variants, faults, timing
  • Saved simulation examples (samples)
  • Server variables
8
To re-import: click ⬆ Import → source = RedfireForge export → paste or upload the JSON → choose Merge or Replace → click Import.

Part E — Variables Tab

9
Open the Variables dock tab. Click + Add. Enter key baseUrl and value https://api.internal.corp.
10
In a route response body, use {{variables.baseUrl}}. When the server is running, update the variable value — all subsequent requests get the updated value without a server restart.
11
Server variables are saved with the server definition and round-trip through the native export/import.
💡 Proxy fallback for golden-path flows Set fallback to Proxy to upstream pointing at a staging API. Configure explicit routes only for the endpoints you want to override. Unmatched requests pass through transparently — ideal for partial mocking (mock only the broken endpoint; let the rest hit real staging).

Self-Practice Exercises

  1. Create 3 servers. Open all 3 as tabs. Try to open a 4th tab beyond the limit — observe the error. Park one tab and open the 4th.
  2. Change the Multiple-match policy to reject_multiple. Create two overlapping routes. Start the server and send a request. Observe the ambiguous outcome in the Transactions log.
  3. Export a server with multiple routes. Delete the server. Re-import via the native export source. Verify all routes are restored exactly.
  4. Enable the Closest-match debug fallback. Send a request that nearly matches a route but one predicate fails. Inspect the 404 response body — it should contain the near-miss trace.
