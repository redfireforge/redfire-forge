API Mock: Simulate Without Running

Medium   ⚗ Simulate Modal · Predicate Trace · Near-Miss · Saved Samples

What You Will Learn

  • Open the Simulate modal for any route
  • Send a simulated request and read the Trace tab (per-predicate pass/fail)
  • Understand "near-miss" — why a request didn't match a route
  • Read the Rendered tab to see the evaluated response body
  • Save a named simulation sample for future one-click replay
  • Export a simulation trace file

What is Simulate?

The Simulate modal fires a test request entirely in-memory against your current route configuration — no HTTP listener is started, no port is used. You see exactly how the server's predicate engine would evaluate your request against every rule, which variant would be selected, and what the rendered response body looks like. This is ideal for rule debugging before going live.

⚠️ Faults don't fire in Simulate Connection-level faults (timeout, reset, dribble) only operate on the live listener. In Simulate, the server renders the intended response as if the fault were absent.

Step-by-Step Walkthrough

Part A — Open the Simulate Modal

1
Select any route in the sidebar. In the Route Editor header (above the tabs), find the ⚗ (flask) button. Click it. The Simulate modal opens.
2
The modal has two panes:
  • Request form (left): method, path, headers (raw text), body
  • Results pane (right): Trace / Request / Rendered / Assertions tabs
The method and path pre-fill from the route's configuration.

Part B — Send a Simulated Request

3
In the Request form, optionally add headers (one per line, Header-Name: value format) and a request body if the route has body predicates.
4
Click ▶ Run (or press Ctrl/Cmd+Enter). The results pane switches to the Trace tab.

Part C — Read the Trace Tab

5
The Trace tab shows the predicate evaluation tree for the current request. For each predicate:
  • ✅ Green — predicate satisfied
  • ❌ Red — predicate failed
  • The actual value extracted from the request is shown alongside the expected value
6
If the route matched, the top of the Trace pane shows Matched: [Variant Name] with a green banner. If not matched, it shows Unmatched in red.
7
Near-miss: when a request came close to matching but one predicate failed, the trace shows a Near-miss summary at the top — which predicates passed, which failed, and how many predicates matched out of the total. This tells you exactly what to fix in your request or rule.

Part D — Read the Rendered Tab

8
Click the Rendered tab. This shows the actual response body after evaluating all template expressions against the simulated request. For example, {{request.headers.Authorization}} shows the value you put in the headers field.
9
The Rendered tab also shows the selected variant name, status code, and response headers that would be sent.

Part E — Save a Sample

10
After a successful simulation, click Save as Sample. A name input appears (pre-filled with a suggested name based on the path). Edit the name (e.g. Happy path — list users) and press Enter.
11
The sample appears in the samples list at the left of the modal (or in the route's Examples tab). Click a saved sample to reload its request into the form and re-run with one click.
12
Samples persist with the server definition. They also appear under the route's Examples tab in the Route Editor — your teammates see the same samples without re-typing requests.

Part F — Export Simulation Trace

13
After running a simulation, click the ⬇ Export trace button. A JSON file downloads containing the full predicate evaluation tree — useful for bug reports or offline analysis.

Trace Tab — Reading Predicate Results

IndicatorMeaning
✅ PassPredicate condition was satisfied by the request value
❌ FailPredicate condition was not satisfied; request value shown in red
Near-miss bannerRoute was not chosen, but N of M predicates passed — shows exactly which failed
Matched bannerRoute was selected; shows which variant was chosen and why
Assertions tabIf the route has associated assertions, shows pass/fail per assertion
💡 Debugging ambiguous routes If multiple routes have overlapping match conditions, the Trace tab shows which route "won" (highest priority) and which other routes also matched. This is how you discover unintended rule overlap before going live.

Self-Practice Exercises

  1. Add a body predicate to a route (e.g. require $.type == "order"). Open Simulate, send a request with a body that does NOT have type: "order". Read the near-miss trace to see which predicate failed.
  2. Save three named samples for one route (happy path, missing header, wrong body). Click each in turn and verify the Trace result differs.
  3. Use the Rendered tab to verify a template expression like {{request.headers.X-Correlation-Id}} echoes back the value you put in the headers field.
