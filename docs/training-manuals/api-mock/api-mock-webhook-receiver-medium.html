API Mock: Webhook Receiver & Outbound Callbacks

Medium   Inbound Capture · Event Routing · Journal Inspection · Outbound Fire-and-Forget

What You Will Learn

  • Create a webhook receiver route that accepts any POST with a JSON payload
  • Route to different response variants based on the event type in the payload
  • Inspect captured webhook payloads in the Transactions journal
  • Configure outbound HTTP callbacks that fire after a match (fire-and-forget)
  • Observe outbound errors in the Console dock tab

How Webhook Receiving Works

The mock server can act as a webhook receiver — it accepts inbound POST requests from any external system (payment processor, CI/CD pipeline, SaaS tool) and records them in the Transactions journal. You use body predicates to differentiate event types and respond appropriately.

Part A — Create the Webhook Receiver Route

1
Add a new route. Set Method to POST, Path to /webhooks.
2
In the Match tab, no predicates are required at the route level — all differentiation happens at the variant level. The route accepts any POST to /webhooks.

Part B — Add Per-Event Variants

3
Open the Response tab. Rename the default variant to user.created. Set:
  • Status: 200
  • Body: 
    {"received": true, "event": "user.created", "processingId": "{{random.uuid}}"}
4
Add a second variant named payment.processed:
  • Status: 200
  • Body: 
    {"received": true, "event": "payment.processed", "amount": "{{request.body.$.data.amount}}"}
5
Add a third variant named Unknown Event (the catch-all):
  • Status: 422
  • Body: 
    {"error": "Unrecognised event type", "received": "{{request.body.$.event}}"}
Mark this variant as isDefault.

Part C — Configure Event Routing (Condition Mode)

6
Open Behavior → Selection. Set mode to Condition.
7
For the user.created variant, add condition:
  • Source: body, Selector: $.event, Operator: jsonPath_equals, Expected: user.created
8
For the payment.processed variant:
  • Source: body, Selector: $.event, Operator: jsonPath_equals, Expected: payment.processed
9
The Unknown Event variant (isDefault) fires when no condition matches.

Part D — Inspect Webhooks in the Journal

10
Start the server. Send a test webhook payload: 
curl -X POST http://127.0.0.1:4001/webhooks \
  -H "Content-Type: application/json" \
  -d '{"event": "user.created", "data": {"id": "u-123", "email": "alice@example.com"}}'
11
In the Transactions dock tab, a new row appears for the POST. Click it to open Transaction Detail. The full request body is visible — you can inspect exactly what the external system sent.
12
Send a payload with an unknown event type ("event": "order.shipped"). The 422 variant fires and appears as matched with the Unknown Event variant name in the Transactions log.

Part E — Outbound Callbacks

13
Select the user.created variant in the sidebar. Open the Behavior tab → find the Outbound panel (or "Callbacks" sub-section).
14
Click + Add Callback. Configure:
  • URL: http://localhost:3001/audit (or any target)
  • Method: POST
  • Headers: Content-Type: application/json
  • Body: 
    {"source": "api-mock", "event": "{{request.body.$.event}}", "timestamp": "{{datetime.now}}"}
15
Callbacks are fire-and-forget: the mock sends the callback request after the response has been sent to the caller. The original caller does not wait for the callback to complete.
16
If the callback target is unreachable, the error appears in the Console dock tab (not as a failure for the original request).
💡 Outbound delay Callbacks fire asynchronously. If you need to verify they were sent, check the Console dock tab for the outbound request log entry.

Self-Practice Exercises

  1. Add a subscription.cancelled event variant with a 200 response. Verify routing from the Transactions tab.
  2. Configure an outbound callback on the payment.processed variant that fires to http://localhost:9000/notify. Start a simple HTTP listener on that port (python3 -m http.server 9000) and verify the callback arrives.
  3. Send a payload with no event field. Verify the Unknown Event variant (422) is selected.
