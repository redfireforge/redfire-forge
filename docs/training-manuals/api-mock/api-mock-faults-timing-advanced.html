Part A — Pattern Toolbox (🪄)

The Pattern Toolbox is a guided builder for complex predicate patterns. It opens from the 🪄 wand button next to any selector/value field on the Match tab.

Toolbox TabPurposeExample output
RegexBuild and test a regex pattern interactively^/users/[0-9]+/orders$
Path TemplateConvert a URL template to a glob or regex for path matching/orders/{id}/items/{itemId} → /orders/*/items/*
JSON Body / JSONPathPaste a sample JSON body, click a field to auto-generate its JSONPath$.customer.billing.zipCode
XPathPaste XML, click an element to generate its XPath/order/customer/address/zip
SchemaPaste a JSON Schema or XML Schema for schema-validation matchingValidates body structure on match
Query & HeadersCompose multi-field query string / header constraints visuallypage=present AND size=regex:\d+

Using the JSON Body Tab

1
In a route's Match tab, add a body predicate. Next to the Selector field, click the 🪄 button. The Pattern Toolbox opens.
2
Select the JSON Body / JSONPath tab. Paste a sample request body: 
{"order": {"id": "ord-1", "customer": {"email": "alice@ex.com"}, "items": [{"sku": "WIDGET"}]}}
3
Click the email field in the rendered JSON tree. The toolbox shows the auto-generated path: $.order.customer.email. Click Insert — the path is copied into the Selector field automatically.

Using the Regex Tab

4
Open the Regex tab. Type your pattern in the Pattern field, e.g. ^v[0-9]+\.[0-9]+$. In the Test Samples area, enter values like v1.0 (should match) and latest (should not match). The tool highlights each sample green or red in real-time.
5
Click Insert when satisfied. The pattern is pasted into the predicate's Expected field and the operator is set to regex.

Part B — Faults

Faults are configured in the Behavior tab → Faults panel. Each route variant can have at most one active fault type.

⚠️ Faults are live-server-only Faults only fire when the live HTTP listener is running. In the Simulate modal, the server renders the intended response body as if no fault were configured. Verify faults with real HTTP requests (e.g. curl) against the running server.
Fault TypeBehaviourConfig options
noneNo fault — normal response (default)—
timeoutOpens the socket but holds it open without sending any data for the configured duration, then closesHold duration (ms); capped by server longRunningMaxMs
resetSends TCP RST mid-response — connection is abruptly dropped—
dribbleSends the response body in small chunks with pauses between them (slow drip)Chunk schedule (bytes per interval, interval ms)
closeSends an empty response body and closes the connection immediately—
malformedSends invalid HTTP framing bytes — causes most clients to error with a parse failure—

Configuring a Timeout Fault

6
Select a route variant. Open Behavior → Faults. Click the Timeout card to enable it.
7
Set the Hold duration to 30000 ms (30 seconds). Note: the effective maximum is the server's longRunningMaxMs setting (configurable in Server Settings).
8
Start the server. Send a request to this route via curl. Your curl command will hang for 30 seconds before the connection closes. Your application's timeout handling should trigger before that if properly configured.

Configuring a Dribble Fault

9
Enable the Dribble fault card. Set:
  • Chunk size: 10 bytes
  • Interval: 500 ms
The response body is sent 10 bytes every 500 ms — mimicking a very slow upstream or saturated connection.

Part C — Timing Panel

The Timing panel is in Behavior → Timing. Settings apply to the variant, not the fault.

SettingEffect
Delay (ms)Fixed latency added before the response is sent. Use to simulate a slow API.
Jitter (ms)Random variation added to the delay on each request (uniformly distributed ± jitter). Combines with Delay.
Max matchesAfter this many successful matches, the variant is automatically disabled. Leave blank for unlimited.
Expires atCalendar/datetime picker. The variant is automatically disabled after this moment.
10
Set Delay = 200 ms, Jitter = 50 ms. Start the server and send several requests. The Transactions log duration column shows varied response times in the 150–250 ms range.
11
Set Max matches = 3. Send 4 requests. The 4th request matches a different variant (or is unmatched if none exist). Check the State tab to see the match counter reach the limit.
12
Set Expires at to 2 minutes from now (use the datetime picker). After the time passes, the variant is automatically disabled. The route continues to exist — only this variant is skipped.
💡 Chaos testing combination Combine Timing + Sequence mode: Variant 1 (200 OK, no delay), Variant 2 (200 OK, 1000 ms delay + 200 ms jitter), Variant 3 (timeout fault). Every 3rd request simulates a network timeout. This is a simple chaos testing pattern without external tooling.

Self-Practice Exercises

  1. Use the Regex Toolbox tab to build a pattern that matches semantic version strings (v1.2.3). Insert it into a path predicate for a route like GET /releases/{version}.
  2. Use the JSON Body tab to auto-generate the JSONPath for a deeply nested field in your domain's request body. Insert it into a body predicate.
  3. Configure a Reset fault on a variant. Start the server. Run curl -v http://127.0.0.1:4001/test and observe the "connection reset by peer" error.
  4. Set Max matches to 1 on a variant. Send two requests. The second should hit a different variant or be unmatched. Verify in the Transactions log.
