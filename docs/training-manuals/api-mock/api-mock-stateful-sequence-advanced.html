Selection Modes for Multi-Step Behaviour

ModeBehaviourCounter persists until
SequenceReturns variants in order: 1st request → Variant 1, 2nd → Variant 2, then wraps back to Variant 1Server restart or Reset State
StateEach variant maps to a named state; progresses through states as requests arrive; stops at the last stateServer restart or Reset State

Part A — Sequence Mode (Round-Robin)

1
Create route GET /health. Add three variants: Healthy (200 {"status":"ok"}), Degraded (200 {"status":"degraded"}), Down (503 {"status":"down"}).
2
Open Behavior → Selection. Set mode to Sequence. The order of variants in the sidebar is the sequence order — drag to reorder if needed.
3
Start the server. Send three requests to GET /health:
  • Request 1 → 200 {"status":"ok"}
  • Request 2 → 200 {"status":"degraded"}
  • Request 3 → 503 {"status":"down"}
  • Request 4 → back to 200 {"status":"ok"} (wraps)
4
Check the State dock tab. The GET /health row shows the current index (0, 1, 2, …).

Part B — State Mode (Order Lifecycle Example)

This example models an order that progresses: pending → processing → completed.

Create the Route

5
Create route GET /orders/{id} (path type: Path Template). Add three variants named after each lifecycle state:
6
Variant 1 — Pending: 
{"id": "{{request.pathParam.id}}", "status": "pending", "createdAt": "{{datetime.now}}"}
7
Variant 2 — Processing: 
{"id": "{{request.pathParam.id}}", "status": "processing", "estimatedCompletion": "{{datetime.now}}"}
8
Variant 3 — Completed: 
{"id": "{{request.pathParam.id}}", "status": "completed", "completedAt": "{{datetime.now}}"}
9
Open Behavior → Selection. Set mode to State. Assign state names to each variant:
  • Variant 1 → state name: pending
  • Variant 2 → state name: processing
  • Variant 3 → state name: completed
The initial state is the first variant (pending).

Test the Lifecycle

10
Start the server. Send GET /orders/ord-001 three times. Watch the response progress through pending → processing → completed.
11
Open the State dock tab. The row for GET /orders/{id} shows current state: completed.
12
Click Reset State. The state resets to pending. The next request again returns the Pending response.
💡 State vs Sequence Use Sequence when you want infinite round-robin cycling (e.g. simulating intermittent failures). Use State when you need a one-way progression that stops at the final state (e.g. resource lifecycle: pending → processing → completed).
⚠️ State is per-server-instance State counters reset when the server is stopped and restarted. They also reset when you call Reset State in the dock. If you need state to persist across restarts, save the current counter value from the State dock before stopping.
