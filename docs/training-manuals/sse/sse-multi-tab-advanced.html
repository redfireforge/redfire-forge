Multi-Tab Connection Management

Tab Bar

The SSE Studio tab bar runs across the top of the studio. Each tab represents an independent SSE connection with its own URL, headers, auth, event buffer, and console log. Tabs are completely isolated — disconnecting one tab has no effect on others.

OperationHow
Add a tabClick the + button in the tab bar (disabled when 8 tabs are open)
Switch tabsClick any tab label
Close a tabClick the × on the tab label; a confirmation prompt appears if the tab is connected
Rename a tabThe tab label is auto-derived from the connected URL (host + path); it updates when you connect
Max open tabs8 — beyond this the + button is disabled

Step-by-Step Walkthrough

Part 1 — Running Two Simultaneous Streams

1
In Tab 1 (the existing tab), enter https://sse.dev/test and click Connect.
2
Click the + button to open Tab 2. The left pane resets to an empty connection config — Tab 2 is completely independent of Tab 1.
3
In Tab 2, enter a different SSE URL, for example https://sse.dev/test with a different path or a local endpoint you have running. Click Connect.
4
Switch between Tab 1 and Tab 2 by clicking the tab labels. Each tab retains its own event log and console — events from Tab 1 do not appear in Tab 2 and vice versa.
5
Check the state dots on each tab label — both should show green (connected) simultaneously. This confirms that both streams are running in parallel.
6
Disconnect Tab 2 by switching to it and clicking Disconnect. Tab 1 remains connected and unaffected.

Part 2 — Different Auth Per Tab

7
A common real-world pattern: Tab 1 connects to the production SSE stream (with production credentials), Tab 2 connects to the staging stream (with staging credentials). Each tab's Auth tab configuration is stored independently.
8
In Tab 2, go to the Auth tab and set a different Bearer token than Tab 1. Connect both tabs. Use the Console tab on each to verify that the handshake entries show the correct per-tab auth headers.

Part 3 — Tab Persistence

9
With multiple tabs open and connected, perform a full browser page refresh (F5 / Cmd+R).
10
After the page reloads, SSE Studio restores all tabs with their URLs, headers, and auth configuration intact. Event buffers are not persisted (they are cleared on reload), but the connection configuration is fully restored.
11
You need to manually reconnect each tab after a page reload — connections are not automatically re-established.
Tab naming tip Tab labels are automatically set to the host + path of the connected URL. If you connect Tab 1 to https://sse.dev/test and Tab 2 to https://api.example.com/events, the labels make it easy to identify which stream is which at a glance.

SSE Wire Format — Deep Dive

How SSE Works at the Transport Level

When SSE Studio connects, it sends a standard HTTP GET request with two mandatory headers:

GET /api/events HTTP/1.1
Accept: text/event-stream
Cache-Control: no-cache

The server responds with Content-Type: text/event-stream and keeps the body open, writing event blocks as they become available. Each event block is terminated by a blank line.

Event Fields

FieldSyntaxDescription
event:event: price-updateNames the event type. If omitted, defaults to message. Shown as the type badge in the event log.
data:data: {"price":67300}The payload. Multiple data: lines in a single event block are joined with \n.
id:id: evt-1042Sets the Last-Event-ID. Sent in the Last-Event-ID header on reconnect so the server can resume from this point.
retry:retry: 5000Tells the studio to wait 5000 ms before reconnecting if the stream drops. Overrides the default 3000 ms.
:: keep-alive pingComment — ignored by the parser. Servers send these to prevent proxy timeouts on long-lived connections.

Multi-Line Data

Multiple data: lines within a single event block are concatenated with \n. This is commonly used to embed pre-formatted text or JSON split across lines:

event: status-report
data: {
data:   "service": "payments",
data:   "status": "degraded",
data:   "latency_p99_ms": 2400
data: }

In the event detail panel, this appears as a single data string with embedded newlines. If the concatenated result is valid JSON, the studio auto-detects it and pretty-prints it.

Null character in id: field If an id: field value contains a null character (\0), the W3C spec requires that the id is silently ignored. The studio implements this rule — the Last-Event-ID is not updated for invalid id values.

Reconnect Resume Flow

When the studio reconnects after a drop, it includes the Last-Event-ID from the last successfully processed event:

GET /api/events HTTP/1.1
Accept: text/event-stream
Cache-Control: no-cache
Last-Event-ID: evt-1042

The server uses this to skip already-delivered events and resume the stream from the correct position. This is why persistent event IDs are critical for resumable feeds. If the server sends no id: fields, reconnects always start from the current tail of the stream — potentially missing events that arrived during the disconnection window.

Keep-Alive Comments

Many reverse proxies and CDNs will close idle HTTP connections after 60–120 seconds. SSE servers work around this by sending a comment-only line every 15–30 seconds:

: ping

This resets the idle timer without creating an event in the log. You may notice these in the raw HTTP stream but you will not see them in the SSE Studio event log — the parser correctly skips all comment lines.

Writing an SSE-Compatible Server Endpoint

A minimal Node.js/Express SSE endpoint:

app.get('/events', (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('Connection', 'keep-alive');
  res.setHeader('Access-Control-Allow-Origin', '*');
  res.flushHeaders();

  let id = 0;
  const timer = setInterval(() => {
    id++;
    res.write(`id: ${id}\n`);
    res.write(`event: update\n`);
    res.write(`data: ${JSON.stringify({ tick: id, ts: Date.now() })}\n\n`);
  }, 1000);

  // Keep-alive comment every 30s
  const ping = setInterval(() => res.write(': ping\n\n'), 30000);

  req.on('close', () => {
    clearInterval(timer);
    clearInterval(ping);
  });
});

Practice Exercises

  1. Open 3 tabs, each connected to a different SSE URL. Verify that closing one tab does not affect the others.
  2. Find a stream that sends id: fields. Disconnect and reconnect — confirm the Last-Event-ID header appears in the Console handshake entry with the last id value you received.
  3. Write a local SSE endpoint that sends events with and without id: fields. Connect SSE Studio and observe the Last-Event-ID value in the status strip — does it stop updating when you stop sending ids?
  4. Send a multi-line data event from your local endpoint. Click the event in the log and verify the detail panel joins the lines correctly with newlines.
