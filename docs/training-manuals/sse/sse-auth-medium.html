Authentication for Protected SSE Streams

Medium   Auth tab · Bearer token · API Key · Global auth profiles · "Will send" preview · Dot indicator

What You Will Learn

  • Switch to the Auth tab in the left pane
  • Configure a Bearer token for a protected SSE endpoint
  • Configure an API Key (header or query parameter)
  • Inherit auth from a global auth profile
  • Read the "Will send" resolved-auth preview
  • Identify when auth is configured via the Auth tab dot indicator
SSE auth advantage over WebSocket SSE connects via a standard HTTP GET request, so the studio can inject custom headers (Authorization, X-API-Key, etc.) directly in the fetch call — no proxy is required. WebSocket auth needs a proxy workaround because the browser's native WebSocket API does not allow custom upgrade headers.

Opening the Auth Tab

1
In the left pane, click the Auth tab (second tab in the left-pane tab strip, after Connect).
2
The Auth panel loads with the current auth mode. Default is None. When auth is configured, a small dot appears on the Auth tab label so you can see at a glance that this connection uses auth.

Step-by-Step Walkthrough

Part 1 — Bearer Token

3
In the Auth tab, open the Auth type dropdown and select Bearer token.
4
A token input field appears. Enter your token (for this walkthrough use a placeholder such as my-test-jwt-token). The token is stored masked — click the eye icon to reveal it.
5
Look at the Will send section near the bottom of the auth panel. It shows the resolved description of the auth, for example: Authorization: Bearer my-test-jwt-token. This confirms exactly which header will be included in the SSE GET request.
6
Switch to the Connect tab — the Auth tab label now has a presence dot (a small coloured circle) indicating auth is configured. This is useful when you have multiple tabs open and need to know which connections use auth.
7
Disconnect and reconnect to apply the new auth. Open the Console tab (right pane) — the handshake log entry will show the resolved URL and the auth header that was sent.

Part 2 — API Key in a Custom Header

8
Go back to the Auth tab. Change the auth type to API Key.
9
Two new fields appear: Header name (default: X-API-Key) and Key value. Enter a header name your API uses, e.g. X-Service-Token, and a value.
10
Confirm the Will send preview updates to show X-Service-Token: <value>.
11
Reconnect and verify in the Console tab that the custom header appears in the handshake entry.

Part 3 — Global Auth Profile

12
Global auth profiles are created in the Environment Manager. If your team has shared credentials stored there (e.g. a staging Bearer token), you can inherit them here instead of entering the token directly in every SSE tab.
13
In the Auth tab, change the auth type to Global profile. A dropdown appears listing all profiles available in the current environment.
14
Select a profile. The Will send preview shows the resolved auth from that profile — e.g. Authorization: Bearer <resolved-token>.
15
When the profile token is rotated in Environment Manager, all SSE tabs using that profile automatically pick up the new token on the next reconnect.

Part 4 — Verify and Debug

16
If your endpoint returns HTTP 401, the studio enters the error state (red dot) and the Console tab shows an error entry. Check the handshake log to verify the auth header that was actually sent.
17
Common debugging steps:
  1. Open the Console tab — expand the handshake entry to see the full request headers
  2. Check the "Will send" preview on the Auth tab — does it show the correct token?
  3. Verify the token has not expired (check expiry in Environment Manager if using a profile)
  4. Try connecting with auth mode set to None to confirm the endpoint is reachable without auth, then add auth back

Token security Tokens are stored per-tab in the browser's local storage for the current session. Do not enter production secrets into a shared or public browser profile. Use global auth profiles backed by environment-level secrets instead.

Practice Exercises

  1. Configure Bearer auth, connect, open the Console tab, and confirm the Authorization header appears in the handshake log entry.
  2. Switch between Bearer and API Key auth on the same tab without disconnecting, then reconnect and compare console entries.
  3. If you have a global auth profile: select it, check the "Will send" preview, and confirm the profile's resolved value matches what you see in the Console handshake entry.
