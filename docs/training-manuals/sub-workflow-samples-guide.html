1. Sub-Workflow Feature Overview

Sub-Workflows allow you to compose workflows from reusable building blocks. A parent workflow can invoke a child workflow via the Sub-Workflow node, passing data in through input mappings and receiving results back through output mappings.

Why Sub-Workflows?

  • Reusability — Build once, use in many parent workflows
  • Modularity — Break complex flows into manageable pieces
  • Iteration — Process collections with multi-instance forEach
  • Resilience — Configure retry, timeout, and failure handling per child
  • Dynamic dispatch — Select child workflows at runtime via expressions

How It Works

┌──────────────────┐ Input Mappings ┌──────────────────┐ │ │ ──────────────────────► │ │ │ Parent Workflow │ │ Child Workflow │ │ │ ◄────────────────────── │ │ └──────────────────┘ Output Mappings └──────────────────┘ Parent variables → Child initial variables Child final variables → Parent variables

Sub-Workflow Node Properties

PropertyTypeDefaultDescription

VariableSet WhenValue

__subWorkflowFailedonChildFailure=continue + failure"true" — indicates at least one iteration failed.

💡 Dynamic Workflow ID Set workflowId to an expression like {{rollbackWorkflowId}} to select the child workflow at runtime based on a variable. The expression is resolved against the parent's variable context before looking up the child. Validation will show a warning icon (⚠) for dynamic IDs since static checks (self-reference, cycle detection) cannot be performed.
🔗 Input Mappings

Map parent {{expression}} → child variable. Resolved at execution time against parent context.

📤 Output Mappings

Map child final variable → parent variable. Captured from child's variable snapshot after execution completes.

🔄 Multi-Instance

Iterate over a JSON array, running the child once per element. Sequential or parallel execution modes.

🛡️ Resilience

Retry on failure with configurable count and delay. Timeout with automatic abort. Continue-on-failure mode.

ƒ Dynamic Dispatch

Use {{variable}} expressions in workflowId to select the child workflow at runtime.

👁️ Canvas Preview

See child workflow node/edge counts and pass/fail status directly on the Sub-Workflow node.

3. Sample 1 — Sub-Workflow Orchestrator Basic

3.1 Purpose & Use Case

This sample demonstrates the foundational sub-workflow pattern: a parent workflow fetches a list of users from an API, then uses a multi-instance forEach sub-workflow node to process each user individually through a child workflow. Results are checked for partial failures.

Real-world analogy: A batch job that processes user records one by one — e.g., sending welcome emails, syncing profiles to a CRM, or running compliance checks per user.

3.2 Architecture & Flow Diagram

┌─────────────┐ │ Start │ inputVariables: { apiBase } └──────┬──────┘ ▼ ┌─────────────────────┐ │ 1. Fetch User List │ GET {{apiBase}}/users │ (HTTP) │ extracts: usersJson, userCount └──────┬──────────────┘ ▼ ┌─────────────────────┐ │ 2. Extract User IDs │ userIds = [1,2,3] │ (SetVariable) │ processedCount = 0 └──────┬──────────────┘ ▼ ┌─────────────────────────────────────────────┐ │ 3. Process Each User (Sub-Workflow) │ │ │ │ workflowId: "sample-subwf-child" │ │ multiInstance: │ │ collection: {{userIds}} │ │ elementVariable: userId │ │ mode: sequential │ │ retryCount: 1 · retryDelay: 2s │ │ onChildFailure: continue │ │ timeout: 30s │ └──────┬──────────────────────────────────────┘ ▼ ┌─────────────────────┐ │ 4. Log Results │ "Sub-workflow completed. Last status: {{lastUserStatus}}" │ (LogDebug) │ └──────┬──────────────┘ ▼ ┌─────────────────────┐ │ 5. All Succeeded? │ {{__subWorkflowFailed}} != "true" │ (Condition) │ └──┬──────────────┬───┘ │ Yes │ No ▼ ▼ ┌────────┐ ┌───────────────┐ │All Good│ │Partial Failure│ └───┬────┘ └──────┬────────┘ └───────┬───────┘ ▼ ┌─────────┐ │ End │ └─────────┘

3.3 Node-by-Node Walkthrough

1 Fetch User List (HTTP Node)

URL{{apiBase}}/users
MethodGET
ExtractionsusersJson ← full body, userCount ← $.length

Calls the JSONPlaceholder API to fetch the user list. The full JSON array is stored for reference, and the count is extracted for logging.

2 Extract User IDs (SetVariable Node)

userIds[1,2,3] — a JSON array of user IDs to process
processedCount0 — counter for tracking

Creates the collection array that the multi-instance sub-workflow will iterate over. In production, you'd use an expression like {{$map(usersJson, 'id')}}.

3 Process Each User (Sub-Workflow Node) — Key Node

Child workflowsample-subwf-child (User Processor)
Input mappings{{apiBase}} → apiBase
Output mappingsuserStatus → lastUserStatus
Multi-instanceCollection: {{userIds}}, Element: userId, Mode: sequential
Retry1 retry with 2s delay
On failurecontinue — sets __subWorkflowFailed=true but doesn't stop
Timeout30 seconds
📘 How Multi-Instance Works The engine parses {{userIds}} → [1,2,3], then runs the child workflow 3 times sequentially. Each run receives userId set to the current element (e.g., "1", "2", "3") and __subWorkflowIndex set to "0", "1", "2".

4 Log Results (LogDebug Node)

Logs the last output mapping value. With snapshotVariables: true, captures all variables at this point for debugging.

5 All Succeeded? (Condition Node)

Checks the engine-set __subWorkflowFailed variable. If any iteration failed and onChildFailure=continue was used, this variable is "true".

3.4 Child Workflow: User Processor

┌────────┐ ┌────────────────┐ ┌──────────────┐ ┌──────┐ │ Start │──►│ Fetch User │──►│ Build Status │──►│ End │ │ │ │ GET /users/{{ │ │ userStatus = │ │ │ │userId=1│ │ userId}} │ │ processed: │ │ │ │apiBase │ │ → userName │ │ {{userName}} │ │ │ └────────┘ │ → userEmail │ └──────────────┘ └──────┘ └────────────────┘

A minimal 4-node workflow. Receives apiBase and userId from the parent, fetches the user, builds a status string, and returns userStatus via output mapping.

3.5 Step-by-Step Development Guide

  1. Create the child workflow first.
    Go to Workflows → + New. Name it "User Processor". Add: Start → HTTP → SetVariable → End.
    Configure the HTTP node with {{apiBase}}/users/{{userId}} and extract userName.
    In SetVariable, set userStatus = processed:{{userName}}.
    In Start, define input variables: apiBase, userId.
  2. Create the parent workflow.
    Name it "User Orchestrator". Add: Start → HTTP → SetVariable → Sub-Workflow → LogDebug → Condition → two LogDebug → End.
  3. Configure the Sub-Workflow node.
    Click the Sub-Workflow node → open the config panel:
    • Select workflow: Choose "User Processor" from the dropdown
    • Input Mappings: Add {{apiBase}} → apiBase
    • Output Mappings: Add userStatus → lastUserStatus
  4. Enable multi-instance.
    Check the "Multi-Instance (forEach)" checkbox:
    • Collection Expression: {{userIds}}
    • Element Variable: userId
    • Execution Mode: Sequential
  5. Configure resilience.
    • Retry Count: 1
    • Retry Delay: 2000ms
    • On Child Failure: Continue
    • Timeout: 30000ms
  6. Wire the condition.
    Set Condition left to {{__subWorkflowFailed}}, operator !=, right to true.
    Connect Yes → "All Good", No → "Partial Failure". Both → End.
  7. Test. Click Quick Test. Watch the console — you'll see [sub] prefixed logs for each child iteration.

4. Sample 2 — Order Pipeline with Sub-Workflow Medium

4.1 Purpose & Use Case

This sample demonstrates conditional sub-workflow dispatch: a parent workflow fetches an order, checks whether it requires express or standard shipping, and routes to the appropriate sub-workflow branch. Both branches call the same child workflow but with different input parameters.

Real-world analogy: An e-commerce order pipeline that routes to different fulfillment processes based on shipping tier — same processor, different configurations.

Standard │ │ Shipping │ │ Shipping │ │(Sub-Workflow) │ │ (Sub-Workflow) │ │ │ │ │ │ tier=express │ │ tier=standard │ │ retry=2 │ │ timeout=30s │ │ timeout=15s │ │ │ └──────┬────────┘ └───────┬────────┘ └──────┬────────────┘ ▼ ┌──────────────────────┐ │ 4. Build Confirmation│ confirmation = "Order {{orderId}} shipped..." │ (SetVariable) │ └──────┬───────────────┘ ▼ ┌──────────┐ │ 5. 4.3 Node-by-Node Walkthrough

1 Fetch Order (HTTP Node)

URLhttps://jsonplaceholder.typicode.com/posts/{{orderId}}
MethodGET
ExtractionsorderTitle ← $.title, orderBody ← $.body

2 Express Shipping? (Condition Node)

Evaluates {{shippingType}} == "express". Routes to the express branch (Yes) or standard branch (No).

3a Express Shipping (Sub-Workflow Node)

Child workflowsample-shipping-child (Shipping Processor)
Input mappings{{orderId}} → orderId, "express" → tier
Output mappingstrackingNumber → trackingNumber
Retry2 retries, 1s delay
On failurefail (express shipments are critical)
Timeout15s (faster SLA for express)

3b Standard Shipping (Sub-Workflow Node)

Child workflowsample-shipping-child (same child!)
Input mappings{{orderId}} → orderId, "standard" → tier
Output mappingstrackingNumber → trackingNumber
Retry0 (no retry for standard)
Timeout30s (relaxed SLA)
⚠ Key Pattern: Same Child, Different Config Both branches reference the same sample-shipping-child workflow but pass different tier values and have different retry/timeout policies. This is a powerful pattern for reusing a workflow with environment-specific or tier-specific configurations.

4 Build Confirmation (SetVariable Node)

Both branches converge here. Builds a confirmation string using the trackingNumber returned by whichever branch executed.

4.4 Child Workflow: Shipping Processor

┌────────┐ ┌──────────────────────┐ ┌───────────────────┐ ┌──────┐ │ Start │──►│ Ship Order │──►│ Build Tracking │──►│ End │ │ │ │ POST /posts │ │ trackingNumber = │ │ │ │orderId │ │ {"orderId","tier"} │ │ TRK-{{tier}}- │ │ │ │tier │ │ → shipmentId │ │ {{shipmentId}} │ │ │ └────────┘ └──────────────────────┘ └───────────────────┘ └──────┘

A 4-node child workflow. POSTs a shipment request, extracts the shipmentId, and builds a tracking number like TRK-express-101. The trackingNumber variable is captured by the parent's output mapping.

4.5 Step-by-Step Development Guide

  1. Create the Shipping Processor child.
    New workflow → Start (inputs: orderId, tier) → HTTP POST → SetVariable (trackingNumber) → End.
  2. Create the parent Order Pipeline.
    Start (inputs: orderId, shippingType) → HTTP GET → Condition → two Sub-Workflow nodes → SetVariable → LogDebug → End.
  3. Wire the condition branches.
    From the Condition node: connect the Yes handle to "Express Shipping" and No handle to "Standard Shipping".
    Both sub-workflow outputs connect to the same "Build Confirmation" node.
  4. Configure each Sub-Workflow node.
    Both point to the same child workflow. Set different tier input values and different retry/timeout policies.
  5. Configure output mapping.
    Both sub-workflow nodes map trackingNumber → trackingNumber. Since only one branch executes, the parent receives the result from whichever path was taken.
  6. Test with both scenarios.
    Run Quick Test with shippingType=express → verify express branch executes with 15s timeout.
    Change to shippingType=standard → verify standard branch executes with 30s timeout.
💡 Design Tip: Convergence Points When two branches of a condition merge into a single downstream node (like "Build Confirmation"), the engine automatically handles the convergence. The skipped branch's subtree won't block the taken branch from reaching the convergence point.

5. Sample 3 — Multi-Region Deploy Orchestrator Advanced

5.1 Purpose & Use Case

This is the most complex sample — a full CI/CD deployment pipeline that validates a build artifact, runs parallel pre-checks via Fork/Join, deploys to multiple regions in parallel using multi-instance forEach, analyzes results, and conditionally triggers a dynamic rollback sub-workflow.

Real-world analogy: A deployment orchestrator like Spinnaker or ArgoCD — validate → pre-check → deploy → monitor → rollback.

Key Sub-Workflow Features Demonstrated

🔄 Multi-Instance Parallel

Deploys to 3 regions concurrently using mode: "parallel"

ƒ Dynamic Workflow ID

Rollback uses {{rollbackWorkflowId}} — selected at runtime

🛡️ Continue on Failure

Deploy continues even if one region fails (onChildFailure: continue)

⑃ Fork/Join + Sub-Workflow

Combines parallel pre-checks with sub-workflow orchestration

5.5 Step-by-Step Development Guide

  1. Create both child workflows first.
    Region Deployer: Start (region, version) → HTTP POST → SetVariable (regionStatus) → End.
    Rollback Handler: Start (version, regions) → LogDebug → HTTP POST → SetVariable (rollbackStatus) → End.
  2. Create the parent orchestrator.
    Add: Start → HTTP → Fork → 2× HTTP → Join → Sub-Workflow → SetVariable → Condition → LogDebug + Sub-Workflow → End.
  3. Configure the deploy Sub-Workflow node.
    Select "Region Deployer". Enable multi-instance:
    • Collection: {{regions}}
    • Element variable: region
    • Mode: Parallel
    Set onChildFailure: continue so one failed region doesn't abort others.
  4. Configure the rollback Sub-Workflow node.
    Instead of selecting a workflow from the dropdown, click the ⇄ Expression toggle.
    Enter {{rollbackWorkflowId}} as the workflow ID expression. This makes the child workflow selection dynamic.
  5. Define Start variables.
    version=v2.5.0, regions=["us-east-1","eu-west-1","ap-southeast-1"], rollbackWorkflowId=sample-rollback-child.
  6. Test the happy path.
    Quick Test → all 3 regions deploy in parallel → condition evaluates true → "Deploy Success" log.
  7. Test the failure path.
    Modify the Region Deployer child to fail (e.g., invalid URL) → re-run → condition evaluates false → dynamic rollback sub-workflow executes.

7. Best Practices & Tips

Design Guidelines

  1. Build children first, then wire parents. The child must exist before you can select it in the Sub-Workflow config dropdown.
  2. Use explicit input/output mappings over propagateAllOutputs. Explicit mappings make data flow visible and avoid variable name collisions.
  3. Set maxDepth conservatively. Default is 10, but most use cases need 2-3 levels. Lower values catch accidental infinite recursion faster.
  4. Always configure a timeout for sub-workflows that call external APIs. Without a timeout, a hanging API call will block the parent indefinitely.
  5. Use onChildFailure: continue for batch/multi-instance patterns where partial success is acceptable. Check __subWorkflowFailed afterward.

Multi-Instance Tips

  1. Keep collections small for sequential mode. 10-50 items is fine. For 100+ items, use parallel mode.
  2. Parallel mode fires all at once. If the target API has rate limits, prefer sequential or add delays in the child.
  3. Empty collections skip cleanly. The engine sets __subWorkflowResults=[] and continues without error.
  4. Access per-item results via {{__subWorkflowResults}} — a JSON array of {passed, vars} objects.

Dynamic Workflow ID Tips

  1. Validation shows warnings, not errors. Static checks (cycle detection, self-reference) are skipped for dynamic IDs — the target isn't known until runtime.
  2. Canvas shows ƒ {{...}} indicator. The "Open" button and inline preview are hidden since the target can't be resolved statically.
  3. Always provide a fallback. If the expression resolves to a non-existent workflow, the node fails with "not found". Use a Condition before the node to validate the ID.

Debugging Sub-Workflows

  1. Console logs are prefixed with [sub]. Child workflow output is indented under the parent's log entries.
  2. Use Debug mode. Step-through debugging pauses at each node, including inside child workflows.
  3. Check __subWorkflowResults. After multi-instance execution, this JSON array shows which iterations passed and what variables each produced.
  4. LogDebug with snapshotVariables: true captures all variables (including __ internals) at that point for forensic analysis.
