Pre-Validation (Dry Run)

Data-Driven Testing — Training Manual

Medium ★★☆ · Pre-Validate · Bulk Data Check · Before Full Run

RedfireForge v0.5.6

1. Purpose & Use Case

Before running a full 100-row parameterized test suite, you want confidence your data and validation rules are correct. Pre-validation sends a quick probe request for each data row and reports pass/fail without saving results or updating baselines.

Use cases:

  • Data QA — verify imported CSV/Excel data matches real API responses before committing.
  • Rule tuning — adjust JSON paths and expected values iteratively without creating test history.
  • New API version — check which rows will break before upgrading your baseline.

2. Prerequisite

Complete Parameterized Validation first. You should understand validate columns and baselines.

3. Tutorial: Pre-Validate Country Data

Step 1: Load the Sample

  1. Load the "Country Validation Suite" from the Gallery.
  2. Open the test editor and go to the Data Source tab.

Step 2: Run Pre-Validation

  1. In the Test Editor toolbar, click Pre-Validate (🔍 icon).
  2. RedfireForge sends 8 requests (one per row) against the REST Countries API.
  3. Results appear inline — each row shows ✅ or ❌ next to the validate columns.

Step 3: Interpret Results

Row StatusMeaningAction
✅ All greenAll validate columns match the API responseReady for full run
❌ Red cellExpected value doesn't match actualFix data or update the expected value
⚠️ Yellow cellJSON path not found in responseCheck your JSON path mapping

Step 4: Fix and Re-Validate

  1. If any rows failed, edit the expected values directly in the table.
  2. Click Pre-Validate again to re-check just those rows.
  3. Once all rows are green, proceed to a full run from the Runner tab.
💡 Key difference from "Run" Pre-validate does not save results to history, does not update baselines, and does not count toward test statistics. It's purely for data verification.

4. Practical Example: Pokémon Data QA

  1. Load the Pokémon Contract Sweep sample.
  2. Change Pikachu's expected type from "electric" to "fire" (intentional error).
  3. Run Pre-Validate — Pikachu's row shows ❌ with diff: expected "fire", actual "electric".
  4. Fix it back to "electric" and re-validate — all green.
⚠️ Rate Limiting Some public APIs have rate limits. Pre-validation sends requests quickly — if you have 100+ rows, consider enabling only a subset for the initial check.

5. Try It Yourself

  1. Import test-data/sample_pokemon_15.csv into a new test targeting https://pokeapi.co/api/v2/pokemon/{{name}}.
  2. Run Pre-Validate to check all 15 rows.
  3. Intentionally break 2–3 expected values and observe the inline error indicators.
  4. Fix them and confirm all rows pass before doing a full run.

6. Verify Modal: The Full-Featured Alternative

Pre-validation gives quick inline pass/fail indicators. For deeper analysis, use the Verify & Inspect modal (click ▶ Verify All in the Data Source toolbar):

  • Side-by-side comparison of expected vs. actual values per cell
  • Failure pattern grouping — see how many rows share the same mismatch
  • Run & Capture to auto-populate expected values from live API
  • Accept Changes to update your expected values to match new API behavior
  • Re-fetch Failed to retry only the rows that errored

See Verify & Validation Contract for a full walkthrough.
