Verify & Validation Contract

Automated Data Verification & Expected-Value Contracts — Training Manual

Advanced ★★★ · Data-Driven · Regression

RedfireForge v0.5.7

1. Purpose & Use Case

The Verify feature lets you validate all data source rows against the live API in a single pass — without running a full test. It catches stale expected values, broken endpoints, and regressions before they reach your test results.

The Validation Contract takes this further: define which JSON paths in the response you care about, and RedfireForge automatically tracks changes to those paths across runs.

Prerequisite You need a data source with validate-type columns (expected values). See Parameterized Validation.

2. The Verify Modal

Opening the Verify Modal

  1. Open a test in the Test Editor.
  2. Switch to the Data Source tab.
  3. Click ▶ Verify All in the Data Source toolbar.
  4. The Verify modal opens, showing all enabled data source rows.

Understanding the Verify UI

The modal displays each row with its status:

StatusIconMeaning
Pending⏳Not yet verified
Pass✅Expected values match API response
Fail❌Mismatch between expected and actual values
Error⚠️Request failed (network error, 5xx, etc.)

3. Verify All

  1. Click ▶ Verify All in the modal toolbar.
  2. Each row is executed against the live API (sequentially).
  3. For each row, the actual response is compared to the expected values in validate columns.
  4. Results update in real time — green checks for passing rows, red X for failures.
  5. Click any failed row to see the diff: expected vs actual value, with the JSON path highlighted.

4. Run & Capture

Run & Capture executes all rows and captures the actual API response values into your validate columns — overwriting existing expected values with what the API actually returns.

  1. Click ⬇ Run & Capture in the modal toolbar.
  2. All rows execute against the live API.
  3. Each row's validate columns are populated with actual response values.
  4. After capture, all rows show as ✅ (since expected now equals actual).
  5. To run capture again on the same rows, click ⬇ Re-capture in the modal toolbar.
⚠️ When to Use Run & Capture Use this when setting up a new data source for the first time, or after a known, intentional API change. It overwrites expected values — do not use it blindly on an established regression suite.

5. Re-Fetch Failed & Accept Changes

Re-Fetch Failed

After a verify pass, click ↻ Re-fetch Failed (n) (the label includes the failure count) to retry only the rows that failed or errored. This is useful when failures were caused by transient issues (network timeouts, server restarts).

Accept All Changes

When the API has legitimately changed, click Accept All Changes to update all failed rows' expected values to the actual values returned by the API.

Per-Row Accept

Click the ✅ accept button on an individual failed row to accept just that row's actual value as the new expected value. Use this when only some failures represent intentional changes.

6. Failure Pattern Grouping

When many rows fail for the same reason, the Verify modal groups them by failure pattern:

  • Same JSON path mismatch — e.g., all rows fail on $.status (expected "active", got "inactive")
  • Same error type — e.g., 10 rows got 503 Service Unavailable

This helps you quickly identify whether failures are a systemic API change (fix once) or scattered data issues (fix individually).

7. Validation Contract

A validation contract is a set of JSON response paths that you "care about" for a data source. When you define a contract, RedfireForge monitors those paths and flags any structural changes — even if you haven't written explicit expected values for every row.

How It Works

  1. In the Data Source tab toolbar, click Contract.
  2. Add JSON path patterns you want to monitor, for example:
    • $.id — the root ID field
    • $.name — the name field
    • $.items[*].price — price field in every item of an array
  3. During verification, each response is checked against the contract paths.
  4. If a path is missing or its type has changed, it's flagged as a contract violation — distinct from a value mismatch.

Contract Path Patterns

PatternMatchesExample
$.fieldTop-level field$.id, $.name
$.parent.childNested field$.address.city
$.items[*].fieldField in every array item$.items[*].price
$.data[*].tags[*]Nested arraysEvery tag in every data item

Managing Contract Patterns

  • Add — type a JSON path pattern and press Enter
  • Toggle — disable a pattern without deleting it (useful for temporary exclusions)
  • Remove — delete a pattern permanently
  • Array mode toggle — switch between [*] (check all items) and [0] (check first item only)
💡 Contract vs. Validate Columns Validate columns check specific values per row (e.g., "user 42's name must be Alice"). Contracts check structure across all rows (e.g., "every response must have a name field of type string"). Use both together for comprehensive coverage.

8. Step-by-Step Walkthrough

  1. Load the User Lookup Sweep gallery sample.
  2. Open the Data Source tab — notice validate columns with expected values.
  3. Click ▶ Verify All in the Data Source toolbar to open the Verify modal. In the modal toolbar, click ▶ Verify All to run verification on all rows.
  4. Watch rows turn green (✅) or red (❌).
  5. Click a failed row to see the expected vs actual diff.
  6. Click Accept on one failed row to update its expected value.
  7. Click ↻ Re-fetch Failed (n) to retry remaining failures.
  8. Now set up a contract: click Contract.
  9. Add: $.id, $.name, $.email.
  10. Run Verify All again — contract violations (if any) appear separately from value mismatches.

9. Try It Yourself

  1. Create a test pointing to https://dummyjson.com/products.
  2. Use ⬇ From API to populate 30 product rows.
  3. Add a validate column for $.title.
  4. Use ⬇ Run & Capture to auto-fill expected titles.
  5. Manually change one row's expected title to "WRONG VALUE".
  6. Run ▶ Verify All — the modified row should fail, all others pass.
  7. Click Accept on the failed row.
  8. Set up a contract with $.id, $.title, $.price, $.images[*].
  9. Verify again — all rows should pass with no contract violations.
