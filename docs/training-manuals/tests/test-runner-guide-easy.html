Test Runner Guide

Run Standard Tests as Performance Tests — Training Manual

Easy ★☆☆ · Testing · Performance

1. Learning Objectives

By the end of this manual, you will be able to:

  • Navigate to the Test Runner tab
  • Understand what scenarios appear in the Test Runner
  • Configure iterations, concurrency, and execution mode
  • Read the execution plan preview
  • Run a test and view results

2. What is the Test Runner?

The Test Runner executes standard test scenarios as load tests. It runs individual HTTP requests independently — each test runs N times based on the configured iterations.

Standard Scenarios Only The Test Runner only shows scenarios created with the Standard type. Parameterized scenarios (with data sources) appear in the Parameterized Runner tab instead.

When to use the Test Runner:

  • API endpoint load testing
  • Regression testing across multiple endpoints
  • Contract validation (response schema checks)
  • Baseline performance measurement

3. Getting Started

1 Navigate to the Test Runner

Click Testing in the Activity Bar (left sidebar), then select Test Runner from the sub-navigation tabs.

2 Select Scenarios

The scenario selector shows all standard scenarios organized by Feature Group. Check the boxes next to the scenarios you want to include in the test run.

Use Select All to include all available scenarios, or pick individual ones.

3 Configure Execution

Set the execution parameters:

SettingDescription
IterationsHow many times each test runs (e.g., 10 = each test executes 10 times)
ConcurrencyParallel in-flight limit: Batch and Continuous Pool support 1–100; Sequential is fixed at 1; Load Profile uses the concurrency fields in the profile (not this control).
Execution ModeSequential, Batch, Continuous Pool, or Load Profile
TimeoutPer-request timeout in seconds

4 Review the Execution Plan

The Execution Plan Preview shows exactly what will happen:

5 iterations × 3 tests = 15 requests

This preview uses the same computeAllocation() engine as the executor, so the numbers always match the actual run.

5 Run the Test

Click ▶ Run Test. The live progress panel shows completion percentage, TPS, average response time, and error rate. Click ■ Stop to abort early.

4. Execution Modes

ModeConcurrencyBehavior
Sequential 1 One request at a time, in order.
Batch N Fire N requests simultaneously, wait for all to complete, then fire next N.
Continuous Pool N Maintain exactly N requests in-flight. When one completes, a new one starts immediately.
Load Profile Variable Time-based execution with ramp-up, sustained, or spike patterns.

5. Host Selection

Choose which base URL is used for requests:

OptionBehavior
OriginalUses the URL from the test definition as-is
SettingsReplaces the hostname with the base URL from environment settings
CustomType a temporary base URL for one-off testing

6. Understanding Results

After a test run completes, results are automatically shown in the Results tab. Key metrics:

MetricDescription
Avg ResponseAverage response time across all requests
TPSRequests per second (throughput)
Error RatePercentage of failed requests
P9595th percentile response time

7. Tips

  • Start with low iterations (5–10) and sequential mode to validate your tests before scaling up
  • Use Skip Validation for pure throughput testing when you don't need response checks
  • All settings (concurrency, iterations, host mode, execution mode) are persisted across sessions
  • The execution plan preview always matches the actual execution — if it says 50 requests, exactly 50 will run
💡 Iteration = Per-Test Count Setting iterations to 5 with 3 selected tests means each test runs 5 times, for 15 total requests. Unlike the old "Transactions" setting which was a total budget, iterations are straightforward and predictable.
