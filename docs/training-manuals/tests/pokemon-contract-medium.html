Pokémon Data Contract

Test Sample — Training Manual

1. Purpose & Use Case

The Pokémon Data Contract test validates that the PokéAPI conforms to its expected response schema. Contract tests ensure that the API returns all required fields with correct data types — catching breaking changes before they impact downstream consumers.

This test is ideal for:

  • Learning contract testing — a testing discipline focused on API shape rather than specific values.
  • Verifying that required fields (name, id, types, stats) exist in responses.
  • Testing error handling — confirming the API returns 404 for non-existent resources.
  • Understanding how to combine multiple assertion types in a single scenario.

All scenarios target the PokéAPI (pokeapi.co), a free and comprehensive API for Pokémon data.

2. Concepts You'll Learn

  • Contract testing — validating API response structure matches the expected schema.
  • Field existence via regex — using regex assertions to verify fields are present and non-empty.
  • Numeric assertions — checking that numeric fields like id have valid values.
  • Array length assertions — verifying that array fields like types and stats contain items.
  • Negative testing — asserting that invalid requests return appropriate error codes (404).
📋 Note Contract tests are different from functional tests. They don't care what values the API returns — only that the response shape is correct. This makes them resilient to data changes while catching structural breaks.

3. Test Scenarios

This test contains 3 scenarios covering valid resources, collections, and error handling:

# Scenario Name Method URL Assertions
1 Pikachu Shape GET /api/v2/pokemon/pikachu Status = 200, name exists, id > 0, types array, stats array
2 Type List GET /api/v2/type Status = 200, results array has items
3 404 Handling GET /api/v2/pokemon/notreal Status = 404

4. Assertion Details

Scenario 1 — Pikachu Shape

This is the core contract scenario. It verifies that a Pokémon resource includes all the key fields that downstream applications depend on.

Assertion TypeTargetOperatorExpectedWhat It Checks
status Response status code equals 200 Pikachu exists and is returned successfully.
regex $.name matches ^pikachu$ The name field matches the requested Pokémon.
numeric $.id greaterThan 0 The id field is a positive integer.
arrayLength $.types greaterThan 0 The types array is present and contains at least one type.
arrayLength $.stats greaterThan 0 The stats array is present and contains stat entries.

Scenario 2 — Type List

Assertion TypeTargetOperatorExpectedWhat It Checks
status Response status code equals 200 The type list endpoint is accessible.
arrayLength $.results greaterThan 0 The results array contains Pokémon types (fire, water, etc.).

Scenario 3 — 404 Handling

Assertion TypeTargetOperatorExpectedWhat It Checks
status Response status code equals 404 The API correctly returns 404 Not Found for a non-existent Pokémon.
💡 Tip Scenario 3 is a negative test — it intentionally requests something that doesn't exist. Negative tests are just as important as positive ones: they verify that the API fails gracefully instead of returning misleading data or crashing.

5. Step-by-Step Guide

Step 1 — Import the Test

  1. Open the Gallery panel and navigate to the Tests tab.
  2. Find 📋 Pokémon Data Contract in the list.
  3. Click Import Test to add all 3 scenarios to your workspace.

Step 2 — Review Scenarios

  1. Open the imported test in the Test Editor.
  2. Examine Scenario 1 closely — it has 5 assertions on a single response, demonstrating how contract tests validate multiple fields at once.
  3. Note how Scenario 3 expects a 404 instead of 200 — this is intentional.

Step 3 — Run the Test

  1. Click Run All to execute all 3 scenarios.
  2. All scenarios should pass, including the 404 test.

Step 4 — Check Results

  1. Open the Results Panel and verify all scenarios pass.
  2. Expand Scenario 1 to see all 5 assertions and their actual values.
  3. For Scenario 3, confirm that the status code assertion correctly matched 404.

6. Try It Yourself

Exercise 1 — Expand the Contract

Add assertions to Scenario 1 to verify that $.abilities is an array and $.base_experience is a positive number.

Exercise 2 — Test Another Pokémon

Add a new scenario for GET /api/v2/pokemon/charizard with the same contract assertions as Scenario 1. All fields should be present regardless of which Pokémon is requested.

Exercise 3 — Validate Type Count

In Scenario 2, add a numeric assertion to verify that $.count is greater than 15 (there are 20+ Pokémon types). This ensures the type catalog is complete.

📋 Note The PokéAPI is rate-limited. If you add many scenarios, consider adding small delays between them to avoid hitting rate limits during test execution.
