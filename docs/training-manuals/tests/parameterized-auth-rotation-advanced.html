1. Purpose & Use Case

Authentication endpoints are prime candidates for parameterized testing — you need to verify that multiple users can log in successfully, receive valid tokens, and return correct profile data.

This sample demonstrates:

  • Body variable substitution — {{username}} and {{password}} injected into the POST body.
  • Token validation — regex assertion that $.accessToken is non-empty.
  • Profile field validation — checking $.firstName per user.
  • Row tags — tagging users as "admin" or "user" for selective runs.

2. Prerequisites

  • Complete Parameterized Testing Basics.
  • Familiarity with POST requests and JSON request bodies.

3. Tutorial

Step 1: Load the Sample

  1. Open Gallery → Tests.
  2. Load "Auth Token Rotation".
  3. Open the test editor for POST /auth/login.

Step 2: Understand the Body Template

The request body uses {{variable}} placeholders:

{"username":"{{username}}","password":"{{password}}"}

Each data row provides different credentials:

How Body Columns Work Columns with type body replace {{variable}} placeholders in the request body, just like path columns replace URL placeholders. The column mapping specifies the variable name.

Step 3: Examine the Assertions

The test has two assertions that apply to every data row:

  1. status = 200 — all logins should succeed.
  2. $.accessToken matches regex .+ — token must be non-empty.

Additionally, the validate column $.firstName checks the profile data per row.

Step 4: Run and Verify

  1. Go to Runner and run the test.
  2. 5 requests are sent — one per user credential pair.
  3. Check that all rows return 200, have a valid access token, and the correct first name.

Step 5: Use Row Tags

  1. Notice that rows are tagged "admin" or "user".
  2. In the Runner, set Tags filter to "admin".
  3. Run again — only 2 requests (Emily and Emma) are executed.
  4. This lets you run targeted subsets without disabling rows manually.
💡 CLI Tag Filtering From the command line: redfireforge run test.yaml --tags admin runs only admin-tagged rows. Use --tag-mode all to require all tags match.

4. Pattern: POST Body Parameterization

Body columns work with any request body format:

JSON Body

{"email":"{{email}}","name":"{{name}}","role":"{{role}}"}

Form Data

Body columns map to form field keys when body type is form.

Multiple Body Fields

You can have as many body columns as you need — each replaces a different placeholder in the request body.

⚠️ Security Note Never store real production credentials in data sources. Use test/sandbox credentials only. DummyJSON provides safe test accounts specifically for this purpose.

5. Try It Yourself

  1. Add a 6th row with username averyp and password averyppass.
  2. Run pre-validate to discover the expected firstName.
  3. Fill in the validate column with the actual value.
  4. Tag the new row as "user" and run with tag filter "user" to verify.

6. Advanced: Named Subsets for Tag Filtering

Beyond ad-hoc tag filtering, you can create named subsets — saved tag-based selection criteria that persist with the data source:

  1. In the Data Source toolbar, click the Tags dropdown.
  2. Click + Add Subset.
  3. Give it a name (e.g., "CI Smoke") and select the tags to include (e.g., "admin", "critical").
  4. Choose mode: Any (rows matching any tag) or All (rows matching all tags).
  5. The subset appears in the filter dropdown — select it to filter rows instantly.

Subsets are stored in the data source definition, so they survive export/import and are available in the CLI runner.
