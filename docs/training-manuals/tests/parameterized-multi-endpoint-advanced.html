1. Purpose & Use Case

Real-world regression suites test multiple API endpoints — not just one. This sample demonstrates how to build a comprehensive data-driven regression suite that covers users, products, recipes, and quotes across a single API platform (DummyJSON).

Each endpoint gets its own scenario with its own data source, but they share a single feature group — making them runnable as one cohesive suite.

2. Architecture

ScenarioEndpointRowsValidate Column
Users SweepGET /users/{{id}}5$.firstName
Products SweepGET /products/{{id}}5$.category
Recipes SweepGET /recipes/{{id}}5$.cuisine
Quotes SweepGET /quotes/{{id}}5$.author

Total: 4 scenarios × 5 rows = 20 requests per test run.

3. Tutorial

Step 1: Load the Sample

  1. Open Gallery → Tests.
  2. Load "Multi-Endpoint Regression".
  3. In the Feature Groups tab, you'll see 4 scenarios under one feature group.

Step 2: Explore Each Data Source

  1. Click each test to open its editor.
  2. Each has its own Data Source tab with endpoint-specific columns and data.
  3. Note how each uses path:id to sweep different IDs on different endpoints.

Step 3: Run All at Once

  1. Go to Testing → Parameterized Runner.
  2. Check the entire "Multi-Endpoint Regression" feature group.
  3. The execution summary shows: "4 tests × 5 data rows each = 20 requests".
  4. Click Run.

Step 4: Analyze Results

  1. In Results, expand each scenario to see per-row outcomes.
  2. The data row summary table shows pass/fail breakdown per endpoint.
  3. Use the Failed Row Quick Filter to focus on regressions.
💡 Real-world pattern In production, you'd target your own API microservices: /api/v2/users/{{id}}, /api/v2/orders/{{id}}, etc. Each scenario tests one microservice endpoint, and the feature group runs them all as a regression gate.

4. Design Patterns

4.1 One Scenario per Endpoint

Each endpoint gets its own scenario with tailored columns. Don't mix /users and /products data in one table — their response shapes are different, so their validate columns differ too.

4.2 Shared Feature Group

Grouping related endpoints into one feature group means they run together and their results are shown side-by-side. Use separate feature groups for unrelated APIs.

4.3 Row Tags for Selective Runs

Add tags to data rows (e.g., "smoke", "critical", "edge-case") and use the Parameterized Runner's tag filter to run only critical rows during quick CI checks, or all rows for nightly regression.

5. Try It Yourself

  1. Add a 5th scenario: Posts Sweep targeting https://dummyjson.com/posts/{{id}}.
  2. Add columns: id (path) and expectedUserId (validate: $.userId).
  3. Add 5 rows with post IDs 1–5.
  4. Run the full suite (now 25 requests) and verify all pass.

6. Scaling Up: Subsets & Populate from API

When managing large multi-endpoint suites, these features help:

  • Named Subsets — Save tag-based filters like "smoke" or "nightly" that apply across all data rows. Use them in the Parameterized Runner or CLI to run only a subset of rows per endpoint.
  • Populate from API — Instead of manually entering 100 product rows, call ⬇ From API to fetch /products and auto-generate rows from the response array. Each array item becomes a data row with columns auto-mapped to JSON fields.
  • Verify All — After populating, click ▶ Verify All to validate every row against the live API. The Verify modal groups failure patterns so you can spot systematic issues across endpoints.
