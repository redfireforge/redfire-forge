Shared DS with Fetch Config

API-Driven Data Population — Training Manual

Medium ★★☆ · Fetch Config · dummyjson.com

RedfireForge v0.5.7

1. Purpose & Use Case

Fetch Config is an optional setting on shared data sources that stores the API endpoint and request details used to populate or verify the data. This enables:

  • Pre-Validation — Verify your expected values against live API responses
  • Auto-Population — Fetch real data from an API to build your test data
  • Contract Updates — Re-fetch when APIs change to update baselines

This manual uses the Shared Product Catalog gallery sample — 8 DummyJSON products with a configured fetch URL for API-driven verification.

Before You Start This tutorial builds on Shared DS Basics. Make sure you understand how to create and link shared data sources before continuing.

2. What is Fetch Config?

Fetch Config consists of:

FieldDescriptionExample
urlAPI endpoint with variable placeholdershttps://dummyjson.com/products/{{id}}
methodHTTP method (GET, POST, etc.)GET
headersRequest headersAccept: application/json
bodyRequest body (for POST/PUT){"username":"{{username}}"}
authAuthentication confignone or inherit
💡 Key Insight The URL uses the same {{variable}} placeholders as your data source columns. When you verify or fetch data, each row substitutes its values into the URL template.

3. Step-by-Step Tutorial

Step 1: Load the Gallery Sample

  1. Open the Gallery panel.
  2. Find "Shared Product Catalog" in the Tests tab.
  3. Click Load Test.

This creates:

  • A shared data source "Product Catalog (8 products)" with fetch config
  • A feature group with 2 tests using this shared data

Step 2: Explore the Fetch Config

  1. Open Shared Data Sources (sidebar).
  2. Select "Product Catalog (8 products)".
  3. At the top of the editor, use the method and URL bar, then open the Params, Auth, Headers, and (for non-GET) Body tabs to match your request. The same area includes Configure Variables + Auth…, cURL Import, and Populate Rows from API. You should see a URL template like:
URL: https://dummyjson.com/products/{{id}}
Method: GET
Headers: Accept: application/json

This URL uses the id column from your data to fetch each product individually.

Column Mappings
  • id → type: path, mapping: id — replaces {{id}} in the URL
  • expectedTitle → type: validate, mapping: $.title — checked against response
  • expectedCategory → type: validate, mapping: $.category
  • expectedBrand → type: validate, mapping: $.brand

Step 4: Verify Data Against the API

  1. In the Shared Data Sources modal, click ▶ Verify All in the data toolbar.
  2. The Verify & Inspect modal opens.
  3. Click ▶ Verify All in the modal to run checks (after a pass, the same control reads ▶ Re-verify).
  4. Each row shows:
    • ✓ Pass — All validate columns match the live API
    • ✗ Fail — One or more columns don't match
    • HTTP status code for each request
  5. Click a row to see the full response and field comparisons.
💡 When to Verify Run verification periodically to catch API changes. If a product title changes in DummyJSON, verification will show the mismatch so you can update your expected values.

Step 5: Auto-Populate from API (Optional)

If you want to replace expected values with fresh data from the API:

  1. In the Verify modal, check the rows you want to update.
  2. Click ✓ Accept All Changes.
  3. The validate columns are updated with the live API response.
  4. Save the shared data source.
⚠️ Caution Applying actual values overwrites your expected data. This is useful for building initial baselines but should be used carefully after tests are established.

Step 6: Run Linked Tests

  1. Go to Testing → Parameterized Runner.
  2. Select the "Gallery: Shared Product Catalog" feature group.
  3. Run the tests.

Both tests (Product Validation and Product Reviews) use the same 8 products from the shared data source.

4. Setting Up Fetch Config

For a New Shared Data Source

  1. Create or open a shared data source in Shared Data Sources.
  2. In the editor header, set HTTP method and URL (with {{variable}} placeholders matching your columns).
  3. Use the Params, Auth, Headers, and Body tabs for query, auth, headers, and body; use Configure Variables + Auth… for the full mapping wizard when needed.
  4. Optional: cURL Import → paste a command → Import & Apply; or Populate Rows from API after the URL is set.
  5. Click Save in the modal footer when finished.

For POST/PUT APIs

For APIs that require a request body (like login endpoints), add a body template:

URL: https://dummyjson.com/auth/login
Method: POST
Headers: Content-Type: application/json
Body: {"username":"{{username}}","password":"{{password}}"}

The {{username}} and {{password}} placeholders are filled from columns with those mappings.

5. Practical Patterns

Pattern A: ID-Based Lookup

Most common pattern — fetch by ID:

URL: https://api.example.com/users/{{id}}
Columns: id (path), expectedName (validate: $.name)

Pattern B: Search/Query Parameters

For search endpoints:

URL: https://api.example.com/search
Columns: query (param → q), expectedCount (validate: $.total)

Pattern C: Auth Token Verification

For login/auth endpoints:

URL: https://api.example.com/auth/login
Method: POST
Body: {"user":"{{username}}","pass":"{{password}}"}
Columns: username (body), password (body), expectedToken (validate: $.token)

6. Try It Yourself

Create a shared data source with fetch config for REST Countries:

  1. Create a new shared DS named "Countries by Code"
  2. Add columns: code (path), expectedName (validate: $[0].name.common)
  3. Add rows: US, GB, JP, FR, DE
  4. Set fetch config:
    • URL: https://restcountries.com/v3.1/alpha/{{code}}
    • Method: GET
  5. Run verification — all rows should pass
  6. Create a test linked to this shared DS
