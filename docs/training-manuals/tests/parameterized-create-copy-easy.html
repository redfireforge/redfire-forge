1. Purpose & Use Case

You've created a test that works great for a single user ID. Now you want to run it against 10 different IDs to ensure the API handles all of them correctly. Instead of manually copying the test 10 times and editing each one, use Create Parameterized Copy to instantly convert your test into a data-driven version.

Normal Test
GET /users/123
↓ Create Parameterized Copy
Parameterized Test
GET /users/{{id}}
+ Data Source Table

The original test remains unchanged — you get a new test with automatic variable detection and a pre-populated data source ready for expansion.

Before You Start You should have an existing test that you want to parameterize. This tutorial uses JSONPlaceholder (jsonplaceholder.typicode.com), a free public API.

2. Concepts You'll Learn

  • Variable detection — how RedfireForge identifies values that can become parameters.
  • URL template conversion — replacing literal values with {{variable}} placeholders.
  • Data source initialization — the original values become the first row of your data table.
  • Independent copy — the parameterized test is separate from the original.

3. Step-by-Step Tutorial

Step 1: Create a Normal Test

First, let's create a simple test that we'll later parameterize.

  1. Go to the Scenarios tab.
  2. Create a new feature group or select an existing one.
  3. Click + Test to create a new test.
  4. Configure the test:
    • Name: Get User Profile
    • Method: GET
    • URL: https://jsonplaceholder.typicode.com/users/1
  5. Click Save.
💡 Tip You can also start with an existing test. Any normal (non-parameterized) test can be converted.

Step 2: Open the Parameterize Action

  1. Click on the test name to open the Test Editor.
  2. In the Test Editor, look for the ⚡ Parameterize button in the toolbar (or right-click the test for context menu options).
  3. Click Parameterize → Create Parameterized Copy.

Step 3: Review Variable Detection

RedfireForge analyzes your URL and detects values that look like variables:

Detected ValueVariable NameTypeReasoning
1idpathNumeric ID at end of path

The wizard shows you:

  • The original URL: /users/1
  • The parameterized URL: /users/{{id}}
  • Variable mappings with editable names
What Gets Detected?
  • Path segments that look like IDs (numeric, UUID, alphanumeric patterns)
  • Query parameters — each becomes a param: column
  • Body fields (for POST/PUT) — JSON keys become body: columns

Step 4: Customize Variable Names (Optional)

The default variable name id is often fine, but you can rename it:

  1. Click the variable name field.
  2. Change id to userId if you prefer.
  3. The URL preview updates: /users/{{userId}}

Step 5: Create the Parameterized Copy

  1. Click Create Copy.
  2. A new test appears: "Get User Profile (Parameterized)"
  3. The new test opens in the editor, showing the Data Source tab.

Step 6: Explore the Generated Data Source

The Data Source tab now shows a table with:

ColumnTypeMappingFirst Row Value
idpathid1

The original value (1) is preserved as the first row. Your test is ready to run immediately with one data row.

Step 7: Add More Data Rows

Now expand your test coverage:

  1. Click + Row to add new rows.
  2. Enter different user IDs: 2, 3, 4, etc.
  3. Add as many rows as you need (JSONPlaceholder has users 1–10).

Step 8: Run the Parameterized Test

  1. Go to the Runner tab.
  2. Check your parameterized test.
  3. Notice: "1 test × 5 data rows = 5 requests".
  4. Click Run.

Each data row generates a separate HTTP request. Results show pass/fail status per row.

4. What Gets Detected as Variables?

Path Segments

Numeric IDs, UUIDs, and alphanumeric strings in URL paths:

/users/123           →  /users/{{id}}
/posts/abc-def-456   →  /posts/{{postId}}
/items/a1b2c3d4      →  /items/{{itemId}}

Query Parameters

All query parameters become param: columns:

/search?q=phone&limit=10  →  /search?q={{q}}&limit={{limit}}

Request Body (POST/PUT)

JSON keys in the request body become body: columns:

Body: {"username": "john", "email": "john@example.com"}
  ↓
Columns: username (body), email (body)

5. Original vs. Parameterized Test

AspectOriginal TestParameterized Copy
URL/users/1/users/{{id}}
Data SourceNoneTable with columns + rows
Execution1 requestN requests (one per row)
ResultsSingle resultGrouped by data row
RelationshipIndependentIndependent copy
⚠️ Important The parameterized copy is independent — changes to the original test do not affect the parameterized version, and vice versa. They are two separate tests.

6. Adding Validation Columns

After creating the parameterized copy, you can add validation columns to verify response data:

  1. In the Data Source tab, click + Column.
  2. Set:
    • Name: expectedName
    • Type: validate
    • Mapping: $.name (JSON path to the name field)
  3. Fill in expected values for each row.

7. Try It Yourself

Practice the full workflow:

  1. Create a normal test: GET https://jsonplaceholder.typicode.com/posts/42
  2. Use Create Parameterized Copy to convert it.
  3. Verify the URL becomes /posts/{{id}} with first row value 42.
  4. Add 4 more rows with post IDs: 1, 10, 50, 100.
  5. Add a validation column for $.userId (the author's user ID).
  6. Run and verify all 5 rows pass.
💡 Bonus Challenge Try parameterizing a POST request. Create a test that posts to https://jsonplaceholder.typicode.com/posts with a JSON body, then parameterize it to test different title/body combinations.
