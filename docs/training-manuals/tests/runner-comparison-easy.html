2. The Three Runners

RedfireForge provides three specialized tools for running performance tests. Each runner is designed for a specific type of testing:

🏃 Test Runner

Purpose: Run standard test scenarios as load tests

Best for: API endpoint testing, regression testing, contract validation

Input: Standard scenarios from Feature Groups (no data sources)

Key setting: Iterations — how many times each test runs

Results grouped by: Environment → Feature → Scenario → Test

📊 Parameterized Runner

Purpose: Run parameterized scenarios with data-driven testing

Best for: CSV/Excel data sweeps, boundary testing, multi-variant validation

Input: Parameterized scenarios (tests with data sources)

Key setting: Iterations × Data Rows = total requests

Results grouped by: Environment → Feature → Scenario → Test → Data Row

⚡ Workflow Runner

Purpose: Run workflows as load tests with full graph execution

Best for: Multi-step business flows, conditional logic, end-to-end journeys

Input: Workflows from the Workflow Designer

Key setting: Iterations — how many times the full workflow runs

Results grouped by: Workflow → Step → Iteration

3. Scenarios and Runners

The connection between scenarios and runners is enforced by design:

Key Concept: Scenario Types When you create a scenario in a Feature Group, you choose its type:
  • Standard — contains regular HTTP tests → runs in Test Runner
  • Parameterized (PARAM badge) — contains data-driven tests → runs in Parameterized Runner
A scenario can only contain one type of test. This prevents confusion about how iterations and data rows interact.

5. Decision Flowchart

Use this flowchart to decide which runner to use:

What are you testing?
│
├─ A single API endpoint (no data variations)?
│ └─ YES → Test Runner
│
├─ Same endpoint with different data inputs (CSV/Excel)?
│ └─ YES → Parameterized Runner
│
├─ Multiple independent endpoints?
│ └─ YES → Test Runner (multiple tests in one scenario)
│
├─ Multiple endpoints in sequence with data sharing?
│ └─ YES → Workflow Runner
│
├─ Need conditional logic (if/else)?
│ └─ YES → Workflow Runner
│
└─ Testing a user journey (login → action → logout)?
└─ YES → Workflow Runner

6. Use Case Examples

Use Test Runner For:

  • API Load Testing — "Can /users handle 1000 requests/second?"
  • Regression Testing — "Do all 50 endpoints still return 200 OK?"
  • Contract Validation — "Does the response match the expected schema?"
  • Comparing Endpoints — "Which version (v1 vs v2) is faster?"

Use Parameterized Runner For:

  • Data-Driven Testing — "Test search with 100 different keywords from CSV"
  • Boundary Testing — "Test with valid/invalid/edge-case inputs from a spreadsheet"
  • User Sweep — "Look up 500 user IDs and validate each response"
  • Multi-Variant Validation — "Check 50 products have correct prices from Excel"

Use Workflow Runner For:

  • User Journeys — "Login → Browse → Add to Cart → Checkout"
  • Data Dependencies — "Create user → Get user ID → Create user's order"
  • Conditional Flows — "If user exists, update; otherwise, create"
  • Business Process Testing — "Submit order → Wait for processing → Verify status"

7. Hands-On Exercise: All Three Runners

Part A: Test Runner

  1. Go to Gallery → Samples
  2. Find "JSONPlaceholder — List Users"
  3. Click Import to add it as a test scenario
  4. Go to Testing → Test Runner
  5. Select the imported scenario
  6. Set: 5 iterations, concurrency 2
  7. Click ▶ Run
  8. Observe: Results show 5 requests (one per iteration)

Part B: Parameterized Runner

  1. Go to Gallery → Samples
  2. Find "User Lookup Sweep" (parameterized sample)
  3. Click Import to add it as a parameterized scenario
  4. Go to Testing → Parameterized Runner
  5. Select the imported scenario
  6. Set: 2 iterations
  7. Click ▶ Run
  8. Observe: Results show 2 × N rows requests (each data row runs twice)

Part C: Workflow Runner

  1. Go to Gallery → Samples
  2. Find "Sample: Create → Extract → Verify"
  3. Click Import to add it as a workflow
  4. Go to Testing → Workflow Runner
  5. Select the imported workflow
  6. Set: 5 iterations, concurrency 2
  7. Click ▶ Run Workflow
  8. Observe: Results show 10 requests (2 steps × 5 iterations)

8. Complementary Testing Strategy

The three runners complement each other for complete test coverage:

💡 Recommended Approach
  1. Test Runner: Load test individual endpoints to find baseline performance
  2. Parameterized Runner: Validate correctness with diverse data inputs
  3. Workflow Runner: Test the full user journey to find integration issues

Example: E-commerce Testing

Test TypeRunnerWhat You Learn
Product search endpoint Test Runner Search handles 500 req/s
Search with 200 keywords Param Runner All keywords return valid results
Checkout endpoint Test Runner Checkout handles 100 req/s
Browse → Add → Checkout flow Workflow Runner Full journey takes 2.5s average

10. Summary

RunnerChoose When...
🏃 Test Runner • Testing individual endpoints
• Independent requests without data files
• API contract validation
• Baseline performance measurement
📊 Param Runner • Testing with CSV/Excel data variations
• Boundary and edge-case testing
• Multi-variant validation
• Data-driven regression testing
⚡ Workflow Runner • Multi-step flows
• Data dependencies between requests
• Conditional/branching logic
• User journey simulation
Remember All three runners use the same underlying execution engine and produce results in the same format. The difference is in how you define, organize, and execute your tests. Scenario type (Standard or Parameterized) determines which runner can use it.
