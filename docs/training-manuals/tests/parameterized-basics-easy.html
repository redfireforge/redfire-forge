Parameterized Testing Basics

Data-Driven Testing — Training Manual

Easy ★☆☆ · Data-Driven · jsonplaceholder.typicode.com

RedfireForge v0.5.6

1. Purpose & Use Case

Parameterized testing (also called data-driven testing) lets you define one test pattern and run it against many data rows. Instead of copying the same test 10 times with different IDs, you create a single test with a data source table.

This manual teaches the fundamentals using the User Lookup Sweep gallery sample — a simple GET request tested against 10 different user IDs.

Before You Start No setup required. This tutorial uses JSONPlaceholder (jsonplaceholder.typicode.com), a free public API that always returns predictable data.

2. Concepts You'll Learn

  • Data Source — an inline table of test data rows attached to a test.
  • Path variables — columns that replace {{variable}} placeholders in the URL.
  • Row expansion — how one test becomes N requests at execution time.
  • Grouped results — how results are displayed per data row.

3. Step-by-Step Tutorial

Step 1: Load the Gallery Sample

  1. Open the Gallery panel (sidebar icon or Ctrl+Shift+G).
  2. Switch to the Tests tab.
  3. Find "User Lookup Sweep" (tagged 📊 parameterized).
  4. Click Load Sample.

A new feature group appears in the Scenarios tab with one scenario containing one test — but that test has 10 data rows attached.

Step 2: Explore the Data Source

  1. Click the test name to open the Test Editor.
  2. Switch to the Data Source tab.
  3. You'll see an inline table with 3 columns and 10 rows:
id (path)expectedName (validate)expectedEmail (validate)
1Leanne GrahamSincere@april.biz
2Ervin HowellShanna@melissa.tv
3Clementine BauchNathan@yesenia.net
………
10Clementina DuBuqueRey.Padberg@karina.biz
💡 How it works The id column has type path — it replaces {{id}} in the URL /users/{{id}}. The expectedName and expectedEmail columns have type validate — they're checked against the response JSON paths $.name and $.email.

Step 3: Run the Test

  1. Go to the Runner tab.
  2. Check the "User Lookup Sweep" feature group.
  3. Notice the execution summary: "1 test × 10 data rows = 10 requests".
  4. Click Run.

The runner expands the single test into 10 separate HTTP requests — one per row — each with the user ID substituted into the URL.

Step 4: View Grouped Results

  1. Switch to the Results tab after execution completes.
  2. Results are grouped by data row — you can see which rows passed and which failed.
  3. Click any row to see the full request/response details for that specific data point.

4. How Data Source Columns Work

Column TypeWhat It DoesExample
pathReplaces {{var}} in the URLid → /users/1
paramAdds a query parameterq → ?q=phone
headerSets a request headerX-Token → header value
bodyReplaces {{var}} in the bodyusername → body field
validateChecks response JSON path$.name → expected value

5. Creating Your Own Data Source

  1. Open any test in the Test Editor.
  2. Switch to the Data Source tab.
  3. Click + Add Column to define your columns.
  4. Set the column type (path, param, body, header, or validate).
  5. Set the column mapping (the variable name or JSON path).
  6. Add rows with your test data.
  7. Your URL should use {{variable}} placeholders matching your path/param column mappings.

6. Try It Yourself

Create a parameterized test for the JSONPlaceholder Posts API:

  1. Create a new test with URL: https://jsonplaceholder.typicode.com/posts/{{id}}
  2. Add a Data Source with columns: id (path) and expectedTitle (validate: $.title)
  3. Add 3 rows with post IDs 1, 2, 3 and their expected titles
  4. Run and verify all 3 rows pass
💡 Tip: Find expected values Visit https://jsonplaceholder.typicode.com/posts/1 in your browser to see the real response and copy the title for your expected value.
