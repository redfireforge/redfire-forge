1. Learning Objectives

By the end of this manual, you will be able to:

  • Navigate to the Parameterized Runner tab
  • Understand what scenarios appear in the Parameterized Runner
  • Understand the iterations × data rows formula
  • Read the execution plan with per-test row counts
  • Run a parameterized test and view per-row results

2. What is the Parameterized Runner?

The Parameterized Runner executes parameterized test scenarios — tests that use CSV, Excel, or JSON data sources to drive multiple request variations. Each enabled data row becomes a separate request, and the iterations setting controls how many times the full row set is repeated.

Parameterized Scenarios Only The Parameterized Runner only shows scenarios created with the Parameterized type (shown with a PARAM badge). Standard scenarios appear in the Test Runner tab instead.

When to use the Parameterized Runner:

  • Testing the same endpoint with many different inputs from CSV/Excel
  • Boundary and edge-case validation across data sets
  • Multi-variant API validation (100 user IDs, 50 product searches, etc.)
  • Data-driven regression testing with expected values in data rows

3. The Execution Formula

Total Requests = Iterations × Enabled Data Rows × Tests

For example, with 3 iterations, 10 enabled rows, and 2 tests:

3 iterations × 10 rows × 2 tests = 60 requests
💡 Every Row Runs — No Surprises Unlike the old "Transactions" model, the Parameterized Runner guarantees every enabled data row runs exactly the configured number of iterations. There is no silent truncation or cap.

4. Getting Started

1 Navigate to the Parameterized Runner

Click Testing in the Activity Bar, then select Parameterized Runner from the sub-navigation tabs.

2 Select Scenarios

The scenario selector shows all parameterized scenarios organized by Feature Group. Each scenario shows a PARAM badge.

3 Configure Iterations

Set the number of iterations. Each iteration runs through all enabled data rows for every selected test.

4 Review the Execution Plan

The execution plan shows a per-test breakdown:

Test: User Lookup          → 3 iterations × 10 rows = 30 requests
Test: Product Validation   → 3 iterations × 5 rows  = 15 requests
───────────────────────────────────────────────────────────
Total:                                                45 requests

This plan uses the same computeAllocation() engine as the executor — the numbers always match.

5 Run the Test

Click ▶ Run Test. Progress shows completion percentage with total request count.

5. Execution Plan Details

The Parameterized Runner's execution plan shows more detail than the Test Runner because each test may have a different number of enabled data rows:

ColumnDescription
Test NameThe test being executed
IterationsHow many times the row set repeats
RowsNumber of enabled data rows
Total RequestsIterations × Rows

6. Understanding Results

Parameterized test results include data row context:

  • Grouped by data row — See which rows passed and which failed
  • Row values visible — Each result shows the data values used
  • Executed vs Expected — The Data Row Summary table shows both counts so you can verify all rows ran
  • Re-run failed rows — After a run, selectively re-execute only the failed rows

7. Creating Parameterized Scenarios

To populate the Parameterized Runner, create scenarios with the Parameterized type:

  1. Go to Testing → Feature Groups
  2. Open a Feature Group and click + Add Scenario
  3. Select Parameterized as the scenario type
  4. Add tests and configure their data sources (CSV, Excel, or inline)
⚠️ Scenario Type is Permanent A scenario's type (Standard or Parameterized) is set at creation and enforced throughout. You cannot mix standard and parameterized tests in the same scenario. When moving or copying tests, the target scenario must be the same type.

8. Tips

  • Disable rows you don't want to test by unchecking them in the data source editor
  • Use row tags (e.g., smoke, regression) to filter subsets
  • Start with 1 iteration to validate data mappings before scaling up
  • Use Pre-Validation to check expected values before a full run
