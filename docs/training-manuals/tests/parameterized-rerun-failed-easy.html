Re-Run Failed Rows

Selective Retry for Data-Driven Tests — Training Manual

Easy ★☆☆ · Workflow · All APIs

RedfireForge v0.5.6

1. Purpose & Use Case

After running a parameterized test with 100 data rows, 3 rows failed. Instead of re-running all 100 rows (wasting time and API quota), you want to re-run only the 3 failed rows to confirm they now pass after a fix.

Run Test (100 rows)
↓
3 rows failed, 97 passed
↓ Fix the issue
Re-Run Failed Only (3 rows)
↓
All 3 now pass ✓

RedfireForge tracks which data rows failed and lets you selectively re-run just those rows, saving time and reducing unnecessary API calls.

Before You Start Complete Parameterized Testing Basics first. You should be familiar with running tests with data sources.

2. Concepts You'll Learn

  • Failed row tracking — how results are linked back to specific data rows.
  • Results filtering — viewing only failed rows in the Results Dashboard.
  • Selective re-run — re-running only the rows that failed.
  • Result merging — how re-run results combine with original results.

3. Step-by-Step Tutorial

Step 1: Run a Parameterized Test

First, run a test with multiple data rows. For this tutorial, we'll use a test that intentionally has some failing rows.

  1. Load any parameterized test gallery sample (e.g., "User Lookup Sweep").
  2. Go to Testing → Parameterized Runner.
  3. Select the test and click Run.
  4. Wait for execution to complete.

Step 2: Identify Failed Rows

After the run completes:

  1. Switch to the Results tab.
  2. The summary shows total requests, passed, and failed counts.
  3. In the results table, failed rows are highlighted in red.
  4. Click the Failed Only filter to show only failed rows.
💡 Understanding Failures Each failed row shows the data row ID and label. Click the row to see the full error details: status code, response body, and validation failures.

Step 3: View Failed Row Details

For each failed row, you can see:

  • Data Row ID — the unique identifier for the row in your data source
  • Data Row Label — the human-readable label (if set)
  • Error Message — why the request failed
  • Response Body — the actual API response
  • Validation Failures — which assertions failed and why

Step 4: Fix the Issue

Before re-running, identify and fix the root cause:

  • Data issue — incorrect expected values in your data source
  • API issue — the API returned unexpected data (report as bug)
  • Test issue — your validation rules need adjustment
  • Environment issue — wrong environment, expired auth, etc.

Step 5: Re-Run Failed Rows Only

Once you've addressed the issue:

  1. In the Results tab, look for the Re-Run Failed button.
  2. Click it to open the re-run dialog.
  3. The dialog shows which rows will be re-run (only the failed ones).
  4. Confirm to start the re-run.
What Gets Re-Run? Only the specific data rows that failed in the original run are executed. Passed rows are not re-run, saving time and API calls.

Step 6: Review Merged Results

After the re-run completes:

  1. The Results view updates with the combined results.
  2. Originally passed rows keep their original results.
  3. Re-run rows show their new results (hopefully passing now).
  4. The summary recalculates based on the merged data.

4. How Re-Run Works Internally

AspectDescription
Row SelectionOnly rows with status: 'failed' or validation failures are selected
Data SourceThe test's current data source is used (not a snapshot from the original run)
ConfigurationUses the same Parameterized Runner config (concurrency, timeout, etc.) as the original run
Result MergingNew results replace the failed row results; passed rows are unchanged
Run HistoryA new run entry is created, linked to the original run

5. Alternative: Manual Row Filtering

Instead of using "Re-Run Failed", you can manually disable rows:

  1. Open the test in the Test Editor.
  2. Go to the Data Source tab.
  3. Uncheck the rows you don't want to run (disable them).
  4. Run the test — only enabled rows execute.
  5. Re-enable rows after you're done.
⚠️ Caution Manual disabling is more work and doesn't merge results. Use "Re-Run Failed" for the best experience.

6. Using Row Tags for Selective Runs

For more control, use row tags to group rows:

  1. Tag certain rows as flaky, slow, or edge-case.
  2. In the Parameterized Runner, filter by tag to run specific subsets.
  3. Re-run only rows with a specific tag if they tend to fail intermittently.
Tag PatternUse Case
flakyMark rows that sometimes fail due to timing or external factors
slowMark rows that take longer than average to execute
criticalMark rows that must always pass (regression candidates)
edge-caseMark rows testing boundary conditions

7. Best Practices

When to Use Re-Run Failed

  • After fixing a bug that caused specific rows to fail
  • After updating expected values in your data source
  • After environment issues are resolved (auth, connectivity)
  • When investigating flaky tests (run failed rows multiple times)

When NOT to Use Re-Run Failed

  • If the failure is in the test logic itself (fix and re-run all)
  • If you changed the test URL, method, or headers (re-run all)
  • If you need a fresh baseline (run all rows from scratch)

8. Try It Yourself

Practice the re-run workflow:

  1. Load the "User Lookup Sweep" gallery sample.
  2. Intentionally break one row: change an expected value to something wrong.
  3. Run the test — one row should fail.
  4. Fix the expected value.
  5. Use "Re-Run Failed" to verify just that row.
  6. Confirm the merged results show all rows passing.
