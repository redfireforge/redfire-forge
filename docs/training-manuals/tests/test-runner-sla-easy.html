1. Purpose & Use Case

SLA (Service Level Agreement) targets let you define performance thresholds — such as "95th-percentile response time must be under 800 ms" or "error rate must not exceed 1%". RedfireForge evaluates every target after a run and marks each one as Pass or Fail.

The API Health Check with SLA gallery sample gives you a ready-made test with SLA targets already configured so you can see the full SLA workflow without building from scratch.

This manual covers the complete end-to-end journey:

  • Importing the sample from the Gallery.
  • Reviewing scenario structure and SLA targets.
  • Launching a load run from the Test Runner.
  • Reading SLA pass/fail results in the Results Dashboard.
  • Exporting results to JSON.
  • Running the same test from the CLI and saving output.
  • Re-importing CLI results back into the UI.

2. Concepts You'll Learn

  • SLA targets — response-time or error-rate thresholds applied to a scenario or individual test.
  • Percentile metrics (p50, p95, p99) — the response time below which N% of requests fall; p95 ≤ 800 ms means "95% of requests completed within 800 ms".
  • Error rate — percentage of requests that failed (non-2xx or network error).
  • Warn threshold (warnAt) — an optional early-warning level below the hard limit. Results show amber/yellow when the warn is exceeded but the hard limit is not.
  • SLA Override panel — the 🎯 SLA Override (optional) bar in the Test Runner that lets you swap in different thresholds for a single run without modifying the saved test.
  • CLI export & re-import — how to hand off a test to CI/CD via redfireforge run and bring results back into the UI for analysis.

4. Prerequisites

  • RedfireForge is open in your browser.
  • You have internet access (the test uses jsonplaceholder.typicode.com).
  • For the CLI steps: redfireforge CLI is installed (npm i -g @redfire/redfireforge or via the dist bundle).

5. Step-by-Step Walkthrough

Step 1 — Import from the Gallery

  1. Click the Gallery icon in the left sidebar (or open the Gallery panel).
  2. Select the Tests tab.
  3. Locate 🎯 API Health Check with SLA. It is tagged smoke, sla, and health-check.
  4. Click Import Test. The test appears in your workspace with all 3 scenarios and their SLA targets intact.
💡 Tip You can filter the Gallery by the tag sla to find all SLA-related samples quickly.

Step 2 — Review the Scenarios & SLA Targets

  1. Open the imported test in the Test Editor.
  2. Click each scenario name to expand it. Notice the SLA targets list shown below the scenario header — these are the thresholds that will be evaluated after the run.
  3. Hover over a target row to see the metric label and units (e.g., "p95 — 95th percentile response time, ms").
  4. Observe that the third scenario (Todos Endpoint Health) has a warnAt value of 500 ms for its p95 target — results will show a warning colour if the p95 lands between 500 ms and 700 ms.

Step 3 — Open the Test Runner

  1. Click Test Runner in the top navigation or sidebar.
  2. In the Test selector, choose API Health Check with SLA.
  3. Set Iterations to 20 and Concurrency to 2. This gives 20 complete passes with 2 virtual users at a time — enough data for meaningful percentile calculations.

Step 4 — Configure the SLA Override Panel (optional)

  1. Locate the 🎯 SLA Override (optional) bar below the run settings. It shows a summary of how many SLA targets are configured.
  2. Click Configure to open the SLA modal.
  3. The Configured Targets section lists all targets from the saved test (read-only). Each row shows the scope (scenario name), metric, operator, and limit.
  4. To test the warn threshold on the Todos p95 target, click Override on the Todos Endpoint Health — p95 ≤ 700 ms row and change the hard limit to 500. This will likely trigger the warning colour after the run.
  5. Click Save to apply the override. The trigger bar stats update to show "1 override".
⚠️ Override scope Overrides apply only to this run session. The saved test is not modified. To reset, re-open the panel and delete the override rows.

Step 5 — Run the Test

  1. Click Run. The runner executes 20 iterations (2 concurrent) across all 3 scenarios.
  2. Watch the progress bar and live stats panel. You can see requests/sec, current pass rate, and elapsed time.
  3. When complete, the run summary appears with a SLA Results section.

Step 6 — Inspect SLA Results

  1. In the run summary, expand the SLA Results section. Each target is shown with its measured value and a Pass (✅) or Fail (❌) badge.
  2. Switch to the Results Dashboard tab for a more detailed breakdown:
    • The SLA Summary card shows overall pass/fail counts.
    • The Scenario table shows per-scenario p50/p95/p99/errorRate columns alongside their limits.
  3. If you set the override to 500 ms in Step 4, the Todos p95 row will show a ⚠️ warning badge if the measured value is between 500 ms and 700 ms.
💡 Tip Click any scenario row in the Results Dashboard to drill into per-test breakdown charts showing response time distribution.

Step 7 — Export Test Results to JSON

  1. In the Results Dashboard, click Export (or the export icon) and choose Export as JSON.
  2. Save the file as health-sla-results.json in a convenient location.
  3. This JSON file is the canonical test result format — it can be shared, archived, or re-imported.

Step 8 — Export the Test Definition for CLI

  1. Open the Test Editor for the API Health Check with SLA test.
  2. Click Export and choose Export as JSON (this exports the test definition, not results).
  3. Save as api-health-sla.json.

Step 9 — Run via CLI

Open a terminal and run:

redfireforge run api-health-sla.json -c 2 -i 20 -o health-sla-cli-results.json

Flags:

FlagValueMeaning
-c 22Concurrency — 2 virtual users run in parallel.
-i 2020Iterations — 20 complete passes of all scenarios.
-o health-sla-cli-results.jsonpathOutput — save results to this file.

You will see scenario-level SLA pass/fail printed in the terminal. The full result JSON is written to health-sla-cli-results.json.

ℹ️ CLI requires the CLI binary If redfireforge is not found, check your PATH or use the full path to the binary (e.g., node dist-cli/redfireforge.mjs run ...).

Step 10 — Re-import CLI Results into the UI

  1. Switch to the Results tab in RedfireForge.
  2. Click 📥 Import Test Results.
  3. Browse to health-sla-cli-results.json and confirm.
  4. The results appear in the Results Dashboard exactly as if you had run from the UI. All SLA target evaluations are preserved.
  5. Compare the CLI results with the UI run from Step 5. You should see similar percentile values for the same test under the same network conditions.
💡 CI/CD tip In CI pipelines you can run redfireforge run ... -o results.json, then upload results.json as a build artifact. Developers can import it locally for investigation without re-running the test.

6. Try It Yourself

Exercise 1 — Tighten a Threshold Until It Fails

Open the SLA Override panel before a run and set the Users Endpoint Health — p95 limit to 50 ms. Run the test. Observe the Fail badge. Then reset and re-run — the badge should turn green again.

Exercise 2 — Add a New SLA Target in the Editor

Open the Test Editor and add a new SLA target to the Posts Endpoint Health scenario: p50 ≤ 350 ms. Re-run and check whether the new target passes.

Exercise 3 — CLI with Different Concurrency

Run the CLI command with -c 5 -i 50. Compare the p95 values against the run you did with -c 2 -i 20. Do higher concurrency runs produce different percentiles for this API?

Exercise 4 — Import & Overlay Two Result Sets

Import both health-sla-results.json (from Step 7) and health-sla-cli-results.json (from Step 10) into the Results Dashboard. Compare the two runs side by side.

📋 Note These exercises build on the imported gallery sample. You can modify it freely — the Gallery always has the original version if you need to start over.
