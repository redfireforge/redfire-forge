1. Purpose & Use Case

Beyond simply sweeping URLs with different IDs, parameterized tests become powerful when each row defines expected values to validate against API responses. This transforms your data table into a regression contract.

This manual teaches you to:

  • Add validate columns that check response JSON paths per data row.
  • Capture baselines from a known-good API response.
  • Detect regressions when an API changes its response shape or values.

2. Prerequisite

Complete Parameterized Testing Basics first. This tutorial builds on that knowledge.

3. Tutorial: Country Validation Suite

Step 1: Load the Gallery Sample

  1. Open Gallery → Tests.
  2. Load the "Country Validation Suite" sample.
  3. Open the test editor for GET /v3.1/name/{{name}}.

Step 2: Understand Validate Columns

In the Data Source tab, notice the three columns:

ColumnTypeMappingPurpose
namepathnameReplaces {{name}} in URL
expectedCapitalvalidate$[0].capital[0]Checks the first capital name in response
expectedRegionvalidate$[0].regionChecks the region field

For each row, the engine:

  1. Substitutes {{name}} with the row's name value (e.g., "japan").
  2. Sends GET https://restcountries.com/v3.1/name/japan.
  3. Extracts $[0].capital[0] from the response → compares to "Tokyo".
  4. Extracts $[0].region from the response → compares to "Asia".

Step 3: Run and Review Results

  1. Run the test from Testing → Parameterized Runner.
  2. In Results, expand the test row to see per-row validation outcomes.
  3. Green rows = all validate columns matched. Red rows = at least one mismatch.
💡 Spot a regression Try changing "Tokyo" to "Kyoto" in row 1. Re-run — that row will fail with a clear diff showing expected "Kyoto" vs actual "Tokyo". This is exactly how regressions are caught.

Step 4: Capture a Baseline

Instead of typing expected values manually, you can capture them from a live response:

  1. In the Test Editor, click Fetch Sample Response.
  2. Review the response body.
  3. Click Keep Rules & Update Response or Replace All to save the response as your validation baseline.
  4. The validate columns now contain the actual API values — any future changes will trigger failures.

4. Adding Validate Columns to Existing Tests

  1. In the Data Source tab, click + Column.
  2. Set type to validate.
  3. Enter a JSON path in the mapping field (e.g., $.status, $.data[0].name).
  4. Fill in expected values for each row.
⚠️ JSON Path Tips REST Countries returns an array, so paths start with $[0]. Most APIs return an object, so paths start with $. — check your API's response shape first.

5. Pokémon Contract Sweep

For a more complex example, load the "Pokémon Contract Sweep" gallery sample. It validates 10 Pokémon against their expected primary types and Pokédex IDs — demonstrating multi-field validation per row with deeply nested JSON paths like $.types[0].type.name.

6. Try It Yourself

  1. Load the User Lookup Sweep sample.
  2. Add a third validate column: $.company.name (expected company name).
  3. Fill in expected values (hint: user 1's company is "Romaguera-Crona").
  4. Run and verify all rows pass.
  5. Intentionally break one value and confirm the regression is detected.

7. Beyond Manual Validation

Once you're comfortable setting up validate columns manually, explore these powerful automation features:

  • Verify Modal — Click ▶ Verify All in the Data Source toolbar to open the Verify & Inspect modal. It sends requests for every enabled row, compares response values against your expected values, and shows pass/fail per row with failure pattern grouping.
  • Run & Capture — In the Verify modal, click ⬇ Run & Capture to auto-populate validate columns from live API responses — no manual data entry needed. This is the fastest way to create a baseline.
  • Accept Changes — When the API returns new values, click ✓ Accept All Changes to update your expected values to match the current API state.
  • Populate from API — Click ⬇ From API to detect arrays in an API response and auto-generate data rows from them (e.g., populate 100 product rows from /api/products).
  • Validation Contract — Define which JSON paths must always be present in responses, with support for dynamic array patterns like items[*].price.
