Test Data Across Feature Groups — Training Manual

1. Purpose & Use Case

In real projects, you often organize tests into multiple Feature Groups — one per team, microservice, or test domain. But the same test data (user accounts, product IDs, etc.) may be needed across all of them.

Cross-FG Shared Data Sources solve this by providing test data that any feature group can reference. This is the highest level of data sharing in RedfireForge.

This manual uses the Cross-FG Pokémon Roster gallery sample — 6 Pokémon shared between 2 independent feature groups testing different aspects of the PokéAPI.

Before You Start This tutorial builds on Shared DS Basics. You should understand how to create shared data sources and link tests before continuing.

Key points:

  • One shared data source exists at the top level (not inside any feature group)
  • Multiple feature groups reference it via sharedDataSourceId
  • Each feature group can have different tests using the same data
  • Updating the roster updates all linked tests across all feature groups

3. Step-by-Step Tutorial

Step 1: Load the Gallery Sample

  1. Open the Gallery panel.
  2. Find "Cross-FG Pokémon Roster" in the Tests tab.
  3. Click Load Test.

This creates:

  • A shared data source "Pokémon Roster (6 Pokémon)"
  • Two feature groups: "Pokémon Stats" and "Pokémon Abilities"
  • 3 total scenarios spread across the 2 feature groups

Step 2: Verify the Shared Data Source

  1. Open Shared Data Sources (sidebar).
  2. Select "Pokémon Roster (6 Pokémon)".
  3. Verify the data:

pikachuelectric25starter, electric
charizardfire6fire, flying
bulbasaurgrass1starter, grass

gengarghost94ghost, poison

Step 3: Check the "Used by" Section

  1. In the Shared DS modal, look at the Used by section.
  2. You should see 3 tests across 2 feature groups:
    • Pokémon Stats › Type Verify › Primary Type
    • Pokémon Abilities › Ability Check › Abilities
    • Pokémon Abilities › Move Count › Moves Count
  3. Hover a badge to see the full test path in a tooltip (badges are not clickable).

Step 4: Explore Both Feature Groups

  1. Go to the Feature Groups tab.
  2. You'll see two feature groups prefixed with "Gallery:"
  3. Expand Gallery: Pokémon Stats:
    • "Type Verification" scenario with 1 test (checks primary type)
  4. Expand Gallery: Pokémon Abilities:
    • "Ability Check" scenario with 1 test (verifies abilities array)
    • "Move Count" scenario with 1 test (verifies moves array size)
💡 Independent Feature Groups These feature groups are completely independent — different teams could own them. The shared data source is the only connection between them.

Step 5: Run Tests Across Feature Groups

  1. Go to Testing → Parameterized Runner.
  2. Check both feature groups.
  3. Notice: "3 tests × 6 data rows = 18 requests".
  4. Click Run.

All 3 tests execute against the same 6 Pokémon. Results are grouped by feature group, then test, then data row.

Step 6: Update the Shared Data

  1. Open Shared Data Sources.
  2. Add a new row: mewtwo | psychic | 150 with tag legendary.
  3. Save.
  4. Return to Parameterized Runner and run both feature groups again.
  5. All 3 tests now run with 7 Pokémon — 21 requests total.
⚠️ Impact Awareness When you save changes, a confirmation modal shows which tests will be affected. With cross-FG data, this list may include tests from multiple feature groups owned by different teams.

5. Practical Patterns

Pattern A: Team Ownership Model

One team owns the shared data source (e.g., QA Platform team), other teams reference it:

  • Owner team maintains data accuracy and adds new rows
  • Consumer teams link their tests to the shared DS
  • Owner runs verification periodically to ensure data is current

Pattern B: Test Pyramid Layers

Same data used across different test types:

  • Smoke tests FG — quick checks with subset of rows
  • Regression tests FG — full coverage with all rows
  • Contract tests FG — validate response shapes

Use row tags (e.g., smoke, full) to filter which rows each FG uses.

Pattern C: Multi-Environment Testing

Data that's valid across environments:

  • Product IDs that exist in dev, staging, and prod
  • User accounts created in all environments
  • Tests in different FGs target different environments but share the data

6. Try It Yourself

Create your own cross-FG shared data setup:

  1. Create a shared DS named "Country Codes" with 5 country codes
  2. Create Feature Group A: "Country Names" with a test for restcountries.com/v3.1/alpha/{{code}}
  3. Create Feature Group B: "Country Flags" with a test checking $.flags.png exists
  4. Link both tests to the same "Country Codes" shared DS
  5. Run both FGs and verify they share the data
  6. Add a new country code and confirm both FGs pick it up
