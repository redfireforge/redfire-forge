Testing the Correlation Wait API YAML Spec

Step-by-step guide to testing every endpoint in the correlation-wait-api.yaml spec using the API Catalog "Try" feature or cURL.

Prerequisites

  1. RedfireForge server running on http://localhost:3001
  2. Import the spec — Open API Catalog → Import → Sample Gallery → select "Correlation Wait API" → Import
  3. Once imported, each endpoint shows a "Try" button in the Catalog detail view
💡 Two Ways to Test You can use the "Try" button in the API Catalog UI, or copy the cURL commands below into your terminal. Both hit the same server at localhost:3001.

Endpoint Map

#MethodEndpointPurpose
1POST/api/correlations/pauseRegister a paused correlation
2GET/api/correlationsList all paused correlations
3POST/webhooks/callback/{path}Send webhook to resume workflow
4POST/api/correlations/resumeResume directly (manual / test)
5DEL/api/correlations/{id}Cancel a paused correlation
6POST/api/correlations/cleanupCleanup expired correlations
7GET/api/correlations/unmatchedView unmatched webhook log
8GET/api/correlations/idempotencyIdempotency cache stats

Test Scenario A: Full Webhook Lifecycle

This is the most important test — it simulates the complete pause → webhook → resume flow.

Step 1: Pause Step 2: List Step 3: Webhook Step 4: Verify ┌──────────┐ ┌──────────┐ ┌──────────────┐ ┌──────────┐ │ POST │────✓────▶│ GET │────✓────▶│ POST │────✓────▶│ GET │ │ /pause │ 201 │ /list │ shows │ /webhooks/ │ 200 │ /list │ │ │ │ │ 1 entry │ callback/ │ resumed │ │ └──────────┘ └──────────┘ │ payment │ └──────────┘ └──────────────┘ 0 entries

1 Register a Paused Correlation

POST /api/correlations/pause

curl -X POST http://localhost:3001/api/correlations/pause \
  -H "Content-Type: application/json" \
  -d '{
    "correlationId": "pay_4kF9xR2mNqLp",
    "webhookPath": "/webhooks/callback/payment",
    "executionId": "exec-try-001",
    "workflowId": "wf-try-test",
    "pausedNodeId": "cw-1",
    "timeoutMs": 300000,
    "correlationSource": "body",
    "correlationJsonPath": "$.paymentId"
  }'

201 Expected Response

{
  "paused": true,
  "correlationId": "pay_4kF9xR2mNqLp",
  "timeoutAt": 1706097600000
}
📋 What Just Happened The server registered pay_4kF9xR2mNqLp as a waiting correlation. Any webhook to /webhooks/callback/payment whose body has $.paymentId == "pay_4kF9xR2mNqLp" will match and resume this entry.

2 Verify It's Listed

GET /api/correlations

curl http://localhost:3001/api/correlations

200 Expected Response

{
  "correlations": [
    {
      "correlationId": "pay_4kF9xR2mNqLp",
      "webhookPath": "/webhooks/callback/payment",
      "executionId": "exec-try-001",
      "workflowId": "wf-try-test",
      "pausedNodeId": "cw-1",
      "pausedAt": 1706097300000,
      "timeoutAt": 1706097600000,
      "correlationSource": "body",
      "correlationJsonPath": "$.paymentId"
    }
  ],
  "count": 1
}

3 Send the Webhook Callback

POST /webhooks/callback/payment

This simulates what a payment gateway (Stripe, PayPal, etc.) sends back after processing:

curl -X POST http://localhost:3001/webhooks/callback/payment \
  -H "Content-Type: application/json" \
  -H "x-idempotency-key: pay_4kF9xR2mNqLp-result" \
  -d '{
    "paymentId": "pay_4kF9xR2mNqLp",
    "status": "approved",
    "transactionId": "txn_8mK3vP7wXjRs",
    "amount": 99.99,
    "currency": "USD",
    "cardBrand": "visa",
    "last4": "4242",
    "authorizationCode": "AUTH-779231",
    "riskScore": 12,
    "processedAt": "2024-01-15T10:26:14.392Z",
    "receiptUrl": "https://pay.example.com/receipts/txn_8mK3vP7wXjRs"
  }'

200 Expected Response

{
  "resumed": true,
  "correlationId": "pay_4kF9xR2mNqLp",
  "executionId": "exec-try-001",
  "workflowId": "wf-try-test",
  "webhookData": {
    "paymentId": "pay_4kF9xR2mNqLp",
    "status": "approved",
    "transactionId": "txn_8mK3vP7wXjRs",
    "amount": 99.99,
    "currency": "USD",
    "cardBrand": "visa",
    "last4": "4242",
    "authorizationCode": "AUTH-779231",
    "riskScore": 12,
    "processedAt": "2024-01-15T10:26:14.392Z",
    "receiptUrl": "https://pay.example.com/receipts/txn_8mK3vP7wXjRs"
  }
}
💡 Key Insight The server matched $.paymentId in the webhook body to the paused correlation. The full webhook body is echoed back in webhookData.

4 Verify It's Removed

GET /api/correlations

curl http://localhost:3001/api/correlations

200 Expected Response

{
  "correlations": [],
  "count": 0
}

The matched correlation was consumed and removed from the paused list.

Test Scenario B: Idempotent Duplicate Webhook

Verify that sending the same webhook twice (same x-idempotency-key) returns a cached response without resuming the workflow again.

1 Register (same as Scenario A Step 1)

curl -X POST http://localhost:3001/api/correlations/pause \
  -H "Content-Type: application/json" \
  -d '{
    "correlationId": "pay_IDEMP_test",
    "webhookPath": "/webhooks/callback/payment",
    "executionId": "exec-idemp-001",
    "workflowId": "wf-idemp-test",
    "pausedNodeId": "cw-1",
    "timeoutMs": 300000,
    "correlationSource": "body",
    "correlationJsonPath": "$.paymentId"
  }'

2 Send Webhook (first time)

curl -X POST http://localhost:3001/webhooks/callback/payment \
  -H "Content-Type: application/json" \
  -H "x-idempotency-key: idemp-key-001" \
  -d '{ "paymentId": "pay_IDEMP_test", "status": "approved" }'

200 → "resumed": true

3 Send Same Webhook Again (duplicate)

# Exact same request — same idempotency key
curl -X POST http://localhost:3001/webhooks/callback/payment \
  -H "Content-Type: application/json" \
  -H "x-idempotency-key: idemp-key-001" \
  -d '{ "paymentId": "pay_IDEMP_test", "status": "approved" }'

200 Expected (Cached)

{
  "resumed": true,
  "correlationId": "pay_IDEMP_test",
  "idempotent": true,
  "cachedResponse": {
    "resumed": true,
    "correlationId": "pay_IDEMP_test",
    "executionId": "exec-idemp-001"
  }
}
💡 No Duplicate Execution The workflow was NOT resumed twice. The server returned the cached first response. Always send x-idempotency-key to prevent accidental duplicate processing.

4 Verify Idempotency Cache

GET /api/correlations/idempotency

curl http://localhost:3001/api/correlations/idempotency

200 Response

{ "size": 1 }

Test Scenario C: Unmatched Webhook (404)

Send a webhook that doesn't match any paused correlation.

# No correlation paused for "pay_DOES_NOT_EXIST"
curl -X POST http://localhost:3001/webhooks/callback/payment \
  -H "Content-Type: application/json" \
  -d '{
    "paymentId": "pay_DOES_NOT_EXIST",
    "status": "approved"
  }'

404 Expected Response

{
  "resumed": false,
  "error": "No matching paused workflow found",
  "webhookPath": "/webhooks/callback/payment"
}

Then Check Unmatched Log

curl http://localhost:3001/api/correlations/unmatched

200 Expected

{
  "unmatched": [
    {
      "path": "/webhooks/callback/payment",
      "correlationId": "pay_DOES_NOT_EXIST",
      "payload": {
        "paymentId": "pay_DOES_NOT_EXIST",
        "status": "approved"
      },
      "receivedAt": 1706097400000
    }
  ],
  "count": 1
}
⚠️ Debugging 404s Common causes: wrong paymentId, wrong webhook path (/payment vs /payment-result), correlation already timed out, or correlation already consumed by a previous webhook. Check GET /api/correlations to see what's currently paused.

Test Scenario F: Duplicate Pause (409)

Verify that pausing the same correlation ID twice is rejected.

# First pause — succeeds (201)
curl -X POST http://localhost:3001/api/correlations/pause \
  -H "Content-Type: application/json" \
  -d '{
    "correlationId": "dup-test-001",
    "webhookPath": "/webhooks/callback/payment",
    "executionId": "exec-dup-001",
    "correlationSource": "body",
    "correlationJsonPath": "$.paymentId"
  }'

# Second pause with same correlationId — rejected (409)
curl -X POST http://localhost:3001/api/correlations/pause \
  -H "Content-Type: application/json" \
  -d '{
    "correlationId": "dup-test-001",
    "webhookPath": "/webhooks/callback/payment",
    "executionId": "exec-dup-002",
    "correlationSource": "body",
    "correlationJsonPath": "$.paymentId"
  }'

409 Expected Response

{
  "error": "Correlation ID \"dup-test-001\" is already paused"
}

Quick Reference: Response Codes

CodeMeaningWhen It Happens
201Correlation pausedPOST /pause success
200Resumed / Listed / CleanedMost GET and POST operations
200Idempotent duplicateSame x-idempotency-key sent again
401Bad HMAC signatureSecurity enabled, wrong signature
403IP blockedSecurity enabled, IP not whitelisted
404No matchWebhook didn't match any paused entry
409Already pausedDuplicate correlationId in pause
422Filter rejectedWebhook filter expression returned false

Using "Try" in the API Catalog

  1. Open the API Catalog tab
  2. Select "Correlation Wait API" from the catalog list
  3. Click any endpoint to expand its detail panel
  4. Click the "Try" button
  5. The request body is pre-filled from the YAML spec examples
  6. Click "Send" to execute against localhost:3001
  7. The response panel shows the status code, headers, and body
⚠️ Order Matters for Webhook Tests Always call POST /pause first to register a correlation, then call POST /webhooks/callback/{path} to match it. Without a paused correlation, the webhook endpoint returns 404.
💡 Quick Full-Cycle Test (4 Clicks)
  1. Try POST /pause → verify 201
  2. Try GET /correlations → verify count: 1
  3. Try POST /webhooks/callback/payment → verify resumed: true
  4. Try GET /correlations → verify count: 0
