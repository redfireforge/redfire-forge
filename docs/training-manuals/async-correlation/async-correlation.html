1. Overview & Concepts

The Correlation Wait node pauses a workflow execution and waits for an external system to send a webhook callback before resuming. This is the fundamental building block for asynchronous, event-driven workflows.

When to Use

  • Payment gateways — Wait for a charge confirmation callback
  • Manager approvals — Wait for an approve/reject decision
  • CI/CD builds — Wait for a build-complete notification
  • Async APIs — Any process that calls back when done

Key Capabilities

🔗 Correlation Matching

Match webhooks by body JSONPath, HTTP header, or query parameter

📦 Variable Extraction

Pull fields from webhook payload into workflow context

🔒 HMAC Security

Signed URLs, request signatures, IP whitelist

🔄 Idempotency

Automatic deduplication of repeated webhook deliveries

🎯 Webhook Filters

Accept only webhooks matching expressions (==, contains, exists, &&, ||)

⏱ Configurable Timeout

5 minutes to 72 hours. 0 = wait forever

2. How It Works

┌───────────────────────────────────────────────────────────────────┐ │ Workflow Execution │ │ │ │ Start → HTTP (submit) → CorrelationWait → HTTP (process) → End │ │ │ ▲ │ │ │ │ │ │ ┌─────────▼─────┴──────────┐ │ │ │ Server │ │ │ │ │ │ │ │ 1. Register correlation │ │ │ │ 2. Wait for webhook │ │ │ │ 3. Match & resume │ │ │ └──────────▲────────────────┘ │ │ │ │ │ ┌──────────┴────────────┐ │ │ │ External System │ │ │ │ POST /webhooks/ │ │ │ │ callback/payment │ │ │ │ { paymentId: "abc" } │ │ │ └───────────────────────┘ │ └───────────────────────────────────────────────────────────────────┘

Step-by-Step Flow

  1. 1 Workflow reaches the CorrelationWait node
  2. 2 Node evaluates the Correlation ID Expression (e.g., {{paymentId}})
  3. 3 Workflow PAUSES — node shows amber "⏸ PAUSED" indicator on the canvas
  4. 4 External system sends POST to /webhooks/callback/<path>
  5. 5 Server matches incoming webhook to paused workflow by correlation ID
  6. 6 Extracted variables are injected into workflow context
  7. 7 Workflow RESUMES — execution continues to the next node

4. Correlation Sources

Body (JSONPath) — Most Common

The correlation ID is inside the JSON body. Use a JSONPath expression to extract it.

// Config:
Correlation Source: body
Correlation JSONPath: $.paymentId

// Incoming webhook:
POST /webhooks/callback/payment
{
  "paymentId": "pay_123",
  "status": "approved",
  "transactionId": "txn_456"
}

Header

Useful for systems that use standard correlation headers (GitHub, Stripe, etc.).

// Config:
Correlation Source: header
Header Name: X-Correlation-ID

// Incoming webhook:
POST /webhooks/callback/approval
X-Correlation-ID: REQ-2024-0042

{ "decision": "approved", "comment": "Looks good" }

Query Parameter

The correlation ID is in the URL query string. Useful for simple callback URLs.

// Config:
Correlation Source: query
Query Parameter: buildId

// Incoming webhook:
POST /webhooks/callback/build-complete?buildId=build_789

{ "status": "success", "artifactUrl": "https://..." }

5. Extract Variables

Pull fields from the webhook payload into workflow variables for use in subsequent nodes.

Variable NameJSONPathExample Value
paymentStatus$.status"approved"
transactionId$.transactionId"txn_456"
processedAt$.processedAt"2024-01-15T10:30:00Z"

Extracted variables are available as {{paymentStatus}}, {{transactionId}}, etc. in all subsequent nodes.

💡 Tip: Nested Paths Use dot notation in JSONPath for nested objects: $.data.payment.status

6. Webhook Filter Expressions

Only accept webhooks that match your filter expression. The filter is evaluated before the workflow resumes.

OperatorExampleDescription
=={{webhook.type}} == paymentEquality
!={{webhook.status}} != pendingInequality
contains{{webhook.message}} contains successSubstring match
exists{{webhook.paymentId}} existsField existence
>, <, >=, <={{webhook.amount}} > 100Numeric comparison
&&{{type}} == payment && {{status}} == successLogical AND
||{{type}} == payment || {{type}} == refundLogical OR

Filter Examples

# Only accept "payment" type webhooks
{{webhook.type}} == payment

# Accept approved payments over $100
{{webhook.status}} == approved && {{webhook.amount}} > 100

# Accept either payment or refund events
{{webhook.type}} == payment || {{webhook.type}} == refund

# Only accept when transaction ID exists
{{webhook.transactionId}} exists

8. Security (Production)

Enable webhook security by setting environment variables:

VariableDefaultDescription
WEBHOOK_SECURITY_ENABLEDfalseEnable HMAC + IP security
WEBHOOK_HMAC_SECRET(random)HMAC-SHA256 secret key
WEBHOOK_TOKEN_EXPIRY_MS86400000 (24h)Token expiration

Request Signature Validation

When security is enabled, incoming webhooks are validated against these headers (priority order):

  1. x-webhook-signature — raw HMAC-SHA256 hex digest
  2. x-hub-signature-256 — GitHub-style sha256=<hex>
  3. x-signature — generic signature header

Signing Example

const crypto = require('crypto');
const body = JSON.stringify(payload);
const signature = crypto
  .createHmac('sha256', WEBHOOK_HMAC_SECRET)
  .update(body)
  .digest('hex');

// Send as header:
headers['x-webhook-signature'] = signature;

IP Whitelist

Restrict webhook origins using CIDR notation. Requests from non-whitelisted IPs receive a 403 response.

9. Idempotency & Deduplication

Duplicate webhooks are automatically handled. The first webhook resumes the workflow; subsequent duplicates return the cached response.

Idempotency Key Priority

  1. x-idempotency-key header (explicit)
  2. x-request-id header (fallback)
  3. correlationId + webhookPath (implicit)
💡 Tip Always include an x-idempotency-key header from your external system to guarantee exactly-once processing.

11. Common Patterns

Pattern 1: Submit → Wait → Process Easy

Start → HTTP (submit) → CorrelationWait → HTTP (process result) → End

The simplest pattern. Submit a request, wait for callback, process the result.

📄 See: Payment Callback Sample

Pattern 2: Submit → Wait → Branch Medium

Start → HTTP (submit) → CorrelationWait → Switch/Condition → [Branch A | Branch B] → End

Wait for callback, then route based on the result (approved vs rejected).

📄 See: Approval Workflow Sample

Pattern 3: Parallel Waits (Fork/Join) Hard

Start → Fork → [CorrelationWait A | CorrelationWait B] → Join → Process → End

Wait for multiple async callbacks in parallel, then aggregate results.

📄 See: Parallel Payment Sample

12b. Server Response Reference

Every webhook callback to /webhooks/callback/* returns one of these responses. External systems should handle each case appropriately.

✅ 200 — Workflow Resumed

Webhook matched a paused correlation. Workflow resumes immediately.

{
  "resumed": true,
  "correlationId": "pay_4kF9xR2mNqLp",
  "executionId": "exec-abc-001",
  "workflowId": "wf-payment-flow",
  "webhookData": {
    "paymentId": "pay_4kF9xR2mNqLp",
    "status": "approved",
    "transactionId": "txn_8mK3vP7wXjRs"
  }
}

🔁 200 — Idempotent Duplicate (Cached)

Same webhook already processed (matched by x-idempotency-key or x-request-id). Returns the original cached response. No duplicate workflow execution.

// Identical to the original 200 response — cached
{
  "resumed": true,
  "correlationId": "pay_4kF9xR2mNqLp",
  "executionId": "exec-abc-001",
  ... same as first call ...
}

🔐 401 — Signature Invalid

When WEBHOOK_SECURITY_ENABLED=true, the request signature failed validation.

{ "error": "Invalid HMAC signature" }

🚫 403 — IP Not Allowed

Request came from an IP not in the whitelist.

{ "error": "IP not allowed", "ip": "203.0.113.42" }

❌ 404 — No Matching Paused Workflow

No paused workflow has a correlation matching this webhook.

{
  "resumed": false,
  "error": "No matching paused workflow found",
  "webhookPath": "/webhooks/callback/payment"
}

🎯 422 — Webhook Filter Rejected

Correlation matched but the webhook filter expression evaluated to false.

{
  "resumed": false,
  "error": "Webhook filter rejected: {{webhook.type}} == approval evaluated to false",
  "correlationId": "REQ-2024-0042"
}
📋 Response Code Quick Reference
CodeMeaningAction
200Resumed (or idempotent duplicate)Success — no retry needed
401Bad signatureFix HMAC signing
403IP blockedAdd IP to whitelist
404No matchCheck correlation ID / path / timeout
422Filter rejectedCheck filter expression & payload

14. Troubleshooting & FAQ

Webhook not matching (404)

Symptoms: Webhook returns "No matching paused workflow found"
  1. Verify the webhook path is exactly right (e.g., /webhooks/callback/payment)
  2. Check the correlation ID in the webhook body/header/query matches what the workflow sent
  3. Check the "Paused" tab in Execution History — has the workflow timed out?
  4. Check the unmatched log: GET /api/correlations/unmatched

Workflow stuck in PAUSED state

Symptoms: Node shows amber "⏸ PAUSED" but never resumes
  1. Has the external system actually sent the callback?
  2. Is the webhook filter rejecting the incoming payload? (check 422 responses)
  3. Use the "Resume Manually" button in Execution History to test

Duplicate webhook handling

Q: What happens if the external system sends the same webhook twice?

A: The first webhook resumes the workflow. The second returns the cached response (idempotency). No duplicate execution occurs.

Extract variables empty

  1. Verify the JSONPath matches the actual webhook payload structure
  2. Use the Test Webhook feature to inspect the payload
  3. Check for nested paths (e.g., $.data.status not $.status)
