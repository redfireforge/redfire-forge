1. What Is OAuth2 Client Credentials?

The Client Credentials grant is the simplest OAuth2 flow — designed for machine-to-machine communication. There's no user involved. Your app sends its client ID and secret to a token endpoint and receives an access token.

RedfireForge → POST /oauth/token
grant_type=client_credentials
client_id=xxx & client_secret=yyy

Auth Server → { "access_token": "eyJ...", "expires_in": 3600 }

RedfireForge → GET /api/data
Authorization: Bearer eyJ...

When to Use Client Credentials

  • Service accounts — Backend services calling other APIs
  • Azure/AWS/GCP APIs — Cloud service authentication
  • CI/CD integration — Automated test pipelines
  • API gateways — Centralized auth via identity providers

How It Differs from Bearer Token

FeatureBearer (manual)OAuth2 Client Credentials
Token sourceYou paste it manuallyAuto-acquired from token endpoint
Expiry handlingManual — token expires, tests failAuto-refresh before expiry
ConfigurationToken stringToken URL + client ID + client secret
Best forQuick one-off testingAutomated test suites

3. The TokenManager

RedfireForge's TokenManager class handles the full OAuth2 lifecycle automatically:

Token Acquisition

// acquireOAuth2Token — sends the grant request
async function acquireOAuth2Token(auth: AuthConfig): Promise<string> {
  const response = await fetch(auth.tokenUrl!, {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: new URLSearchParams({
      grant_type: 'client_credentials',
      client_id: auth.clientId!,
      client_secret: auth.clientSecret!,
    }),
  });
  const data = await response.json();
  return data.access_token;
}

Token Caching

The TokenManager caches tokens to avoid unnecessary requests:

  • Cache key — Based on tokenUrl + clientId
  • Expiry tracking — Parses JWT exp claim or uses expires_in from response
  • 30-second buffer — Refreshes 30 seconds before actual expiry
  • In-flight deduplication — If 5 tests request a token simultaneously, only 1 HTTP call is made

Token Lifecycle Flow

Test starts → Check cache → Cached & valid?

Yes → Use cached token
No → In-flight request?
    Yes → Wait for existing request
    No → POST /oauth/token → Cache result → Use token
💡 JWT Expiry Parsing If the access token is a JWT, the TokenManager parses the exp claim (base64-decoded middle segment) to determine the exact expiry time. The 30-second buffer ensures the token is refreshed before it actually expires, preventing race conditions during long test runs.

4. Configuring OAuth2 in the UI

Step 1: Select OAuth2

  1. Open the test → Auth tab.
  2. Select OAuth2 from the Type dropdown.

Step 2: Enter Credentials

FieldDescriptionExample
Token URLThe auth server's token endpointhttps://auth.example.com/oauth/token
Client IDYour application's client identifiermy-app-client-id
Client SecretYour application's secretmy-app-client-secret

Step 3: Verify

Click Verify. For OAuth2, this performs a real token acquisition:

  • Sends a client_credentials grant to the token URL
  • If successful: shows the token, decoded JWT payload (issuer, expiry, scopes), and "Token acquired OK"
  • If failed: shows the error response from the auth server
⚠ Verify Makes a Real Request Unlike Bearer/Basic verify (which just checks field presence), OAuth2 verify actually contacts the auth server. Make sure your client credentials are valid and the token URL is reachable.

6. OAuth2 with the Auth Verify Hook

The useAuthVerify hook provides rich feedback for OAuth2:

// useAuthVerify result for OAuth2
{
  ok: true,
  message: "Token acquired OK",
  detail: {
    token: "eyJhbGci...",     // truncated for display
    expiresIn: 3600,
    issuer: "https://auth.example.com",
    scopes: ["read", "write"],
    jwtPayload: { sub: "my-app", iss: "...", exp: 1714567890 }
  }
}

If the credentials are wrong:

// Failed verification
{
  ok: false,
  message: "Token acquisition failed: 401 Unauthorized",
  detail: { error: "invalid_client", error_description: "Client not found" }
}

7. Variable Interpolation

All OAuth2 fields support {{variable}} interpolation:

{
  type: 'oauth2',
  tokenUrl: '{{authServerUrl}}/oauth/token',
  clientId: '{{oauth2ClientId}}',
  clientSecret: '{{oauth2ClientSecret}}'
}

This is especially useful for:

  • Per-environment credentials — Dev, staging, and prod each have different client IDs
  • Shared Global Auth Profiles — One profile, different secrets per environment
  • CI/CD pipelines — Inject secrets from environment variables

8. Exercises

Exercise 1: Understand the Flow

Goal: Trace the token acquisition flow conceptually.

  1. Draw the 3-step flow: App → Auth Server → API.
  2. Identify what data goes in each request (grant type, client ID, token).
  3. What header does the final API call use?

Exercise 2: Configure OAuth2 Auth

Goal: Set up OAuth2 auth and use Verify to test it.

  1. Create a new test with any URL.
  2. Set auth type to OAuth2.
  3. Enter a token URL (use your own auth server, or a mock).
  4. Click Verify and observe the result — token details, expiry, or error message.

Exercise 3: Compare with Manual Bearer

Goal: Understand why OAuth2 is better than manual Bearer for long-lived test suites.

  1. Create two versions of the same test — one with manual Bearer, one with OAuth2.
  2. Run both. Note the console differences (manual has no token acquisition step).
  3. Wait for the Bearer token to expire. Which test still works? Why?
