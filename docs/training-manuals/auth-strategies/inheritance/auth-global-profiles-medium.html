1. Why Global Profiles?

In the Auth Hierarchy manual, you learned that feature groups can have inline auth. But what if multiple feature groups use the same credentials?

Without Global ProfilesWith Global Profiles
FG "Users" → bearer token X
FG "Orders" → bearer token X
FG "Products" → bearer token X		 Profile "Prod OAuth2" → token X
FG "Users" → links to profile
FG "Orders" → links to profile
FG "Products" → links to profile
Token changes → update 3 FGs manually Token changes → update 1 profile → all 3 FGs auto-update

Global Auth Profiles are the single source of truth for credentials that span multiple feature groups, environments, or even projects.

2. The GlobalAuthProfile Interface

// src/shared/types/index.ts

interface GlobalAuthProfile {
  id: string;       // UUID — auto-generated
  name: string;     // Human-readable label, e.g., "Production OAuth2"
  auth: AuthConfig; // Full auth configuration (bearer, basic, apikey, etc.)
}

3. Managing Profiles in Settings

Open Settings → Global Auth Profiles (the default tab when Settings opens).

Creating a Profile

  1. Type a name in the "Profile name" input (e.g., "Production OAuth2").
  2. Click Add.
  3. A new profile card appears with type: 'none'.
  4. Click Configure to expand the card.

Configuring Auth Type

The expanded card shows the same auth type selector used in the test editor:

Auth TypeFields Shown
none(no fields)
basicUsername, Password (with 👁 toggle)
bearerToken, Prefix (default: "Bearer")
apikeyKey Name, Key Value, Location (header/query)
digestUsername, Password
oauth2Token URL, Client ID, Client Secret (with 👁 toggle)

Profile Card Features

  • Auth type badge — color-coded pill showing the configured type
  • Verify Auth button — sends a test request to validate the credentials work
  • Secret toggle — eye icon to show/hide passwords and client secrets
  • Delete button — removes the profile (linked FGs fall back to next chain level)
  • Collapse/Expand — toggle card detail view
⚠ Deleting a Linked Profile If you delete a profile that feature groups are linked to, those feature groups won't break — the resolveAuth() function gracefully handles missing profiles by continuing down the chain. But the link becomes a dead reference until you either create a new profile with the same ID or update the feature group.

4. Linking Profiles to Feature Groups

Feature groups connect to global profiles through the globalAuthProfileId field:

// src/shared/types/index.ts

interface FeatureGroup {
  id: string;
  name: string;
  auth?: AuthConfig;            // inline auth (Level 3)
  globalAuthProfileId?: string; // link to global profile (Level 4)
  // ... other fields
}

How It Works in the Chain

Feature Group with inline auth AND global profile

Level 3: FG inline auth → checked first
↓ (if 'none'/'inherit')
Level 4: Global profile → checked second
↓ (if profile missing or 'none')
Level 5: Env fallback

The feature group's inline auth is checked at Level 3. Only if it's 'none' or 'inherit' does the resolver move to Level 4 and look up the globalAuthProfileId.

💡 Inline Auth vs. Global Profile If a feature group has both inline auth (auth: { type: 'bearer', ... }) and a globalAuthProfileId, the inline auth wins. The global profile is only checked when the FG's inline auth is 'none' or 'inherit'. This lets you temporarily override a global profile for testing.

5. Environment-Specific Profiles

A common pattern: different environments need different credentials. RedfireForge supports this through the Microservice.authProfileIds mapping:

// src/shared/types/index.ts

interface Microservice {
  id: string;
  name: string;
  baseUrls: Record<string, string>;        // envId → base URL
  authProfileIds?: Record<string, string>; // envId → GlobalAuthProfile id
  customEnvs?: Environment[];
}

Example: Three Environments, Three Profiles

// Three global auth profiles
profiles = [
  { id: 'prof-dev',  name: 'Dev API Key',  auth: { type: 'apikey', ... } },
  { id: 'prof-stg',  name: 'Staging OAuth', auth: { type: 'oauth2', ... } },
  { id: 'prof-prod', name: 'Prod OAuth',   auth: { type: 'oauth2', ... } },
];

// Microservice links each environment to its profile
microservice = {
  id: 'svc-user-api',
  name: 'User API',
  baseUrls: {
    dev:     'http://localhost:3000',
    staging: 'https://staging.api.example.com',
    prod:    'https://api.example.com',
  },
  authProfileIds: {
    dev:     'prof-dev',   // API key for local dev
    staging: 'prof-stg',   // OAuth for staging
    prod:    'prof-prod',  // OAuth for production
  },
};

When a test runs with the "staging" environment selected, the engine resolves authProfileIds['staging'] → 'prof-stg' → looks up the "Staging OAuth" profile → passes it as the envFallbackAuth parameter to resolveAuth().

6. Sharing Profiles Across Feature Groups

Multiple feature groups can reference the same profile ID:

// All three FGs link to the same profile
featureGroups = [
  { id: 'fg-users',    globalAuthProfileId: 'prof-prod-oauth', ... },
  { id: 'fg-orders',   globalAuthProfileId: 'prof-prod-oauth', ... },
  { id: 'fg-products', globalAuthProfileId: 'prof-prod-oauth', ... },
];

When you update the "Prod OAuth" profile's credentials in Settings, all three feature groups automatically use the new credentials on their next test run — no per-FG updates needed.

Common Sharing Patterns

PatternSetup
All FGs share one profile Create 1 profile, link all FGs to it
Team-based profiles Create "Team A Creds" and "Team B Creds" profiles, link FGs by team ownership
Service-based profiles Create "User Service Auth" and "Payment Service Auth", link FGs by which service they test
Role-based profiles Create "Admin Auth" and "User Auth", link FGs by required permission level

7. Workflow Service Auth

Global profiles also power auth in workflow HTTP nodes. The workflow engine resolves service auth through a similar chain:

// src/features/workflow/utils/workflowHostResolve.ts

function resolveEnvAuth(
  svc, envId, microservices, globalAuthProfiles
): AuthConfig | undefined

// Priority for workflow HTTP nodes:
// 1. Endpoint custom auth (authMode: 'custom')
// 2. Env auth (inherit mode) — via microservice.authProfileIds
// 3. Service default auth
// 4. Legacy svc.authPerEnv[envId]
// 5. svc.auth

This means the same global profile used by your tests can also be used by workflow HTTP nodes targeting the same service — one profile, two execution contexts.

8. Exercises

Exercise 1: Create a Global OAuth2 Profile

Goal: Create a reusable OAuth2 profile and verify it works.

  1. Open Settings → Global Auth Profiles.
  2. Enter name: "DummyJSON Auth" → click Add.
  3. Click Configure on the new profile card.
  4. Select auth type: Bearer.
  5. Enter token: test-token, prefix: Bearer.
  6. Click Verify Auth — confirm it sends the correct header.

Exercise 2: Link Profile to Feature Group

Goal: Link a global profile and verify tests inherit from it.

  1. Create a feature group. Leave its inline auth as none.
  2. Set the feature group's globalAuthProfileId to the profile from Exercise 1.
  3. Add a scenario with a test (auth = none).
  4. Run the test — verify it sends Authorization: Bearer test-token.
  5. The auth was resolved at Level 4 (Global Profile) in the chain.

Exercise 3: Change Profile, All FGs Update

Goal: See the single-source-of-truth benefit.

  1. Link a second feature group to the same profile.
  2. Run tests in both FGs — both use test-token.
  3. Go to Settings, change the profile's token to new-token-456.
  4. Run tests again in both FGs — both now use new-token-456 automatically.
