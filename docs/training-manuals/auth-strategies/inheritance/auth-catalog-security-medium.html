1. What Are Catalog Security Schemes?

When you import an OpenAPI specification into the API Catalog, the spec often defines security schemes — formal declarations of how the API expects authentication.

// OpenAPI 3.x — securitySchemes section
components:
  securitySchemes:
    BearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
    ApiKeyAuth:
      type: apiKey
      name: X-API-Key
      in: header
    OAuth2:
      type: oauth2
      flows:
        clientCredentials:
          tokenUrl: https://auth.example.com/token

RedfireForge parses these schemes and offers three auth modes for each catalog entry:

ModeDescription
Inherit from SpecAuto-detect auth type from the scheme, pre-fill settings (key name, location), and prompt only for credentials
From EnvironmentLink to a Global Auth Profile — same as the test inheritance chain
ManualConfigure auth type and credentials directly, ignoring the spec

2. The CatalogSecurityScheme Interface

// src/features/catalog/types/catalog.ts

interface CatalogSecurityScheme {
  type: 'apiKey' | 'http' | 'oauth2' | 'openIdConnect';
  name?: string;          // API key name (e.g., "X-API-Key")
  in?: 'header' | 'query' | 'cookie';  // API key location
  scheme?: string;        // HTTP scheme: "basic", "bearer", "digest"
  bearerFormat?: string;  // e.g., "JWT"
  description?: string;   // Human-readable description
}

3. The schemeToAuthType() Function

When "Inherit from Spec" mode is active, the catalog panel needs to convert an OpenAPI security scheme into a RedfireForge AuthType. This mapping is handled by schemeToAuthType():

// src/features/catalog/components/CatalogAuthPanel.tsx

function schemeToAuthType(scheme: CatalogSecurityScheme): AuthConfig['type'] {
  if (scheme.type === 'apiKey') return 'apikey';
  if (scheme.type === 'http') {
    if (scheme.scheme === 'basic') return 'basic';
    return 'bearer';   // bearer, digest, or unknown → bearer
  }
  if (scheme.type === 'oauth2') return 'bearer';
  return 'bearer';     // openIdConnect → bearer
}

Mapping Summary

OpenAPI SchemeRedfireForge AuthTypeWhy
apiKeyapikeyDirect mapping — key name and location from spec
http (basic)basicUsername + password → Base64 header
http (bearer)bearerToken → Authorization header
oauth2bearerOAuth2 produces a bearer token
openIdConnectbearerOIDC produces a bearer token
📘 Why OAuth2 Maps to Bearer OAuth2 is an auth flow that ultimately produces a bearer token. The catalog panel detects the OAuth2 scheme type and maps it to bearer — the user provides the token (or uses the OAuth2 token manager from Phase 1 to obtain it).

4. CatalogAuthConfig and Resolution Strategies

Each catalog entry stores its auth configuration in a CatalogAuthConfig:

// src/features/catalog/types/catalog.ts

interface CatalogAuthConfig {
  strategy: ResolutionStrategy;   // how auth is resolved
  hardcoded?: AuthConfig;         // for 'hardcoded' strategy
  globalProfileId?: string;       // for 'global' strategy
  inheritedSchemeId?: string;     // for 'inherited' strategy
}

type ResolutionStrategy =
  | 'global'       // use a Global Auth Profile
  | 'inherited'    // inherit from OpenAPI spec security scheme
  | 'hardcoded'    // manual inline config
  | 'environment'; // resolve from microservice env mapping

Strategy Priority in Catalog Entry Init

When you select a catalog entry, auth is initialized with this priority:

Catalog Auth Initialization

1. Saved auth from previous session?
↓ (if none)
2. Saved auth has __globalProfileId? → resolve live profile
↓ (if none)
3. Entry has microserviceId? → microservice.authProfileIds[envId]
↓ (if none)
4. Entry has security schemes? → auto-select first, set __inherit: true
↓ (if none)
5. { type: 'none' }

5. Auth Modes in CatalogAuthPanel

The CatalogAuthPanel component renders the auth configuration UI for catalog entries. It supports these modes:

type AuthMode = 'inherit' | 'global' | 'none'
              | 'bearer' | 'basic' | 'apikey' | 'oauth2';

Mode Detection from AuthConfig

// Determine current mode from the AuthConfig
const mode: AuthMode =
  auth.__inherit    ? 'inherit'              // "Inherit from Spec"
  : auth.__globalProfileId ? 'global'        // "From Environment"
  : auth.type === 'none'   ? 'none'          // No auth
  : auth.type as AuthMode;                   // Manual (bearer, basic, etc.)

Metadata Fields on AuthConfig

Catalog auth modes use special double-underscore fields to track UI state:

FieldPurpose
__inherittrue when using "Inherit from Spec" mode
__schemeNameName of the selected OpenAPI security scheme (e.g., "BearerAuth")
__globalProfileIdID of the linked Global Auth Profile
__globalProfileNameDisplay name of the linked profile (for the UI badge)
💡 Double-Underscore Convention Fields prefixed with __ are UI state metadata — they are stored on the AuthConfig for the catalog panel to remember the user's mode selection. They are not used by resolveAuthHeaders() when building actual HTTP headers.

6. "Inherit from Spec" Mode in Detail

When you select "Inherit from Spec" in the catalog auth panel:

  1. Scheme selector — If the spec has multiple security schemes, a dropdown lets you choose which one (e.g., "BearerAuth", "ApiKeyAuth").
  2. Auto-detection — schemeToAuthType() converts the selected scheme into a RedfireForge auth type.
  3. Pre-fill — For apiKey schemes, the name and in fields are auto-populated from the spec definition.
  4. Scheme badge — Shows the scheme type (APIKEY / HTTP / OAUTH2) with its description.
  5. Credential fields — Only the credential fields are shown (token, username/password, API key value) — the structure is already known from the spec.

Example: API Key Scheme

// OpenAPI spec defines:
ApiKeyAuth:
  type: apiKey
  name: X-API-Key
  in: header

// CatalogAuthPanel auto-fills:
{
  type: 'apikey',
  apiKeyName: 'X-API-Key',    // ← from spec
  apiKeyIn: 'header',          // ← from spec
  apiKeyValue: '',             // ← user fills in
  __inherit: true,
  __schemeName: 'ApiKeyAuth',
}

Example: Bearer Scheme

// OpenAPI spec defines:
BearerAuth:
  type: http
  scheme: bearer
  bearerFormat: JWT

// CatalogAuthPanel auto-fills:
{
  type: 'bearer',
  token: '',                   // ← user fills in
  prefix: 'Bearer',
  __inherit: true,
  __schemeName: 'BearerAuth',
}

7. "From Environment" Mode

This mode links the catalog entry to a Global Auth Profile, similar to how feature groups link to profiles:

// When user selects "From Environment" and picks a profile:
{
  type: 'bearer',              // resolved from the profile
  token: 'the-profile-token',
  __globalProfileId: 'prof-prod-oauth',
  __globalProfileName: 'Production OAuth2',
}

The catalog panel shows a dropdown of all available Global Auth Profiles. When you select one, its auth configuration is applied to the catalog entry.

⚠ Catalog Auth vs. Test Auth Catalog auth (CatalogAuthPanel) is used when making requests from the API Catalog — browsing endpoints, trying them out. Test auth (the 5-level chain) is used when running tests from feature groups. They are separate configurations, though both can reference the same Global Auth Profiles.

8. Multiple Security Schemes

Many APIs support multiple security schemes — for example, both API key and OAuth2. The catalog panel handles this with a scheme selector dropdown.

// OpenAPI spec with multiple schemes:
components:
  securitySchemes:
    ApiKeyAuth:
      type: apiKey
      name: X-API-Key
      in: header
    BearerAuth:
      type: http
      scheme: bearer
    OAuth2:
      type: oauth2
      flows:
        clientCredentials:
          tokenUrl: https://auth.example.com/token

In "Inherit from Spec" mode, the dropdown shows:

  • APIKEY ApiKeyAuth
  • HTTP BearerAuth
  • OAUTH2 OAuth2

Selecting a different scheme updates the __schemeName, re-runs schemeToAuthType(), and switches the credential fields shown.

9. Exercises

Exercise 1: Import a Spec with Security Schemes

Goal: See how RedfireForge parses security schemes from an OpenAPI spec.

  1. Open API Catalog → Import.
  2. Import an OpenAPI 3.x spec that defines at least one security scheme (e.g., the Petstore spec).
  3. Select an endpoint from the imported spec.
  4. Look at the auth panel — it should show "Inherit from Spec" with the scheme type badge.
  5. Note the auto-filled fields (key name, location for API key schemes).

Exercise 2: Switch Between Auth Modes

Goal: Compare all three catalog auth modes.

  1. Select a catalog entry that has security schemes.
  2. Inherit from Spec: Note the auto-detected type and pre-filled fields.
  3. From Environment: Select a Global Auth Profile — note how it replaces the spec-based config.
  4. Manual (e.g., Bearer): Override everything manually.
  5. None: Disable auth entirely.

Exercise 3: Multiple Schemes

Goal: Switch between security schemes when the spec defines several.

  1. Import a spec with 2+ security schemes (apiKey + bearer, for example).
  2. In "Inherit from Spec" mode, use the scheme selector dropdown.
  3. Select the API key scheme — note apiKeyName and apiKeyIn are auto-filled.
  4. Switch to the bearer scheme — note the fields change to token + prefix.
  5. Enter credentials for the bearer scheme and make a test request.
