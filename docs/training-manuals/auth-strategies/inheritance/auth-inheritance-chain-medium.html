The Auth Hierarchy

Medium — Auth Strategies Training Manual

Understand how RedfireForge resolves authentication through a 5-level inheritance chain. Learn how to configure auth at any level, override parent settings, and leverage inheritance to eliminate repetitive auth configuration across hundreds of tests.

RedfireForge v0.5.6
Difficulty: ★★☆
Phase 2 — Auth Inheritance and Profiles
Scenario: Multi-Team API Suite — Shared Auth Across Feature Groups

1. The Problem: Auth Repetition

Imagine a project with 5 feature groups, each containing 20 scenarios with 10 tests. That's 1,000 tests — all calling the same API with the same bearer token.

Without inheritance, you'd configure auth on each test individually. When the token changes, you update 1,000 tests. That's not sustainable.

The Solution: Auth Inheritance

RedfireForge uses a cascading inheritance chain — configure auth once at a high level, and every test below automatically inherits it. Override at any level to customize specific branches.

The 5-Level Auth Chain

① Test → ② Scenario → ③ Feature Group → ④ Global Profile → ⑤ Env Fallback → none

← Highest priority                                           Lowest priority →

The resolver walks from left to right: it checks the test first; if the test says "inherit," it checks the scenario; if the scenario also says "inherit," it checks the feature group; and so on. The first level with a real auth config wins.

2. The resolveAuth() Function

The entire chain is implemented in a single function — ~15 lines of code that handle all 5 levels:

// src/features/requests/utils/authResolver.ts

export function resolveAuth(
  test: Scenario,
  scenario: Pick<TestScenario, 'auth'>,
  featureGroup: Pick<FeatureGroup, 'auth' | 'globalAuthProfileId'>,
  globalAuthProfiles: Pick<GlobalAuthProfile, 'id' | 'auth'>[],
  envFallbackAuth?: AuthConfig,
): AuthConfig {
  // Level 1: Test — highest priority
  if (test.auth.type !== 'inherit' && test.auth.type !== 'none')
    return test.auth;

  // Level 2: Scenario
  const scAuth = scenario.auth;
  if (scAuth && scAuth.type !== 'none' && scAuth.type !== 'inherit')
    return scAuth as AuthConfig;

  // Level 3: Feature Group
  const fgAuth = featureGroup.auth;
  if (fgAuth && fgAuth.type !== 'none' && fgAuth.type !== 'inherit')
    return fgAuth as AuthConfig;

  // Level 4: Global Auth Profile (linked via featureGroup.globalAuthProfileId)
  if (featureGroup.globalAuthProfileId) {
    const profile = globalAuthProfiles.find(
      (p) => p.id === featureGroup.globalAuthProfileId
    );
    if (profile && profile.auth.type !== 'none')
      return profile.auth;
  }

  // Level 5: Environment Fallback
  if (envFallbackAuth && envFallbackAuth.type !== 'none')
    return envFallbackAuth;

  // Nothing configured at any level
  return { type: 'none' };
}
💡 Key Insight: Both 'inherit' and 'none' Walk Up At the test level, both type: 'inherit' and type: 'none' cause the resolver to walk up the chain. This means a test with no auth configured (type: 'none') automatically inherits from its parent — you don't need to explicitly set type: 'inherit'.

3. Each Level Explained

Level 1: Test (Highest Priority)

Every test (Scenario) has an auth: AuthConfig field. If you set an explicit auth type (bearer, basic, apikey, etc.), it always wins — the chain stops here.

// Test with explicit bearer auth — chain stops at Level 1
{
  id: 'test-123',
  auth: { type: 'bearer', token: 'my-token', prefix: 'Bearer' }
}

Default for new tests: { type: 'none' } — falls through to Level 2.

Level 2: Scenario

The scenario (TestScenario) can have optional auth. This is useful when all tests in a scenario share the same credentials but other scenarios in the feature group don't.

// Scenario auth — applies to all tests with 'inherit'/'none'
{
  id: 'scenario-456',
  auth: { type: 'basic', username: 'admin', password: 'secret' },
  scenarios: [ /* tests */ ]
}

Level 3: Feature Group

The feature group (FeatureGroup) can set auth that covers all scenarios and tests within it.

// Feature group auth — applies to all scenarios/tests below
{
  id: 'fg-789',
  auth: { type: 'apikey', apiKeyName: 'X-Api-Key', apiKeyValue: '...', apiKeyIn: 'header' }
}

Level 4: Global Auth Profile

Instead of inline auth, a feature group can link to a Global Auth Profile via globalAuthProfileId. The profile is a reusable, named auth configuration managed in Settings.

// Feature group linked to a global profile
{
  id: 'fg-789',
  auth: { type: 'none' },                       // no inline auth
  globalAuthProfileId: 'profile-production-oauth' // links to global profile
}

The resolver looks up the profile by ID from the global profiles list. If found and not type: 'none', it uses the profile's auth.

Level 5: Environment Fallback

The last resort before { type: 'none' }. Each microservice can map environments to global auth profiles via authProfileIds. The engine resolves the profile for the current environment and passes it as envFallbackAuth.

// Microservice with per-environment auth profiles
{
  id: 'svc-api',
  name: 'User API',
  baseUrls: { prod: 'https://api.example.com', staging: 'https://staging.api.example.com' },
  authProfileIds: { prod: 'profile-prod-key', staging: 'profile-staging-key' }
}

4. The AuthConfig Type

Every level in the chain uses the same AuthConfig interface:

type AuthType = 'none' | 'inherit' | 'basic' | 'bearer'
              | 'apikey' | 'digest' | 'oauth2';

interface AuthConfig {
  type: AuthType;

  // Basic & Digest
  username?: string;
  password?: string;

  // Bearer
  token?: string;
  prefix?: string;          // defaults to 'Bearer'

  // API Key
  apiKeyName?: string;
  apiKeyValue?: string;
  apiKeyIn?: 'header' | 'query';

  // OAuth2 Client Credentials
  tokenUrl?: string;
  clientId?: string;
  clientSecret?: string;

  // Links to GlobalAuthProfile
  globalProfileId?: string;
}

5. Override Patterns

The power of inheritance is in selective overrides — set auth at a high level, then override at a lower level only where needed.

Pattern: Feature Group Default + Test Override

LevelAuthEffect
Feature Groupbearer with prod tokenAll tests use this token
Test Anone (inherit)Uses FG's bearer token ✅
Test Bnone (inherit)Uses FG's bearer token ✅
Test C (admin)bearer with admin tokenUses its own token — overrides FG ✅
Test D (no auth)apikey with empty valueStops inheritance — sends no real auth ✅

Pattern: Scenario-Level Override

Feature Group: auth = { type: 'bearer', token: 'user-token' }
  ├── Scenario "User Tests":    auth = undefined  → inherits FG's bearer
  ├── Scenario "Admin Tests":   auth = { type: 'bearer', token: 'admin-token' }
  │   └── All tests here get admin-token (Level 2 overrides Level 3)
  └── Scenario "Public Tests":  auth = { type: 'basic', username: 'guest', password: '' }
      └── All tests here get basic auth (Level 2 overrides Level 3)
⚠ Stopping Inheritance Setting an explicit auth type at any level stops the chain. Even setting type: 'basic' with empty credentials prevents walking up to the feature group. This is intentional — it lets you run tests without auth on endpoints that don't require it, even when the parent has auth configured.

6. Edge Cases

The resolver handles several edge cases gracefully:

Edge CaseBehavior
Missing globalAuthProfileId No profile lookup — skips Level 4, falls to Level 5
globalAuthProfileId references deleted profile find() returns undefined — skips Level 4
scenario.auth is undefined Guard scAuth && catches it — skips Level 2
featureGroup.auth is undefined Guard fgAuth && catches it — skips Level 3
Global profile exists but has type: 'none' profile.auth.type !== 'none' check skips it
Env fallback has type: 'none' Skipped — final return is { type: 'none' }
No auth configured at any level Returns { type: 'none' } — request sent without auth
📘 Test Coverage All edge cases above are covered by 16 unit tests in authResolver.test.ts. Each test sets up a specific chain configuration and verifies the resolved auth matches expectations.

7. UI: Inheritance Hints

When a test or scenario has type: 'inherit' or type: 'none', the UI shows a hint explaining what auth will actually be used:

// src/features/scenarios/utils/scenarioAuth.ts

function buildScenarioInheritHint(
  fg: FeatureGroup,
  allAuthProfiles: GlobalAuthProfile[]
): string

This function produces messages like:

  • "Inherits Bearer token from Feature Group 'Payment API'"
  • "Inherits OAuth2 from Global Profile 'Production Credentials'"
  • "No auth configured — request will be sent without authentication"

The companion function resolveScenarioInheritedAuth() resolves the effective auth from the feature group + global profile, returning both the AuthConfig and a human-readable label.

8. Exercises

Exercise 1: Basic Inheritance

Goal: Set auth on a feature group and verify tests inherit it.

  1. Create a new feature group.
  2. Set the feature group's auth to bearer with token test-token-123.
  3. Add a scenario with 2 tests — leave both tests' auth as none.
  4. Run the tests. In the request details, verify both tests sent Authorization: Bearer test-token-123.
  5. Check the UI hint on each test — it should say "Inherits Bearer from Feature Group."

Exercise 2: Scenario Override

Goal: Override feature group auth at the scenario level.

  1. Using the feature group from Exercise 1 (bearer on FG).
  2. Add a second scenario. Set its auth to apikey with name X-Api-Key and value my-key.
  3. Add a test to this scenario — leave the test auth as none.
  4. Run — verify the test sends X-Api-Key: my-key (not the bearer token).
  5. The first scenario's tests should still use the bearer token.

Exercise 3: Test-Level Override

Goal: Override at the test level, the highest priority.

  1. In the first scenario from Exercise 1, set one test to basic with username admin and password secret.
  2. Run both tests in the scenario.
  3. Test 1 (inherit): sends Bearer token from FG.
  4. Test 2 (basic override): sends Authorization: Basic YWRtaW46c2VjcmV0.

Exercise 4: Walk the Full Chain

Goal: See all 5 levels in action.

  1. Remove all auth from the feature group, scenario, and test (set all to none).
  2. Run a test — no auth header should be sent.
  3. Now create a Global Auth Profile with bearer auth (see the Global Auth Profiles manual).
  4. Link the feature group to this profile via globalAuthProfileId.
  5. Run — the test should now inherit from the global profile (Level 4).
