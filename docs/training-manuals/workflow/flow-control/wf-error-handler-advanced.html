1. Purpose & Use Case

This workflow demonstrates the Workflow Error Handler — a global safety net that fires when any node in the workflow throws an uncaught error. Unlike a TryCatch (which wraps specific nodes), the Workflow Error Handler sits outside the main flow and activates regardless of where the failure occurs.

Real-world analogy: A nightly ETL pipeline pulls data from an API, transforms it, and loads it into a database. If any step fails — HTTP timeout, transformation error, DB write failure — the Workflow Error Handler sends an email to the on-call engineer with the error details and marks the run as failed.

Examples of this pattern in production:

  • Sending PagerDuty / Slack alerts when a critical scheduled workflow fails
  • Writing error details to an audit log for compliance tracking
  • Updating a status dashboard to reflect pipeline health
  • Triggering a compensating workflow to roll back partial changes

2. Concepts You'll Learn

  • Configuring a Workflow Error Handler (OnWorkflowError) as a global catch-all
  • Difference between workflow-level and node-level (TryCatch) error handling
  • Accessing error context variables: {{error.message}}, {{error.statusCode}}, {{error.failedCount}}
  • Sending failure notifications (HTTP POST to a webhook) with structured error payloads
  • Using Log nodes inside the error handler for audit trails
  • Understanding error handler execution order — TryCatch fires first; only uncaught errors reach the Workflow Error Handler

9 nodes — a main pipeline (Start → Fetch User → Log Success → Call Bad URL → Never Runs → End) plus a detached error handler subgraph (⚠ Error Caught → POST Notification → ✅ Notification Sent). The error handler subgraph is not connected to the main flow; it activates automatically when any uncaught error occurs. Node 3 (Call Bad URL) intentionally fails to demonstrate the error handler firing.

📘 Workflow-Level vs. Node-Level Error Handling The OnWorkflowError handler is a global catch-all. It fires only for errors that are not caught by a TryCatch node. If a node is wrapped in a TryCatch block, its errors are handled locally and never reach the Workflow Error Handler. Use both together: TryCatch for expected, recoverable failures; OnWorkflowError for unexpected, unrecoverable ones.

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "🚨 Workflow Error Handler – Failure Notification" in the Flow Control category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Workflow Error Handler – Failure Notification".
  3. Build the main flow.
    Add three nodes to the canvas:
    • 1. Fetch User (HTTP GET) — URL: https://jsonplaceholder.typicode.com/users/{{userId}}, Method: GET. Extract userName ← $.name. Add Accept header.
    • 2. Log Success (LogDebug) — Level: info, message: "Fetched user: {{userName}}".
    • 3. Call Bad URL (HTTP GET) — URL: https://jsonplaceholder.typicode.com/invalid-endpoint-404. Add status assertion: expected 200. This intentionally fails.
    • 4. This Never Runs (LogDebug) — Level: info. Should never execute.
    Connect Start → Fetch User → Log Success → Call Bad URL → This Never Runs → End. Also add the Start node's input variable: userId = "1".
  4. Enable the Workflow Error Handler.
    Open the workflow settings (gear icon) and toggle Enable Workflow Error Handler to ON. This creates the OnWorkflowError region on the canvas.
  5. Build the error handler.
    Inside the OnWorkflowError region, add three nodes:
    • ⚠ Error Caught (LogDebug) — Level: error, message: "Workflow-level error handler triggered! Error: {{error.message}} Status: {{error.statusCode}} Failed: {{error.failedCount}}", snapshotVariables=true. This is the entry node.
    • 📧 POST Notification (HTTP POST) — URL: {{notifyUrl}}, body: {"channel":"#alerts","text":"Workflow failed! Error: {{error.message}} | Status: {{error.statusCode}} | Failed: {{error.failedCount}} node(s)"}. Extract notificationId ← $.id.
    • ✅ Notification Sent (LogDebug) — Level: info, message: "Error notification posted (id={{notificationId}}). Recovery complete."
    Connect ⚠ Error Caught → 📧 POST Notification → ✅ Notification Sent.
  6. Test the happy path.
    Click Quick Test. The workflow fetches user 1, logs success, then Call Bad URL fails. it, and the workflow completes. The error handler should not activate.
  7. Test the error path.
    Change the HTTP URL to https://jsonplaceholder.typicode.com/invalid/999 The Call Bad URL node is already configured to fail (status assertion on 404 → 200 expected). Re-run and verify:
    • ⚠ Error Caught logs the error with {{error.message}}, {{error.statusCode}}, {{error.failedCount}}
    • Send Notification fires the POST
    • ✅ Notification Sent logs completion

⚠️ Error Handler Failures If a node inside the OnWorkflowError handler itself fails (e.g., the notification webhook is down), the workflow terminates with an unhandled error. Keep error handler logic as simple and reliable as possible — avoid complex transformations or external calls that could themselves fail.

7. Try It Yourself — Exercises

Exercise 1: Add a TryCatch Inside the Main Flow

Wrap the HTTP GET node in a TryCatch with a local fallback. Verify that the TryCatch handles 404 errors locally and the Workflow Error Handler does not fire. Then introduce an error in another node (outside the Error Handler boundary) and confirm the Workflow Error Handler catches it.

Exercise 2: Enrich the Notification Payload

Add more fields to the notification POST body: workflow execution ID, environment name (dev/staging/prod), and the number of nodes that executed before the failure. Use {{wf_executionId}} and {{wf_environment}} context variables.

Exercise 3: Conditional Notification Routing

Add a Condition node in the error handler that checks {{error.statusCode}}. If the failing node is "HTTP GET", send the notification to a #api-alerts channel. For any other node, send to a generic #workflow-errors channel.

Exercise 4: Build a Dead-Letter Queue

Instead of (or in addition to) sending a notification, have the error handler POST the failed workflow's input data and error details to a "dead-letter" API endpoint. A separate workflow can later consume the dead-letter queue and retry the failed executions.
