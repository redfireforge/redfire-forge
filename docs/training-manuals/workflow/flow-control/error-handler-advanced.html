1. Purpose & Use Case

This workflow demonstrates node-level error handling using a TryCatch node. The happy path calls an API and processes the response. If the API call fails (timeout, 5xx, network error), execution is diverted to the OnError branch where the failure is logged, retried, and — if all retries fail — a fallback response is returned so downstream consumers always receive valid data.

Real-world analogy: A price-comparison service fetches prices from a third-party supplier API. If the supplier is down, the service retries once, then returns the last cached price rather than propagating a 500 to the end user.

Examples of this pattern in production:

  • Retrying a payment gateway call before returning "Payment unavailable"
  • Falling back to a cached product catalog when the catalog API times out
  • Logging transient database errors and returning a stale read
  • Sending a Slack alert on repeated failures while still serving a default response

2. Concepts You'll Learn

  • Wrapping nodes inside a TryCatch boundary for error isolation
  • Implementing an OnError branch with logging, retry, and fallback
  • Using retry logic to recover from transient API failures
  • Returning a fallback response so downstream nodes always receive data
  • Distinguishing between retriable (5xx, timeout) and non-retriable (4xx) errors
  • Accessing error context variables ({{errorMessage}}, {{errorCode}}) inside the OnError branch

7 nodes, 8 edges — a TryCatch pipeline. The happy path flows through the HTTP GET and Process nodes. On failure, execution diverts to the OnError branch (Log → Retry → Fallback) before converging at End.

4. Node-by-Node Walkthrough

NodeTypePurpose
S Start Start Entry point. No input variables — the target URL is configured in the HTTP node.
1 HTTP GET HTTP Sends a GET request to https://jsonplaceholder.typicode.com/posts/1. Wrapped inside the TryCatch try-block.
2 Process Response Set Variable Extracts title and body from the HTTP response and stores them in workflow variables for downstream use.
3 Log Error Log Logs "API call failed: {{errorMessage}} (code: {{errorCode}})". First node in the OnError branch.
4 Retry HTTP Re-attempts the same GET request. If successful, execution continues to End. If it fails again, falls through to Fallback.
5 Fallback Set Variable Sets title = "Unavailable" and body = "The service is temporarily unavailable. Please try again later."

📘 TryCatch vs. Workflow Error Handler A TryCatch node catches errors from specific nodes inside its boundary. A Workflow Error Handler (covered in the companion manual) catches any uncaught error across the entire workflow. Use TryCatch when you want fine-grained control; use the Workflow Error Handler as a global safety net.

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "🛡️ Resilient API with Error Handling" in the Flow Control category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Resilient API with Error Handling".
  3. Add a TryCatch node.
    Drag a TryCatch node onto the canvas. This creates two regions: the try block (top) and the OnError block (bottom). Connect Start → TryCatch.
  4. Build the try block.
    Inside the TryCatch try-block, add:
    • HTTP GET — URL: https://jsonplaceholder.typicode.com/posts/1, Method: GET, Timeout: 5000 ms. Add extractions for title and body.
    • Process Response (Set Variable) — Maps extracted fields to workflow-level variables.
    Connect HTTP GET → Process Response inside the try block.
  5. Build the OnError block.
    Inside the OnError region, add three nodes:
    • Log Error — Message: "API call failed: {{errorMessage}} (code: {{errorCode}})"
    • Retry (HTTP) — Same URL and method as Node 1. This is the single retry attempt.
    • Fallback (Set Variable) — Set title = "Unavailable", body = "The service is temporarily unavailable. Please try again later."
    Connect Log Error → Retry → Fallback inside the OnError block.
  6. Connect TryCatch to End.
    Connect the TryCatch output → End. Both the try-block success and OnError fallback paths converge at this single output.
  7. Test the happy path.
    Click Quick Test. The API should return 200 OK and the Process Response node should set title and body.
  8. Test the error path.
    Change the URL to an invalid endpoint (e.g., https://jsonplaceholder.typicode.com/invalid/999) and re-run. Verify that Log Error fires, Retry attempts the call, and Fallback sets default values.

⚠️ Retry Strategy This sample uses a single synchronous retry for simplicity. In production, consider exponential back-off, jitter, and a configurable max-retry count. Avoid retrying on 4xx errors — those indicate client-side issues that won't resolve by retrying.

7. Try It Yourself — Exercises

Exercise 1: Add a Retry Counter

Introduce a retryCount variable initialized to 0. In the OnError branch, increment it before the Retry node. Add a Condition after Retry: if {{retryCount}} < 3, loop back to the Retry node; otherwise, proceed to Fallback.

Exercise 2: Differentiate Error Types

Add a Condition node in the OnError branch that checks {{errorCode}}. If it starts with 4 (client error), skip retry and go directly to Fallback with a "Bad Request" message. Only retry on 5xx or timeout errors.

Exercise 3: Send an Alert on Failure

After the Fallback node, add an HTTP POST that sends a notification to a Slack webhook URL with the error details: node name, error message, and timestamp. This transforms the workflow into a self-healing + alerting pipeline.

Exercise 4: Combine with Workflow Error Handler

Add a Workflow Error Handler to this workflow as a global safety net. Intentionally introduce a bug in the Fallback node (e.g., invalid variable reference). Observe how the Workflow Error Handler catches errors that escape the TryCatch boundary. See the Workflow Error Handler manual.

💡 Learning Path Master node-level error handling here, then explore the Workflow Error Handler sample to learn global error catching and failure notifications across the entire workflow.
