1. Purpose & Use Case

This workflow demonstrates multi-path routing with a Switch node. Instead of a simple true/false branch, the Switch node evaluates a variable against multiple named cases and routes execution to the matching path.

Real-world analogy: An order management system fetches an order and routes it to different processing pipelines based on its status — pending orders go to the warehouse queue, shipped orders trigger tracking notifications, and delivered orders update the customer's order history.

Examples of this pattern in production:

  • Routing customer support tickets by severity level (low/medium/high/critical)
  • Processing payments by method (credit card/PayPal/wire transfer/crypto)
  • Handling webhook events by type (created/updated/deleted)
  • Dispatching notifications by channel (email/SMS/push/Slack)

2. Concepts You'll Learn

  • Using a Switch node for multi-path routing
  • Defining named cases with exact-match values
  • Implementing a default case for unrecognized values
  • Extracting a routing field from an API response
  • Using Log nodes to trace which path was taken
  • The fan-out / fan-in pattern where multiple branches converge

4. Node-by-Node Walkthrough

📘 Switch vs. Chained Conditions You could achieve the same routing with three nested Condition nodes, but a Switch node is cleaner and easier to maintain. Use Switch when routing on a single variable with three or more possible values.

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "🔀 Switch Order Router" in the Flow Control category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Switch Order Router".
  3. Add the HTTP GET node.
    Drag an HTTP node onto the canvas. Configure:
    • URL: https://fakestoreapi.com/products/1
    • Method: GET
    • Extractions: Add orderStatus ← body $.status
    Connect Start → Get Order.
  4. Add the Switch node.
    Drag a Switch node. Configure:
    • Variable: {{orderStatus}}
    • Cases: Add pending, shipped, delivered
    • Default: Enable the default output
    Connect Get Order → Route by Status.
  5. Add four Log nodes.
    Drag four Log nodes onto the canvas. Configure each with the appropriate message. Connect each Switch output to its corresponding Log node.
  6. Connect all Log nodes to End.
    Draw edges from all four Log nodes to the End node, creating the fan-in pattern.
  7. Run the workflow.
    Click Quick Test. The API will return a status value, and the Switch will route to the matching Log node. Check the execution trace to confirm the correct branch was taken.

7. Try It Yourself — Exercises

Exercise 1: Add Processing Logic

Replace the Log nodes with real processing: on "pending", POST to a warehouse API; on "shipped", POST a tracking notification; on "delivered", PATCH the order to mark it complete.

Exercise 2: Add a Fifth Case

Add a "cancelled" case to the Switch node. Route it to a Log node that records "Order cancelled — initiating refund". This demonstrates how easy it is to extend a Switch-based routing workflow.

Exercise 3: Parameterize the Order ID

Add an orderId input variable to the Start node. Update the HTTP URL to include {{orderId}}. Run the workflow multiple times with different order IDs to trigger different Switch cases.

Exercise 4: Combine with Condition

On the "pending" branch, add a Condition node that checks if the order total exceeds $100. If yes, route to a "priority processing" Log; if no, route to "standard processing". This combines Switch and Condition patterns.
