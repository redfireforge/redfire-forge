1. Purpose & Use Case

This workflow demonstrates multi-path routing with a Switch node. Instead of a simple true/false branch, the Switch node evaluates an expression against multiple named cases and routes execution to the matching HTTP processing path.

Real-world analogy: An order management system fetches an order and routes it to different processing pipelines based on its type — standard orders use normal fulfillment, express orders get priority handling, and gift orders require special wrapping instructions.

Examples of this pattern in production:

  • Routing customer support tickets by severity level (low/medium/high/critical)
  • Processing payments by method (credit card/PayPal/wire transfer/crypto)
  • Handling webhook events by type (created/updated/deleted)
  • Dispatching notifications by channel (email/SMS/push/Slack)

2. Concepts You'll Learn

  • Using a Switch node for multi-path routing
  • Defining named cases with exact-match values
  • Implementing a default case for unrecognized values
  • Extracting a routing field from an API response
  • Using HTTP POST branches for different processing paths
  • The fan-out / fan-in pattern where multiple branches converge

8 nodes, 10 edges — a fan-out/fan-in pipeline. The Switch node splits execution into four possible paths (three cases + default), all of which converge at the End node.

📘 Switch vs. Chained Conditions You could achieve the same routing with three nested Condition nodes, but a Switch node is cleaner and easier to maintain. Use Switch when routing on a single variable with three or more possible values.

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "🔀 Switch Order Router" in the Flow Control category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Switch Order Router".
  3. Add the HTTP GET node (node 1).
    Drag an HTTP node onto the canvas. Configure:
    • URL: https://jsonplaceholder.typicode.com/posts/1
    • Method: GET
    • Extractions: orderType ← body $.userId
    • Extractions: orderTitle ← body $.title
    Connect Start → Fetch Order.
  4. Add the Switch node (node 2).
    Drag a Switch node. Configure:
    • Expression: {{orderType}}
    • Cases: Add 1 (Standard), 2 (Express), 3 (Gift)
    • Default: Enable the default output
    Connect Fetch Order → Route by Type.
  5. Add four HTTP POST nodes (nodes 3a–3d).
    Drag four HTTP nodes. Configure each with method POST and URL https://jsonplaceholder.typicode.com/posts, with different JSON bodies:
    • Standard Processing: {"type":"standard","order":"{{orderTitle}}"}
    • Express Processing: {"type":"express","priority":"high","order":"{{orderTitle}}"}
    • Gift Processing: {"type":"gift","wrapping":true,"order":"{{orderTitle}}"}
    • Default Handler: {"type":"unknown","order":"{{orderTitle}}"}
    Connect each Switch output to its corresponding HTTP node.
  6. Connect all processing nodes to End.
    Draw edges from all four HTTP POST nodes to the End node, creating the fan-in pattern.
  7. Run the workflow.
    Click Quick Test. The API returns userId: 1 for /posts/1, so orderType = 1 and the Switch routes to Standard Processing. Check the execution trace to confirm the correct branch was taken.

7. Try It Yourself — Exercises

Exercise 1: Add More Processing Logic

Extend each HTTP POST branch: add an extraction that captures the response id (e.g., processedId) from each branch. Confirm in Quick Test that the correct branch's response is captured.

Exercise 2: Add a Fourth Case

Add a 4 case to the Switch node representing "Bulk" orders. Add an HTTP POST branch with {"type":"bulk","discount":true,"order":"{{orderTitle}}"}. This demonstrates how easy it is to extend a Switch-based routing workflow.

Exercise 3: Parameterize the Post ID

Add a postId input variable to the Start node. Update the HTTP URL to include {{postId}}. Run the workflow multiple times with different post IDs — different userId values (1–3) will trigger different Switch cases.

Exercise 4: Combine with Condition

On the "Standard" branch, add a Condition node that checks if {{orderType}} is less than 2. If yes, route to a second HTTP node with priority processing; if no, proceed normally. This combines Switch and Condition patterns.
