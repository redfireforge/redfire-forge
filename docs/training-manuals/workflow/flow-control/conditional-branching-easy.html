1. Purpose & Use Case

This workflow demonstrates conditional branching — the most basic flow-control pattern. You fetch a user from an API, inspect a field in the response, and route execution down one of two paths based on the result.

Real-world analogy: An account provisioning system fetches a user profile. If the user is active, it proceeds with order processing. If inactive, it logs a warning and skips the order.

Examples of this pattern in production:

  • Checking payment status before shipping an order
  • Validating user permissions before granting access
  • Routing support tickets to different queues based on priority
  • Enabling/disabling features based on a feature-flag API response

2. Concepts You'll Learn

  • Sending an HTTP GET request and extracting response fields
  • Using a Condition node to evaluate a boolean expression
  • Routing execution down true and false branches
  • Using Log nodes to record outcomes for debugging
  • The branch-and-converge pattern where divergent paths rejoin

4. Node-by-Node Walkthrough

NodeTypePurpose
S Start Start Entry point. No input variables needed — the user ID is hardcoded for this sample.
1 Get User HTTP Sends a GET request to jsonplaceholder.typicode.com/users/1. Extracts the active field from the response body into userActive.
2 Is Active? Condition Evaluates {{userActive}} == true. Routes to the true branch (Log Success) or false branch (Log Inactive).
3a Log Success Log Logs "User is active — proceeding with order". Reached only when userActive is true.
3b Log Inactive Log Logs "User is inactive — skipping order". Reached only when userActive is false.

📘 Why Use a Condition Node? The Condition node is the simplest decision point in a workflow. It evaluates a single expression to a boolean result and offers exactly two exits: true and false. For more than two paths, use a Switch node instead.

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "🔀 Conditional Branching" in the Flow Control category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Conditional Branching".
  3. Add the HTTP GET node.
    Drag an HTTP node onto the canvas. Configure:
    • URL: https://jsonplaceholder.typicode.com/users/1
    • Method: GET
    • Extractions: Add userActive ← body $.active
    Connect Start → Get User.
  4. Add the Condition node.
    Drag a Condition node. Configure:
    • Expression: {{userActive}} == true
    Connect Get User → Is Active?.
  5. Add two Log nodes.
    Drag two Log nodes onto the canvas:
    • Log Success: Message = "User is active — proceeding with order"
    • Log Inactive: Message = "User is inactive — skipping order"
    Connect the Condition node's true output → Log Success, and false output → Log Inactive. Connect both Log nodes → End.
  6. Run the workflow.
    Click Quick Test. Verify the GET returns user data, the Condition evaluates the active field, and the correct branch executes.

7. Try It Yourself — Exercises

Exercise 1: Parameterize the User ID

Add a userId input variable to the Start node. Update the HTTP URL to https://jsonplaceholder.typicode.com/users/{{userId}}. Run the workflow with different user IDs (1–10).

Exercise 2: Add a Third Branch

Replace the Condition node with a Switch node that checks the user's company.name field. Create three cases: "Romaguera-Crona", "Deckow-Crist", and a default. Log a different message for each.

Exercise 3: Chain a Follow-Up Action

On the true branch, instead of just logging, add an HTTP POST node that creates an order for the active user. Use the Create → Extract → Verify pattern to POST and verify the order.

Exercise 4: Nested Conditions

After the "Is Active?" check, add a second Condition node on the true branch that checks {{userEmail}} contains "@april". This creates a nested decision tree: active → email domain check → specific action.
