1. Purpose & Use Case

This workflow demonstrates conditional branching — the most basic flow-control pattern. You fetch a user from an API, inspect a field in the response, and route execution down one of two paths based on the result.

Real-world analogy: An account provisioning system fetches a user profile. If the user is active, it proceeds with order processing. If inactive, it logs a warning and skips the order.

Examples of this pattern in production:

  • Checking payment status before shipping an order
  • Attempting to GET a resource and creating it if not found ("upsert" pattern)
  • Routing API calls based on HTTP response codes (200 vs 404)
  • Validating a user account exists before proceeding with order processing

2. Concepts You'll Learn

  • Sending an HTTP GET request and extracting the response status code
  • Using a Condition node to branch on httpStatus == 200
  • Routing execution down true (user found) and false (not found) branches
  • Running different HTTP calls on each branch (fetch posts vs create user)
  • The found/not-found pattern for API-driven workflow routing

4. Node-by-Node Walkthrough

NodeTypePurpose
S Start Start Entry point. No input variables needed — the user ID is hardcoded as user 1.
1 Get User HTTP GET jsonplaceholder.typicode.com/users/1. Extracts userName from $.name and httpStatus from the status code.
2 User Found? Condition Evaluates {{httpStatus}} == 200. Routes to Get User Posts (true, user exists) or Create User (false, user not found).
3a Get User Posts HTTP GET jsonplaceholder.typicode.com/users/1/posts. Extracts firstPostTitle from $[0].title. Reached only when user exists.
3b Create User HTTP POST jsonplaceholder.typicode.com/users with body {name: 'New User', username: 'newuser', email: 'new@example.com'}. Reached only when user not found.

📘 Why Use a Condition Node? The Condition node is the simplest decision point in a workflow. It evaluates a single expression to a boolean result and offers exactly two exits: true and false. For more than two paths, use a Switch node instead.

5. Step-by-Step Development Guide

  1. Import from Gallery.
    In the Workflow Designer, open Gallery → search for "Sample: Conditional Branching" and click Import. The 5-node workflow loads ready to run.

    — OR build manually: —
  2. Create a new workflow.
    Click + New Workflow. Name it "Conditional Branching".
  3. Add the HTTP GET node (node 1).
    Drag an HTTP node. Configure:
    • Label: 1. Get User
    • URL: https://jsonplaceholder.typicode.com/users/1
    • Method: GET
    • Extractions: userName ← body $.name
    • Extractions: httpStatus ← status code
    Connect Start → Get User.
  4. Add the Condition node (node 2).
    Drag a Condition node. Configure:
    • Label: 2. User Found?
    • Left: {{httpStatus}}
    • Operator: ==
    • Right: 200
    Connect Get User → User Found?.
  5. Add the true-branch HTTP node (node 3a).
    Drag an HTTP node. Configure:
    • Label: 3a. Get User Posts
    • URL: https://jsonplaceholder.typicode.com/users/1/posts
    • Method: GET
    • Extractions: firstPostTitle ← body $[0].title
    Connect User Found? true → Get User Posts.
  6. Add the false-branch HTTP node (node 3b).
    Drag an HTTP node. Configure:
    • Label: 3b. Create User
    • URL: https://jsonplaceholder.typicode.com/users
    • Method: POST
    • Body: {"name":"New User","username":"newuser","email":"new@example.com"}
    Connect User Found? false → Create User.
  7. Run the workflow.
    Click Quick Test. Node 1 returns HTTP 200 for user 1. The Condition evaluates httpStatus == 200 as true, routing to Get User Posts which returns their post list.

7. Try It Yourself — Exercises

Exercise 1: Parameterize the User ID

Add a userId input variable to the Start node. Update the HTTP URL to https://jsonplaceholder.typicode.com/users/{{userId}}. Run the workflow with different user IDs (1–10).

Exercise 2: Add a Third Branch

Replace the Condition node with a Switch node that checks the user's company.name field. Create three cases: "Romaguera-Crona", "Deckow-Crist", and a default. Log a different message for each.

Exercise 3: Chain a Follow-Up Action

On the true branch, instead of just logging, add an HTTP POST node that creates an order for the active user. Use the Create → Extract → Verify pattern to POST and verify the order.

Exercise 4: Nested Conditions

After the "Is Active?" check, add a second Condition node on the true branch that checks {{userEmail}} contains "@april". This creates a nested decision tree: active → email domain check → specific action.
