1. Purpose & Use Case

Workflows orchestrate multiple HTTP calls in sequence or in parallel. Adding SLA targets to a workflow lets you assert aggregate performance expectations across the entire pipeline — for example, "the overall p95 latency must stay under 900 ms" or "the pipeline error rate must not exceed 1%".

The SLA-Monitored API Pipeline gallery sample provides a three-node HTTP workflow pre-configured with workflow-level SLA targets. It is the fastest way to see all SLA features in context without building a workflow from scratch.

This manual walks you through the complete end-to-end journey:

  • Importing the sample workflow from the Gallery.
  • Reviewing the workflow structure in the Designer.
  • Running the workflow in the Workflow Runner with SLA Override.
  • Interpreting SLA pass/fail results in the Results Explorer.
  • Exporting the workflow definition for CLI use.
  • Running the workflow from the CLI and saving results.
  • Re-importing CLI results into the UI for analysis.

2. Concepts You'll Learn

  • Workflow SLA targets — thresholds defined at the workflow level, evaluated across all iterations of a workflow run.
  • SLA Override panel — the 🎯 SLA Override (optional) bar in the Workflow Runner that lets you replace thresholds for a single run without modifying the saved workflow.
  • Aggregate scope — a target with no scenario filter applies to all requests across all nodes in the workflow.
  • p95 / p99 — the 95th/99th percentile response time: N% of requests completed faster than this value.
  • Error rate — the percentage of workflow iterations that encountered a failed HTTP call (non-2xx or network error).
  • Workflow Replay import — loading a CLI-produced result file into the Workflow Results Explorer for visual analysis.

3. Workflow Structure

The SLA-Monitored API Pipeline contains 5 nodes connected in sequence:

# Node Type Label Purpose
1StartStartEntry point of the workflow
2HTTP1. List UsersGET /users — fetches all 10 users into users variable
3HTTP2. List PostsGET /posts — fetches 100 posts into posts variable
4HTTP3. Create PostPOST /posts — creates a new post, result in newPost
5EndDoneExit point of the workflow

Built-in SLA Targets

Scope Metric Condition Limit
Aggregate (all nodes)p95≤900 ms
Aggregate (all nodes)Error Rate≤1%
ℹ️ Aggregate targets These targets cover the combined response times of all HTTP nodes across all iterations. A single slow node or failed request can pull the aggregate above the limit.

4. Prerequisites

  • RedfireForge is open in your browser.
  • Internet access is available (the workflow uses jsonplaceholder.typicode.com).
  • For CLI steps: the redfireforge CLI is installed on your machine.

5. Step-by-Step Walkthrough

Step 1 — Import from the Gallery

  1. Click the Gallery icon in the sidebar.
  2. Switch to the Workflows tab.
  3. Find 🎯 SLA-Monitored API Pipeline. It is tagged sla, runner, and health-check.
  4. Click Import Workflow. The workflow appears in your workspace.
💡 Tip Filter the Gallery by tag sla to surface all SLA-related samples in both the Tests and Workflows tabs.

Step 2 — Review the Workflow in the Designer

  1. Open the Workflow Designer for SLA-Monitored API Pipeline.
  2. Observe the five-node linear flow: Start → List Users → List Posts → Create Post → End.
  3. Click the List Users node to inspect its HTTP configuration. Note the Output Variable field set to users.
  4. Click the Create Post node. Observe the POST body and the Content-Type: application/json header.
  5. Open the SLA Targets panel within the Designer (or the workflow properties sidebar) to see the two workflow-level targets.

Step 3 — Navigate to the Workflow Runner

  1. Click Workflow Runner in the navigation bar.
  2. In the Workflow selector, choose SLA-Monitored API Pipeline.
  3. Set Iterations to 20 and Concurrency to 3.

Step 4 — Configure the SLA Override Panel

  1. Find the 🎯 SLA Override (optional) bar in the runner settings. It shows "2 configured" (the two built-in targets).
  2. Click Configure to open the SLA modal.
  3. The Configured Targets section shows the two aggregate targets (read-only).
  4. To simulate a stricter threshold: click Override next to the Aggregate — p95 ≤ 900 ms row and change it to 500 ms. This is tighter than the JSONPlaceholder API typically delivers, so you will likely see a Fail result — good for learning what a failure looks like.
  5. Click Save. The trigger bar now reads "1 override".
⚠️ Override scope Overrides apply to this run session only. The saved workflow is not modified. Remove the override row and save again to restore original thresholds.

Step 5 — Run the Workflow

  1. Click Run. The runner executes 20 workflow iterations with concurrency 3.
  2. Watch the live stats panel. The three HTTP nodes execute for each iteration.
  3. When complete, a summary with SLA Results appears.

Step 6 — Inspect Results in the Results Explorer

  1. In the run summary panel, view the SLA Results block. Each target shows its measured value and a Pass (✅) or Fail (❌) badge.
  2. Click Open in Results Explorer (or navigate to the Results tab and select the run).
  3. In the Results Explorer:
    • The Diagram view shows each node coloured by its pass/fail status and response time heat.
    • The Metrics table shows per-node p50/p95/p99 and total requests.
    • The SLA Summary card shows pass/fail counts and the measured values vs. limits.
  4. If you set the override to 500 ms in Step 4, the p95 row will show ❌ Fail. Remove the override, re-run, and confirm it becomes ✅ Pass.
💡 Tip Use the Timeline View (Gantt Chart) to see how individual node durations stack across iterations. This is useful for finding which node is the bottleneck.

Step 7 — Export the Workflow Definition

  1. In the Workflow Designer, click Export → Export as JSON.
  2. Save the file as workflow-sla-monitor.json.
  3. Open the file in a text editor and confirm it contains a top-level "slaTargets" array with two entries.

Step 8 — Run via CLI

Open a terminal and run:

redfireforge workflow workflow-sla-monitor.json -c 3 -i 20 -o workflow-sla-results.json

Flags:

FlagValueMeaning
-c 33Concurrency — 3 parallel workflow instances.
-i 2020Iterations — 20 complete workflow runs.
-o workflow-sla-results.jsonpathOutput — save the replay result to this file.

The CLI prints a per-node summary and SLA pass/fail for each target. The full replay JSON is written to workflow-sla-results.json.

ℹ️ CLI command for workflows Use redfireforge workflow (not redfireforge run) to execute a workflow definition file.

Step 9 — Re-import CLI Results into the UI

  1. Switch to the Results tab in RedfireForge.
  2. Click 📂 Import Workflow Replay.
  3. Browse to workflow-sla-results.json and confirm.
  4. The Results Explorer opens with the imported replay. All SLA evaluations are shown exactly as produced by the CLI.
  5. Compare the CLI run with your earlier UI run (Step 5). Under the same network conditions, percentile values should be similar.
💡 CI/CD tip Run redfireforge workflow ... -o results.json in a CI pipeline, upload results.json as a build artifact, and import it locally after a deployment to visually audit performance without re-running the workflow.

6. Try It Yourself

Exercise 1 — Force a Failure

Open the SLA Override panel and set the aggregate p95 limit to 10 ms. Run the workflow. Confirm the ❌ Fail badge appears. Then remove the override and re-run to restore the ✅ Pass state.

Exercise 2 — Add a New SLA Target in the Designer

Open the workflow in the Designer and add a new workflow-level SLA target: p99 ≤ 1200 ms. Re-run and check whether the new target passes alongside the existing two.

Exercise 3 — CLI with Higher Load

Run from the CLI with -c 10 -i 100. How does higher concurrency affect the p95? Import the results and compare with the -c 3 -i 20 run using the side-by-side comparison feature.

Exercise 4 — Extend the Workflow

In the Workflow Designer, add a fourth HTTP node after "Create Post": GET /posts/{{newPost.id}} to verify the newly created post is readable. Does the new node increase the aggregate p95?

Exercise 5 — Combine with Test Runner

Complete the SLA Targets in Test Runner manual and run both the test sample and the workflow sample. Compare the SLA pass/fail patterns. Both use the same JSONPlaceholder API — do they report similar latencies?

📋 Note The gallery sample is always the original version. Modify freely in your workspace — return to the Gallery to re-import a clean copy if needed.
