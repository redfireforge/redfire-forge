1. Purpose & Use Case

This workflow demonstrates a multi-stage sequential pipeline that integrates a reusable sub-workflow for validation. Each stage depends on the previous stage's output, forming a strict processing chain.

Real-world analogy: An e-commerce platform receives an order. The system fetches the full order details, validates them (checking stock, pricing, customer status) via a shared validation service, charges the customer's payment method, decrements inventory, and sends a confirmation email.

Examples of this pattern in production:

  • Order fulfillment pipelines (validate → pay → ship → confirm)
  • Insurance claim processing (receive → verify → assess → approve → pay)
  • Employee onboarding (create account → assign roles → provision tools → notify)
  • Content publishing (draft → review → approve → publish → distribute)

2. Concepts You'll Learn

  • Building a multi-stage pipeline with sequential dependencies
  • Integrating a sub-workflow as a validation stage in a pipeline
  • Using HTTP GET to fetch data and HTTP POST/PUT to mutate state
  • Stage-gate pattern — each stage must succeed before the next begins
  • Sending confirmation notifications as the final pipeline stage

4. Node-by-Node Walkthrough

NodeTypePurpose
S Start Start Entry point. Receives orderId as input variable.
1 HTTP GET Order HTTP Fetches the full order from GET /api/orders/{{orderId}}. Extracts orderData including items, customer, and totals.
2 Validate Order Sub-Workflow Calls the "Order Validation" sub-workflow with orderData. If validationResult.isValid is false, the pipeline stops and the order is rejected.
3 Process Payment HTTP Sends POST /api/payments with order amount and payment method. Extracts paymentId and paymentStatus.
4 Update Inventory HTTP Sends PUT /api/inventory to decrement stock for each order line item. Extracts inventoryStatus.
5 Send Confirmation HTTP Sends POST /api/notifications to email the customer an order confirmation with paymentId and estimated delivery.
E End End Pipeline complete. Order is validated, paid, inventory updated, and customer notified.

Sub-Workflow Gate (Node 2)

Target WorkflowOrder Validation
Input Mappingorder ← {{orderData}}
Output MappingvalidationResult ← sub-workflow output result
Gate ConditionIf validationResult.isValid == false, fail the pipeline with validation errors
📘 Stage-Gate Pattern In a sequential pipeline, each stage acts as a gate: it must succeed before the next stage executes. If validation fails, the pipeline aborts — no payment is processed, no inventory is decremented, and no confirmation is sent. This prevents partial state changes that are hard to clean up.

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "🎭 Order Pipeline with Sub-Workflow" in the Orchestration category. Click Use Template.

    — OR build manually: —
  2. Ensure the "Order Validation" sub-workflow exists.
    If you haven't already, create it from the Sub-Workflow Orchestrator sample.
  3. Create the pipeline workflow.
    Click Workflows → + New. Name it "Order Pipeline with Sub-Workflow".
  4. Add the HTTP GET node.
    Configure: GET /api/orders/{{orderId}}. Extract orderData from the response body. Connect Start → HTTP GET Order.
  5. Add the Sub-Workflow node.
    Select "Order Validation". Map input/output. Add a Condition node after it to check validationResult.isValid — fail on false. Connect HTTP GET Order → Validate Order.
  6. Add the payment, inventory, and confirmation nodes.
    Chain three HTTP nodes in sequence:
    • Process Payment: POST /api/payments
    • Update Inventory: PUT /api/inventory
    • Send Confirmation: POST /api/notifications
    Connect each in sequence → End.
  7. Test the full pipeline.
    Run with a valid order ID. Verify each stage executes in order. Then test with an invalid order to confirm the pipeline stops at validation.

⚠️ Compensating Actions If payment succeeds but inventory update fails, you need a compensating action (refund). For production pipelines, consider implementing the Saga pattern where each stage has an undo action that runs on failure of subsequent stages.

7. Try It Yourself — Exercises

Exercise 1: Add a Fraud Check Stage

Insert a "Fraud Detection" sub-workflow call between Validate Order and Process Payment. If the fraud score exceeds a threshold, reject the order before charging.

Exercise 2: Implement Saga Rollback

If the inventory update fails (step 4), add a compensating action that refunds the payment (step 3). Use a Condition node after step 4 to trigger the refund on failure.

Exercise 3: Parallel Notifications

Replace the single Send Confirmation node with parallel branches: one sends an email, another sends an SMS, and a third updates the order dashboard via WebSocket.

Exercise 4: Retry Failed Payments

If Process Payment returns a 503 (service unavailable), retry up to 3 times with exponential backoff. Only fail the pipeline if all retries are exhausted.
