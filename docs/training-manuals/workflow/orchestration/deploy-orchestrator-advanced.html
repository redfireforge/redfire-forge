1. Purpose & Use Case

This workflow demonstrates multi-region parallel deployment with health verification and automatic rollback. It combines parallel fan-out, health checks, and compensating actions into a single orchestration workflow.

Real-world analogy: A SaaS platform deploys a new release to US-East, EU-West, and APAC-Southeast simultaneously. After deployment, each region's health endpoint is checked. If any region fails the health check, that region is rolled back to the previous version while successful regions remain on the new version.

Examples of this pattern in production:

  • Multi-region application deployments (AWS, Azure, GCP)
  • CDN cache invalidation across global edge nodes
  • Database schema migrations across regional replicas
  • Feature flag rollouts with per-region kill switches

2. Concepts You'll Learn

  • Building and tagging a deployment artifact (Docker image, package)
  • Parallel fan-out — deploying to multiple regions simultaneously
  • Health check verification — validating each deployment post-deploy
  • Selective rollback — reverting only failed regions
  • Result aggregation — merging parallel branch outcomes into a unified report
  • The canary/rollback decision pattern for safe deployments

4. Node-by-Node Walkthrough

NodeTypePurpose
S Start Start Entry point. Receives version (e.g., "2.4.0") and imageTag (e.g., "app:2.4.0").
1 Build Artifact HTTP Triggers a CI build via POST /api/builds. Waits for the build to complete and extracts artifactUrl (the container image registry URL).
2a Deploy US-East HTTP Parallel branch: POST /api/deploy with { region: "us-east-1", artifact: "{{artifactUrl}}" }. Extracts deployStatusUS.
2b Deploy EU-West HTTP Parallel branch: POST /api/deploy with { region: "eu-west-1", artifact: "{{artifactUrl}}" }. Extracts deployStatusEU.
2c Deploy APAC-SE HTTP Parallel branch: POST /api/deploy with { region: "ap-southeast-1", artifact: "{{artifactUrl}}" }. Extracts deployStatusAPAC.
3 Health Checks Script + HTTP Calls GET /health on each region's endpoint. Collects results into healthResults[] array with { region, status, responseTime }.
4 Rollback on Failure Condition + HTTP Checks healthResults for any failed regions. For each unhealthy region, sends POST /api/rollback with the previous version. Healthy regions are left on the new version.
5 Deployment Report Log Logs a summary: regions deployed, health check results, any rollbacks performed, and final deployment state per region.

Parallel Deploy Configuration

PatternFan-out: 3 parallel branches from Build Artifact
Sync PointAll 3 branches must complete before Health Checks
Timeout5 minutes per region deployment
On TimeoutMark region as failed, continue to health checks
📘 Parallel Fan-Out / Fan-In The parallel deploy uses a fan-out pattern: one node (Build Artifact) feeds into three parallel branches. After all branches complete, execution fans in to the Health Checks node. RedfireForge waits for all parallel branches to finish (or timeout) before proceeding.

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "🎭 Multi-Region Deploy Orchestrator" in the Orchestration category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Multi-Region Deploy Orchestrator".
  3. Add the Build Artifact node.
    Drag an HTTP node. Configure: POST /api/builds with body { "repo": "myapp", "tag": "{{imageTag}}", "version": "{{version}}" }. Extract artifactUrl. Connect Start → Build Artifact.
  4. Add three parallel Deploy nodes.
    From Build Artifact, create three parallel connections to three HTTP nodes:
    • Deploy US-East: region = us-east-1
    • Deploy EU-West: region = eu-west-1
    • Deploy APAC-SE: region = ap-southeast-1
    Each sends POST /api/deploy with the region and artifact URL.
  5. Add the Health Checks node.
    Connect all three deploy nodes to a single Script node. The script calls GET /health on each region's endpoint and builds the healthResults[] array.
  6. Add the Rollback node.
    Add a Condition node: if any healthResults[].status == "unhealthy", loop through failed regions and send POST /api/rollback for each. Connect Health Checks → Rollback on Failure.
  7. Add the Deployment Report node.
    Add a Log node that outputs the full deployment summary. Connect Rollback on Failure → Deployment Report → End.
  8. Test the workflow.
    Run with a test version. Verify all three regions deploy in parallel, health checks execute, and rollback triggers correctly for failed regions.

⚠️ Health Check Timing Allow sufficient warm-up time between deployment and health checks. New deployments may need 10–30 seconds to initialize. Configure a delay or retry loop in the Health Checks node to avoid false negatives from cold-start latency.

7. Try It Yourself — Exercises

Exercise 1: Canary Deployment

Instead of deploying to all regions simultaneously, deploy to US-East first as a canary. Run health checks on just that region. If healthy, proceed to deploy EU-West and APAC-SE in parallel. This reduces blast radius.

Exercise 2: Add a Fourth Region

Add a "Middle East" region (me-south-1) to the parallel deploy. Update the health checks and rollback logic to handle 4 regions. Verify the fan-out/fan-in pattern scales correctly.

Exercise 3: Slack Notifications

After the Deployment Report, add an HTTP POST node that sends the deployment summary to a Slack channel via webhook. Include the version, per-region status, and any rollback details. Color the message green (all healthy) or orange (partial rollback).

Exercise 4: Full Rollback on Majority Failure

If more than 50% of regions fail health checks, roll back all regions (including healthy ones) to the previous version. Add a Condition node that counts unhealthy regions and triggers a full rollback when the threshold is exceeded.
