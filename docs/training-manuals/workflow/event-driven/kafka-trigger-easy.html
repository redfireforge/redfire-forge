1. Purpose & Use Case

The KafkaTrigger node transforms a workflow into a long-running subscriber. When a Kafka message arrives that matches the configured topic (and optional filters), the engine launches a new workflow instance automatically — no polling or manual trigger needed.

Common patterns:

  • React to orders.created events by notifying the warehouse team
  • Process IoT sensor readings as they stream in from devices
  • Fan-in: multiple upstream services all publish to one topic; your workflow reacts to each
  • Real-time fraud screening: check every payment event as it arrives

This sample subscribes to orders.created, extracts the orderId, customerId, and amount, enriches the order with customer details from HTTP, then branches to either priority or standard processing based on the order amount.

2. Concepts You'll Learn

  • Configuring the KafkaTrigger node (topic, startPosition, maxConcurrentRuns)
  • Extract variables — pulling fields from the Kafka message body using JSONPath
  • JSON path filters — filtering messages before they trigger a run (e.g., status == CREATED)
  • Sample payload — how Quick Test bypasses the real broker for local testing
  • Combining Kafka trigger with HTTP enrichment and conditional branching

5. Step-by-Step Walkthrough

1 Load the Sample

  1. Go to Gallery → Workflows, filter by Event-Driven
  2. Click Load on "Kafka: Event-Triggered Processor" Easy
  3. The workflow opens in the editor with the KafkaTrigger node at the top

2 Inspect the KafkaTrigger Node

  1. Click the Order Event Trigger node (the rounded square with the Kafka icon)
  2. Note the config fields:
    • Cluster: local-plaintext
    • Topic: orders.created
    • Start Position: latest — only processes new messages (not replays)
    • Max Concurrent Runs: 5 — at most 5 workflow instances run in parallel
    • JSON Path Filters: $.status == CREATED — skips messages with other statuses
    • Extract Variables: orderId ← $.orderId, customerId ← $.customerId, amount ← $.amount
    • Sample Payload: A JSON blob used by Quick Test to simulate a message
💡 Sample Payload The KafkaTrigger node has a Sample Payload field. When you click Quick Test, the engine uses this payload as the incoming Kafka message instead of waiting for a real message. This lets you develop and test trigger-based workflows without needing a live broker.

3 Run with Quick Test

  1. Click Quick Test (▶) in the toolbar
  2. The engine uses the sample payload: { orderId: "ORD-2001", customerId: "CUST-100", amount: "149.99", status: "CREATED" }
  3. The trigger fires, extract variables are populated, and the workflow runs through all nodes
  4. Since amount (149.99) > 100, the Priority Processing path is taken

4 Inspect Results

  1. Click the Log Received Event node → Results tab → see all extracted variables snapshot
  2. Click the Enrich: Get Customer node → Results tab → see customerName and customerEmail
  3. Click the High Value Order? Condition node → Results show which branch was taken (true/false)
  4. Click Priority Processing → see the formatted log message

5 Test the Standard Path

  1. Click the KafkaTrigger node config
  2. Edit the Sample Payload — change "amount": "149.99" to "amount": "49.99"
  3. Click Quick Test again
  4. This time the Standard Processing path is taken (amount ≤ 100)

6 Live Testing (Optional)

To test with a real Kafka message:

  1. Ensure Local Plaintext cluster is Connected in Settings → Kafka
  2. The workflow is now deployed and listening on orders.created
  3. Navigate to Protocols → Kafka → Publish tab
  4. Set Topic to orders.created, Key to CUST-100, and body to: 
    {"orderId":"ORD-LIVE-001","customerId":"CUST-100","amount":"299.99","status":"CREATED"}
  5. Click Send Once — the workflow trigger fires a new run
  6. View the run in Workflow Runner → Execution History

6. Expected Results

  • All nodes show green ✅ badges
  • Log Received Event shows variables snapshot with orderId, customerId, amount
  • For amount=149.99 (>100): Priority Processing log entry at warn level reads:
    HIGH VALUE: Order ORD-2001 ($149.99) from ... — flagged for priority processing
  • For amount=49.99 (≤100): Standard Processing log at info level:
    Order ORD-2001 ($49.99) from ... — routed to standard queue

7. Try It Yourself

  1. Add a new filter: add a JSON path filter for $.amount > 0 to reject zero-value orders. Verify it works by setting amount=0 in the sample payload.
  2. Add a header filter: add a header filter requiring source=order-service. Test with and without that header in the sample payload.
  3. Change the routing threshold: update the Condition node from > 100 to > 500. Which test orders now go priority?
  4. Publish a real message: with the broker connected, use Message Studio Publish tab to send a message. Watch the Workflow Runner execute a new run.
