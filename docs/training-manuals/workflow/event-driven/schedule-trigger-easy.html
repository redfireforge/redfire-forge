1. Purpose & Use Case

This workflow demonstrates the schedule trigger pattern — a time-based entry point that fires automatically at regular intervals using a cron expression. No external event or manual action is required.

Real-world analogy: An operations team configures a health check that pings their production API every 5 minutes. If the service responds with anything other than HTTP 200, an alert is logged for the on-call engineer.

Examples of this pattern in production:

  • Periodic health checks for microservices and APIs
  • Nightly data export jobs that run at midnight
  • Hourly report generation for dashboards
  • Scheduled cache invalidation or cleanup tasks

2. Concepts You'll Learn

  • Configuring a ScheduleTrigger node with a cron expression
  • Understanding cron syntax: minute, hour, day, month, weekday
  • Sending an HTTP GET request and checking the response status
  • Using a Condition node to branch on a health check result
  • Logging outcomes for monitoring and alerting

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "⏰ Schedule Trigger" in the Event-Driven category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Schedule Trigger".
  3. Add the ScheduleTrigger node.
    Drag a ScheduleTrigger node onto the canvas. Configure:
    • Cron Expression: */5 * * * *
  4. Add the HTTP GET node.
    Drag an HTTP node. Configure:
    • URL: https://httpbin.org/status/200
    • Method: GET
    • Extractions: Add statusCode ← response status code
    Connect ScheduleTrigger → Health Check.
  5. Add the Condition node.
    Drag a Condition node. Configure:
    • Expression: {{statusCode}} == 200
    Connect Health Check → Healthy?.
  6. Add two Log nodes.
    • Log Healthy: Message = "Service is healthy — HTTP 200"
    • Log Degraded: Message = "Service is degraded — HTTP {{statusCode}}"
    Connect the Condition's true output → Log Healthy, and false output → Log Degraded.
  7. Test manually.
    Click Quick Test to run the workflow once immediately without waiting for the cron schedule. Verify the health check passes and the correct log branch executes.

7. Try It Yourself — Exercises

Exercise 1: Check Multiple Endpoints

Add a second HTTP node that checks a different URL (e.g., https://httpbin.org/status/200 for service A and https://httpbin.org/get for service B). Use two Condition nodes to evaluate both health checks independently.

Exercise 2: Send an Alert

On the degraded branch, instead of just logging, add an HTTP POST node that sends an alert to a Slack webhook URL or an email API. Include the {{statusCode}} in the alert message body.

Exercise 3: Change the Schedule

Modify the cron expression to run at different intervals:

  • */1 * * * * — every minute (for testing)
  • 0 */2 * * * — every 2 hours
  • 0 8 * * 1-5 — weekdays at 8:00 AM only

Exercise 4: Measure Response Time

Extract the response time from the HTTP node's execution metadata. Add a second Condition node that checks if response time exceeds 2000ms. Log a "Slow response" warning when the service is healthy but sluggish.
