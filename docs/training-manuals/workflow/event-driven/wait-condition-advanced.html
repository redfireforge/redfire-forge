1. Purpose & Use Case

This workflow demonstrates the polling with wait-for-condition pattern — a pull-based approach for monitoring long-running asynchronous operations. You start a job, then repeatedly check its status at intervals until it reports completion.

Real-world analogy: A CI/CD pipeline triggers a deployment, then polls the deployment service every few seconds asking "Is it done yet?" until the service responds with "completed" or "failed".

Examples of this pattern in production:

  • Monitoring a machine learning model training job until completion
  • Waiting for a database migration to finish before running smoke tests
  • Polling a payment processor for transaction settlement status
  • Checking a file-processing pipeline until the output file is available
  • Waiting for a container deployment to reach "Running" state

2. Concepts You'll Learn

  • Using a waitForCondition node to poll until a target state is reached
  • Configuring pollIntervalMs, timeoutMs, and maxAttempts
  • The body outlet (fired each poll) vs the done outlet (fired when finished)
  • Reading {{wait.conditionMet}}, {{wait.attempts}}, and {{wait.elapsed}}
  • Branching on timeout vs. success via a Condition node on {{wait.conditionMet}}
  • Snapshot variables in LogDebug to capture final state

💡 Why the body outlet loops back The body outlet fires after each poll action (2. Poll Status). Connect it back to the Wait node so the next poll reads the freshly-updated jobStatus variable. The Wait node tracks the attempt count internally.

5. Step-by-Step Development Guide

  1. Load from Gallery.
    Click Workflows → Gallery. Find "Sample: Polling with Wait for Condition" in the Event-Driven category. Click Import.

    — OR build manually: —
  2. Add Start node. Input variable: jobName = "data-import".
  3. Add 1. Create Job (HTTP POST).
    URL: https://jsonplaceholder.typicode.com/posts. Body type: JSON.
    Body: {"title":"Import Job","body":"Processing data...","userId":1}.
    Extraction: jobId ← $.id. Connect Start → Create Job.
  4. Add Log: Job Created (LogDebug info).
    Message: Job {{jobId}} ({{jobName}}) created. Starting polling... Connect Create Job → Log: Job Created.
  5. Add Wait: Job Complete (waitForCondition).
    Condition: {{jobStatus}} == 1. Interval: 2000 ms. Timeout: 30 000 ms. Max attempts: 15.
    Connect Log: Job Created → Wait: Job Complete.
  6. Add 2. Poll Status (HTTP GET).
    URL: https://jsonplaceholder.typicode.com/posts/1.
    Extraction: jobStatus ← $.userId.
    Connect Wait body outlet → Poll Status, and Poll Status → Wait (loop back).
  7. Add Completed? (Condition).
    Left: {{wait.conditionMet}}, Operator: ==, Right: true.
    Connect Wait done outlet → Completed?
  8. Add Log: Success and Log: Timeout.
    Success: info · message with {{wait.attempts}} and {{wait.elapsed}}.
    Timeout: warn · message with {{wait.attempts}}.
    Both: snapshotVariables: true. Connect to End.

7. Try It Yourself — Exercises

Exercise 1: Simulate Delayed Completion

Change the Poll Status URL to /posts/5 and the condition to {{jobStatus}} == 5. The condition is still met immediately (userId=5). Try pointing it at a URL that returns a different userId to simulate a real delay.

Exercise 2: Reduce the Timeout

Set timeoutMs: 5000 and maxAttempts: 2. Change the condition to {{jobStatus}} == 99 (never true). Observe the timeout branch being taken and the Log: Timeout message.

Exercise 3: Add a Retry Notification

After Log: Timeout, add an HTTP POST to /posts that sends a retry-request notification. This simulates alerting an operator when the job doesn't finish in time.
