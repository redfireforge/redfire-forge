1. Purpose & Use Case

This workflow demonstrates the polling with wait-for-condition pattern — a pull-based approach for monitoring long-running asynchronous operations. You start a job, then repeatedly check its status at intervals until it reports completion.

Real-world analogy: A CI/CD pipeline triggers a deployment, then polls the deployment service every few seconds asking "Is it done yet?" until the service responds with "completed" or "failed".

Examples of this pattern in production:

  • Monitoring a machine learning model training job until completion
  • Waiting for a database migration to finish before running smoke tests
  • Polling a payment processor for transaction settlement status
  • Checking a file-processing pipeline until the output file is available
  • Waiting for a container deployment to reach "Running" state

2. Concepts You'll Learn

  • Initiating a long-running job via HTTP POST and extracting a job ID
  • Building a polling loop with a back-edge that repeats until a condition is met
  • Using a Wait node to introduce a delay between poll attempts
  • Checking job status with an HTTP GET request inside the loop
  • Using a Condition node as the loop exit gate
  • Processing the final result after the loop completes

4. Node-by-Node Walkthrough

NodeTypePurpose
S Start Start Entry point. No input variables — the job ID is obtained from the Start Job response.
1 Start Job HTTP Sends POST to start a long-running job. Extracts jobId from the response.
2 Wait 5s Wait Pauses execution for 5 seconds before the next poll attempt. Prevents overwhelming the status endpoint.
3 Check Status HTTP Sends GET to check the job's current status. Extracts jobStatus from the response.
4 Done? Condition Evaluates {{jobStatus}} == "completed". If false, loops back to Wait 5s. If true, exits the loop.
5 Process Result Log Logs "Job {{jobId}} completed with status: {{jobStatus}}". Final processing after the job finishes.

Condition Configuration (Loop Exit)

Expression{{jobStatus}} == "completed"
True path→ Process Result (exit loop)
False path→ Wait 5s (continue polling)
📘 Polling Loop Mechanics The loop is created by connecting the Condition node's false output back to the Wait node, forming a cycle. Each iteration: wait → check → decide. The loop exits only when the Condition evaluates to true. Always include a Wait node to avoid hammering the external service.
⚠️ Infinite Loop Protection In production, always add a max iterations counter or a timeout check to prevent infinite polling. If the job never completes, the loop will run forever. Add a second Condition that checks {{loopCount}} > 60 (5 minutes at 5s intervals) and exits with an error.

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "🔄 Polling with Wait for Condition" in the Event-Driven category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Polling with Wait for Condition".
  3. Add the Start Job HTTP node.
    Drag an HTTP node. Configure:
    • URL: https://httpbin.org/post
    • Method: POST
    • Body: {"action":"start","type":"data-export"}
    • Extractions: jobId ← body $.json.action
    Connect Start → Start Job.
  4. Add the Wait node.
    Drag a Wait node. Set delay to 5000 ms. Connect Start Job → Wait 5s.
  5. Add the Check Status HTTP node.
    Drag an HTTP node. Configure:
    • URL: https://httpbin.org/get?status=completed
    • Method: GET
    • Extractions: jobStatus ← body $.args.status
    Connect Wait 5s → Check Status.
  6. Add the Condition node.
    Drag a Condition node. Configure:
    • Expression: {{jobStatus}} == "completed"
    Connect Check Status → Done?.

    Create the loop: Connect the Condition's false output back to the Wait 5s node.
  7. Add the Process Result node.
    Drag a Log node. Set message to "Job {{jobId}} completed with status: {{jobStatus}}". Connect the Condition's true output → Process Result → End.
  8. Run the workflow.
    Click Quick Test. Since the simulated endpoint always returns status=completed, the loop will exit after one iteration. To test multiple iterations, change the status query parameter to a different value for the first few runs.

7. Try It Yourself — Exercises

Exercise 1: Add a Max Retries Guard

Add a pollCount variable that increments on each loop iteration. Add a second Condition node that checks {{pollCount}} > 12 (1 minute at 5s intervals). If exceeded, log an error "Job timed out after 12 attempts" and exit the loop.

Exercise 2: Exponential Backoff

Instead of a fixed 5-second wait, implement increasing delays: 2s, 4s, 8s, 16s… Use a waitTime variable that doubles each iteration. Cap it at 30 seconds. This reduces load on the status endpoint for long-running jobs.

Exercise 3: Handle Failure Status

Modify the Condition node to also check for {{jobStatus}} == "failed". Use a Switch node with three cases: completed → process result, failed → log error, default → continue polling.

Exercise 4: Replace Polling with a Webhook Callback

Redesign the workflow to eliminate polling entirely. Start the job with a callback URL pointing to a WebhookTrigger in a second workflow. The job service calls the webhook when done. Compare the two approaches in terms of efficiency and complexity. See the Async Correlation samples for this pattern.
