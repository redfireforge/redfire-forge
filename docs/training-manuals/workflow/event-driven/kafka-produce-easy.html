1. Purpose & Use Case

The KafkaProduce node publishes a message to a Kafka topic. It is the output side of event-driven architectures — your workflow produces an event that downstream services (other workflows, microservices, analytics pipelines) can consume independently.

Common patterns:

  • Publishing domain events when a resource changes (order.created, user.updated)
  • Feeding a real-time analytics pipeline with click events or metrics
  • Sending commands to asynchronous workers (send-email, generate-report)
  • Fanout: one event consumed independently by many downstream services

This sample creates an order via a public API, then publishes a structured order event to the orders.created Kafka topic. After publishing, it captures the partition and offset into workflow variables using output bindings.

2. Concepts You'll Learn

  • The KafkaProduce node and its configuration panel
  • Message key template — how to set a consistent key from a workflow variable
  • Body template — composing a JSON message body using {{variable}} syntax
  • Headers — attaching metadata headers to the message
  • Output bindings — capturing partition and offset from the produce result
  • Ack mode — choosing between all, leader, and none durability levels

3. Prerequisites

🟡 Kafka Broker Required This sample requires a running Kafka broker. Use the bundled Docker profile: cd docker/kafka/plaintext && docker compose up -d
Then create a Local Plaintext cluster in Settings → Kafka pointing to localhost:19092.
  1. Start the dev server: npm run dev:server (port 3001)
  2. Start the Kafka Docker profile: cd docker/kafka/plaintext && docker compose up -d
  3. In RedfireForge → Settings → Kafka → create a cluster named Local Plaintext, broker 127.0.0.1:19092, auth None
  4. Click Connect — the cluster card should show Connected

5. Step-by-Step Walkthrough

1 Load the Sample from Gallery

  1. Navigate to Gallery in the left sidebar
  2. Select the Workflows tab
  3. Filter by category Event-Driven or search for "Kafka"
  4. Find "Kafka: Publish Order Event" Easy and click Load
  5. The workflow opens in the Workflow Editor

2 Inspect the Start Node

  1. Click the Start node to open its config
  2. You'll see four input variables pre-filled: orderId=ORD-2001, customerId=CUST-100, amount=149.99, status=CREATED
  3. These are the values used by all downstream {{variable}} references

3 Inspect the HTTP Node

  1. Click Create Order to open the HTTP config panel
  2. Method: POST, URL: https://jsonplaceholder.typicode.com/posts
  3. The body uses {{orderId}}, {{customerId}}, etc. to interpolate variables
  4. The Extractions tab captures postId from the response body ($.id)

4 Inspect the KafkaProduce Node

  1. Click Publish to orders.created to open the Kafka Produce config
  2. Note these key fields:
    • Cluster: local-plaintext — must match your connected cluster
    • Topic: orders.created
    • Key Template: {{customerId}} — ensures all orders for a customer go to the same partition
    • Body Template: a JSON object with {{variable}} placeholders resolved at runtime
    • Headers: source=order-service, eventType=order.created
    • Ack Mode: all — waits for all in-sync replicas to acknowledge before continuing
  3. Scroll to the Output Bindings section — two bindings are configured: kafkaPartition and kafkaOffset
💡 Output Bindings After a successful produce, the node captures the broker-assigned partition and offset into workflow variables. You can use {{kafkaPartition}} and {{kafkaOffset}} in downstream nodes to log, store, or route based on the publish result.

5 Run with Quick Test

  1. Click Quick Test in the toolbar (▶)
  2. The workflow executes node by node:
    1. Start → variables injected
    2. HTTP → POST to jsonplaceholder, postId extracted
    3. KafkaProduce → message published to orders.created
    4. Log → partition and offset logged
  3. Each node shows a ✅ green badge when it succeeds
  4. Click any node → Results tab to inspect its output variables

6 Verify the Message was Published

  1. Navigate to Protocols → Kafka
  2. Click the Consume tab
  3. Set Topic to orders.created, Start Position to Earliest
  4. Click Consume Once
  5. Find the row with key CUST-100 — click it to see the full message body and the headers (source, eventType)

6. Expected Results

7. Try It Yourself

  1. Change the topic: modify the KafkaProduce node to publish to orders.premium instead. Run again and verify in the Consume tab.
  2. Add a header: add a header priority=high to the KafkaProduce node. After running, verify the header appears in Message Studio.
  3. Add a second binding: add an output binding for timestamp → publishedTs. Update the Log node message to include {{publishedTs}}.
  4. Try ackMode=none: change Ack Mode to none and observe that the workflow continues without waiting for broker acknowledgment (fastest but least durable).
