1. Purpose & Use Case

Event-driven workflows start execution in response to an external event rather than a manual trigger. They are the backbone of reactive systems — processing incoming data the moment it arrives, running maintenance tasks on a schedule, or monitoring long-running jobs until completion.

Real-world scenarios:

  • A payment gateway sends a webhook when a transaction completes
  • A cron-based health check pings all services every 5 minutes
  • A CI/CD pipeline polls a build server until a deployment finishes
  • An order system waits for an asynchronous fulfillment callback

This category covers three core trigger patterns: webhook triggers, schedule triggers, and polling with wait-for-condition.

4. Key Concepts Deep Dive

Webhooks

A webhook is a push-based integration pattern. An external system sends an HTTP request to your workflow's endpoint when an event occurs. The WebhookTrigger node registers a URL (e.g., /webhook) and starts the workflow when a request arrives. Benefits: real-time, no wasted polling cycles, minimal latency.

Schedules

Schedule triggers use cron expressions to start workflows at fixed intervals. The ScheduleTrigger node fires automatically based on its cron configuration (e.g., */5 * * * * for every 5 minutes). Ideal for periodic health checks, report generation, and batch processing.

Polling

Polling is a pull-based pattern where the workflow actively checks an external system for status changes. A loop repeatedly sends a request, evaluates a condition, and either continues polling (with a delay) or exits when the condition is met. Used when the external system does not support webhooks or callbacks.

Correlation (Async Callbacks)

For advanced async patterns, the async-correlation subdirectory contains workflows that combine webhooks with correlation IDs — sending a request, then parking the workflow until a matching callback arrives. This bridges the gap between polling and pure push-based patterns.

📘 Push vs. Pull Prefer webhooks (push) when available — they are more efficient and provide lower latency. Use polling (pull) only when the external system does not support callbacks or when you need to monitor a system that only exposes a status endpoint.

6. Learning Path

  1. Start with Webhook Trigger (Easy)
    Learn how a workflow listens for an incoming HTTP request and responds.
  2. Then try Schedule Trigger (Easy)
    Configure cron-based execution and periodic health checking.
  3. Advance to Polling with Wait for Condition (Advanced)
    Build a polling loop that monitors a long-running job until completion.
  4. Explore Async Correlation (Advanced)
    Combine webhooks with correlation IDs for request-callback patterns.
