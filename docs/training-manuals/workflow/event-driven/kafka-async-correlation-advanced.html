1. Purpose & Use Case

The Kafka async request–reply pattern solves a fundamental challenge in event-driven systems: how do you wait for a response to a specific request when both parties communicate through Kafka topics?

Traditional HTTP has a synchronous request-response model. With Kafka, you publish a request message and a separate service publishes the response to a different topic. Your workflow needs to wait for the response that belongs to this specific request — identified by a shared correlation ID (here: the orderId).

Real-world applications:

  • Payment processing: submit payment request → wait for bank authorization response
  • Fraud scoring: submit transaction → wait for risk engine decision
  • Inventory reservation: submit hold request → wait for warehouse confirmation
  • KYC verification: submit document → wait for compliance team approval (with long timeout)

2. Concepts You'll Learn

  • KafkaWait — the correlation wait node that pauses execution until a matching reply arrives
  • Correlation source — matching by message body ($.orderId), header, or message key
  • Correlation ID expression — the expected value, sourced from workflow variables ({{orderId}})
  • Synthetic inject mode — configurable-delay mock injection for load testing
  • Handling both success (APPROVED) and failure (DECLINED) response paths
  • How KafkaWait differs from KafkaConsume (correlation vs. simple key regex)

3. The Correlation Pattern Explained

The correlation works like this:

  1. Workflow receives a payment request for orderId ORD-5001
  2. Workflow publishes to payments.processing with correlationId=ORD-5001 in the header
  3. A payment processor service consumes from payments.processing and processes the payment
  4. The payment processor publishes a response to payments.responses containing "orderId": "ORD-5001"
  5. The KafkaWait node is watching payments.responses for a message where $.orderId == "ORD-5001"
  6. When the matching message arrives, the wait resolves and execution continues
💡 Correlation vs. Key-Based Filtering KafkaConsume uses keyRegex to filter messages by the message key field. KafkaWait uses a correlation expression that matches a value extracted from the message body, header, or key — giving you full flexibility. Most payment/response systems put the correlation ID in the body.

4. Workflow Architecture

KafkaTrigger: payments.requests │ extractVars: orderId, amount, currency, customerId ▼ ① Log: Log Payment Request ▼ ② HTTP: Pre-validate (GET merchant info) → extracts: merchantName ▼ ③ KafkaProduce: payments.processing │ key: {{orderId}} header: correlationId={{orderId}} │ body: {orderId, amount, currency, customerId, merchant, requestedAt} ▼ ④ KafkaWait: payments.responses ← WAITS HERE until matching reply │ correlationSource: body │ correlationJsonPath: $.orderId │ correlationIdExpression: {{orderId}} │ timeoutMs: 60000 │ extractVars: paymentStatus, transactionId, failureReason │ loadTestBehavior: synthetic-inject (delay=500ms) ▼ ⑤ Condition: paymentStatus == APPROVED? │ true │ false ▼ ▼ ⑥a Log: Payment Approved ⑥b Log: Payment Failed (info: transactionId) (error: failureReason) │ │ └──────────┬────────────────────┘ ▼ End

6. Step-by-Step Walkthrough

1 Load the Sample

  1. Gallery → Workflows → Event-Driven → "Kafka: Async Request–Reply" Advanced → Load
  2. The workflow opens. Note the KafkaWait node in the middle — this is the correlation point

2 Inspect the KafkaTrigger Node

  1. Click Payment Request Trigger
  2. Sample payload: { orderId: "ORD-5001", amount: "499.99", currency: "USD", customerId: "CUST-300" }
  3. The four extracted variables become available to all downstream nodes

3 Inspect the KafkaProduce Node

  1. Click Submit to Payment Processor
  2. The body template includes all payment fields plus requestedAt: {{$now}}
  3. The correlationId header ({{orderId}}) is the signal to the downstream processor

4 Inspect the KafkaWait Node — The Core of This Pattern

  1. Click Wait for Payment Result
  2. Understand each config field:
    • Topic: payments.responses — where reply messages arrive
    • Correlation ID Expression: {{orderId}} — the value to match against
    • Correlation Source: body — extract from the message body
    • Correlation JSON Path: $.orderId — the path within the body to extract
    • Timeout: 60,000ms — fails if no matching message arrives within 60 seconds
    • Extract Variables: paymentStatus, transactionId, failureReason — pulled from the matching message
  3. In the Load Test Behavior section:
    • Mode: synthetic-inject
    • Delay: 500ms — simulates realistic payment processing latency
    • Mock payload: { orderId: "{{orderId}}", status: "APPROVED", transactionId: "TXN-..." }
🟡 How KafkaWait Matching Works When messages arrive on payments.responses, the KafkaWait node extracts $.orderId from each message body and compares it to {{orderId}} (resolved from the current workflow context). Only the matching message triggers resume. All non-matching messages on that topic are discarded (they may belong to other workflow instances).

5 Run Quick Test

  1. Ensure Local Plaintext is Connected (required for KafkaProduce)
  2. Click Quick Test
  3. Execution flow:
    1. Trigger fires with sample payload (orderId=ORD-5001)
    2. Log records the payment request
    3. HTTP fetches merchant info
    4. KafkaProduce publishes to payments.processing
    5. KafkaWait enters wait state… then synthetic-inject fires after 500ms with APPROVED payload
    6. Condition: APPROVED → Payment Approved log

6 Test the Failure Path

  1. Click the KafkaWait node → Load Test Behavior
  2. Edit the mock payload: change "status": "APPROVED" to "status": "DECLINED" and add "failureReason": "Insufficient funds"
  3. Run Quick Test again — now the Payment Failed path is taken
  4. The Log node records the failure reason at error level

7 End-to-End with Real Services

To test with a real payment processor:

  1. Deploy this workflow (it listens on payments.requests)
  2. Create a "simulator" workflow that:
    • Produces test messages to payments.requests
    • Consumes from payments.processing
    • Produces a response to payments.responses with the same orderId
  3. Or use Message Studio Consume to watch payments.processing and manually reply via Publish

7. Load Testing with Synthetic Inject

The synthetic-inject load test mode is ideal for performance testing:

  • The KafkaWait node injects the mock payload after the configured delay (500ms ± 100ms jitter)
  • This simulates realistic payment processor latency without needing a real upstream service
  • You can measure end-to-end workflow throughput at any simulated latency: 100ms, 500ms, 2000ms
  • Jitter (±100ms by default) simulates natural variation in processing times

To run a load test: Workflow Runner → select this workflow → configure run count → Run.

9. Try It Yourself

  1. Change correlation to key: edit the KafkaWait node — change correlationSource from body to key. Update the KafkaProduce node to set the message key to {{orderId}}. Update the mock payload. Does it still correlate correctly?
  2. Add timeout handling: add a Condition node after KafkaWait checking if paymentStatus is empty (timeout scenario). Route to an error log node: "Payment timed out for order {{orderId}}".
  3. Vary the synthetic delay: change syntheticDelayMs to 2000ms and run a load test. Compare the p95 latency to the 500ms version.
  4. Add header correlation: modify both KafkaProduce (add header X-Order-ID: {{orderId}}) and KafkaWait (correlationSource=header, correlationHeader=X-Order-ID). Test the header-based correlation path.
