1. Purpose & Use Case

This workflow demonstrates the webhook trigger pattern — the most common event-driven entry point. An external system sends an HTTP request to your workflow's registered endpoint, triggering automatic execution without manual intervention.

Real-world analogy: A payment provider (Stripe, PayPal) sends a webhook notification when a customer completes a purchase. Your workflow receives the event, logs it, processes the order, and responds with an acknowledgment.

Examples of this pattern in production:

  • Receiving GitHub webhook events (push, PR, issue) to trigger CI/CD pipelines
  • Processing Slack slash commands via incoming HTTP POST requests
  • Handling IoT device event notifications from an MQTT-to-HTTP bridge
  • Receiving form submissions from a frontend application

2. Concepts You'll Learn

  • Configuring a WebhookTrigger node to listen on a specific endpoint path
  • Extracting fields from the incoming HTTP payload (headers, body, query params)
  • Using a Log node to record the received event for debugging
  • Returning an HTTP response to the caller with a status code and body
  • Understanding synchronous webhook handling — process and respond in one flow

4. Node-by-Node Walkthrough

📘 WebhookTrigger vs. Start Node A WebhookTrigger replaces the standard Start node. It automatically registers an HTTP endpoint and begins the workflow when a matching request arrives. The trigger node extracts data from the request, making it available to downstream nodes via variables.

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "⚡ Webhook Trigger" in the Event-Driven category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Webhook Trigger".
  3. Add the WebhookTrigger node.
    Drag a WebhookTrigger node onto the canvas. Configure:
    • Endpoint Path: /webhook
    • Method: POST
    • Extractions: Add eventType ← body $.eventType and payload ← body $.data
  4. Add the Log Payload node.
    Drag a Log node. Set message to "Received {{eventType}}: {{payload}}". Connect WebhookTrigger → Log Payload.
  5. Add the Process Event node.
    Drag another Log node. Set message to "Processing event {{eventType}}...". Connect Log Payload → Process Event.
  6. Add the HTTP Response node.
    Drag an HTTPResponse node. Configure:
    • Status: 200
    • Body: {"status":"received","event":"{{eventType}}"}
    Connect Process Event → HTTP Response.
  7. Test the webhook.
    Click Quick Test. RedfireForge will simulate an incoming POST request. Alternatively, use curl: 
    curl -X POST http://localhost:3000/webhook \
  -H "Content-Type: application/json" \
  -d '{"eventType":"order.created","data":{"orderId":"ORD-123"}}'

7. Try It Yourself — Exercises

Exercise 1: Add Payload Validation

Insert a Condition node after the Log Payload step. Check if {{eventType}} is not empty. If empty, return HTTP 400 with {"error":"Missing eventType"}. If valid, continue with processing.

Exercise 2: Route by Event Type

Replace the Process Event log with a Switch node that routes based on {{eventType}}. Add cases for order.created, order.cancelled, and a default. Each case should log a different message.

Exercise 3: Forward to an External API

Instead of logging, add an HTTP POST node that forwards the received payload to a downstream service (e.g., https://httpbin.org/post). Extract and log the downstream response before returning the acknowledgment.

Exercise 4: Add Idempotency

Extract a unique eventId from the payload. Use a Condition node to check if this event was already processed (simulated via a variable). Skip processing for duplicate events.
