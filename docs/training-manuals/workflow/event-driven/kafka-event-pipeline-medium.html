1. Purpose & Use Case

This sample demonstrates a full Kafka event pipeline where every step of order processing is mediated by Kafka topics. This pattern is the backbone of microservices architectures with event sourcing:

  • An upstream service produces to orders.created
  • This workflow consumes the event, validates it, and produces the result to orders.processed
  • A downstream service (or another workflow) consumes orders.processed

Using KafkaConsume at the end to confirm delivery closes the loop — the workflow verifies that its own produce message reached the topic and is readable.

2. Concepts You'll Learn

  • KafkaTrigger — subscribe once, react to every message
  • KafkaProduce — publish result events after processing
  • KafkaConsume — one-shot fetch to verify delivery or read from upstream
  • SetVariable — computing derived state (processedStatus) before producing
  • Load test behavior — auto-resume mode on KafkaConsume for CI/performance testing
  • The difference between KafkaConsume startPosition: committed vs earliest/latest

3. Prerequisites

4. Pipeline Architecture

KafkaTrigger: orders.created │ extractVars: orderId, customerId, amount, status ▼ ① HTTP: Validate Order → GET /posts/{{orderId}} │ extracts: validationStatus (HTTP status code) ▼ ② Condition: status == 200? │ true │ false ▼ ▼ ③a SetVar: VALIDATED ③b SetVar: REJECTED │ │ └──────────┬─────────────┘ ▼ ④ KafkaProduce: orders.processed │ key: {{orderId}} body: {orderId, status, processedStatus, processedAt} │ outputBindings: resultOffset ▼ ⑤ KafkaConsume: orders.processed (key regex: {{orderId}}, load: auto-resume) │ outputBindings: confirmedOffset ▼ ⑥ Log: Pipeline Complete │ ▼ End

6. Step-by-Step Walkthrough

1 Load and Open the Sample

  1. Gallery → Workflows → filter Event-Driven → "Kafka: Full Event Pipeline" → Load
  2. The workflow canvas shows 9 nodes in a vertical pipeline layout

2 Understand the Trigger

  1. Click the New Order Trigger node
  2. The sample payload simulates: { orderId: "ORD-3001", customerId: "CUST-200", amount: "299.50", status: "CREATED" }
  3. Four variables are extracted from the message body via JSONPath

3 Understand the KafkaProduce Configuration

  1. Click the Publish Result Event node
  2. The body template combines original and derived fields: orderId, customerId, amount, originalStatus, processedStatus, processedAt
  3. The key is {{orderId}} — ensures the result event is co-located with the trigger message in the same partition
  4. The pipeline=order-processor header allows downstream consumers to filter by source system
  5. Output binding captures resultOffset for verification

4 Understand KafkaConsume and Load Test Behavior

  1. Click the Confirm Delivery node
  2. This is a one-shot consume: it fetches at most 1 message matching the key regex {{orderId}}
  3. Note the Load Test Behavior setting: auto-resume
    • auto-resume: during Quick Test or load tests, the node immediately resumes with the mock payload instead of waiting for a real Kafka message
    • In production workflow runs (not quick test), it waits for the real message to appear
  4. The startPosition: committed means: consume only messages after the last committed offset for this consumer group — it won't re-process old messages
💡 Why Use KafkaConsume for Confirmation? Producing a message doesn't guarantee a downstream service received it. KafkaConsume after KafkaProduce is a pattern for produce-then-verify — the workflow confirms the message is actually readable in the topic before declaring success.

5 Run Quick Test

  1. Click Quick Test (▶)
  2. The trigger fires with the sample payload
  3. HTTP validates (jsonplaceholder returns 200 for post IDs 1-100), so the VALIDATED path is taken
  4. KafkaProduce publishes the result event (requires live broker)
  5. KafkaConsume immediately resumes via auto-resume with the mock payload
  6. Log records all offset values
⚠️ Broker Requirement for KafkaProduce The KafkaProduce node always connects to a real broker — it does not have a Quick Test bypass. Ensure Local Plaintext is Connected before running Quick Test. KafkaConsume uses auto-resume to skip waiting for confirmation, so it works without a real consumer group.

6 Inspect the Full Variable Timeline

  1. After running, click the Log Pipeline Complete node → Results → see the snapshotted variables
  2. You should see: orderId, customerId, amount, status, validationStatus, processedStatus, processedAt, resultOffset, confirmedOffset

7. Load Testing Behavior

When running this workflow in the Workflow Runner (load test mode), the KafkaConsume node's auto-resume setting prevents the runner from getting stuck waiting for confirmation messages during each test iteration. The mock payload is injected as the confirmation, allowing the runner to measure the full pipeline throughput without blocking on I/O.

To change this behavior, click the Confirm Delivery node and change Load Test Behavior:

  • auto-resume: skip wait, use mock payload (fastest for CI)
  • synthetic-inject: inject mock after a configurable delay (realistic latency simulation)
  • wait-for-real: wait for an actual message in the topic (full end-to-end, slowest)

8. Expected Results

  • All 9 nodes show green ✅ badges
  • The Log node output contains all pipeline variables including two offset values
  • In the Topic Explorer (Protocols → Kafka → Topics), a new message appears in orders.processed with key = orderId

9. Try It Yourself

  1. Force the rejected path: edit the HTTP node URL to https://jsonplaceholder.typicode.com/posts/999999 (returns 404). Run Quick Test and verify REJECTED is published.
  2. Add a third topic: add another KafkaProduce node for REJECTED orders that publishes to orders.rejected. Connect it from the Mark Rejected branch.
  3. Switch to wait-for-real: change KafkaConsume to wait-for-real. Observe the behavior difference — the node waits up to the timeout for an actual message.
  4. Add schema validation: open KafkaProduce and enable Schema Registry with your local schema registry URL. Produce an Avro-encoded message.
