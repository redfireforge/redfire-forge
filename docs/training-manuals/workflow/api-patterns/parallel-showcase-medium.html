1. What Are Swim Lanes?

When a workflow uses Fork/Join nodes, multiple branches execute in parallel. The Results Explorer automatically detects these parallel groups and draws colored rectangles (swim lanes) behind each branch's nodes.

Content Pipeline
Fetch Posts → Fetch Comments → Create Summary
⏱ CRITICAL PATH
Quick Check
Fetch Albums
Activity Pipeline
Fetch Todos → Check Status

Why it matters:

  • Visual grouping — instantly see which nodes run simultaneously
  • Critical path — identifies the slowest branch (the bottleneck that gates the Join)
  • Branch comparison — compare timing, pass rates, and node counts across branches
Key Concept The critical path is the slowest parallel branch. The Join node waits for ALL branches to complete, so the total parallel section time equals the critical path's duration. Optimizing the critical path directly reduces overall workflow time.

4. Reading the Swim Lanes

In the Results Explorer diagram view, you'll see three colored rectangles behind the parallel nodes:

ColorBranchNodes InsideBorder Style
■ Blue Content Pipeline 3a → 3b → 3c Solid (if critical)
■ Purple Quick Check 4a Dashed
■ Amber Activity Pipeline 5a → 5b Dashed

What Each Visual Cue Means

  • Colored background — groups nodes that belong to the same parallel branch
  • Label in top-left — shows the branch name (derived from first/last node names)
  • Dashed border — regular branch
  • Solid border + "⏱ Critical Path" — the slowest branch (bottleneck)
When No Critical Path Appears If all branches have similar durations (within 10% or 5ms), no branch is marked as critical — this means your parallel execution is well-balanced. The critical path only appears when there's a meaningful performance difference.

5. Understanding Critical Path

The critical path determines the total time of the parallel section:

Total parallel time = max(Branch A time, Branch B time, Branch C time)

Example:
  Branch A (3 steps): 120ms + 80ms + 45ms = 245ms  ← Critical Path
  Branch B (1 step):  35ms                 = 35ms
  Branch C (2 steps): 40ms + 55ms          = 95ms

Join node waits: 245ms (gated by Branch A)

Optimization insight: Speeding up Branch B or C won't help — the Join still waits for Branch A. To reduce parallel section time, you must optimize Branch A.

When Critical Path Shifts

Under load testing with many iterations, the critical path can shift between branches:

  • At low load: Branch A (most steps) is typically critical
  • At high load: a single-step branch might become critical if its endpoint slows under pressure
  • Comparing iterations helps identify if the bottleneck is consistent or variable

7. Tips & Best Practices

Designing Parallel Workflows

  • Balance branches — distribute work evenly to minimize idle time at the Join
  • Keep branches independent — don't share variables between parallel branches (race conditions)
  • Use extractions wisely — variable extractions in one branch are NOT available in other branches until after the Join

Analyzing Results

  • Run 5+ iterations for meaningful averages in the branch comparison
  • Watch for shifting critical paths — if the slowest branch changes between runs, investigate endpoint stability
  • Check pass rates per branch — a branch with low pass rate might be failing silently
  • Use the Timeline view for a time-based Gantt chart showing when each node executed

Performance Optimization

  • Always optimize the critical path first — other branches won't reduce total time
  • Consider splitting a heavy branch into smaller independent branches
  • Add Delay nodes to simulate network latency and test how it affects the critical path
