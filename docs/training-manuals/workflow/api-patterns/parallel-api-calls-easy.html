1. Purpose & Use Case

This workflow demonstrates the Fork/Join parallel execution pattern — splitting execution into concurrent branches using an explicit Fork node, running independent API calls simultaneously, and recombining with a Join node. After joining, a final POST node assembles all collected data into a summary request.

Real-world analogy: A dashboard page needs to display user info, recent orders, and notifications. Rather than loading each section sequentially (3× the wait time), the page fetches all three data sources simultaneously and renders them as each response arrives.

When to use parallel execution:

  • Fetching data from multiple independent API endpoints
  • Running health checks against several services simultaneously
  • Aggregating data from different microservices into a unified view
  • Any scenario where requests don't depend on each other's results

2. Concepts You'll Learn

  • How the Fork node explicitly splits execution into parallel branches
  • How the Join node waits for all branches before continuing
  • Multiple HTTP nodes executing concurrently after a Fork
  • Each branch writing to its own independent variables
  • How parallel execution reduces total latency
  • Combining parallel results in a downstream HTTP node

7 nodes, 6 edges — Start → Get Post → Fork → [Get Users | Get Comments] → Join → Post Summary. The Fork node explicitly splits execution; the Join node waits for both branches before continuing.

📘 Fork & Join Nodes RedfireForge uses explicit Fork and Join nodes to manage parallel execution. Fork splits one path into multiple concurrent branches. Join waits for all incoming branches to complete before allowing the workflow to continue. This explicit model makes parallelism visible and debuggable in the workflow editor.

4. Node-by-Node Walkthrough

NodeTypePurpose
S Start Start Entry point. No input variables needed.
1 Get Post HTTP GET jsonplaceholder.typicode.com/posts/1. Extracts postTitle ($.title) and postUserId ($.userId). Runs before the Fork.
2 Parallel Fork Fork Splits execution into two concurrent branches. Both Get Users and Get Comments start simultaneously.
3a Get Users HTTP GET jsonplaceholder.typicode.com/users. Extracts firstUserName ($[0].name) and firstUserEmail ($[0].email).
3b Get Comments HTTP GET jsonplaceholder.typicode.com/posts/1/comments. Extracts firstCommentName ($[0].name) and firstCommentEmail ($[0].email).
4 Join Join Waits for both parallel branches to complete. All extracted variables are now available to the next node.
5 Post Summary HTTP POST jsonplaceholder.typicode.com/posts. Body combines all extracted variables: {{firstUserName}}, {{firstUserEmail}}, {{firstCommentName}}, {{firstCommentEmail}}.
💡 Performance Benefit If each API call takes ~200ms, a sequential workflow would take ~600ms total. With parallel execution, total time is ~200ms (the slowest single call). That's a 3× speedup — and the benefit grows with more parallel branches.

5. Step-by-Step Development Guide

  1. Import from Gallery.
    In the Workflow Designer, open Gallery → search for "Sample: Parallel API Calls" and click Import. The 7-node workflow loads ready to run.

    — OR build manually: —
  2. Create a new workflow.
    Click + New Workflow. Name it "Parallel API Calls".
  3. Add the initial HTTP GET node (node 1).
    Drag an HTTP node. Configure:
    • Label: 1. Get Post
    • URL: https://jsonplaceholder.typicode.com/posts/1
    • Method: GET
    • Extractions: postTitle ← body $.title
    • Extractions: postUserId ← body $.userId
    Connect Start → Get Post.
  4. Add the Fork node (node 2).
    Drag a Fork node. Label it 2. Parallel Fork. Connect Get Post → Fork. This is the split point.
  5. Add the two parallel HTTP nodes (nodes 3a and 3b).
    Drag two HTTP nodes:
    • Get Users: URL https://jsonplaceholder.typicode.com/users, extractions firstUserName ← $[0].name, firstUserEmail ← $[0].email
    • Get Comments: URL https://jsonplaceholder.typicode.com/posts/1/comments, extractions firstCommentName ← $[0].name, firstCommentEmail ← $[0].email
    Connect Fork → Get Users and Fork → Get Comments.
  6. Add the Join node (node 4).
    Drag a Join node. Label it 4. Join. Connect Get Users → Join and Get Comments → Join. The Join waits for both branches before continuing.
  7. Add the POST HTTP node (node 5).
    Drag an HTTP node. Configure:
    • Label: 5. Post Summary
    • URL: https://jsonplaceholder.typicode.com/posts
    • Method: POST
    • Body: {"title":"Workflow Summary","body":"First user: {{firstUserName}} ({{firstUserEmail}}), First commenter: {{firstCommentName}} ({{firstCommentEmail}})","userId":1}
    Connect Join → Post Summary.
  8. Run the workflow.
    Click Quick Test. Get Post fetches post 1, Fork splits to run Get Users and Get Comments simultaneously, Join waits for both, then Post Summary assembles the results.

7. Try It Yourself — Exercises

Exercise 1: Add a Fourth Parallel Branch

Add a fourth HTTP node that fetches /comments?_limit=3 in parallel Add a fourth parallel branch: GET /posts/1/todos (note: JSONPlaceholder doesn't have this endpoint; use /albums/1/photos?_limit=3 instead). Connect Fork → new node → Join.

Exercise 2: Add a Summary Script

Replace the HTTP Post Summary node with a Script node that computes a summary count and logs it. across all three responses (users + posts + todos) and outputs a totalItems variable.

Exercise 3: Add Error Handling

What happens if one of the parallel calls fails? Add a Condition node after the Merge that checks whether all three variables are non-empty. Route to different End nodes for "All Succeeded" vs "Partial Failure".

Exercise 4: Parameterize the Limit

Add a userId input variable to the Start node. Update the Get Post URL to use /posts?userId={{userId}}. to use ?_limit={{limit}}. Run with different limits (1, 5, 10) and observe the varying response sizes.
