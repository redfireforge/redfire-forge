1. Purpose & Use Case

This workflow demonstrates the fan-out/fan-in pattern — splitting execution into multiple parallel branches and then merging the results. Instead of calling APIs one after another (sequential), you call them all at once (parallel), dramatically reducing total execution time.

Real-world analogy: A dashboard page needs to display user info, recent orders, and notifications. Rather than loading each section sequentially (3× the wait time), the page fetches all three data sources simultaneously and renders them as each response arrives.

When to use parallel execution:

  • Fetching data from multiple independent API endpoints
  • Running health checks against several services simultaneously
  • Aggregating data from different microservices into a unified view
  • Any scenario where requests don't depend on each other's results

2. Concepts You'll Learn

  • How to create parallel branches from a single node (fan-out)
  • How the workflow engine waits for all branches before continuing (fan-in)
  • Multiple HTTP nodes executing concurrently
  • Each branch writing to its own independent variables
  • How parallel execution reduces total latency
  • Using a merge point to synchronize parallel branches

GET │ │ Users │ │ Posts │ │ Todos │ │ (HTTP) │ │ (HTTP) │ │ (HTTP) │ └────┬────┘ └────┬────┘ └────┬────┘ │ │ │ └────────┬───┘────────────┘ │ ▼ ┌─────────────┐ │ 4. Merge │ (all variables │ (SetVar) │ now available) └──────┬──────┘ ▼ ┌─────────────┐ │ End │ └─────────────┘

7 nodes, 6 edges — a fan-out/fan-in pattern. The Start node connects to three parallel HTTP nodes. Each node fetches data independently. The Merge node waits for all three to complete before the workflow continues to End.

📘 How Parallel Execution Works When a node has multiple outgoing edges, the workflow engine starts all target nodes simultaneously. The merge node (any node with multiple incoming edges) waits for all incoming branches to complete before executing. This is an implicit fork/join — no special configuration required.

4. Node-by-Node Walkthrough

NodeTypePurpose
S Start Start Entry point. Fans out to three parallel HTTP nodes.
1 GET Users HTTP GET jsonplaceholder.typicode.com/users?_limit=3. Extracts usersData (full body). Fetches the first 3 users.
2 GET Posts HTTP GET jsonplaceholder.typicode.com/posts?_limit=3. Extracts postsData (full body). Fetches the first 3 posts.
3 GET Todos HTTP GET jsonplaceholder.typicode.com/todos?_limit=3. Extracts todosData (full body). Fetches the first 3 todos.
4 Merge SetVariable Merge/sync point. Waits for all three branches. Sets totalEndpoints = 3 to confirm all sources returned.
E End End Workflow complete. Variables usersData, postsData, todosData, and totalEndpoints are all available.
💡 Performance Benefit If each API call takes ~200ms, a sequential workflow would take ~600ms total. With parallel execution, total time is ~200ms (the slowest single call). That's a 3× speedup — and the benefit grows with more parallel branches.

5. Step-by-Step Development Guide

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "🔗 Parallel API Calls" in the API Patterns category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Parallel API Calls".
  3. Add three HTTP nodes.
    Drag three HTTP nodes onto the canvas. Configure each:
    • GET Users: URL https://jsonplaceholder.typicode.com/users?_limit=3, extraction usersData ← body $
    • GET Posts: URL https://jsonplaceholder.typicode.com/posts?_limit=3, extraction postsData ← body $
    • GET Todos: URL https://jsonplaceholder.typicode.com/todos?_limit=3, extraction todosData ← body $
  4. Connect Start to all three.
    Draw edges from Start → GET Users, Start → GET Posts, Start → GET Todos. This creates the parallel fan-out.
  5. Add the Merge node.
    Drag a SetVariable node. Set totalEndpoints = 3. Connect all three HTTP nodes → Merge. This creates the fan-in.
  6. Connect Merge → End.
    Draw the final edge.
  7. Run the workflow.
    Click Quick Test. Observe that all three HTTP nodes execute simultaneously and the total time is roughly equal to the slowest single call.

7. Try It Yourself — Exercises

Exercise 1: Add a Fourth Parallel Branch

Add a fourth HTTP node that fetches /comments?_limit=3 in parallel with the other three. Update the Merge node to set totalEndpoints = 4.

Exercise 2: Add a Summary Script

Replace the Merge SetVariable node with a Script node that counts the total items across all three responses (users + posts + todos) and outputs a totalItems variable.

Exercise 3: Add Error Handling

What happens if one of the parallel calls fails? Add a Condition node after the Merge that checks whether all three variables are non-empty. Route to different End nodes for "All Succeeded" vs "Partial Failure".

Exercise 4: Parameterize the Limit

Add a limit input variable to the Start node. Update all three HTTP URLs to use ?_limit={{limit}}. Run with different limits (1, 5, 10) and observe the varying response sizes.
