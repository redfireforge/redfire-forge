1. Purpose & Use Case

This sample demonstrates deep linked-resource traversal — a pattern where each API response contains a URL pointing to the next resource you need to fetch. Instead of knowing all endpoints upfront, you follow the links embedded in each response.

Real-world analogy: Many REST APIs use HATEOAS-style links. A product API might return a manufacturer_url, which you fetch to get supplier details, which in turn has a certifications_url. You chain HTTP nodes, passing URLs from one response to the next.

Examples:

  • Following pagination links across API pages
  • Traversing parent→child resource relationships
  • Building a resource graph by following embedded URLs
  • Discovering API data that isn't available in a single call

2. Concepts You'll Learn

  • Chaining multiple HTTP nodes where each URL comes from the previous response
  • Using JSONPath extractions to pull nested URLs from API responses
  • Using {{variable}} interpolation in HTTP node URL fields
  • Traversing linked resources across 3 API endpoints
  • Using a Condition node to verify data was found
  • Understanding HATEOAS / linked-data patterns in REST APIs

4. Node-by-Node Walkthrough

S Start Node

Input VariablespokemonName = "pikachu"

The workflow starts with a Pokémon name. You can change this to any valid Pokémon name (e.g., bulbasaur, charmander, eevee).

1 Fetch Pokémon (HTTP Node)

URLhttps://pokeapi.co/api/v2/pokemon/{{pokemonName}}
MethodGET
HeadersAccept: application/json
ExtractionsspeciesUrl ← $.species.url

Fetches basic Pokémon data. The response contains hundreds of fields, but we only extract species.url — a link to the species resource with richer data.

📘 Why Not Fetch Everything Here? The /pokemon endpoint returns stats, moves, and sprites but not evolution or habitat data. That data lives on the /pokemon-species endpoint, linked via species.url. This is the essence of linked-resource traversal.

2 Fetch Species (HTTP Node)

URL{{speciesUrl}}
MethodGET
Extractions habitat ← $.habitat.name
evolutionChainUrl ← $.evolution_chain.url

The URL is entirely dynamic — it comes from the previous response. We extract the habitat name and another linked URL pointing to the evolution chain resource.

3 Fetch Evolution Chain (HTTP Node)

URL{{evolutionChainUrl}}
MethodGET
Extractions baseSpecies ← $.chain.species.name
evolvesTo ← $.chain.evolves_to[0].species.name

Fetches the evolution chain. For Pikachu, the chain is: pichu → pikachu → raichu. We extract the base species and the first evolution target.

4 Has Evolution? (Condition Node)

Left{{evolvesTo}}
Operator!= (not equal)
Right (empty string)

Verifies the Pokémon has an evolution. Most Pokémon do, but some (like Mew) have no evolutions, and the extraction would return empty. The true branch connects to Done.

E Done (End Node)

Marks the workflow as complete. All variables — speciesUrl, habitat, evolutionChainUrl, baseSpecies, evolvesTo — are available in the workflow context.

6. Step-by-Step Development Guide

Follow these steps to build this workflow from scratch:

  1. Load from Template Gallery.
    Click New Workflow → Template Gallery. Find "🐾 Pokémon Evolution Chain" in the API Patterns category. Click Use Template.

    — OR build manually: —
  2. Create a new workflow.
    Click Workflows → + New. Name it "Pokémon Evolution Chain". Add input variable pokemonName with default value pikachu.
  3. Add the first HTTP node (Fetch Pokémon).
    Drag an HTTP node onto the canvas. Configure:
    • URL: https://pokeapi.co/api/v2/pokemon/{{pokemonName}}
    • Method: GET
    • Extractions: Add speciesUrl ← $.species.url
    Connect Start → HTTP.
  4. Add the second HTTP node (Fetch Species).
    Drag another HTTP node. Configure:
    • URL: {{speciesUrl}}
    • Method: GET
    • Extractions: habitat ← $.habitat.name, evolutionChainUrl ← $.evolution_chain.url
    Connect HTTP 1 → HTTP 2.
  5. Add the third HTTP node (Fetch Evolution Chain).
    Drag another HTTP node. Configure:
    • URL: {{evolutionChainUrl}}
    • Method: GET
    • Extractions: baseSpecies ← $.chain.species.name, evolvesTo ← $.chain.evolves_to[0].species.name
    Connect HTTP 2 → HTTP 3.
  6. Add the Condition node.
    Drag a Condition node. Configure:
    • Left: {{evolvesTo}}
    • Operator: !=
    • Right: (leave empty)
    Connect HTTP 3 → Condition. Connect Condition (true) → End.
  7. Run the workflow.
    Click Quick Test. Watch the workflow traverse three API calls, each URL discovered from the previous response. Verify the Condition passes.

8. Try It Yourself — Exercises

Exercise 1: Try a Different Pokémon

Change pokemonName to eevee. Eevee has multiple evolution paths (Vaporeon, Jolteon, Flareon, etc.). Observe what evolvesTo returns — it will only show the first evolution. Can you modify the extraction to get all of them?

Exercise 2: Extract Type Information

The /pokemon response includes a types array. Add an extraction for primaryType using $.types[0].type.name. Verify Pikachu's type is electric.

Exercise 3: Handle Non-Evolving Pokémon

Try pokemonName = "mew". Mew has no evolutions, so evolvesTo will be empty. The Condition node should take the false branch. Add an End node on the false branch labeled "No Evolution Found".

Exercise 4: Build a Full Evolution Summary

Add a Script node after the evolution chain fetch. Parse the full chain and build a summary string like "pichu → pikachu → raichu". Store it in an evolutionSummary output variable.
