Parallel Payment Processing Hard

Split payment across card and loyalty points, wait for both callbacks in parallel, aggregate results, then confirm or cancel the order.

Key Concepts in This Sample

🔀 Fork / Join

Split into parallel branches and wait for both to complete

🔗 Two CorrelationWaits

Each branch waits independently for its own callback

📊 Aggregate Node

Combine results from parallel branches into a unified view

🛡 ErrorHandler

Wraps the entire fork to catch timeouts and failures

Step-by-Step Setup

1 Start Node — Input Variables

VariableValue
orderIdORD-2024-0099
totalAmount150.00
loyaltyPoints5000

2 SetVariable Node: Calculate Split

Calculate how much goes to card vs loyalty:

VariableExpression
loyaltyAmount50.00 (from points)
cardAmount100.00 (remainder)
📝 Why no cardPaymentId / loyaltyPaymentId here? Each branch's HTTP response returns its own gateway id (extracted as $.id), then a per-branch SetVariable step prefixes it with card- or loyalty- to guarantee the two parallel CorrelationWaits get distinct keys — even when the upstream gateway echoes the same numeric id (e.g. test sandboxes returning 101).

3 ErrorHandler Node

Wrap the Fork → Join section to catch timeouts and payment failures:

FieldValue
Error ActionContinue with error data
ContainsFork → Join (all parallel branches)
🛡 Why ErrorHandler? If either CorrelationWait times out, the ErrorHandler catches the error and routes to the "Cancel Order" path instead of crashing the entire workflow.

4 Fork Node

Split into two parallel branches:

  • Branch A: Card payment → CorrelationWait (card callback)
  • Branch B: Loyalty payment → CorrelationWait (loyalty callback)

5 Branch A: Card Payment

HTTP Node: Charge Card

POST {{paymentBase}}/posts
{
  "orderId": "{{orderId}}",
  "amount": {{cardAmount}},
  "currency": "USD",
  "cardToken": "{{cardToken}}",
  "callbackUrl": "http://localhost:3001/webhooks/callback/card-payment"
}

Extract: cardPaymentId = $.id from the response body.

SetVariable Node: Tag Card Payment ID

VariableExpression
cardPaymentIdcard-{{cardPaymentId}}

Prefixes the gateway id so the card branch's correlation key cannot collide with the loyalty branch.

7 Join Node

Waits for both branches to complete before continuing.

8 Aggregate Node

Combines the results from both branches:

Output VariableExpression
allPaymentsApproved{{cardStatus}} == approved && {{loyaltyStatus}} == approved

9 Condition Node: Both Approved?

ExpressionRoute
{{allPaymentsApproved}} == true→ HTTP: Confirm Order
else→ HTTP: Cancel Order

10 HTTP: Confirm Order (success path)

POST https://api.example.com/orders/{{orderId}}/confirm
{
  "cardTransactionId": "{{cardTransactionId}}",
  "loyaltyConfirmationId": "{{loyaltyConfirmationId}}",
  "totalCharged": {{totalAmount}}
}

11 HTTP: Cancel Order (failure path)

POST https://api.example.com/orders/{{orderId}}/cancel
{
  "reason": "Payment partially failed",
  "cardStatus": "{{cardStatus}}",
  "loyaltyStatus": "{{loyaltyStatus}}"
}

Architecture Notes

Why Fork/Join for Parallel Payments?

  • Speed — Both payment processors run simultaneously, reducing total wait time
  • Independence — Each has its own webhook path and correlation ID
  • Atomicity — The Condition node ensures both must succeed for confirmation

Error Scenarios

ScenarioResult
Both approved→ Confirm Order
Card approved, loyalty declined→ Cancel Order (refund card)
Card declined, loyalty approved→ Cancel Order (restore points)
Card timeout (5 min)→ ErrorHandler catches → Cancel Order
Both timeout→ ErrorHandler catches → Cancel Order
