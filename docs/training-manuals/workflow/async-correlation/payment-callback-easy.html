Payment Gateway Callback Easy

Submit a payment, wait for the gateway callback, then process the result.

Workflow Diagram

┌─────────┐ ┌──────────────────┐ ┌─────────────────────┐ ┌──────────────────┐ ┌─────┐ │ Start │────▶│ Submit Payment │────▶│ CorrelationWait │────▶│ Confirm Order │────▶│ End │ │ │ │ Payment │ │ "Wait for Payment" │ │ Payment Status │ │ │ └─────────┘ └──────────────────┘ └─────────────────────┘ └──────────────────┘ └─────┘ │ ▲ │ extracts: │ webhook callback: │ {{paymentId}} │ POST /webhooks/callback/payment │ │ { paymentId, status, transactionId } ▼ │ Payment Gateway ──────────────────┘

What You'll Learn

  • How to configure a CorrelationWait node with body-based correlation
  • How to extract variables from the webhook payload
  • How to chain the extracted data into the next HTTP node
  • How to test the flow using the Test Webhook feature

Step-by-Step Setup

1 Create the Workflow

Open the Workflow Designer and create a new workflow. You can also import the YAML file examples/easy-payment-callback-workflow.yaml from the Template Gallery.

2 Add the Start Node

Configure input variables:

VariableValue
orderIdORD-2024-0042
amount99.99
currencyUSD

3 Add HTTP Node: Submit Payment

FieldValue
URLhttps://payments.example.com/charges
MethodPOST
Body 
{
  "orderId": "{{orderId}}",
  "amount": {{amount}},
  "currency": "{{currency}}",
  "callbackUrl": "http://localhost:3001/webhooks/callback/payment"
}
ExtractpaymentId from $.id
💡 Key Detail The callbackUrl in the body tells the payment gateway where to send the result. The CorrelationWait node listens on this same path.

4 Add CorrelationWait Node

FieldValue
LabelWait for Payment Callback
Correlation ID Expression{{paymentId}}
Webhook Path/webhooks/callback/payment
Correlation Sourcebody
Correlation JSONPath$.paymentId
Timeout300000 (5 minutes)

Extract Variables

Variable NameJSONPath
paymentStatus$.status
transactionId$.transactionId
processedAt$.processedAt

5 Add HTTP Node: Confirm Order

FieldValue
URLhttps://api.example.com/orders/{{orderId}}/payment-status
MethodGET

This node runs after the webhook resumes the workflow, so {{paymentStatus}} and {{transactionId}} are available.

6 Connect and Run

Connect: Start → HTTP (initiate) → CorrelationWait → HTTP (lookup) → End

Testing the Flow

Option A: Counterpart Simulator (recommended demo)

  1. Open Template Gallery → Event-Driven tab
  2. Pick Sample: Payment Callback (Simulator) → Use Template (in a second tab)
  3. Run the main workflow first — it pauses on the CorrelationWait node
  4. Run the simulator workflow — it waits 3s then POSTs a fake gateway callback
  5. The paused main workflow resumes and completes
💡 Why this works The main sample's Submit Payment HTTP node calls jsonplaceholder.typicode.com/posts which always returns $.id = 101, so {{paymentId}} resolves to 101. The simulator hard-codes paymentId=101 so the body correlation matches.

Option B: Test Webhook (Built-in)

  1. Run the workflow — it pauses at the CorrelationWait node
  2. Click the CorrelationWait node → open config modal
  3. Scroll to "Test Webhook" section
  4. Edit the auto-generated payload if needed
  5. Click "Send Test Webhook"
  6. The workflow resumes and completes

RedfireForge Server Responses

What RedfireForge returns to the calling system when a webhook is received:

✅ Matched — Workflow Resumed (200)

{
  "resumed": true,
  "correlationId": "pay_4kF9xR2mNqLp",
  "executionId": "exec-abc-001",
  "workflowId": "wf-payment-flow",
  "webhookData": {
    "paymentId": "pay_4kF9xR2mNqLp",
    "status": "approved",
    "transactionId": "txn_8mK3vP7wXjRs",
    ... full webhook body echoed back ...
  }
}

❌ No Match Found (404)

{
  "resumed": false,
  "error": "No matching paused workflow found",
  "webhookPath": "/webhooks/callback/payment"
}

🔁 Duplicate — Idempotent (200, cached)

// Second call with same x-idempotency-key returns cached response:
{
  "resumed": true,
  "correlationId": "pay_4kF9xR2mNqLp",
  "executionId": "exec-abc-001",
  ... same response as first call (no duplicate execution) ...
}
💡 Idempotency Always send an x-idempotency-key header. If your gateway retries the callback, RedfireForge returns the cached response without resuming the workflow twice.
