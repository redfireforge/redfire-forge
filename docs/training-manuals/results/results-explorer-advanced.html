Results Explorer: Advanced Features

Advanced   Sub-Workflow Drilldown · Parallel Branch Analysis · Data Mapper Overlay · Export Trace

What You Will Learn

  • Drill into a Sub-Workflow node to inspect its inner execution trace
  • Navigate the trace stack breadcrumb and return to the parent workflow
  • Understand parallel branch visualization in the Explorer (fork/join topology)
  • Open the Data Mapper overlay for a mapper node and read its field traces
  • Export the execution trace as JSON for offline analysis or sharing

Part A — Sub-Workflow Drilldown

What is a Sub-Workflow Node?

A Sub-Workflow node calls another workflow as a nested execution. In the canvas, it appears with a purple border (vs green for regular nodes). The top-level trace covers only the entry/exit of the sub-workflow as a unit; to see what happened inside, you must drill down.

1
In the Explorer canvas, identify a purple-bordered node. These are sub-workflow nodes. Click to select it — the detail panel opens.
2
In the detail panel (Overview or Request tab), look for a Open inner trace or Drill down button. Click it.
3
The canvas replaces its content with the inner workflow's execution trace. A breadcrumb bar appears at the top of the modal: 
Parent Workflow  ›  Sub-Workflow Name
You are now viewing the sub-workflow's nodes, iterations, and timing independently.
4
Navigate the inner trace exactly like the parent: select nodes, read detail tabs, check iterations.
5
Click Parent Workflow in the breadcrumb (or the ← back button) to return up one level. The canvas restores the parent trace and the breadcrumb shrinks.
6
If the sub-workflow itself calls another sub-workflow, you can drilldown again — the trace stack grows: 
Parent  ›  Sub-1  ›  Sub-2
Each level is independently navigable.
💡 Sub-workflow failure diagnosis A sub-workflow node shows 🔴 if any of its internal nodes failed. Drill down to find exactly which inner node failed and on which iteration.

Part B — Parallel Branch Analysis

What Fork/Join Looks Like

When a workflow splits into parallel branches (fork node → multiple branches → join node), the Explorer renders each branch as a separate column. After selecting the fork node, the detail panel shows Branch Stats: per-branch pass/fail counts and duration.

7
Find a fork node in the canvas (a node with multiple outgoing edges going to parallel nodes). Click it.
8
The detail panel Overview tab shows a branch breakdown table:
  • Branch A: N pass, N fail, avg duration
  • Branch B: N pass, N fail, avg duration
  • …
Colour-coded by branch (uses the branch colour palette from the diagram — each branch has a distinct border colour on its nodes).
9
Click a node inside one of the parallel branches. The detail panel switches to that node. Check the Assertions tab to see if a specific branch's node is failing while other branches pass.
10
In Timeline view, parallel branches appear as overlapping bars at the same X positions (they ran concurrently). The width of the longest bar is the actual wall-clock time spent in the parallel section.

Part C — Data Mapper Overlay

What is the Mapper Overlay?

Data Mapper nodes transform JSON payloads by mapping fields from input to output. The Mapping Trace Overlay shows the exact field-by-field trace: which input value was picked, any transformation applied, and the resulting output value.

11
Click a node of type Data Mapper in the canvas (label usually includes "Mapper" or "Transform"). Its detail panel opens.
12
In the detail panel, find the Open in Mapper button (or Mapping Trace link). Click it.
13
The Mapping Trace Overlay opens over the explorer canvas. It shows a list of mapping rules evaluated during execution:
  • Input path — the JSONPath or expression that was read from the source
  • Input value — the actual value at runtime
  • Transformation — any function applied (e.g. toString, concat)
  • Output path — where the result was written in the output object
  • Output value — the final mapped value
  • Error indicator if a mapping rule failed (e.g. input path not found)
14
Close the overlay with the × button to return to the Explorer.
⚠️ Mapper overlay requires full capture level The mapping trace is only available when the run was captured at full or debug capture level. At minimal or standard, no mapping trace is stored and the button will not appear.

Part D — Export and Import Trace JSON

Export the Trace

15
In the Explorer modal toolbar, find the Export Trace button. Click it. A .json file downloads containing the full execution trace (workflow snapshot + all iterations + events).
16
This file can be:
  • Shared with a colleague who can import it without re-running the test
  • Archived alongside CI artifacts
  • Compared with traces from other runs using external tooling

Import a Trace

17
Close the Explorer modal (if open). In the Results Dashboard header, click 📂 Import Trace. A file picker opens.
18
Select the exported .json trace file. The Explorer opens immediately showing the imported trace. An Imported: filename.json banner shows at the top, and the Export button is hidden (it is already from an export).
19
You can drill down, switch iterations, and open the console exactly as with a live run trace.

Self-Practice Exercises

  1. If your workflow contains a sub-workflow, drilldown and count how many inner nodes ran. Navigate back to the parent. Confirm the sub-workflow node's pass/fail state matches the inner trace's overall result.
  2. In Timeline view, identify a parallel section. Measure the wall-clock duration of the parallel section by looking at the rightmost end of the overlapping bars. Compare it to the longest individual branch bar.
  3. Export a trace from a run with a known failure. Close the Explorer and import the file using the Import Trace button. Verify you can still see the failure details.
  4. Export the trace, then share the JSON file path with a colleague. Ask them to import it and describe the first failing node — verify it matches what you saw.
