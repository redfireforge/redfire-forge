gRPC: Interpolation & Variables

Advanced   Dynamic values · Environment switching · CI injection

What You Will Learn

  • Use {{variableName}} syntax in target hosts, metadata headers, and request JSON fields
  • Set and manage environment variables in the Environment Manager
  • Use the preview panel to resolve variables before sending
  • Understand interpolation error banners and missing variable warnings
  • Real-world patterns: environment switching, CI token injection, parameterised test automation

Why Use Interpolation?

Hard-coding endpoints, API tokens, and test data in saved requests creates friction when switching between environments (dev, staging, production). Interpolation lets you write one request template and parameterise the values that change per environment.

Without interpolationWith interpolation
Separate saved requests for dev, staging, prodOne request; switch environments by changing a variable
Token hardcoded in metadata — leaked if exportedAuthorization: Bearer {{auth_token}} — safe to share
Test data varies per test run — must edit JSON manuallySet userId variable before each run

The {{variableName}} Syntax

Any field that accepts text input in gRPC Studio supports the {{variableName}} interpolation syntax. The variable name must:

  • Start with a letter or underscore
  • Contain only letters, digits, underscores, and hyphens
  • Be surrounded by exactly double curly braces: {{name}}
⚠️ Interpolation syntax errors Malformed syntax (e.g., single braces {name}, unclosed braces {{name, or spaces inside braces {{ name }}) triggers the interpolation error banner. The request cannot be sent until the syntax is corrected.

Where Interpolation Works

FieldExample
Target host{{grpc_host}}:{{grpc_port}}
Metadata header valueAuthorization: Bearer {{auth_token}}
Request JSON field (string){ "userId": "{{user_id}}", "action": "query" }
Request JSON field (nested){ "filter": { "region": "{{region}}" } }
💡 Type coercion When a variable value is used inside a JSON string field, it is inserted as a string. If you need a numeric value, the variable must resolve to a number string that the proto field accepts (gRPC Studio performs type coercion at send time based on the proto field type).

Setting Variables in the Environment Manager

1
Open the Environment Manager from the top navigation bar (globe icon, or Environments menu).
2
Click + New Environment. Name it dev.
3
Add variables by clicking + Add Variable:
  • Key: grpc_host / Value: localhost
  • Key: grpc_port / Value: 50051
  • Key: auth_token / Value: dev-secret-token
4
Click Save Environment.
5
Create a second environment called staging with the same keys but different values (e.g., grpc_host: staging.api.example.com).
6
In the top bar, select the active environment from the dropdown (e.g., dev). All interpolated fields in the studio now resolve using the selected environment's variables.

Using Variables in a Request

7
In the connection bar, type the target host as {{grpc_host}}:{{grpc_port}}. The field shows the template syntax in edit mode.
8
In the metadata panel, add a header: authorization → Bearer {{auth_token}}.
9
In the request JSON editor, type:
{
  "message": "hello from {{grpc_host}}"
}

Preview Panel

10
Before sending, click the Preview toggle (eye icon) in the request editor toolbar. The preview mode replaces all {{variable}} placeholders with their resolved values:
Preview (resolved)
Target: localhost:50051
authorization: Bearer dev-secret-token
Body: { "message": "hello from localhost" }
11
Toggle back to edit mode to see the template syntax. The preview is read-only — it is for verification only, not for editing.

Missing Variable Warning

12
If a variable referenced in a field has no value in the active environment, the preview shows the variable name literally (as a placeholder) and the field is highlighted with a yellow warning:
⚠️ Warning — unresolved variable
authorization: Bearer {{auth_token}} (no value in 'dev' environment)

Interpolation Error Banner

If the {{...}} syntax itself is invalid — e.g., unclosed brace or spaces — the studio displays a red error banner at the top of the request panel. The Send button is disabled until the syntax is corrected.

⚠️ Error banner signals a syntax error, not a missing value The error banner (grpc-interpolation-error-banner) appears only for malformed syntax. A missing variable is a yellow warning, not a blocking error — you can still send the request and the placeholder will be sent as a literal string.

Switching Environments

13
In the environment dropdown, switch from dev to staging. All fields immediately re-resolve against the staging variable values — no request edits needed.
14
Click Preview to confirm the resolved target and headers are now pointing at the staging server.
15
Click Send. The request is sent to the staging host with the staging token.

CI Injection Pattern

In CI pipelines, token values are typically stored as pipeline secrets and must not be committed to the repo. Use the following workflow:

  1. Save the request template with {{auth_token}} as a collection entry (no hardcoded value).
  2. In the CI step, set the environment variable before running:
# GitHub Actions example
- name: Run gRPC Integration Test
  env:
    GRPC_AUTH_TOKEN: ${{ secrets.GRPC_AUTH_TOKEN }}
  run: |
    redfireforge run collection "Echo Tests" \
      --env staging \
      --var auth_token=$GRPC_AUTH_TOKEN

The CLI reads the --var overrides and injects them into the interpolation context at runtime, so the token never appears in any committed file.

Practice Exercises

  1. Create dev and staging environments with different grpc_host values. Write a request that interpolates the host. Switch environments and use Preview to confirm the resolved host changes correctly.
  2. Add {{auth_token}} to the authorization metadata header. Set the variable value in dev only (not staging). Switch to staging and confirm the yellow warning appears.
  3. Intentionally break the syntax by typing {{ user id }} (space inside braces). Confirm the error banner appears and Send is disabled. Fix the syntax and confirm the banner disappears.
  4. Save the parameterised request to a collection. Export the collection as JSON and verify no actual secret values appear in the exported file.
