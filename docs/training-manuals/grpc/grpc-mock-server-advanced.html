gRPC: Mock Server

Advanced   Desktop Only

🖥️ Desktop-only feature The gRPC Mock Server runs as a local process inside the Tauri desktop application. It is not available in browser mode because it requires native TCP port binding and HTTP/2 server capabilities. If you are using the browser build, upgrade to the desktop app to access this feature.

What You Will Learn

  • Start and stop the built-in gRPC mock server
  • Define unary method stubs (fixed response JSON)
  • Define streaming stubs (emit N messages on stream request)
  • Use the mock server as a target for gRPC Studio requests
  • Common use cases: CI isolation, offline development, error simulation

Why Use a Mock Server?

A mock gRPC server lets you test your gRPC client code or develop against an API contract before the real backend is ready. It is also ideal for:

  • Reproducing error conditions (status codes, trailers) that are hard to trigger on a real server
  • Running integration tests in CI without network dependencies
  • Simulating slow or degraded responses for resilience testing
  • Iterating on request/response schemas without deploying a service

Navigating to the Mock Server Panel

1
In gRPC Studio (desktop), click the Advanced sub-navigation tab (or icon) in the toolbar. The Advanced panel opens.
2
Inside the Advanced panel, click the Mock Server tab. The mock server panel shows the current server status, listen address, and stub definitions.

Starting the Mock Server

3
In the Mock Server panel, click Start Mock Server. The server binds to a local TCP port (e.g., 127.0.0.1:50071) and the status badge changes to Running.
4
The listen address is shown beneath the status badge, e.g., 127.0.0.1:50071. This is the address you use as the gRPC target in the connection bar.
💡 Port assignment If port 50071 is already in use, the mock server automatically selects the next available port. The assigned port is always shown in the panel — copy it before configuring your target.

Defining Unary Stubs

A unary stub tells the mock server: "when you receive a request for method X, respond with this JSON payload and status code."

5
In the Stubs section of the Mock Server panel, click + Add Unary Stub.
6
Fill in the stub fields:
  • Service: the fully qualified service name, e.g., echo.EchoService
  • Method: the method name, e.g., Echo
  • Response JSON: the JSON payload the server should return
  • Status Code: OK, or any gRPC error code (e.g., NOT_FOUND, INTERNAL)
  • Delay (ms): optional artificial delay before the response is sent (useful for latency testing)
7
Click Save Stub. The stub appears in the list with a summary label.

Example: Echo unary stub returning a fixed message

{
  "service": "echo.EchoService",
  "method": "Echo",
  "response": { "message": "mocked-response" },
  "statusCode": "OK",
  "delayMs": 0
}

Example: Stub returning an error

{
  "service": "echo.EchoService",
  "method": "Echo",
  "response": {},
  "statusCode": "INTERNAL",
  "statusMessage": "simulated internal error",
  "delayMs": 0
}

Defining Streaming Stubs

A streaming stub emits a sequence of messages when the client opens a server-stream or bidi stream.

8
Click + Add Streaming Stub. Fill in the service and method (e.g., ServerStream).
9
In the Messages field, add one JSON object per line. Each object is one stream frame the server will send in order:
{ "message": "stream-frame-1" }
{ "message": "stream-frame-2" }
{ "message": "stream-frame-3" }
10
Set the Inter-message delay (ms) to simulate a real server that produces data at intervals (e.g., 200 ms between frames). Set to 0 for immediate back-to-back frames.
11
Click Save Stub.

Using the Mock Server as a Target

12
In the gRPC Studio connection bar, enter the mock server listen address, e.g., 127.0.0.1:50071.
13
Set the TLS badge to Plaintext (the mock server does not use TLS by default).
14
Load the schema manually (upload proto file or protoset) since the mock server does not expose gRPC reflection.
15
Send a request using the method you stubbed. The mock server returns the defined response. The stream panel shows the stubbed messages for streaming methods.

Stopping the Mock Server

16
In the Mock Server panel, click Stop Mock Server. The status badge changes to Completed and the port is released. Any in-flight connections are terminated.
⚠️ Stubs are ephemeral Mock server stubs defined in the UI are held in memory for the current session. If you close the desktop app, stubs are lost. Export stubs to JSON if you need to preserve them across sessions (File → Export Mock Stubs).

Mock Server Status Reference

StatusMeaning
Not startedServer has not been started. No port is bound.
RunningServer is listening. Ready to accept connections on the shown address.
CompletedServer was running and has since been stopped.
ErrorServer failed to start (e.g., port in use). Check the error message and try again.

Practice Exercises

  1. Start the mock server. Define a unary Echo stub that returns { "message": "hello from mock" }. Connect gRPC Studio to the mock and run the Echo call. Verify the response matches your stub.
  2. Add a second stub for the same method that returns INTERNAL error with a custom message. Verify the error response is received.
  3. Define a streaming stub for ServerStream with 4 frames and a 300 ms delay. Run the call and observe the stream panel filling in with the frames over ~1.2 seconds.
  4. Stop the mock server and attempt a connection. Confirm the request fails with a connection refused error.
