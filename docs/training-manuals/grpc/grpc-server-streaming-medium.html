What is Server Streaming?

In a server-streaming RPC the client sends a single request message and the server responds with a sequence of messages over an open HTTP/2 stream. The stream ends when the server sends a trailing metadata frame with a status code. From the client's perspective: send once, receive many.

Real-world examples of server streaming
  • Log tailing: subscribe once, receive log lines as they are written
  • Progress reporting: one "start job" request, receive percentage-complete updates
  • Large result sets: paginate-free — stream all 10 000 results without client polling
  • Live stock price feeds: single subscribe request, price events pushed as they occur

Step-by-Step Walkthrough

1 — Select the ServerStream Method

1
In the schema panel, expand EchoService (or equivalent). Click ServerStream. The method type badge shows SERVER STREAM.
2
Notice the request composer changes — the Send button is now labelled Start Stream. The response area is replaced by a Stream Panel with a message log and counters.

2 — Configure the Request

3
In the request JSON editor, fill in the stream parameters:
{
  "message": "stream-event",
  "repeat_count": 5,
  "interval_ms": 200
}
4
This tells the echo service to send back the message 5 times with 200 ms between each message. Adjust repeat_count and interval_ms as needed.

3 — Start the Stream

5
Click Start Stream. The stream panel activates. The status badge changes from idle to Streaming.
6
As the server sends messages, each one appears as a new row in the message log, timestamped with the time of receipt. Each row shows:
  • A ↓ arrow (inbound) indicating a server-sent message
  • The decoded JSON payload of that message
  • The elapsed time since stream start
7
Watch the ↓ N counter in the stream panel header increment with each received message. After all messages are received, the counter reads ↓ 5.

4 — Stream Ends

8
When the server closes the stream, the status badge changes to Ended and the trailing status code (OK) appears. The Start Stream button re-enables.
9
Scroll through the message log to review all received messages. Click any message row to expand its full JSON payload.

5 — Cancel Mid-Stream

10
Set interval_ms to 2000 (2 seconds between messages) to give yourself time to cancel. Click Start Stream.
11
After receiving 2 messages, click Cancel Stream. The stream stops immediately. The status badge shows Cancelled and no further messages arrive.
12
Note that the messages received before cancellation remain visible in the log. Cancellation does not clear the log.

Stream Status Lifecycle

StatusMeaning
StartingHTTP/2 HEADERS frame sent, waiting for first message
StreamingMessages are being received
Ended (OK)Server closed the stream with status OK
Ended (ERROR)Server closed the stream with a non-OK status
CancelledClient cancelled before the server closed the stream

Diagnosing Stream Errors

If the stream ends with a non-OK status, the status badge shows the gRPC error code. Common streaming errors:

  • DEADLINE_EXCEEDED — the stream exceeded its configured deadline. Increase the timeout or investigate server-side latency.
  • UNAVAILABLE — the server dropped the connection mid-stream. Usually a transient infrastructure issue; retry.
  • RESOURCE_EXHAUSTED — the server hit a rate limit. Reduce repeat_count or add a delay.

Practice Exercises

  1. Start a server stream with repeat_count: 10 and interval_ms: 500. Watch all 10 messages arrive, then confirm the final status is OK.
  2. Start the same stream but cancel after exactly 3 messages. Confirm the log shows 3 entries and the status is Cancelled.
  3. Export the message log from a completed stream and inspect the JSON file format.
  4. Open a second tab and start a simultaneous server stream on a different method. Confirm both logs are independent.
