TLS Modes Overview

ModeDescriptionUse When
PlaintextNo encryption — raw HTTP/2 over TCPLocal dev servers without TLS (e.g., localhost:50051)
TLSServer identity verified via CA certPublic or staging servers with valid TLS certificates
Mutual TLS (mTLS)Both sides present certificatesZero-trust environments where the server also verifies the client

Opening the TLS Modal

1
In gRPC Studio, enter a target host in the connection bar. The TLS badge appears next to the host field, initially showing Plaintext.
2
Click the TLS badge. The TLS configuration modal opens with three radio buttons: Plaintext, TLS, and mTLS, plus a set of certificate upload fields.

Configuring TLS Mode

Plaintext (default for localhost)

3
Select Plaintext. All certificate fields are hidden. Click Save. Use this for local development servers that do not use TLS.
⚠️ Plaintext and browsers In browser mode, the studio proxies requests through the Express backend. The backend connects to the gRPC server directly, so TLS mode must match the backend-to-server connection, not the browser-to-backend connection.

TLS (server certificate verification)

4
Select TLS. Three optional fields appear: CA Certificate, Server Name Override, and Reject Unauthorized toggle.
5
CA Certificate (optional): upload a custom CA .pem file if the server uses a certificate signed by an internal or private CA that is not in the system trust store. Leave empty for public CAs (Let's Encrypt, DigiCert, etc.).
6
Reject Unauthorized: when toggled on (default), the connection is rejected if the server certificate is invalid or self-signed. Toggle off only for internal test servers with self-signed certs.
7
Server Name Override: override the hostname used for SNI and certificate verification. Useful when the server's certificate CN does not match the IP address or hostname you are connecting to.
8
Click Save. The TLS badge updates to show TLS.

Connecting to grpcb.in (public TLS server)

Target: grpcb.in:443

CA:     (leave empty — uses public CA)

Mutual TLS (mTLS)

mTLS requires the client to present its own certificate to the server. This is used in zero-trust architectures where every service must prove its identity bidirectionally.

9
Select mTLS. Two additional fields appear: Client Certificate (.pem) and Client Key (.pem).
10
Upload the Client Certificate — this is the .pem file containing the client's public certificate, signed by a CA the server trusts.
11
Upload the Client Key — this is the corresponding private key .pem file. It is used to sign the TLS handshake and prove ownership of the certificate.
12
Optionally upload a CA Certificate if the server's certificate is not from a public CA. Click Save. The badge shows mTLS.
⚠️ Private key security Client key files are stored locally and never sent to any remote service other than the target gRPC server during TLS handshake. Do not use production private keys in shared or untrusted environments.

Generating a self-signed mTLS pair (for local testing)

# Generate a CA key and cert
openssl req -new -x509 -keyout ca.key -out ca.pem -days 365 -nodes \
  -subj "/CN=test-ca"

# Generate client key and CSR
openssl req -new -keyout client.key -out client.csr -nodes \
  -subj "/CN=test-client"

# Sign the client cert with the CA
openssl x509 -req -in client.csr -CA ca.pem -CAkey ca.key \
  -CAcreateserial -out client.pem -days 365

Transport Modes: Proxy vs Native

gRPC Studio supports two transport modes that determine how the HTTP/2 connection is established between the studio and the gRPC server.

ModeHow it worksAvailable in
Proxy (default)Browser → Express backend → gRPC server. The Express server acts as a gRPC-Web proxy, translating between the browser's HTTP/1.1 and the server's H2.Browser and desktop
Native (direct H2)Desktop app → gRPC server directly via HTTP/2. No proxy involved. Higher performance, lower overhead.Desktop (Tauri) only

Switching to Native Transport

13
In the gRPC Studio connection bar, click Advanced Settings (the gear icon or Advanced sub-nav tab).
14
Under Transport Mode, switch from Proxy to Native. A warning banner appears if you are running in browser mode (native is not available there).
15
When native mode is active, the connection status badge shows a direct-connection indicator. TLS settings still apply — the desktop app handles the TLS handshake directly.
💡 When to use native transport Use native transport for performance-sensitive testing, for servers that use HTTP/2 trailers in ways that gRPC-Web does not support, or for servers where you cannot add an Envoy sidecar. Use proxy transport (default) for any browser-based usage.

TLS Troubleshooting

ErrorLikely CauseFix
UNAVAILABLE: TLS handshake failedWrong mode (Plaintext to TLS server or vice versa)Match the TLS badge to the server's requirement
CERTIFICATE_VERIFY_FAILEDSelf-signed cert with Reject Unauthorized onUpload the CA cert, or toggle Reject Unauthorized off
SSL_ERROR_HANDSHAKE_FAILURE_ALERTServer requires mTLS but no client cert providedSwitch to mTLS mode and upload client cert + key
ERR_SSL_VERSION_OR_CIPHER_MISMATCHIncompatible TLS version (e.g., server requires TLS 1.3)Upgrade Node.js / OpenSSL on the backend server

Practice Exercises

  1. Connect to grpcb.in:443 in TLS mode. Load the schema via reflection and confirm the connection succeeds.
  2. Temporarily disable Reject Unauthorized, connect to a server with a self-signed cert, and confirm it connects. Then re-enable and confirm it fails.
  3. Generate a self-signed mTLS pair using the OpenSSL commands above. Configure a local test server for mTLS and connect from gRPC Studio using the client cert and key.
  4. (Desktop only) Switch to native transport, connect to a local gRPC server, and compare connection latency to proxy mode.
