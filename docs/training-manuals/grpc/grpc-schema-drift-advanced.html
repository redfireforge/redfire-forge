What is Schema Drift?

Schema drift occurs when a gRPC service's proto definition changes in a way that is incompatible with existing clients. Because protobuf is a binary format without embedded schema negotiation, a client compiled against the old schema may silently misinterpret responses from a server using the new schema — or fail entirely at the field-access layer.

⚠️ Silent failures in gRPC Unlike a REST API where a removed field returns null and is visible in JSON, a removed protobuf field is simply absent from the binary payload. A client expecting field 4 will receive an empty value with no error. This makes schema drift one of the hardest categories of gRPC bugs to detect without tooling.

Breaking vs Non-breaking Changes

Change TypeBreaking?Example
Add a new optional fieldNoAdd string country = 5; to a message
Add a new methodNoAdd rpc Ping to a service
Remove a fieldYesRemove string message = 1;
Remove a methodYesRemove rpc Echo from EchoService
Change a field typeYesChange string message to int32 message
Change a field numberYesRenumber field 1 to field 2
Rename a field (same number)No (wire compat)Rename msg to message — same field number
Change streaming modeYesMake a unary method into a server-stream method

Loading Snapshot A (Baseline)

1
In gRPC Studio, open the Schema Browser (Schema tab → Browse). If you loaded a schema via reflection, it is already available as the active descriptor.
2
Click Save Snapshot (the camera icon). Name it Snapshot A — baseline. The snapshot is stored locally and appears in the Snapshots list.

Simulating a Schema Change (Snapshot B)

To demonstrate drift detection, we will simulate a change by uploading a modified descriptor.

3
In the Schema Ingestion panel, click Upload Protoset and upload a modified .bin descriptor (or use a different proto file that has a changed field or missing method).
4
Once loaded, click Save Snapshot again and name it Snapshot B — candidate.
💡 Generating test descriptors You can generate a second descriptor by editing the .proto file (e.g., removing the Echo method) and recompiling with protoc --descriptor_set_out=modified.bin. Upload the resulting modified.bin as Snapshot B.

Running the Schema Diff

5
In the Schema Browser, click the Compare Schemas button (or the diff icon ⬦ between two snapshot rows).
6
Select Snapshot A as the base and Snapshot B as the candidate. Click Compare.
7
The diff view appears with a three-section breakdown:
  • + Added — elements present in B but not in A (generally safe)
  • − Removed — elements present in A but not in B (potentially breaking)
  • ~ Changed — elements present in both but with different types, numbers, or streaming mode (usually breaking)
8
Breaking changes are highlighted in red and flagged with a Breaking badge. Non-breaking changes are in green or grey.

Reading the Diff View

Example diff output (method removed)

EchoService
  − rpc Echo (EchoRequest) returns (EchoResponse)   [BREAKING]
  ✓ rpc ServerStream (EchoRequest) returns (stream EchoResponse)
  ✓ rpc ClientStream (stream EchoRequest) returns (EchoResponse)
  ✓ rpc BidiStream (stream EchoRequest) returns (stream EchoResponse)

Example diff output (field type changed)

EchoRequest
  ~ message: string → int32   [BREAKING — field 1]
EchoResponse
  + latency_ms: int64         [non-breaking — new optional field]

Exporting a Drift Report

9
After running the diff, click Export Drift Report. A JSON file is downloaded listing all changes with their breaking status, element path, and change description.
10
The JSON report can be consumed by CI pipelines. A non-zero breakingChanges count should fail the build.

Example drift report JSON

{
  "snapshotA": "Snapshot A — baseline",
  "snapshotB": "Snapshot B — candidate",
  "breakingChanges": 1,
  "nonBreakingChanges": 1,
  "changes": [
    {
      "type": "removed",
      "path": "EchoService.Echo",
      "breaking": true,
      "description": "Method rpc Echo removed from service EchoService"
    },
    {
      "type": "added",
      "path": "EchoResponse.latency_ms",
      "breaking": false,
      "description": "Field latency_ms (int64, field 6) added to message EchoResponse"
    }
  ]
}

CI Integration Pattern

The recommended workflow for schema-safe deployments:

  1. At build time, store the current production descriptor as Snapshot A (committed to the repo or fetched from BSR).
  2. After any proto change, compile the new descriptor as Snapshot B.
  3. Run the drift check: if breakingChanges > 0, fail the CI step with an actionable error listing the breaking changes.
  4. If all changes are non-breaking, allow the deployment to proceed.
💡 Buf CLI for automated drift checking The Buf CLI (buf breaking) performs the same check from the command line and integrates with GitHub Actions, GitLab CI, and Bitbucket Pipelines. gRPC Studio's drift tool is ideal for interactive exploration; Buf CLI is ideal for automation.

Practice Exercises

  1. Load the echo proto, save it as Snapshot A. Edit the proto to add a new optional field to EchoRequest. Recompile, upload, save as Snapshot B. Run the diff — confirm it shows the addition as non-breaking.
  2. Edit the proto to remove the Echo method. Recompile and compare. Confirm the diff flags it as breaking.
  3. Change a field number in a message (e.g., field 1 → field 2). Compare and verify it is flagged as breaking.
  4. Export the drift report from exercise 2 to JSON and verify breakingChanges equals 1.
