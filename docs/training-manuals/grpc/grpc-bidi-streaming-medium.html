What is Bidirectional Streaming?

A bidirectional (bidi) streaming RPC keeps both the client-to-server and server-to-client streams open simultaneously. Either side can send messages at any time and in any order. The stream ends when both sides have closed their half. This is the most powerful and complex gRPC method type.

Real-world examples of bidirectional streaming
  • Chat server: clients send messages and receive messages from others interleaved
  • Real-time collaboration: each edit operation sent by the client triggers a broadcast response
  • Interactive ML inference: send audio/image chunks, receive partial results as they are ready
  • Order book: send trade requests, receive live fill confirmations interleaved with market updates

Step-by-Step Walkthrough

1 — Select the BidiStream Method

1
In the schema panel, expand EchoService and click BidiStream. The method type badge shows BIDI STREAM.
2
The stream panel shows a unified message log that interleaves outbound (↑) and inbound (↓) messages chronologically. The JSON editor and Send Message / Close & Finish buttons are at the bottom.

2 — Open the Stream

3
Click Start Stream. The stream opens and status shows Open (full-duplex). Both ↑ and ↓ counters start at zero.

3 — Send and Receive Interleaved

4
Type the first message and click Send Message:
{ "message": "ping-1" }
5
The echo server immediately sends back a response. The log shows:
↑ 12:00:01.000
{ "message": "ping-1" }
↓ 12:00:01.012
{ "message": "ping-1" }
6
Send a second message before the first response has arrived (works because the stream is full-duplex). The server echoes each message independently.
7
Continue sending several messages. Each response appears in the log as soon as it arrives, interleaved with any new outbound messages you send.

4 — Half-Close and Wait for Server

8
When you have finished sending, click Close & Finish. The client sends a half-close (END_STREAM). The studio stops accepting new messages from you but continues receiving server responses already in flight.
9
Once the server receives your half-close it processes any remaining input and closes its side. The status badge changes to Ended (OK).

5 — Review the Full Log

10
The unified log shows all messages in chronological order. The ↑ arrow denotes client-sent messages and ↓ denotes server-sent responses. Scroll up to review the complete exchange.
11
The counters at the top of the stream panel show the final totals: ↑ N messages sent, ↓ N messages received.

Message Log Reference

SymbolMeaning
↑ (blue)Outbound — message sent by this client
↓ (green)Inbound — message received from the server

Flow Control Notes

HTTP/2 flow control governs how many bytes can be in flight between client and server at any moment. In practice, for typical message sizes you will never hit flow control limits. However, if you send very large messages at high frequency, you may see brief pauses. The studio does not expose flow control settings directly.

Ordering Guarantees

gRPC preserves message order within each direction: your outbound messages arrive at the server in the order you sent them, and the server's inbound messages arrive at your client in the order they were sent. The interleaving between directions is determined by network timing and is not guaranteed to be alternating (unlike a strict ping-pong protocol).

⚠️ Bidi streams and reconnection If the connection drops mid-stream (e.g., TLS renegotiation or network interruption), the stream is permanently terminated. Unlike WebSocket, gRPC does not have a built-in reconnect protocol. You must start a new stream from the studio.

Practice Exercises

  1. Open a bidi stream and send 10 messages. Confirm that each one generates a corresponding inbound echo and the ↓ counter ends at 10.
  2. Send 3 messages quickly before any responses arrive. Observe whether the log shows responses interleaved or batched.
  3. Half-close after 5 messages. Verify no further outbound messages are accepted but inbound responses still arrive.
  4. Open two bidi streams in two separate tabs simultaneously. Confirm each tab's logs are completely independent.
