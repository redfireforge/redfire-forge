1. Purpose & Use Case

GraphQL Studio is great for interactive exploration, but when you need to run a sequence of operations automatically — create a user, fetch it back, assert the fields match, then delete it — you need the Workflow Designer. GraphQL workflow nodes bring the full power of the studio into automated, repeatable workflows.

Common patterns:

  • CRUD flows: create → read → update → assert → delete
  • Auth flows: login mutation → extract token → use token in subsequent queries
  • Schema watchdog: scheduled introspect → assert schema fingerprint unchanged
  • Subscription drain: subscribe → collect N events → assert all events match shape

2. GraphQL Node Types

Node typeOperationPrimary use
graphqlQueryQueryFetch data; extract values for downstream nodes
graphqlMutationMutationWrite data; extract created/updated object IDs
graphqlSubscriptionSubscriptionCollect streaming events; bounded by stopAfterMessages
graphqlIntrospectIntrospectionFetch schema; compute fingerprint; compare versions
graphqlAssertAssertionValidate response values; fail workflow if assertion fails

3. Step-by-Step Walkthrough

Step 1 — Import the Health Check Sample

Open the Gallery (gallery icon in the left sidebar). In the search box, type health. Find "GraphQL Health Check" and click Import. The workflow canvas opens with 5 nodes pre-configured.

The sample workflow:

  1. Start — entry point, initialises variables
  2. graphqlIntrospect — fetches the schema and extracts the type count
  3. graphqlQuery — executes a health-check query
  4. graphqlAssert — asserts the response matches expectations
  5. End — marks completion; emits workflow result

Step 2 — Inspect the graphqlIntrospect Node

Click on the graphqlIntrospect node to open its configuration panel. The fields you will see:

FieldValue in samplePurpose
endpoint{{gqlEndpoint}}Variable reference — inherited from workflow config
outputBindings{ "typeCount": "$.data.__schema.types.length" }Extracts the type count to a named variable

The outputBindings field uses JSONPath expressions to extract values from the introspection result and bind them to variables available to downstream nodes.

Step 3 — Inspect the graphqlQuery Node

Click on the graphqlQuery node. Its configuration:

{
  "endpoint": "{{gqlEndpoint}}",
  "query": "query HealthCheck { __typename }",
  "headers": {
    "Authorization": "Bearer {{authToken}}"
  },
  "extractionRules": [
    {
      "path": "$.data.__typename",
      "variableName": "typeName"
    }
  ]
}

Key fields:

  • endpoint — can be a variable reference or a literal URL
  • query — the GraphQL operation string (use Builder or Editor to generate this)
  • headers — optional HTTP headers; supports {{variable}} interpolation
  • extractionRules — JSONPath rules to extract values from the response into named variables

Step 4 — Inspect the graphqlAssert Node

Click on the graphqlAssert node. It validates that the response data meets your expectations. Configuration:

{
  "assertions": [
    {
      "path": "$.data.__typename",
      "operator": "equals",
      "expected": "Query"
    },
    {
      "path": "$.errors",
      "operator": "isUndefined"
    }
  ]
}

If any assertion fails, the workflow node turns red and the workflow is marked as failed. The failure message includes the expected vs actual value.

Step 5 — Configure the Endpoint Variable

Click Workflow Settings (gear icon at the top of the canvas). Find the gqlEndpoint variable and set its default value to your endpoint, e.g. https://countries.trevorblades.com/graphql. Click Save.

Step 6 — Execute the Workflow

Click ▶ Run Workflow. The nodes execute in sequence. Each node shows its status:

  • 🟡 In progress (spinning)
  • 🟢 Passed (green glow)
  • 🔴 Failed (red glow + error badge)

All 5 nodes should complete green. The Run Summary panel shows total duration and the extracted variable values.

Step 7 — Build a CRUD Workflow from Scratch

Now build your own. Open a new workflow (File → New Workflow). Add nodes in sequence:

  1. Drag graphqlMutation from the node palette onto the canvas. Configure it to create a user.
  2. Add a second graphqlQuery node to fetch the user by the ID extracted from the mutation. Use {{createdUserId}} as the variable (set it in the mutation's outputBindings).
  3. Add a graphqlAssert node to verify the fetched user's name equals the name sent in the mutation.
  4. Add a final graphqlMutation node to delete the user by ID.
  5. Connect the nodes: Start → mutation → query → assert → delete → End.

4. graphqlSubscription Node

The subscription node differs from query/mutation because it collects multiple events before completing:

{
  "endpoint": "ws://localhost:4010/graphql",
  "transport": "graphql-ws",
  "subscription": "subscription { orderUpdated { id status } }",
  "stopAfterMessages": 5,
  "outputBindings": {
    "events": "$.messages"
  }
}

The node stays open until stopAfterMessages events have been received, then completes and passes events as an array to downstream nodes. Set stopAfterMessages: 0 to collect indefinitely (use a Condition node or timeout to stop the workflow).

6. Try It Yourself

Exercise 1 — Import All Gallery Samples

Open the Gallery and import all six GraphQL workflow samples. Execute each one. Observe how the variable chaining works — how the output of one node becomes the input of the next.

Exercise 2 — Add an Assertion to the Health Check

In the imported Health Check workflow, add a second graphqlAssert node after the query node. Assert that typeCount (extracted by the introspect node) is greater than 5. Run the workflow — it should pass.

Exercise 3 — Parallel GraphQL Branches

Add a Parallel fork node after the Start node. In branch 1, place a graphqlQuery for users. In branch 2, place a graphqlQuery for orders. After the fork merges, add a graphqlAssert that checks both results. Run and observe that both branches execute concurrently.
