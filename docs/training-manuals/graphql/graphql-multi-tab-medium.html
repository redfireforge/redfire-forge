Multi-Tab Workflow

Medium — Training Guide

Work across multiple GraphQL endpoints simultaneously using independent tabs. Each tab maintains its own endpoint, schema cache, credentials, query, and response — so you can compare APIs or test different environments without losing context.

RedfireForge v0.6.0
Difficulty: ★★☆
GraphQL Studio · Tab bar

1. Purpose & Use Case

Multi-tab support is most useful when you need to:

  • Compare responses between staging and production endpoints
  • Query two different APIs simultaneously (e.g. a user service and an order service)
  • Test the same query with different auth credentials side-by-side
  • Keep a subscription open in one tab while running queries in another
  • Progressively build a complex workflow by designing each step in its own tab

2. Tab Isolation Model

Each tab is fully independent:

SettingPer-tab (isolated)?
Endpoint URL✅ Yes
Introspected schema✅ Yes — schema is cached per endpoint per tab
Auth / Headers✅ Yes
Query text✅ Yes
Variables JSON✅ Yes
Response / history✅ Yes
Polling toggle✅ Yes — each tab polls independently
Active subscription✅ Yes — tabs stream independently
CollectionsShared — collections are global to the workspace

3. Step-by-Step Walkthrough

Step 1 — Open the First Tab

Open GraphQL Studio. The initial tab is Tab 1. Enter the first endpoint:

https://countries.trevorblades.com/graphql

Click Introspect. Write and execute a query:

query Tab1Query {
  country(code: "US") {
    name
    capital
  }
}

The response appears in the right pane.

Step 2 — Add a Second Tab

Click the + button at the right end of the tab bar (or press Ctrl+T / Cmd+T). A new empty tab opens, labelled Tab 2. Note that tab 1 is still intact — its endpoint, query, and response are all preserved.

Step 3 — Configure a Different Endpoint in Tab 2

In Tab 2, enter a different endpoint:

https://api.spacex.land/graphql

(This is the SpaceX public GraphQL API. If it's unavailable, use the same countries endpoint with a different query — the point is that tab 2 has its own endpoint.)

Click Introspect. Tab 2 loads the SpaceX schema independently — the countries schema in Tab 1 is not replaced.

Step 4 — Execute in Tab 2

In Tab 2, write and execute:

query SpaceXLatestLaunch {
  launchLatest {
    id
    mission_name
    launch_date_utc
    rocket {
      rocket_name
    }
  }
}

The response appears in Tab 2's response pane.

Step 5 — Switch Back to Tab 1

Click Tab 1 in the tab bar. Your countries query, variables, and the response from Step 1 are exactly as you left them — nothing was lost when you switched to Tab 2.

Step 6 — Execute in Tab 1 Again

Press Ctrl+Enter / Cmd+Enter to re-execute the query in Tab 1. The new response replaces the old one in Tab 1's pane only. Tab 2's response is unaffected.

💡 Tabs survive page refreshes GraphQL Studio persists each tab's endpoint, query, variables, and auth to local storage. If you close and reopen the app, your tabs are restored.

Step 7 — Per-Tab Auth Isolation

Switch to Tab 2. Open the Auth panel and configure a Bearer Token. Switch back to Tab 1 — its auth is unaffected. This allows you to run the same query as both an authenticated user (Tab 2) and an anonymous user (Tab 1) without interfering.

Step 8 — Per-Tab Polling Isolation

If your endpoint supports polling (repeated query execution on a timer), you can enable the polling toggle independently per tab:

  1. In Tab 1, enable polling at 5-second intervals
  2. Switch to Tab 2 — polling is off here
  3. Tab 1 continues executing in the background; Tab 2 stays idle

This is useful for dashboards where one tab refreshes automatically while you work in another.

Step 9 — Close a Tab

Click the × on Tab 2's label to close it. The tab and its contents (endpoint, query, response, auth) are removed. Tab 1 remains open and active.

4. Endpoint Override vs Global Endpoint

In some configurations there is a global endpoint setting (used by workflow nodes as the default). Each tab can optionally override the global endpoint with a tab-local URL. The override only affects that tab — it doesn't change what workflow nodes use.

This means your exploration tab can point at a staging server while workflow tests continue running against the global production endpoint.

5. Try It Yourself

Exercise 1 — Staging vs Production Comparison

Open two tabs. Point Tab 1 at your staging environment and Tab 2 at production. Execute the same query in both. Compare the responses side-by-side by switching tabs.

Exercise 2 — Subscription in One Tab, Queries in Another

Start a subscription in Tab 1 (it stays connected). Open Tab 2 and run regular queries against the same or different endpoint. Confirm both tabs work concurrently — the subscription stream in Tab 1 continues while you execute queries in Tab 2.

Exercise 3 — Role-Based Testing

Assign admin credentials to Tab 1 and limited-user credentials to Tab 2 (see the Authentication tutorial). Execute a mutation in Tab 1 that Tab 2 is not authorised to perform. Confirm Tab 1 succeeds and Tab 2 returns a permission error.
