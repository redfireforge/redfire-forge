GraphQL Mock Server

Advanced — Training Guide

Run a fully-controllable GraphQL mock server from within the desktop app. Upload your SDL, configure resolver overrides with fixed values or custom functions, set global latency, and validate client behaviour before your real API is ready.

RedfireForge v0.8.0
Difficulty: ★★★
GraphQL Studio · Mock Server tab (Desktop only)
🖥️ Desktop-only feature The GraphQL Mock Server panel is only available in the RedfireForge desktop app (Tauri). When running RedfireForge in a web browser, the Mock Server activity tab is disabled. All steps in this tutorial require the desktop app.

1. Purpose & Use Case

The Mock Server lets you develop and test GraphQL client code without a real backend. It is particularly useful when:

  • The API is still under development by another team
  • You need to test error handling (return specific error payloads on demand)
  • You want to simulate slow responses to test loading states and timeouts
  • You need deterministic, repeatable data for automated test runs

The mock server runs inside the desktop app at http://localhost:3001/api/graphql/mock and is configured through both the UI panel and a REST config endpoint.

3. Step-by-Step Walkthrough

Step 1 — Open the Mock Server Panel

In the desktop app, click the Mock Server icon in the left activity sidebar (looks like a server or theatre mask). The panel opens showing the SDL editor, enable toggle, and resolver configuration section.

Step 2 — Upload or Paste an SDL

Paste the following minimal SDL into the SDL editor:

type Query {
  user(id: ID!): User
  users: [User!]!
}

type Mutation {
  createUser(name: String!, email: String!): User!
  deleteUser(id: ID!): Boolean!
}

type User {
  id: ID!
  name: String!
  email: String!
  role: UserRole!
  createdAt: String!
}

enum UserRole {
  ADMIN
  USER
  GUEST
}

Alternatively, drag a .graphql or .gql file from your filesystem onto the SDL editor area.

Step 3 — Enable the Mock Server

Click the Enable toggle at the top of the Mock Server panel. The status indicator turns green and shows Running. The mock server is now accepting requests at http://localhost:3001/api/graphql/mock.

Step 4 — Connect GraphQL Studio to the Mock

Open a new GraphQL Studio tab (or update the endpoint in the current tab) to:

http://localhost:3001/api/graphql/mock

Click Introspect. The studio loads your SDL as the schema. You can now run queries against the mock.

Step 5 — Execute a Query (Default Mock Data)

Write and execute:

query GetUser {
  user(id: "1") {
    id
    name
    email
    role
  }
}

The mock server returns auto-generated data based on your SDL types. All string fields get plausible random values; ID fields get UUID-style strings; enums return a random valid value.

Step 6 — Configure a Resolver Override (Fixed Value)

In the Mock Server panel, scroll to the Resolver Overrides section. Click + Add Override. Configure:

  • Operation: Query.user
  • Response type: Fixed JSON
  • Fixed value:
{
  "id": "usr-fixed-001",
  "name": "Mock Alice",
  "email": "mock@example.com",
  "role": "ADMIN",
  "createdAt": "2026-01-15T08:00:00Z"
}

Click Save Override. Now re-execute the GetUser query — you will always get the exact fixed response regardless of the id argument.

Step 7 — Set Global Latency

In the Mock Server panel, find the Global Latency slider or input field. Set it to 800 ms. Execute the query again. The response should take approximately 800 ms. This simulates a slow API to test loading spinners and timeout handling in your client.

Step 8 — Configure an Error Override

Add another resolver override for Query.users:

  • Response type: GraphQL Error
  • Error message: Unauthorized: token expired

Execute a users { id name } query. The response pane will show the GraphQL error in the errors array, simulating an auth failure from the real API.

Step 9 — Disable the Mock

Click the Enable toggle to turn it off. The mock server stops. Any queries to the mock endpoint will now time out. Switching back to a real endpoint (e.g. the countries API) works normally.

4. Mock vs Real Server Toggle Workflow

A common development pattern is:

  1. Enable mock → develop client UI against predictable data
  2. Disable mock → test against the staging server
  3. Re-enable mock → reproduce edge cases (error states, slow responses) that are hard to trigger in staging

Because the mock uses the same endpoint URL and same GraphQL schema, no client code changes are needed when switching.

5. Try It Yourself

Exercise 1 — Simulate a Mutation

Add a resolver override for Mutation.createUser that returns a fixed user object. Execute a createUser mutation and confirm the fixed response is returned.

Exercise 2 — Combine Latency + Error

Set global latency to 2000 ms and add a GraphQL error override for a query. Execute and observe: the response takes 2 seconds, then returns the error. This mimics a slow, failing upstream service.

Exercise 3 — Use Mock in a Workflow

Configure a graphqlQuery workflow node to use http://localhost:3001/api/graphql/mock as its endpoint. Execute the workflow with mock enabled, then disable the mock and re-run. Observe how the workflow handles the timeout when the mock is off.
