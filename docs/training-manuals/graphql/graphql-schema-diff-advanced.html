Schema Diff & Changelog

Advanced — Training Guide

Detect breaking and non-breaking changes when a GraphQL schema evolves. RedfireForge automatically snapshots your schema on each introspection and shows a colour-coded diff when the schema changes — so you know exactly what broke before your tests do.

RedfireForge v0.8.0
Difficulty: ★★★
GraphQL Studio · Schema Diff / Changelog

1. Purpose & Use Case

GraphQL APIs evolve. Fields get renamed, types change, required arguments are added, deprecated fields are eventually removed. Without tracking these changes you risk:

  • Queries that silently return null for a renamed field
  • Mutations that fail because an argument type changed
  • Test suites that break after a backend team deploys a schema change

The Schema Diff feature solves this by taking a snapshot of the schema every time you introspect. When the schema changes between introspections, the studio shows a diff — a list of exactly what changed, categorised as Breaking or Non-Breaking.

2. Breaking vs Non-Breaking Changes

Change typeCategoryWhy it matters
Removing a field from a type🔴 BreakingExisting queries that select this field will error
Removing a type entirely🔴 BreakingAny reference to the type becomes invalid
Changing a field type🔴 BreakingClient-side type assumptions no longer hold
Adding a required argument🔴 BreakingExisting calls without the argument fail validation
Removing an enum value🔴 BreakingVariables using the old value fail
Adding a new field to a type🟢 Non-BreakingExisting queries ignore it; opt-in
Adding an optional argument🟢 Non-BreakingExisting callers don't need to change
Adding a new type🟢 Non-BreakingIgnored by existing queries
Marking a field deprecated🟡 Non-Breaking (warning)Still works; you should migrate eventually
Changing a description string🟢 Non-BreakingCosmetic; no runtime impact

3. Step-by-Step Walkthrough

📋 Simulating a schema change To experience Schema Diff, you need an endpoint whose schema changes between introspections. The RedfireForge test server (docker) supports a ?version=v2 query parameter that serves a modified schema. Alternatively, use the local mock server: introspect, then edit the SDL, then re-introspect.

Step 1 — First Introspection (Snapshot A)

Connect to your endpoint (e.g. http://localhost:4010/graphql) and click Introspect. The studio stores a snapshot of the schema (snapshot A) in IndexedDB under the key graphql-schema-snapshots. The Schema Diff icon shows no notifications.

Step 2 — Change the Schema

If using the Mock Server: open the Mock Server panel and remove the email field from the User type in the SDL. Save. If using the test server: append ?version=v2 to the endpoint URL.

Step 3 — Re-Introspect (Snapshot B)

Click Introspect again. The studio fetches the new schema. A "Schema changed" toast notification appears at the top of the studio. The toast has a "View diff →" link button. Click it.

Step 4 — View the Schema Diff Modal

The Schema Diff modal opens. It shows two tabs:

  • Breaking Changes — changes that will break existing queries (shown in red)
  • Non-Breaking Changes — additive changes that are safe (shown in green)

For our example (removing email field from User), you should see:

BREAKING  Field removed: User.email (String)

If fields were added (e.g. User.phoneNumber), those appear in the Non-Breaking tab.

Step 5 — View the SDL Diff

In the diff modal, click SDL View (or the diff icon). This shows a side-by-side or inline diff of the raw SDL — red lines were removed, green lines were added. This is the most detailed view of exactly what changed.

Step 6 — Export the Diff

In the modal toolbar, click:

  • Export JSON — downloads a structured JSON file listing all changes with type, path, and severity
  • Export HTML — downloads a human-readable HTML report you can share with stakeholders or attach to a Jira ticket

Step 7 — Acknowledge the Change

Click Acknowledge in the modal. The notification clears and the current schema becomes the new baseline for future comparisons. The change is logged in the Changelog.

Step 8 — View the Changelog

Click the Changelog tab in the Schema panel (or the history icon). This shows a timestamped list of all schema changes that have been acknowledged, from newest to oldest. Each entry shows the number of breaking and non-breaking changes, the date, and a link to re-open the diff for that version.

4. What the Snapshots Store

Schema snapshots are stored in the browser's IndexedDB under the store name graphql-schema-snapshots. Each snapshot contains:

  • The full introspection result (all types, fields, arguments, descriptions)
  • The endpoint URL
  • The timestamp of the introspection
  • A fingerprint hash for fast equality checking

Snapshots are per-endpoint — changing to a different endpoint creates a separate snapshot series.

5. Try It Yourself

Exercise 1 — Breaking vs Non-Breaking Side by Side

Using the mock server, make two simultaneous changes: remove an existing field (breaking) and add a new field (non-breaking). Re-introspect and open the diff. Confirm the changes appear in the correct tabs.

Exercise 2 — Export and Review

Export the diff as JSON. Open the JSON file and identify the type, path, and severity fields. Write a brief impact statement: "Queries that select User.email will start returning an error. Affected clients: auth service, user profile page."

Exercise 3 — Schema Watchdog Workflow

Import the GraphQL Schema Watchdog workflow from the Gallery. This workflow runs graphqlIntrospect on a schedule and uses a graphqlAssert node to compare the fingerprint against a stored baseline. When the fingerprint changes, the workflow sends an alert. Configure it with your endpoint and run it.
