GraphQL Subscriptions

Medium — Training Guide

Connect to a live GraphQL subscription and receive a stream of real-time events. Choose between WebSocket (graphql-ws) and Server-Sent Events (SSE) transports, observe streaming data in the response pane, and stop the subscription when done.

RedfireForge v0.6.0
Difficulty: ★★☆
GraphQL Studio · subscription keyword

1. Purpose & Use Case

GraphQL subscriptions maintain a persistent connection to the server so the server can push updates to the client. Common use cases:

  • Real-time notifications (onOrderStatusChanged)
  • Live dashboard metrics (onMetricUpdate)
  • Streaming AI completions (onTokenGenerated)
  • Collaborative document editing (onDocumentChanged)

Unlike polling (repeated queries), subscriptions push only when something changes, which is far more efficient for high-frequency or event-driven data.

2. Subscription Transports

TransportProtocolBest for
graphql-wsWebSocket over ws:// or wss://Full-duplex, bidirectional — most common for modern APIs
SSE (Server-Sent Events)HTTP long-poll over http:// or https://Unidirectional server push; simpler infrastructure, works through HTTP proxies
AutoRedfireForge chooses based on endpoint URL schemeWhen you're unsure which transport the server supports

The transport selector appears in the connection bar next to the endpoint URL. The default is Auto.

3. Step-by-Step Walkthrough

📋 Live Subscription Server Required Subscriptions require a server that keeps a persistent connection open. Start the test server with: cd docker/graphql && docker compose up -d. The subscription endpoint is ws://localhost:4010/graphql.

Step 1 — Enter the Subscription Endpoint

In the connection bar, enter:

ws://localhost:4010/graphql

Click Introspect. The schema loads and you can now see the Subscription root type in the Schema Explorer.

Step 2 — Select a Transport

Next to the endpoint input, click the transport selector dropdown (shows Auto by default). The options are:

  • auto — detects from URL scheme
  • graphql-ws — forces the graphql-ws WebSocket sub-protocol
  • sse — forces Server-Sent Events over HTTP

Select graphql-ws for this walkthrough since the test server uses WebSockets.

Step 3 — Write a Subscription

In the editor, write:

subscription OnOrderUpdated {
  orderUpdated {
    id
    status
    updatedAt
    customer {
      name
    }
  }
}

Step 4 — Connect and Stream

Click ▶ Execute (the button may change label to Subscribe or show a connection icon). The studio establishes a WebSocket connection and enters listening mode.

In the response pane you will see:

  • A Connected status badge
  • An event counter incrementing as messages arrive
  • Each event appended as a timestamped JSON block

If the test server emits mock events on a timer, you will see new events arriving automatically.

Step 5 — Inspect Streaming Events

Each event in the response pane is a full GraphQL response object:

{
  "data": {
    "orderUpdated": {
      "id": "ord-42",
      "status": "SHIPPED",
      "updatedAt": "2026-08-14T10:32:11Z",
      "customer": { "name": "Alice Smith" }
    }
  }
}

Click on any event to expand it. The pane shows the raw JSON for that specific event.

Step 6 — Stop the Subscription

Click ■ Stop (or the same button that was labelled Execute/Subscribe). The WebSocket connection closes gracefully. The event list in the response pane remains visible for inspection.

💡 Bounded subscriptions in Workflow nodes When using a graphqlSubscription workflow node, set stopAfterMessages to a positive integer to automatically stop after N events — preventing runaway connections in automated workflows.

4. SSE Transport Walkthrough

Some APIs expose subscriptions over SSE instead of WebSockets. To test SSE:

  1. Change the endpoint to an HTTP URL: http://localhost:4010/graphql
  2. Set the transport selector to SSE
  3. Write and execute the same subscription query

The experience is identical from the user's perspective — events stream in as they arrive. Internally, the studio uses EventSource (HTTP long-poll) rather than WebSocket.

5. Subscription vs Polling

ApproachConnectionLatencyServer load
Polling (repeated queries)New HTTP request every N secondsUp to N secondsHigh — requests run even when nothing changed
Subscriptions (graphql-ws)One persistent WebSocketNear-instantLow — server pushes only on change
Subscriptions (SSE)One long-lived HTTP connectionNear-instantLow — simpler than WebSocket, no upgrade needed

6. Try It Yourself

Exercise 1 — Switch Transports

Connect to the subscription endpoint with graphql-ws, confirm events arrive, then disconnect. Change transport to SSE and reconnect using an http:// URL. Compare the behaviour.

Exercise 2 — Multiple Subscription Tabs

Open a second tab (click + in the tab bar). Connect to the same subscription endpoint in tab 2 and start a different subscription (e.g. onMetricUpdate). Observe that both subscriptions stream independently without interfering with each other.

Exercise 3 — Subscription with Variables

If the subscription accepts a variable (e.g. filter by customer ID), add ($customerId: ID!) to the operation and supply the variable in the Variables panel. This lets you subscribe to a filtered event stream.
