GraphQL Mutations

Medium — Training Guide

Create, update, and delete data using GraphQL mutations with typed input variables. Understand the difference between queries (reads) and mutations (writes), and learn how to inspect mutation return payloads.

RedfireForge v0.6.0
Difficulty: ★★☆
GraphQL Studio · mutation keyword

1. Purpose & Use Case

While queries fetch data, mutations change it. GraphQL mutations are used for:

  • Creating new records (createUser, createOrder)
  • Updating existing records (updateProfile, setStatus)
  • Deleting records (deletePost)
  • Side-effect operations (sendEmail, publishDraft)

Unlike REST where you distinguish operations by HTTP method (POST/PUT/PATCH/DELETE), in GraphQL you always use HTTP POST — the operation keyword (query vs mutation) tells the server which type of operation it is.

2. Mutation Syntax

A mutation looks like a query but starts with the mutation keyword. The selection set is the fields you want returned from the mutated object — like a built-in refetch:

mutation CreateUser($input: CreateUserInput!) {
  createUser(input: $input) {
    id
    name
    email
    createdAt
  }
}

Variables are passed as a separate JSON object (not inline), just like query variables:

{
  "input": {
    "name": "Alice Smith",
    "email": "alice@example.com",
    "role": "USER"
  }
}

3. Step-by-Step Walkthrough

📋 Live API for this tutorial This walkthrough uses the RedfireForge local test server. Start it with: cd docker/graphql && docker compose up -d, then connect to http://localhost:4010/graphql. Alternatively, any writable GraphQL API (your own service, a sandbox environment) works.

Step 1 — Connect and Introspect

Connect to your writable GraphQL endpoint and click Introspect. The mutation root type will appear in the Schema Explorer.

Step 2 — Write a Create Mutation

In the editor, write:

mutation CreateUser($input: CreateUserInput!) {
  createUser(input: $input) {
    id
    name
    email
  }
}

Step 3 — Add Variables

Open the Variables panel and enter:

{
  "input": {
    "name": "Training User",
    "email": "training@example.com"
  }
}

Step 4 — Execute and Inspect

Click ▶ Execute. The response will contain the newly created user with a server-assigned id:

{
  "data": {
    "createUser": {
      "id": "usr-8f2a1c",
      "name": "Training User",
      "email": "training@example.com"
    }
  }
}

Copy the id value — you'll use it in the next step.

Step 5 — Write an Update Mutation

Add a new tab (click + in the tab bar). Write:

mutation UpdateUser($id: ID!, $input: UpdateUserInput!) {
  updateUser(id: $id, input: $input) {
    id
    name
    email
    updatedAt
  }
}

Variables:

{
  "id": "usr-8f2a1c",
  "input": {
    "name": "Updated Training User"
  }
}

Execute. The response will show the updated name and a new updatedAt timestamp.

Step 6 — Write a Delete Mutation

In another tab or replacing the current query:

mutation DeleteUser($id: ID!) {
  deleteUser(id: $id) {
    success
    message
  }
}

Variables: { "id": "usr-8f2a1c" }. Execute. The response confirms deletion.

4. Mutation Return Payloads

Good GraphQL APIs return a payload object from mutations — not just a boolean. The payload typically contains:

  • The created/updated object (so you don't need a separate fetch)
  • Error details if the mutation partially failed
  • Metadata like affectedCount for bulk operations

Always select at least the id and a human-readable field from the mutation return type so you can confirm what was changed.

5. Inline vs Variable Arguments

StyleExampleWhen to use
Inline (literal)createUser(name: "Alice")One-off manual testing; quick exploration
VariablescreateUser(input: $input) + Variables panelAlways preferred for reuse; required in Collections and Workflow nodes
💡 Use variables for workflow automation When you embed a mutation in a workflow node (graphqlMutation), the variables are injected at runtime using {{variableName}} syntax. This is only possible when the mutation uses variable syntax, not inline literals.

6. Try It Yourself

Exercise 1 — Chain Create → Fetch

After creating a user with a mutation, write a separate query that fetches that user by the ID returned. Verify all fields match.

Exercise 2 — Batch Mutation

If your API supports bulk operations, try a mutation that creates multiple records in one call. Observe how the return payload handles the array of results.

Exercise 3 — Handle a Validation Error

Submit a createUser mutation with an invalid email format (e.g. "not-an-email"). Inspect the errors array in the response. Note that the HTTP status is still 200 — GraphQL validation errors are returned inside the response body, not as HTTP error codes.
