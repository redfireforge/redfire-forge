1. Prerequisites

  1. Redpanda running (plaintext, localhost:19092)
  2. Smoke test dataset loaded: ./docker/kafka/e2e/run-all-smoke.sh plaintext — this seeds all test topics
  3. Local Plaintext cluster Connected in Settings → Kafka
  4. Navigate to Protocols → Kafka → Topics tab

2. Topics Tab Overview

The Topics tab is split into two panels:

  • Left panel: Topic list with search bar, domain chips, topic count badge
  • Right panel: Topic detail (Info / Partitions / Messages tabs) — appears when you select a topic

3. Part 1 — Topic List & Domain Chips

1 Read the Topic Count

The header shows "37 of 37 topics" (with the full smoke-test seed). The count updates dynamically as you filter.

2 Use the Search Bar

  1. Type payment in the search bar
  2. The list filters in real time — only topics containing "payment" are shown
  3. Clear the search to restore all topics

3 Use Domain Chips

Domain chips are automatically extracted from topic name prefixes (e.g., orders.*, payments.*, inventory.*). They appear below the search bar.

  1. Click the orders chip — the list filters to only orders.* topics
  2. The count badge updates to show matching count
  3. Click the chip again to deselect and show all topics
  4. Click multiple chips to OR-filter (shows topics matching any selected domain)
💡 Domain Chip Strategy In a production environment with hundreds of topics, domain chips are invaluable for navigation. Topic naming conventions like domain.aggregate.event (e.g., orders.created, orders.processed) allow instant filtering by business domain.

4. Part 2 — Partition Metadata

4 Select a Topic

  1. Click orders.events in the topic list
  2. The right panel opens showing the Info tab

5 Read Topic Info

The Info tab shows:

FieldDescription
Topic NameFull topic name including prefix
PartitionsNumber of partitions (default: 1 for Redpanda dev mode)
Replication FactorNumber of replicas (1 for single-broker)
CreatedBroker-reported creation time (if available)

6 Open the Partitions Tab

  1. Click the Partitions tab in the right panel
  2. The partitions table shows all partitions with their metadata

Partition Table Column Reference

ColumnMeaning
PartitionZero-indexed partition number (0, 1, 2, ...)
LeaderBroker ID of the current leader for this partition
ReplicasComma-separated list of broker IDs holding replicas
ISRIn-Sync Replicas — replicas fully caught up to the leader
EarliestLowest available offset (messages before this are deleted)
LatestNext offset to be written (= total message count if retention is infinite)
MessagesLatest − Earliest = approximate count of retained messages
🟡 Understanding Offsets Earliest offset advances when old messages are deleted (due to retention policy). Latest offset is always the next assigned offset — it increases monotonically. Messages = Latest − Earliest is an estimate; it may not reflect exact counts when log compaction is enabled.

5. Part 3 — Reading Messages from Topics

7 Open the Messages Tab

  1. Click the Messages tab in the right panel of orders.events
  2. You see a consume form at the top and an empty message table below

8 Fetch Messages

  1. Set Start Position to Earliest
  2. Set Max Messages to 10
  3. Click Consume
  4. Messages appear in the table

Messages Table Column Reference

ColumnDescription
#Sequential result row number (1, 2, 3...)
OffsetKafka partition offset of this message
PartitionPartition number the message belongs to
TimestampMessage create time (broker-assigned); NOT shown in standalone Consume tab
KeyMessage key (truncated to 40 chars if long)
ValueMessage body (truncated; click row for full content)

9 Click a Message Row for Details

  1. Click any row — a detail drawer opens on the right side
  2. Sections: Value (formatted JSON), Key, Headers, Metadata (offset, partition, timestamp)
  3. Click Copy Value to copy the full JSON to clipboard

6. Part 4 — Debugging Event Flows

The Topic Explorer is your primary debugging tool for event-driven workflows. Use it to:

Find Messages Published by a Workflow

  1. Run a workflow that publishes to orders.created
  2. Open Topic Explorer → orders.created → Messages tab
  3. Set Start Position to Latest and Max Messages to 5 → Consume
  4. Verify the message from your workflow run appears (check key, body, headers)

Trace a Full Pipeline

  1. For the Kafka Event Pipeline sample: check both orders.created (trigger) and orders.processed (result)
  2. Compare the timestamps to see processing latency
  3. Check the pipeline=order-processor header in the result message

8. Try It Yourself

  1. Find the oldest message: open orders.events → Messages tab → set Start Position Earliest → Consume. What is the earliest offset? How many messages total are in the topic?
  2. Domain filter exploration: how many distinct domain prefixes does your broker have? Use the domain chips to count them. Which domain has the most topics?
  3. Partition inspection: open any topic with more than 1 partition. Check the Partitions tab — are all replicas in ISR? What does it mean if a broker ID is in Replicas but not ISR?
  4. Real-time trace: open orders.created → Messages tab → Latest position. In another tab, publish a message via the Publish tab. Refresh the Messages consume — does the new message appear?
