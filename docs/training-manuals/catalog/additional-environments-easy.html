1. What Are Additional Environments?

Additional environments (also called "custom environments") are deployment targets that belong to a single microservice rather than being shared globally across all services.

Global vs. Additional Environments

TypeScopeExampleVisual
Global Available to all microservices dev, staging, production Standard blue badge
Additional Specific to one microservice perf-env, hotfix-qa, canary + amber badge

When to Use Additional Environments

  • Performance testing — A dedicated perf environment for a single service
  • Hotfix QA — Temporary environment for validating a specific fix
  • Canary deployments — A canary slice that only one service uses
  • Partner integrations — External partner sandbox for one API
  • Feature flags — An env with specific feature flags enabled
Key Benefit Additional environments keep your global environment list clean while still supporting specialized deployment targets that only one service needs.

2. Creating Additional Environments

Step 1: Open Microservice Configuration

  1. Go to Settings (gear icon in sidebar)
  2. Navigate to the Microservices section
  3. Click on the microservice that needs the custom environment

Step 2: Add the Environment

  1. Scroll to the Additional Environments section
  2. Type the environment name (e.g., perf-env)
  3. Click + Add
  4. Enter the base URL for that environment
  5. Click Save
Microservice: user-service

Global environments:
  dev:     https://dev.api.example.com/users
  staging: https://staging.api.example.com/users
  prod:    https://api.example.com/users

Additional environments:
  perf-env:   https://perf.api.example.com/users    ← only for user-service
  hotfix-qa:  https://hotfix.api.example.com/users  ← only for user-service

Page Headers

When an additional environment is selected, the environment badge in page headers (Feature Groups, Test Runner, Parameterized Runner) changes to:

  • Amber/orange background with dashed border
  • A + suffix indicator showing it's non-global
  • The parent microservice name in parentheses in dropdowns

4. Using Additional Environments

In Environment Dropdown

When selecting environments from any dropdown in the application, additional environments appear below a divider with their parent microservice name:

Environment: [Select ▼]
  ├── dev
  ├── staging
  ├── production
  ├── ─ ─ ─ ─ ─ ─ ─ ─
  ├── perf-env (user-service)       ← amber
  └── hotfix-qa (user-service)      ← amber

In Test Runner

  1. Select the additional environment from the environment dropdown
  2. The header badge turns amber with a + indicator
  3. Only the parent microservice is available for that environment
  4. Run tests as normal — URL resolution uses the additional env's base URL

In Workflow Runner

Additional environments work the same as global environments in workflow execution. The services registry resolves URLs from the additional environment's configured base URL.

5. Use Cases

Performance Testing

user-service:
  perf-env: https://perf.internal.company.com/users
  
  → Run load tests against perf-env without affecting global envs
  → Other services still use dev/staging normally

Hotfix Validation

payment-gateway:
  hotfix-7234: https://hotfix-7234.preview.company.com/payments
  
  → Validate the fix in isolation
  → Delete the environment once merged

Partner Sandbox

notification-service:
  partner-sandbox: https://sandbox.partner-api.com/notifications
  
  → Test against partner's sandbox
  → Only notification-service needs this env

6. Tips

  • Keep names descriptive — Include the purpose: perf-env, hotfix-7234, partner-sandbox
  • Clean up when done — Delete temporary environments after hotfix/feature validation
  • Use for isolation — When only one service needs a target, don't pollute the global list
  • Check the amber indicator — If you see amber, you're testing against a service-specific environment
