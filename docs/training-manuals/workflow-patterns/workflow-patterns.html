1. What Is a Workflow?

A workflow in RedfireForge is a visual, directed graph of nodes connected by edges. Each node performs a specific action — sending an HTTP request, evaluating a condition, setting a variable, delaying execution, forking into parallel branches, or invoking a child workflow. The workflow engine executes nodes in topological order, following edges from start to end.

Start → HTTP "Get Users" → Condition "Status OK?" → HTTP "Get Details" → End

Workflows are built on the ReactFlow canvas with drag-and-drop nodes. The execution engine (graphRunner.ts) traverses the graph, resolving variables, running HTTP requests, and tracking pass/fail state for every node.

Key Data Structures

// Core workflow shape
interface Workflow {
  id: string;
  name: string;
  description?: string;
  variables: Record<string, string>;
  nodes: WorkflowNode[];
  edges: WorkflowEdge[];
  services?: WorkflowService[];
  errorConfig?: WorkflowErrorConfig;
}

// Each node on the canvas
interface WorkflowNode {
  id: string;
  type: WorkflowNodeType;  // 'http' | 'condition' | 'delay' | ...
  position: { x: number; y: number };
  data: WorkflowNodeData;  // Type-specific payload
}

// Each connection between nodes
interface WorkflowEdge {
  id: string;
  source: string;     // Source node ID
  target: string;     // Target node ID
  sourceHandle?: string; // e.g. 'true'/'false' for conditions
  label?: string;
}

3. How the Engine Executes a Workflow

The execution engine in graphRunner.ts follows a topological traversal pattern:

  1. Initialize — Create a VariableContext with initial variables and environment layer. Register all workflow nodes for label-based scoped references.
  2. Find start nodes — Prefer nodes of type start, webhook, or schedule. Fall back to nodes with no incoming edges.
  3. Set all nodes to pending — Every node begins in the pending state.
  4. Visit recursively — For each node, dispatch to the appropriate handler (HTTP, Condition, Delay, etc.). After handling, follow outgoing edges to visit the next nodes.
  5. Join barrier — Join nodes track how many branches have arrived vs. how many are expected. Execution only continues past a Join when all branches have completed.
  6. Error handling — If any node fails and a workflow-level error handler is configured, the engine runs the error handler subgraph.
  7. Completion — Mark unvisited End nodes based on overall pass/fail. Report results, duration, and final variable state.

4. Variable System

The VariableContext class manages all variables during workflow execution. Variables can be referenced in any text field using {{variableName}} interpolation.

Three Resolution Layers

When resolving {{name}}, the engine checks layers in priority order:

  1. Extracted (highest) — Variables set during execution (HTTP response extractions, SetVariable assignments)
  2. Manual — Initial variables defined on the Start node or workflow settings
  3. Environment (lowest) — Environment-layer variables (e.g., baseUrl from harness settings)

Per-Node Scoping

Variables can be scoped to a specific node using ctx.setForNode(nodeId, key, value). Access scoped variables with:

{{node:"Step Label".variableName}}
{{node:<nodeId>.variableName}}

8. Recommended Learning Path

  1. Start with Phase 1 — Build a simple 3-node HTTP chain. Understand Start/End, HTTP nodes, and variable extraction.
  2. Add complexity with Phase 2 — Introduce condition branches, then try a fork/join for parallel calls.
  3. Phase 3 — Learn loops for batch processing and error handlers for resilient workflows.
  4. Phase 4 — Compose reusable child workflows, handle webhooks, and use the debugger to step through complex flows.
