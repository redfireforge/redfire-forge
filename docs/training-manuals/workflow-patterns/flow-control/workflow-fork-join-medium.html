1. What Is Fork/Join?

The Fork/Join pattern splits execution into multiple branches that run simultaneously, then waits at a barrier until all branches have completed. This is essential for workflows that need to make parallel API calls — like checking health across multiple services or deploying to multiple regions at once.

Real-world scenario: "Multi-Region Health Check — Parallel Pings"

You need to verify that your API is healthy across 3 regions (US, EU, APAC). Instead of checking them one-by-one (3× slower), you fork into 3 parallel requests and join when all have responded.

Start → Fork

   ├→ GET /health (US) ─┐
   ├→ GET /health (EU) ─┤→ Join → Aggregate → End
   └→ GET /health (APAC)┘

Key Concepts

  • Fork — Splits execution into parallel branches. Each branch gets a unique threadId.
  • Join — Barrier node that waits until all incoming branches have arrived before proceeding.
  • Thread IDs — Each fork branch is identified by a unique ID for tracking and debugging.
  • Waiting state — The Join node displays "waiting (2/3)" as branches arrive.

Prerequisites

  • Completed: Phase 1 manuals and Condition/Switch manuals
  • Comfortable with HTTP nodes, variable extraction, and console log analysis

2. Fork and Join Node Data Models

interface ForkNodeData {
  label: string;
}

interface JoinNodeData {
  label: string;
}

Both nodes are structurally simple — they have only a label. Their behavior comes entirely from the edge topology and the engine's handling of parallel execution.

Fork Behavior

The handleForkNode handler:

  1. Finds all outgoing edges from the Fork node.
  2. Runs all target nodes in parallel using Promise.all().
  3. Each branch receives a unique threadId (e.g., "fork-abc-0", "fork-abc-1", "fork-abc-2").
// handleForkNode — simplified
async function handleForkNode(nodeId, data, context) {
  const outEdges = context.outgoing.get(nodeId) || [];
  // Run ALL branches in parallel
  await Promise.all(
    outEdges.map((edge, i) =>
      context.visit(edge.target, `${context.threadId}-fork-${i}`)
    )
  );
}

Join Behavior

The handleJoinNode uses a barrier counter:

  1. Each time a branch arrives, increment joinArrived.get(nodeId).
  2. Compare against incomingCount.get(nodeId) — the total number of incoming edges.
  3. If arrived < expected, display waiting state and return (don't proceed yet).
  4. When arrived === expected, all branches have joined — proceed to outgoing edges.
// Join barrier logic — simplified
const arrived = joinArrived.get(nodeId) + 1;
joinArrived.set(nodeId, arrived);
const expected = incomingCount.get(nodeId);

if (arrived < expected) {
  callbacks.onNodeStateChange(nodeId, 'running');
  log(`* [${label}] waiting (${arrived}/${expected})`);
  return; // Wait for more branches
}

// All branches arrived!
log(`* [${label}] All branches joined`);
visitOutgoing(nodeId); // Continue workflow

3. Thread IDs and Parallel Tracking

When a Fork splits execution, each branch gets a unique threadId. This allows the engine to track which branch is executing which node — critical for debugging and console log analysis.

BranchThread IDNodes Visited
Branch 0main-fork-0HTTP "US Health" → (arrives at Join)
Branch 1main-fork-1HTTP "EU Health" → (arrives at Join)
Branch 2main-fork-2HTTP "APAC Health" → (arrives at Join)

// Branch 1
> [thread:main-fork-1] GET https://eu.api.example.com/health
< [thread:main-fork-1] 200 OK (142ms)

// Branch 2
> [thread:main-fork-2] GET https://apac.api.example.com/health

// Join waiting states
* [Join] waiting (1/3) — branch 0 arrived
* [Join] waiting (2/3) — branch 1 arrived

< [thread:main-fork-2] 200 OK (203ms)
* [Join] All branches joined (3/3)
📘 Parallel ≠ Concurrent "Parallel" in this context means all branches are initiated simultaneously via Promise.all(). The actual concurrency depends on the JavaScript event loop. HTTP requests will run truly concurrently (async I/O), but CPU-bound operations will interleave.

4. Join Waiting State Display

While the Join node is waiting for branches, the canvas shows a real-time counter:

StateDisplayVisual
No branches arrivedwaiting (0/3)Dimmed, pending
1 of 3 arrivedwaiting (1/3)Blue pulse, running
2 of 3 arrivedwaiting (2/3)Blue pulse, running
All arrivedAll branches joinedGreen border, pass

What Happens If a Branch Fails?

If one branch's HTTP node fails, the branch still "arrives" at the Join node. The Join will eventually proceed once all branches have arrived — but the overall allPassed flag will be false. You can use a Condition node after the Join to check results and handle failures.

Interaction with Condition/Switch Branches

If a condition node before the Join skips one of the fork branches, markSubtreeSkipped() decrements the Join's incomingCount. This means the Join doesn't wait forever for a skipped branch — it adjusts its expected count.

5. Walkthrough: The Gallery Sample

The sample-workflow-deploy-orchestrator demonstrates a real-world Fork/Join pattern for multi-region deployment.

Start → Validate Version → Fork

   ├→ Smoke Test ──┐
   └→ Feature Flags─┤→ Join → Deploy (multi-instance) → Success?

What This Workflow Does

  1. Start — Sets version, regions (JSON array), rollbackWorkflowId, successThreshold.
  2. Validate Version — HTTP call to verify the build artifact exists.
  3. Fork — Splits into 2 parallel pre-checks: smoke test and feature flag validation.
  4. Join — Waits for both pre-checks to complete.
  5. Deploy — Sub-workflow with multi-instance mode: deploys to each region in the regions array in parallel.
  6. Condition — Checks if enough regions succeeded (above successThreshold). If not, triggers a rollback sub-workflow.

6. Building a Fork/Join Workflow

Build a parallel health check workflow that pings 3 different API endpoints simultaneously.

Step 1: Create the Workflow

  1. New workflow: "Parallel Health Check".
  2. Add Start → Fork → 3 HTTP nodes → Join → LogDebug → End.

Step 2: Add the Fork Node

  • Label: Fork: Check All Services
  • Connect 3 outgoing edges to 3 different HTTP nodes.

Step 3: Configure 3 HTTP Nodes

NodeURLExtract
Check Usershttps://jsonplaceholder.typicode.com/users/1usersStatus ← httpStatus
Check Postshttps://jsonplaceholder.typicode.com/posts/1postsStatus ← httpStatus
Check Commentshttps://jsonplaceholder.typicode.com/comments/1commentsStatus ← httpStatus

Step 4: Add the Join Node

  • Label: Join: Wait for All
  • Connect all 3 HTTP nodes' output edges to this Join node.

Step 5: Add a LogDebug After Join

  • Message: All checks complete! Users: {{usersStatus}}, Posts: {{postsStatus}}, Comments: {{commentsStatus}}
  • Enable Snapshot Variables.

Step 6: Run and Observe

  1. Click Run.
  2. Watch all 3 HTTP nodes pulse blue simultaneously.
  3. Watch the Join node show waiting (1/3), waiting (2/3), then All branches joined.
  4. Total execution time should be approximately equal to the slowest branch, not the sum of all three.

7. Variable Sharing Across Branches

All fork branches share the same VariableContext. This means:

  • Variables extracted in one branch are visible to the Join node and all subsequent nodes.
  • If two branches set the same variable name, the last one to complete wins (race condition).
  • Use unique variable names per branch to avoid conflicts (e.g., usersStatus vs. postsStatus).
⚠ Avoid Variable Name Conflicts Since branches run in parallel and share the same variable context, never use the same extraction variable name in multiple branches. Use descriptive, branch-specific names like userResponse, postResponse, commentResponse.

Aggregating Results After Join

After the Join node, use a SetVariable or LogDebug node to combine results from all branches:

// SetVariable after Join
assignments: [
  {
    name: "healthReport",
    expression: "Users: {{usersStatus}}, Posts: {{postsStatus}}, Comments: {{commentsStatus}}"
  },
  {
    name: "allHealthy",
    expression: "{{$if({{usersStatus}} == 200 && {{postsStatus}} == 200 && {{commentsStatus}} == 200, true, false)}}"
  }
]

8. Exercises

Exercise 1: Fork into 3 Parallel HTTP Requests

Goal: Build a fork/join that sends 3 requests simultaneously to different endpoints.

  1. Create a workflow: Start → Fork → 3 HTTP GETs → Join → End.
  2. Use JSONPlaceholder endpoints: /users/1, /posts/1, /todos/1.
  3. Extract a unique variable from each branch.
  4. Run and verify all 3 nodes execute in parallel (check console timestamps).

Exercise 2: Observe Join Waiting Behavior

Goal: See the join barrier in action with different response times.

  1. Extend Exercise 1 — add a Delay node (2000ms) on one branch before its HTTP call.
  2. Run and watch the Join show waiting (1/3) and waiting (2/3) while the delayed branch is still running.
  3. Verify total execution time is ~2 seconds (dominated by the slowest branch).

Exercise 3: Aggregate Results After Join

Goal: Use SetVariable after Join to combine branch results.

  1. After the Join, add a SetVariable node with:
    • report = Users: {{userStatus}}, Posts: {{postStatus}}, Todos: {{todoStatus}}
  2. Add a LogDebug node: Health Report: {{report}}, enable Snapshot Variables.
  3. Run and verify the aggregated report contains all 3 status values.
