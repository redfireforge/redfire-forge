1. What Is a Switch Node?

A Switch node evaluates a single expression and routes execution to the matching case branch. It's the workflow equivalent of a switch/case statement — ideal when you need 3 or more branches based on the same value.

Real-world scenario: "API Response Router — Different Handlers per Status Class"

After calling an API, you want to route to different handlers based on the response status class: 2xx → process normally, 4xx → handle client error, 5xx → trigger retry logic, anything else → log unknown status.

HTTP Request → Switch: Status Class

"2xx" → Process Response
"4xx" → Handle Client Error
"5xx" → Retry Logic
default → Log Unknown

Switch vs. Condition — When to Use Each

2. The Switch Node Data Model

interface SwitchNodeData {
  label: string;
  expression: string;       // The value to match — supports {{var}}
  cases: SwitchCase[];      // Array of case branches
}

interface SwitchCase {
  id: string;       // Unique case identifier
  value: string;    // Match value (compared to expression)
  label?: string;   // Optional display label on edge
}

How Cases Work

Each case has a value that is compared against the resolved expression. The first matching case wins. If no case matches, the default branch is taken (an edge with sourceHandle: 'default').

// Switch configuration: route by HTTP status class
{
  label: "Status Router",
  expression: "{{statusClass}}",
  cases: [
    { id: "c1", value: "2xx", label: "Success" },
    { id: "c2", value: "4xx", label: "Client Error" },
    { id: "c3", value: "5xx", label: "Server Error" }
  ]
}
💡 Variable Interpolation The expression field supports {{variable}} interpolation. You can compute the switch value upstream (e.g., in a SetVariable node) and reference it here.

3. How the Engine Handles Switch

The handleSwitchNode handler follows this process:

  1. Resolve expression — Pass expression through ctx.resolve() to replace {{var}} placeholders.
  2. Find matching case — Iterate through cases and find the first where case.value === resolvedExpression.
  3. Route to matching edge — Follow the outgoing edge whose sourceHandle matches the case id.
  4. Default fallback — If no case matches, follow the edge with sourceHandle: 'default'.
  5. Skip non-matching branches — Call markSubtreeSkipped() on all nodes reachable from non-matching case edges.

Console Log Output

// Matching case found:
* [Status Router] switch: "2xx" → matched case "Success"

// No match, using default:
* [Status Router] switch: "3xx" → no match, using default branch

// No default configured:
* [Status Router] switch: "3xx" → no match, no default branch

Edge Mapping

Each case maps to outgoing edges via sourceHandle:

4. Configuring a Switch Node

  1. Add a Switch node from the node palette.
  2. Double-click to open the config modal.
  3. Set the Expression — the value to match (supports {{var}}).
  4. Add Cases — each with a match value and optional label.
  5. Connect edges from each case handle to the target nodes.
  6. Optionally, connect a default edge for unmatched values.

Canvas Display

The Switch node on the canvas shows:

  • The expression in the node body.
  • Multiple output handles — one per case plus a default handle.
  • Edge labels showing the case value or label.
⚠ Always Add a Default Branch Without a default branch, if the expression resolves to an unexpected value, no branch is taken and the workflow may end prematurely. Always add a default branch for safety, even if it just logs a warning.

5. Walkthrough: API Response Router

Build a workflow that routes API responses to different handlers based on status class.

Step 1: Set Up the Workflow

  1. Create a new workflow: "API Response Router".
  2. Add Start → HTTP node → SetVariable → Switch → branch nodes → End.

Step 2: HTTP Node

  • Label: Call API
  • Method: GET
  • URL: https://jsonplaceholder.typicode.com/posts/1

Step 3: SetVariable — Compute Status Class

Since the Switch does equality matching, compute a status class variable:

assignments: [
  {
    name: "statusClass",
    expression: "{{$if({{httpStatus}} >= 200 && {{httpStatus}} < 300, 2xx, {{$if({{httpStatus}} >= 400 && {{httpStatus}} < 500, 4xx, 5xx)}})}}"
  }
]

Or more simply, just use the raw status for the switch:

assignments: [
  { name: "statusCode", expression: "{{httpStatus}}" }
]

Step 4: Switch Configuration

  • Expression: {{statusCode}}
  • Cases:
    • 200 → LogDebug "Success — processing response"
    • 404 → LogDebug "Not found — creating resource"
    • 500 → LogDebug "Server error — retrying"
  • Default → LogDebug "Unexpected status: {{statusCode}}"

Step 5: Run and Test

With /posts/1, the "200" case is matched. Change the URL to test different paths:

  • /posts/99999 → likely returns 200 from JSONPlaceholder (it returns an empty object), so test with a different API for true 404 behavior.
  • Default branch catches any unexpected status codes.

6. Comparing Switch vs. Nested Conditions

Here's the same 3-way routing logic implemented both ways:

With Nested Conditions (verbose)

Condition: status==200?
Yes → Process
No → Condition: status==404?
        Yes → Create
        No → Error

3 nodes, complex nesting, hard to extend.

With Switch (clean)

Switch: {{statusCode}}

"200" → Process    "404" → Create    default → Error

1 node, flat structure, easy to add more cases.

💡 Rule of Thumb Use Condition for 2-way (if/else). Use Switch for 3+ way. If you need complex operators (contains, regex, greater-than), use Condition — Switch only supports equality matching.

7. Exercises

Exercise 1: Three-Way Switch

Goal: Build a switch that routes to 3 different HTTP nodes based on a variable.

  1. Create a workflow with Start → SetVariable (set action to "create") → Switch.
  2. Cases: "create" → HTTP POST, "read" → HTTP GET, "delete" → HTTP DELETE.
  3. Add End nodes after each HTTP node.
  4. Run and verify the "create" branch executes.
  5. Change the SetVariable to "read" and run again — verify the GET branch executes.

Exercise 2: Default Branch

Goal: Add a default branch for unmatched cases.

  1. Extend Exercise 1 — add a default edge to a LogDebug node: "Unknown action: {{action}}".
  2. Set the action to "update" (not in the cases list).
  3. Run and verify the default branch executes with the log message.

Exercise 3: Compare with Nested Conditions

Goal: Build the same 3-way logic using nested Condition nodes, then compare.

  1. Create a duplicate workflow using nested conditions instead of Switch.
  2. Condition 1: {{action}} == create. Yes → POST. No → Condition 2.
  3. Condition 2: {{action}} == read. Yes → GET. No → DELETE.
  4. Compare the two workflows — which is easier to understand? Easier to extend?
