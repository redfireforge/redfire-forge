1. What Is a Condition Node?

A Condition node evaluates a boolean expression and routes execution to one of two branches: Yes (true) or No (false). It's the workflow equivalent of an if/else statement.

Real-world scenario: "Order Processing — Express vs Standard Shipping"

After fetching an order, you check if the customer selected express shipping. If yes, route to a fast-track fulfillment workflow. If no, route to the standard shipping path.

GET /order → Condition: Express?

Yes → Express Fulfillment
No  → Standard Shipping

Prerequisites

  • Completed: Phase 1 manuals (HTTP Chaining, Delays, Variables)
  • Understand {{variable}} interpolation and HTTP response extraction

2. The Condition Node Data Model

interface ConditionNodeData {
  label: string;
  left: string;      // Left operand — supports {{var}}
  operator: string;  // Comparison operator
  right: string;     // Right operand — supports {{var}}
}

Supported Operators

OperatorMeaningExample
==Equals (string comparison)"200" == "200" → true
!=Not equals"404" != "200" → true
>Greater than (numeric)"10" > "5" → true
>=Greater than or equal"10" >= "10" → true
<Less than (numeric)"3" < "5" → true
<=Less than or equal"3" <= "3" → true
containsString contains substring"hello world" contains "world" → true
not-containsString does not contain"hello" not-contains "xyz" → true
regexMatches regex pattern"user@test.com" regex "^[\\w@.]+" → true
⚠ String Comparison All values are strings in the variable system. For numeric comparisons (>, <, etc.), the engine parses both sides as numbers. If parsing fails, it falls back to string comparison.

3. How Conditions Are Evaluated

The handleConditionNode handler follows this process:

  1. Resolve operands — Both left and right are passed through ctx.resolve() to replace {{var}} placeholders.
  2. Evaluate — Call evaluateCondition(data, ctx) which calls compareValues(left, right, operator).
  3. Route — Follow outgoing edges with sourceHandle: 'true' (Yes branch) or sourceHandle: 'false' (No branch).
  4. Skip untaken branch — Call markSubtreeSkipped() on all nodes reachable from the untaken branch. These nodes transition to the skipped state (gray, dashed border).
// evaluateCondition internals
function evaluateCondition(data: ConditionNodeData, ctx: VariableContext): boolean {
  const left = ctx.resolve(data.left);    // e.g., "{{httpStatus}}" → "201"
  const right = ctx.resolve(data.right);  // e.g., "201"
  return compareValues(left, right, data.operator);  // "201" == "201" → true
}

Console Log Output

* [Express Shipping?] condition: "express" == "express" → true (Yes branch)

// Or when false:
* [Express Shipping?] condition: "standard" == "express" → false (No branch)

Subtree Skipping

When a branch is not taken, markSubtreeSkipped() recursively marks all downstream nodes as skipped. This is important because:

  • Skipped nodes are never executed — no HTTP requests are sent, no variables are set.
  • Skipped nodes show a gray, dashed border on the canvas.
  • If the untaken branch leads to a Join node, the Join's expected count is decremented (so it doesn't wait forever for the skipped branch).

4. Edge Configuration: Yes/No Branches

A Condition node has two output handles:

HandlesourceHandleLabelTaken When
Top/Right"true"YesCondition evaluates to true
Bottom/Right"false"NoCondition evaluates to false

When connecting edges on the canvas, drag from the appropriate handle to route each branch to different nodes.

Multiple Edges per Branch

Each branch can have multiple outgoing edges. When a branch is taken, all edges from that handle are followed — effectively creating parallel execution within a branch.

// Example: Yes branch leads to both "Send Email" AND "Update DB"
edges: [
  { source: "condition-1", target: "send-email",  sourceHandle: "true" },
  { source: "condition-1", target: "update-db",   sourceHandle: "true" },
  { source: "condition-1", target: "log-skipped", sourceHandle: "false" }
]

6. Building a Condition Workflow

Let's build a workflow that checks the HTTP status code and takes different actions for success vs. failure.

Step 1: Create the Workflow

  1. New workflow: "Status Code Router".
  2. Add Start → HTTP node → Condition → two branches → End.

Step 2: Configure the HTTP Node

  • Label: Get Post
  • Method: GET
  • URL: https://jsonplaceholder.typicode.com/posts/1

Step 3: Configure the Condition

  • Label: Status OK?
  • Left: {{httpStatus}}
  • Operator: ==
  • Right: 200

Step 4: Add Branch Nodes

  • Yes branch: LogDebug → "Success! Post retrieved."
  • No branch: LogDebug → "Error! Status: {{httpStatus}}"

Step 5: Run and Observe

The Yes branch executes and turns green; the No branch is skipped (gray, dashed). Change the URL to /posts/99999 to trigger a 404 and see the No branch execute instead.

7. Advanced: Multi-Level Conditions

You can chain conditions to create multi-way branching (before learning the Switch node).

HTTP Request → Status 2xx?

Yes → Process Response
No  → Status 404?

         Yes → Create Resource
         No  → Error Handler

This creates a 3-way branch: success → process, 404 → create, other → error. The No branch of the first condition leads to a second condition node.

📘 When to Use Switch Instead If you need 3+ branches, consider using a Switch node instead of nesting conditions. Switch nodes are cleaner for multi-way routing. See the next manual: Switch Multi-Way Routing.

8. Using Variables in Conditions

Both left and right operands support {{variable}} interpolation:

// Compare two extracted variables
left:     "{{actualCount}}"
operator: ">="
right:    "{{expectedCount}}"

// Use contains to check response body
left:     "{{responseBody}}"
operator: "contains"
right:    "error"

// Regex match on an extracted field
left:     "{{userEmail}}"
operator: "regex"
right:    "^[\\w.]+@company\\.com$"

9. Exercises

Exercise 1: Status Code Routing

Goal: Create a condition that routes based on HTTP status code.

  1. Create a workflow: Start → HTTP GET → Condition → Yes: LogDebug "Success" / No: LogDebug "Failure" → End.
  2. Condition: {{httpStatus}} == 200.
  3. Run with a valid URL — verify Yes branch executes.
  4. Change to an invalid URL (e.g., /posts/99999) — verify No branch executes.

Exercise 2: Three-Way Branching

Goal: Build a 3-way branch: success → process, 404 → create, 5xx → error handler.

  1. After the first HTTP call, add a Condition: {{httpStatus}} == 200.
  2. Yes → LogDebug "Processing response".
  3. No → second Condition: {{httpStatus}} == 404.
  4. Yes → LogDebug "Resource not found — creating".
  5. No → LogDebug "Server error: {{httpStatus}}".

Exercise 3: Body Content Check

Goal: Use contains operator to check response body content.

  1. Create a workflow that GETs a post from JSONPlaceholder.
  2. Add a Condition: {{responseBody}} contains "userId".
  3. Yes → LogDebug "Valid post response".
  4. No → LogDebug "Unexpected response format".
  5. Run and verify the Yes branch is taken (all posts have userId).
