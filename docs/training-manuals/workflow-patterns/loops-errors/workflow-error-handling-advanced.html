1. Two Levels of Error Handling

RedfireForge provides error handling at two levels:

LevelScopePurpose
Node-Level Error Handler node wrapping a subgraph Retry, catch, and continue for specific steps
Workflow-Level WorkflowErrorConfig on the workflow itself Global fallback when any node fails

Both levels can coexist — a node-level handler catches local failures, while the workflow-level handler catches anything that slips through.

2. Error Handler Node

The Error Handler node wraps a subgraph in a try/catch pattern. It has three output handles:

┌────────────────────────────────────┐
│       🛡️ Error Handler           │
│  Retry ×2 (fixed 1000ms)        │
│  Catch all · continue           │
└──────┬──────────┬──────────┬───────┘
     Body      Catch      Done
      ↓          ↓          ↓
  (try this)  (on failure)  (always)
  • Body (25%) — The subgraph to protect. These nodes are retried on failure.
  • Catch (50%) — Runs only when all retries are exhausted and the body still fails. Error variables are available here.
  • Done (75%) — Runs after either success or catch completion. Always executes.

ErrorHandlerNodeData Type

export type ErrorFilter =
  | 'all'               // catch any error
  | 'http-error'        // HTTP 4xx/5xx
  | 'assertion-failure' // assertion checks failed
  | 'network-error';    // connection refused, timeout, etc.

export type RetryBackoffStrategy = 'fixed' | 'exponential';

export interface ErrorHandlerNodeData {
  label: string;
  errorFilter: ErrorFilter;       // which errors to catch
  retryCount: number;             // max retries (default: 2)
  retryDelayMs: number;           // delay between retries (default: 1000)
  retryBackoff: RetryBackoffStrategy;  // fixed or exponential
  retryTimeoutMs: number;         // overall timeout, 0 = unlimited
  continueOnError: boolean;       // true = workflow continues after catch
}

3. Error Classification

When a node in the body fails, the engine classifies the error type:

function classifyErrorType(result: RequestResult): string {
  if (result.httpStatus === 0)          return 'network-error';
  if (result.httpStatus >= 400)         return 'http-error';
  if (result.failureDetails?.length > 0) return 'assertion-failure';
  return 'http-error';
}

function matchesErrorFilter(errorType: string, filter: string): boolean {
  if (filter === 'all') return true;
  return errorType === filter;
}

Error Filter Examples

FilterCatchesIgnores
allEverythingNothing
http-errorHTTP 400, 401, 500, etc.Network errors, assertion failures
assertion-failureAssertion check failuresHTTP errors, network errors
network-errorECONNREFUSED, ETIMEDOUT, DNS errorsHTTP errors, assertion failures
💡 When to Use Specific Filters Use http-error to retry flaky servers (503s) without retrying on bad requests (400s are usually not transient). Use network-error for resilience against connectivity issues. Use all as a catch-all safety net.

4. Retry Strategies

Fixed Backoff

Wait the same duration between each retry:

{ retryCount: 3, retryDelayMs: 1000, retryBackoff: 'fixed' }
// Attempt 1 → fail → wait 1000ms
// Attempt 2 → fail → wait 1000ms
// Attempt 3 → fail → wait 1000ms
// Attempt 4 → fail → enter Catch path

Exponential Backoff

Double the delay after each failure:

{ retryCount: 3, retryDelayMs: 1000, retryBackoff: 'exponential' }
// Attempt 1 → fail → wait 1000ms  (1000 × 2⁰)
// Attempt 2 → fail → wait 2000ms  (1000 × 2¹)
// Attempt 3 → fail → wait 4000ms  (1000 × 2²)
// Attempt 4 → fail → enter Catch path

Retry Timeout

The retryTimeoutMs field sets an overall time limit for all retry attempts:

{ retryCount: 10, retryDelayMs: 500, retryTimeoutMs: 5000 }
// Retries stop after 5 seconds, even if retryCount isn't exhausted
// 0 = no timeout (default)

Badge Display

// retryCount > 0:
"Retry ×2 (fixed 1000ms)"    or    "Retry ×3 (exp 500ms)"

// retryCount = 0:
"No retry"

// Plus filter + continue:
"Catch all · continue"       or    "http error"

5. Error Variables

When the body fails and execution enters the Catch path, six error variables are injected:

VariableTypeDescription
{{error.message}}stringHuman-readable error description
{{error.statusCode}}stringHTTP status code (0 for network errors)
{{error.nodeId}}stringID of the node that failed
{{error.nodeLabel}}stringLabel of the node that failed
{{error.retryCount}}stringNumber of retries attempted
{{error.type}}stringClassification: http-error, network-error, assertion-failure

These variables are available to all nodes in the Catch subgraph:

// Example: Catch path sends a notification
// HTTP POST to Slack webhook:
{
  "text": "⚠️ Node '{{error.nodeLabel}}' failed after {{error.retryCount}} retries. Status: {{error.statusCode}}. Error: {{error.message}}"
}

continueOnError Behavior

SettingAfter Catch PathWorkflow Result
trueState → pass, execute Done edgesWorkflow continues normally
falseState → fail, execute Done edgesWorkflow marked as failed
⚠️ Success Skips Catch If the body succeeds (on the first attempt or after a retry), the entire Catch subgraph is skipped via markSubtreeSkipped. Only the Done edges execute after success.

6. Workflow-Level Error Handling

Independent of node-level handlers, the workflow itself can define a global error strategy:

export type WorkflowErrorMode = 'stop' | 'continue' | 'run-handler';

export interface WorkflowErrorConfig {
  mode: WorkflowErrorMode;
  handlerEntryNodeId?: string;   // entry node for error subgraph
  errorVariable?: string;        // default: 'error.message'
}

Error Modes

ModeBehavior
stopStop execution on first failure (default)
continueContinue executing remaining nodes despite failures
run-handlerAfter all nodes finish, run a dedicated error handler subgraph if any failed

run-handler Mode

When mode is run-handler, the engine waits for all nodes to finish, then checks for failures:

// After all nodes visited:
if (failedResults.length > 0 && errorConfig.mode === 'run-handler') {
  const errVar = errorConfig.errorVariable || 'error.message';
  ctx.set(errVar, summarizeRequestFailure(firstFailed));
  ctx.set('error.statusCode', String(firstFailed.httpStatus));
  ctx.set('error.failedCount', String(failedResults.length));
  await visit(errorConfig.handlerEntryNodeId);
}

Workflow-Level Error Variables

VariableDescription
{{error.message}}Summarized error from first failed node
{{error.statusCode}}HTTP status of first failed node
{{error.failedCount}}Total number of failed nodes (workflow-level only)
📘 Node-Level vs Workflow-Level Variables Node-level error handlers expose 6 variables (including error.nodeId, error.nodeLabel, error.retryCount, error.type). Workflow-level handlers expose 3 variables (including error.failedCount — a count of all failed nodes across the entire workflow).

7. Error Message Helpers

summarizeRequestFailure()

Generates a human-readable summary from a RequestResult:

function summarizeRequestFailure(r: RequestResult): string {
  // Priority 1: errorMessage (humanized)
  if (r.errorMessage?.trim())
    return humanizeError(r.errorMessage.trim());

  // Priority 2: first failure detail
  const fd = r.failureDetails?.[0];
  if (fd) {
    const a = (fd.actual ?? '').slice(0, 240);
    const e = (fd.expected ?? '').slice(0, 120);
    return e ? `${fd.path}: ${a} (expected ${e})` : `${fd.path}: ${a}`;
  }

  // Priority 3: HTTP status
  if (r.httpStatus >= 400) return `HTTP ${r.httpStatus}`;
  if (r.httpStatus === 0)
    return 'Network error — could not reach the server...';

  return 'Step failed';
}

humanizeError()

Transforms raw error codes into friendly messages:

Raw ErrorHumanized Message
ECONNREFUSEDConnection refused — server may be down
ETIMEDOUTConnection timed out
CERT_HAS_EXPIREDSSL certificate has expired
ENOTFOUNDDNS lookup failed — hostname not found

9. Combining Node-Level and Workflow-Level

A robust workflow uses both levels together:

Payment Flow with Failure Notification

Start
→ Error Handler (retry ×3, exp backoff)
   ├── Body: HTTP POST /api/payment
   ├── Catch: HTTP POST /slack (node-level alert)
   └── Done: Condition (check payment result)
→ End

Workflow Error Handler: (catches anything else)
Log → HTTP POST /pagerduty (critical alert)
  • The node-level handler retries the payment API 3 times with exponential backoff. If all retries fail, it sends a Slack alert and continues.
  • The workflow-level handler catches any other unexpected failures (e.g., the Condition node itself erroring) and sends a critical PagerDuty alert.

10. Exercises

Exercise 1: Node-Level Retry

Goal: Create a workflow that retries a failing HTTP request.

  1. Create a workflow. Add an Error Handler node.
  2. Set: retryCount 2, retryDelayMs 500, retryBackoff fixed, errorFilter all.
  3. Connect Body to an HTTP node: GET https://httpstat.us/500 (always returns 500).
  4. Connect Catch to a SetVariable: errorInfo = {{error.message}}.
  5. Connect Done to an End node.
  6. Run — observe 3 attempts (1 original + 2 retries), then the catch path executes.

Exercise 2: Workflow-Level Error Handler

Goal: Add a global error handler that logs failure details.

  1. Open Workflow Settings. Set error mode to run-handler.
  2. Create an error handler subgraph: a SetVariable node that stores {{error.message}}, {{error.statusCode}}, {{error.failedCount}}.
  3. Set handlerEntryNodeId to the first node of the handler subgraph.
  4. Add an HTTP node to the main flow that intentionally fails.
  5. Run — after the main flow fails, the handler subgraph executes with error variables populated.

Exercise 3: Error Classification

Goal: Use different error filters for different failure types.

  1. Create an Error Handler with filter network-error.
  2. In the body: HTTP GET https://nonexistent.invalid/api (DNS failure).
  3. Run — the handler catches it (network error matches the filter).
  4. Change the URL to https://httpstat.us/500 (HTTP error, not network).
  5. Run — the handler does not catch it (filter mismatch). The workflow fails directly.
