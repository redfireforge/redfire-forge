1. Sub-Workflow Node Overview

A Sub-Workflow node executes an entire child workflow as a single step in the parent workflow. The parent passes data in via input mappings and receives results via output mappings.

Parent Workflow

Start → HTTP (get users) → Sub-Workflow → End
                                    ↕ mappings
                         Child Workflow
                      Start → Process → End

SubWorkflowNodeData Type

export interface SubWorkflowNodeData {
  label: string;
  workflowId: string;                    // UUID of child workflow
  workflowName?: string;                 // cached display name
  inputMappings: Array<{
    sourceExpression: string;            // parent → child: "{{users}}"
    targetVariable: string;              // child variable name
  }>;
  outputMappings: Array<{
    sourceVariable: string;              // child variable name
    targetVariable: string;              // parent variable name
  }>;
  propagateAllOutputs?: boolean;         // pass all child vars to parent
  maxDepth?: number;                     // recursion limit (default: 10)
  timeoutMs?: number;                    // child timeout (0 = unlimited)
  retryCount?: number;                   // retry on failure (default: 0)
  retryDelayMs?: number;                 // delay between retries (default: 1000)
  onChildFailure?: 'fail' | 'continue'; // behaviour on child failure
  multiInstance?: {
    collection: string;                  // JSON array expression
    elementVariable: string;             // per-item variable name
    mode: 'sequential' | 'parallel';     // execution order
  };
}

Factory Defaults

{
  label: 'Sub-Workflow',
  workflowId: '',
  inputMappings: [],
  outputMappings: [],
}

2. Input and Output Mappings

Input Mappings (Parent → Child)

Each input mapping resolves a parent expression and injects it as a variable in the child workflow's context:

inputMappings: [
  { sourceExpression: '{{userId}}',    targetVariable: 'userId'    },
  { sourceExpression: '{{authToken}}', targetVariable: 'token'     },
  { sourceExpression: 'production',    targetVariable: 'environment' },
]
// Child sees: {{userId}}, {{token}}, {{environment}}

Output Mappings (Child → Parent)

After the child completes, its final variable state is mapped back to the parent:

outputMappings: [
  { sourceVariable: 'deployStatus', targetVariable: 'childResult' },
  { sourceVariable: 'logUrl',       targetVariable: 'childLogUrl' },
]
// Parent sees: {{childResult}}, {{childLogUrl}}

Propagate All Outputs

When propagateAllOutputs is true, all child variables (except internal __ prefixed ones) are copied to the parent:

// Engine logic:
if (data.propagateAllOutputs) {
  for (const [k, v] of Object.entries(run.childFinalVars)) {
    if (!k.startsWith('__')) hCtx.ctx.set(k, v);
  }
}
⚠️ Variable Name Collisions With propagateAllOutputs, child variables overwrite parent variables of the same name. Use explicit outputMappings with unique target names for production workflows to avoid unintended overwrites.

3. Dynamic Workflow IDs

The workflowId field can contain variable expressions for runtime workflow selection:

// Static: always runs the same child
{ workflowId: 'abc-123-def-456' }

// Dynamic: resolved at runtime from a variable
{ workflowId: '{{targetWorkflowId}}' }

The engine resolves the expression before looking up the child workflow:

const resolvedWorkflowId = data.workflowId.includes('{{')
  ? hCtx.ctx.resolve(data.workflowId)
  : data.workflowId;
const childWorkflow = hCtx.resolveSubWorkflow?.(resolvedWorkflowId);

4. Multi-Instance Mode

Run the child workflow once per item in a collection — like a forEach loop, but the body is an entire workflow:

multiInstance: {
  collection: '{{regions}}',      // JSON array: '["us-east","eu-west","ap-south"]'
  elementVariable: 'region',      // each child run sees {{region}}
  mode: 'parallel',               // or 'sequential'
}

Parallel vs Sequential

ModeBehaviorUse Case
parallelAll items run concurrently via Promise.allIndependent operations (deploy to regions)
sequentialItems run one-by-one in orderOrder-dependent operations (sequential migration)
// Engine logic:
if (mi.mode === 'parallel') {
  await Promise.all(iterationItems.map((item, idx) => runOneItem(item, idx)));
} else {
  for (let idx = 0; idx < iterationItems.length; idx++) {
    await runOneItem(iterationItems[idx], idx);
  }
}

Node Badge

Multi-instance mode shows: ⟳ parallel · region or ⟳ sequential · item

💡 Multi-Instance vs Loop + Sub-Workflow Multi-instance mode is a shortcut for the common pattern of "Loop forEach → Sub-Workflow." It's simpler to configure (one node instead of two) and handles collection parsing, element injection, and result aggregation automatically.

5. Depth Guard and Recursion

Sub-workflows can call other sub-workflows, creating a call chain. The maxDepth field prevents infinite recursion:

// Engine checks depth before execution:
const currentDepth = parseInt(
  hCtx.ctx.get('__subWorkflowDepth') ?? '0', 10
) || 0;
const maxDepth = data.maxDepth ?? 10;

if (currentDepth >= maxDepth) {
  throw new Error(`Sub-workflow depth limit (${maxDepth}) exceeded`);
}

// Each child increments depth:
childCtx.set('__subWorkflowDepth', String(currentDepth + 1));
DepthExample
0Main workflow
1Child workflow called by main
2Grandchild workflow called by child
10 (default limit)Error: depth limit exceeded

Retry Configuration

{ retryCount: 3, retryDelayMs: 2000, onChildFailure: 'fail' }
// Attempt 1 → child fails → wait 2000ms
// Attempt 2 → child fails → wait 2000ms
// Attempt 3 → child fails → wait 2000ms
// Attempt 4 → child fails → parent node fails

SubWorkflowRunSummary

Each child execution produces a summary accessible by the parent:

export interface SubWorkflowRunSummary {
  parentNodeId: string;
  childWorkflowName: string;
  passed: boolean;
  durationMs: number;
  resultCount: number;
  childSteps: Array<{
    nodeId: string;
    label: string;
    state: 'pass' | 'fail' | 'skipped';
    statusCode?: number;
    responseTimeMs?: number;
    error?: string;
  }>;
  attempt: number;  // which retry attempt (1-based)
}

7. Extract to Sub-Workflow

The Extract to Sub-Workflow refactoring tool lets you select existing nodes and convert them into a child workflow with one click:

export function extractToSubWorkflow(
  selectedNodeIds: string[],
  parentNodes: WorkflowNode[],
  parentEdges: WorkflowEdge[],
  childName: string,
): ExtractResult | null

How It Works

  1. Select nodes on the canvas (multi-select).
  2. Right-click → Extract to Sub-Workflow.
  3. The tool:
    • Classifies edges as internal, incoming, or outgoing
    • Creates a child workflow with auto-generated Start and End nodes
    • Replaces the selected nodes with a single Sub-Workflow node
    • Positions the new node at the centroid of the extracted nodes
    • Wires incoming/outgoing edges to the new Sub-Workflow node
⚠️ Non-Extractable Nodes start and end nodes cannot be extracted. They're fundamental to the parent workflow's structure and are auto-generated for the child.

9. Exercises

Exercise 1: Parent-Child with Mappings

Goal: Create a parent and child workflow connected by input/output mappings.

  1. Create a child workflow named "Get User Details": Start → HTTP GET /users/{{userId}} → SetVariable (userName) → End.
  2. Create a parent workflow: Start → SetVariable (userId = 1) → Sub-Workflow node → End.
  3. Configure the Sub-Workflow node:
    • Select the child workflow
    • Input mapping: {{userId}} → userId
    • Output mapping: userName → childUserName
  4. Run the parent — the child executes with the mapped userId and returns the name.

Exercise 2: Multi-Instance Parallel

Goal: Run a child workflow in parallel for each item in a collection.

  1. Create a child workflow that processes a single {{region}}.
  2. In the parent, set {{regions}} = ["us-east","eu-west","ap-south"].
  3. Configure multi-instance: collection {{regions}}, elementVariable region, mode parallel.
  4. Run — observe all three child runs execute concurrently.

Exercise 3: Extract to Sub-Workflow

Goal: Refactor an existing workflow by extracting nodes.

  1. Create a workflow with 5+ nodes in a chain.
  2. Select 3 middle nodes (not Start/End).
  3. Right-click → Extract to Sub-Workflow.
  4. Verify the selected nodes are replaced by a single Sub-Workflow node.
  5. Open the child workflow and confirm it contains the extracted nodes with auto-generated Start/End.
