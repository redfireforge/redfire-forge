1. Debug Mode Overview

Debug mode lets you execute a workflow one node at a time. Each node pauses before execution, showing a ⏸ Paused overlay on the canvas. You can inspect all workflow variables, then step forward or stop.

Normal Run: Start → HTTP → SetVar → Condition → End  (all at once)

Debug Run: Start → ⏸ HTTP → ⏸ SetVar → ⏸ Condition → ⏸ End  (step by step)

Starting a Debug Session

  1. Open any workflow in the editor.
  2. Click the Debug Quick Test button (🐛) in the toolbar.
  3. The workflow starts executing. Each node pauses before running.
  4. Click ⏭ Step on a paused node to execute it and advance.
  5. Click Stop to abort the debug session at any time.

2. The DebugController

The DebugController class orchestrates step-through execution. It manages threads, paused states, and resume signals.

export interface DebugThread {
  id: string;
  currentNodeId: string;
  status: 'paused' | 'running' | 'completed' | 'waiting-join';
}

export class DebugController {
  // Pause before executing a node — returns a Promise
  async waitForStep(nodeId: string, threadId: string): Promise<void>;

  // Mark node as actively running (after step)
  markRunning(nodeId: string, threadId: string): void;

  // Mark thread as completed
  markCompleted(threadId: string): void;

  // Mark thread as waiting at a Join barrier
  markWaitingJoin(nodeId: string, threadId: string): void;

  // Step a single paused node
  stepNode(nodeId: string): void;

  // Step all currently paused nodes at once
  stepAll(): void;

  // Resume — disable pausing, run remaining nodes freely
  resumeAll(): void;

  // Abort the debug session
  stop(): void;

  // Query state
  get isStopped(): boolean;
  get isResumed(): boolean;
  getPausedNodeIds(): string[];
  getThreads(): ReadonlyMap<string, DebugThread>;
}

3. How Debug Integrates with the Engine

The debug controller hooks into the graph runner's visit() function — the core function that executes each node:

// In visit() — before executing any node:
if (debugController) {
  // 1. Show ⏸ Paused overlay on the canvas
  callbacks.onNodeStateChange(nodeId, { state: 'paused' });

  // 2. Wait — this Promise resolves when user clicks "Step"
  await debugController.waitForStep(nodeId, threadId);

  // 3. Check if user stopped the session
  if (debugController.isStopped || abortSignal?.aborted) return;

  // 4. Mark as running — overlay changes to executing state
  debugController.markRunning(nodeId, threadId);
}

// Now execute the node normally...

Abort Checks in Long-Running Handlers

Nodes that run iteratively (loops, waits) also check the debug controller:

// Loop handler:
if (hCtx.abortSignal?.aborted || hCtx.debugController?.isStopped) return false;

// CorrelationWait handler:
const isAbort = hCtx.abortSignal?.aborted || hCtx.debugController?.isStopped;

// WaitForCondition handler:
if (hCtx.abortSignal?.aborted || hCtx.debugController?.isStopped) break;
💡 Debug Is Non-Invasive The debug controller doesn't change how nodes execute — it only adds pause points before each node. The actual execution logic is identical to a normal run. This means debug results are reliable and reproducible.

4. Thread States

In workflows with parallel branches (Fork/Join), the debug controller tracks multiple threads:

StatusMeaningVisual
pausedThread is waiting for user to step⏸ Paused badge on node
runningThread is actively executing a nodeNormal execution state
waiting-joinThread reached a Join barrier, waiting for siblingsJoin barrier indicator
completedThread finished executionPass/fail state on node

Debugging Fork/Join Workflows

Fork
├── Thread A: HTTP (⏸ Paused) → SetVar → Join (waiting-join)
├── Thread B: HTTP (⏸ Paused) → SetVar → Join (waiting-join)
└── Thread C: HTTP (running) → ...

You can step threads independently.
Join releases when all threads arrive.

When debugging parallel branches:

  • Each branch pauses independently — you can step Branch A while Branch B remains paused.
  • When a thread reaches a Join node, it shows waiting-join status.
  • The Join node only releases when all incoming threads have arrived.
  • Use Step All to advance all paused nodes simultaneously.

5. The NodePausedOverlay Component

Every workflow node includes the NodePausedOverlay component for debug visualization:

export function NodePausedOverlay({ nodeId, state, debugStep }) {
  if (state !== 'paused') return null;

  if (debugStep) {
    return (
      <button className="wf-debug-step-btn"
              title="Step this node"
              onClick={(e) => { e.stopPropagation(); debugStep(nodeId); }}>
        ⏭ Step
      </button>
    );
  }

  return <span className="wf-status-badge wf-status-paused">⏸ Paused</span>;
}

Two Modes

ModeShowsWhen
Interactive⏭ Step buttonDebug mode active, debugStep callback provided
Indicator only⏸ Paused badgeNo debugStep callback (read-only view)

This component is included in all node types: HTTP, SetVariable, Condition, Loop, Fork, Join, Aggregate, SubWorkflow, CorrelationWait, Script, ErrorHandler, and more.

6. Debug Controls

The useWorkflowExecution hook exposes three debug actions:

Step Node

const handleDebugStep = useCallback((nodeId: string) => {
  debugControllerRef.current?.stepNode(nodeId);
}, []);

Advances a single paused node. The node executes and the next node in the chain pauses.

Resume All

debugControllerRef.current?.resumeAll();

Disables all future pause points. The workflow runs to completion like a normal run. Useful when you've passed the section you wanted to debug.

Stop

const handleDebugStop = useCallback(() => {
  debugControllerRef.current?.stop();
  abortRef.current?.abort();
  setIsRunning(false);
  setIsDebugMode(false);
  debugControllerRef.current = null;
  setLastRunStatus('stopped');
}, []);

Immediately aborts the debug session. All pending nodes are cancelled. The workflow shows a "stopped" status.

7. Inspecting Variables

At each pause point, all workflow variables are available for inspection. The Variables panel shows the current state of every variable set so far:

  • Before stepping a node: You see all variables set by previously executed nodes.
  • After stepping a node: The variables panel updates with any new or modified variables from that node.

What to Look For

Debug ScenarioWhat to Inspect
HTTP response unexpected{{response.body}}, {{httpStatus}}
Condition taking wrong branchThe variables used in the condition (left/right operands)
Loop not iterating{{i}}, {{item}}, collection variable
Sub-workflow failing{{__subWorkflowDepth}}, input mapping variables
Auth not applied{{authToken}}, {{Authorization}}
📘 Console Log Analysis The workflow console shows prefixed log lines during execution. In debug mode, logs appear incrementally as you step through nodes — making it easy to correlate each log entry with its source node.

8. Common Debugging Patterns

Pattern 1: Find Where a Variable Goes Wrong

  1. Start a debug session.
  2. Step through nodes one at a time.
  3. After each step, check the target variable in the Variables panel.
  4. When the variable value changes unexpectedly, you've found the problem node.

Pattern 2: Debug a Condition Branch

  1. Step to the Condition node — it pauses before evaluation.
  2. Inspect the left and right operand variables.
  3. Step — observe which branch is taken.
  4. If wrong, adjust the condition or fix the upstream variable.

Pattern 3: Debug Fork/Join Timing

  1. Step the Fork node — all branches start paused.
  2. Step one branch at a time to control execution order.
  3. Observe when each thread reaches the Join (waiting-join status).
  4. When all arrive, the Join releases and the next node pauses.

Pattern 4: Skip Past Uninteresting Nodes

  1. Use Step All to advance all paused nodes at once.
  2. When you reach the section you care about, switch to single-stepping.
  3. Or use Resume All to run the rest without pausing.

9. Exercises

Exercise 1: Step-Through a Simple Chain

Goal: Debug a linear workflow and inspect variables at each step.

  1. Create a workflow: Start → HTTP GET /users/1 → SetVariable (userName) → End.
  2. Click Debug Quick Test (🐛).
  3. The HTTP node pauses. Inspect the Variables panel — no response variables yet.
  4. Click ⏭ Step — the HTTP request executes. Check {{response.body}}.
  5. Step the SetVariable — verify {{userName}} is set correctly.
  6. Step the End node — debug session completes.

Exercise 2: Debug a Fork/Join

Goal: Observe parallel thread execution order.

  1. Create a workflow: Start → Fork → (Branch A: HTTP /users, Branch B: HTTP /posts) → Join → End.
  2. Start debug mode.
  3. After Fork, both branch HTTP nodes pause simultaneously.
  4. Step Branch A only — observe it completes while Branch B is still paused.
  5. Step Branch B — both threads reach the Join (waiting-join).
  6. The Join releases and the End node pauses.

Exercise 3: Find a Bug

Goal: Use debugging to diagnose why a condition takes the wrong branch.

  1. Create a workflow where a Condition checks {{status}} == "active".
  2. Intentionally set {{status}} to "Active" (capital A).
  3. Run normally — the condition fails (case-sensitive mismatch).
  4. Start a debug session. Step to the Condition node.
  5. Inspect {{status}} — see "Active" vs expected "active".
  6. Fix the upstream SetVariable or adjust the condition.
