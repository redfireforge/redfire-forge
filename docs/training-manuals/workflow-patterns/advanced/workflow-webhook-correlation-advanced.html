1. Three Trigger and Wait Node Types

RedfireForge provides three nodes for event-driven workflows:

NodePurposeCategory

Schedule TriggerStart a workflow on a cron scheduleTriggers

2. Webhook Trigger Node

The Webhook Trigger starts a workflow when an external system sends an HTTP request to a defined path.

WebhookTriggerNodeData Type

export interface WebhookTriggerNodeData {
  label: string;
  method: 'POST' | 'PUT' | 'PATCH';     // accepted HTTP method
  path: string;                           // webhook endpoint path
  samplePayload: string;                  // JSON for design-time testing
  extractVariables?: Array<{
    name: string;                         // variable name to create
    jsonPath: string;                     // path into the payload
  }>;
  notes?: string;
}

Factory Defaults

{
  label: 'Webhook Trigger',
  method: 'POST',
  path: '/api/webhook',
  samplePayload: '{\n  "event": "example",\n  "data": {}\n}',
  extractVariables: [],
}

Variable Extraction

During design-time testing, the engine parses the samplePayload and extracts variables using JSONPath:

// Engine execution:
const payload = JSON.parse(data.samplePayload || '{}');
for (const { name, jsonPath } of data.extractVariables) {
  const keys = jsonPath.replace(/^\$\./, '').split('.');
  let value = payload;
  for (const key of keys) {
    value = value?.[key];
  }
  if (value !== undefined) hCtx.ctx.set(name, String(value));
}

Example Configuration

// Webhook receives a payment event
{
  method: 'POST',
  path: '/webhooks/payment',
  samplePayload: '{\n  "paymentId": "pay_123",\n  "amount": 99.99,\n  "status": "completed"\n}',
  extractVariables: [
    { name: 'paymentId', jsonPath: '$.paymentId' },
    { name: 'amount',    jsonPath: '$.amount' },
    { name: 'status',    jsonPath: '$.status' },
  ],
}
// After trigger: {{paymentId}} = "pay_123", {{amount}} = "99.99", {{status}} = "completed"

Node Display

Shows POST /webhooks/payment badge and Extracts 3 variables count.

3. Schedule Trigger Node

The Schedule Trigger starts a workflow at specified times using cron expressions.

ScheduleTriggerNodeData Type

export interface ScheduleTriggerNodeData {
  label: string;
  cronExpression: string;            // e.g. '0 9 * * MON-FRI'
  timezone: string;                   // e.g. 'America/New_York'
  scheduleDescription?: string;       // human-readable label
  inputVariables?: Record<string, string>;
  notes?: string;
}

Factory Defaults

{
  label: 'Schedule Trigger',
  cronExpression: '0 9 * * MON-FRI',
  timezone: 'America/New_York',
  scheduleDescription: 'Every weekday at 9:00 AM EST',
  inputVariables: {},
}

4. Correlation Wait Node

The Correlation Wait node is the most powerful event-driven node. It pauses the workflow mid-execution and waits for an external webhook callback that matches a correlation ID.

Payment Callback Flow

Start
→ HTTP POST /api/payments (initiate payment)
→ Correlation Wait (pause — wait for callback)
       ⏸ Paused: correlationId = "pay_123"
       📡 Listening on /webhooks/payment-callback
       ⏱ Timeout: 60 seconds
→ (webhook arrives, matches "pay_123")
→ HTTP GET /api/payments/{{paymentId}} (confirm)
→ End

CorrelationWaitNodeData Type

export interface CorrelationWaitNodeData {
  label: string;
  correlationIdExpression: string;   // expression resolving to correlation ID
  webhookPath: string;               // endpoint to listen on
  correlationSource: 'body' | 'header' | 'query';  // where to find ID in callback
  correlationJsonPath?: string;      // JSONPath (when source is 'body')
  correlationHeader?: string;        // header name (when source is 'header')
  correlationQueryParam?: string;    // query param (when source is 'query')
  extractVariables?: Array<{
    name: string;
    jsonPath: string;
  }>;
  timeoutMs: number;                 // fail after N ms (default: 60000)
  webhookFilter?: string;            // optional payload validation expression
  notes?: string;
}

Factory Defaults

{
  label: 'Correlation Wait',
  correlationIdExpression: '',
  webhookPath: '/webhooks/callback',
  correlationSource: 'body',
  correlationJsonPath: '$.correlationId',
  extractVariables: [],
  timeoutMs: 60000,   // 60 seconds
}

5. How Correlation Matching Works

Step-by-Step Flow

  1. Resolve correlation ID: The engine resolves correlationIdExpression (e.g., {{paymentId}} → "pay_123").
  2. Pause: Node state changes to 'paused'. The workflow is suspended.
  3. Register in store: The correlation ID, webhook path, and timeout are registered in the ICorrelationStore.
  4. Wait: The engine awaits a promise that will resolve when a matching callback arrives (or timeout).
  5. Callback arrives: An external system sends a webhook to the registered path.
  6. Match: The store extracts the correlation ID from the callback (by body JSONPath, header, or query param) and matches it.
  7. Resume: The workflow resumes. Webhook data is injected as variables.

Correlation Source Options

SourceConfig FieldExample
body correlationJsonPath Extract $.correlationId from JSON body
header correlationHeader Read X-Correlation-Id header
query correlationQueryParam Read ?correlationId=pay_123 query param

Variables Set on Resume

VariableSource
{{webhook.body}}Full webhook payload (JSON string)
{{webhook.correlationId}}The matched correlation ID
Custom extractVariablesJSONPath extractions from webhook body

6. The Correlation Store

The ICorrelationStore manages paused correlations:

export interface ICorrelationStore {
  pause(correlationId, webhookPath, state,
        timeoutMs, webhookFilter?, config?): Promise<Record<string, unknown>>;
  resume(correlationId, webhookData): boolean;
  isPaused(correlationId): boolean;
  cancel(correlationId): boolean;
  get(correlationId): PausedEntry | undefined;
  cleanup(): number;
  listPaused(): PausedEntry[];
  readonly size: number;
}

Two Implementations

ImplementationUse
InMemoryCorrelationStoreIn-process; used for local testing and design-time runs
RemoteCorrelationStoreServer-backed; used in production via useWorkflowExecution
💡 Timeout Behavior When timeoutMs elapses without a matching callback, the correlation is cancelled and the node fails. Set timeoutMs: 0 for unlimited wait (not recommended in production — use a generous timeout like 300000ms / 5 minutes instead).

7. Webhook Filter

The optional webhookFilter field lets you validate the callback payload before accepting it. If the filter expression doesn't match, the callback is ignored (the node keeps waiting).

// Only accept callbacks with status "completed"
{
  webhookFilter: '$.status == "completed"',
  // Callbacks with status "pending" are ignored
  // Only "completed" callbacks resume the workflow
}

9. Exercises

Exercise 1: Webhook Trigger with Extraction

Goal: Create a workflow triggered by an external webhook.

  1. Add a Webhook Trigger node: method POST, path /webhooks/order.
  2. Set sample payload: {"orderId": "ord_456", "total": 150}.
  3. Add extract variables: orderId → $.orderId, total → $.total.
  4. Connect to an HTTP node that uses {{orderId}} in the URL.
  5. Run — variables are seeded from the sample payload.

Exercise 2: Payment Callback Flow

Goal: Build a start-and-wait payment flow with correlation matching.

  1. Add an HTTP POST node: /api/payments (initiate payment). Save {{paymentId}} from response.
  2. Add a Correlation Wait node:
    • correlationIdExpression: {{paymentId}}
    • webhookPath: /webhooks/payment-callback
    • correlationSource: body
    • correlationJsonPath: $.paymentId
    • timeoutMs: 30000
  3. After the wait: HTTP GET to confirm payment using {{webhook.body}} data.
  4. Load the Payment Callback Simulator sample and run both workflows.

Exercise 3: Timeout Handling

Goal: Observe timeout behavior when no callback arrives.

  1. Set up a Correlation Wait with timeoutMs: 5000 (5 seconds).
  2. Run the workflow — do not send a callback.
  3. After 5 seconds, the node fails with a timeout error.
  4. Add an Error Handler around the Correlation Wait to handle timeouts gracefully.
