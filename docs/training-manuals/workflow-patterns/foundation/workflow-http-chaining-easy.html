1. What Is HTTP Request Chaining?

HTTP request chaining is the most fundamental workflow pattern: run one API call, extract data from its response, and feed that data into the next API call. This mirrors real-world scenarios like "look up a user, then fetch their orders."

Real-world scenario: "User Lookup → Extract ID → Fetch Details"

You need to test an API integration where you first create a resource (POST), then verify it was created by fetching it back (GET) using the ID returned from the POST response. Without chaining, you'd have to manually copy the ID between tests.

Start → POST /posts → Extract postId → GET /posts/{{postId}} → End

What You'll Learn

  • Start and End nodes — every workflow's entry and exit points
  • HTTP node configuration — method, URL, headers, body, auth
  • Variable extraction — capturing response data for downstream nodes
  • VariableContext — the engine that resolves {{variable}} placeholders
  • Console log analysis — reading the >, <, #, * prefixed log lines

Prerequisites

  • RedfireForge installed and running
  • Basic understanding of HTTP methods (GET, POST) and JSON
  • No workflow experience needed — this is the starting point

2. The Start and End Nodes

Every workflow begins with a Start node and ends with one or more End nodes. These are the entry and exit points of your graph.

Start Node

interface StartNodeData {
  label: string;
  inputVariables: Record<string, string>;
}

The Start node can define input variables — key-value pairs that are injected into the variable context before any other node runs. These act as configuration parameters for the workflow.

FieldPurposeExample
labelDisplay name on the canvas"Start"
inputVariablesPre-set variables for the workflow run{ "baseUrl": "https://jsonplaceholder.typicode.com" }

End Node

interface EndNodeData {
  label: string;
}

The End node marks the workflow as complete. Its final state (pass or fail) depends on whether all preceding nodes passed. A workflow can have multiple End nodes — for example, one on each branch of a condition. Unvisited End nodes are automatically marked based on overall workflow success.

💡 Tip You can have multiple End nodes in a workflow. This is common in conditional workflows where different branches lead to different exit points.

3. The HTTP Node

The HTTP node is the workhorse of every workflow. It sends an API request and captures the response.

interface HttpNodeData {
  label: string;
  scenario: Scenario;        // Contains the request definition
  serviceId?: string;         // Optional service registry reference
  initialVariables?: Record<string, string>;
  hostEnvironmentId?: string; // Environment for base URL resolution
}

The scenario field contains the full request definition — method, URL, headers, body, auth, extractions, and assertions. This is the same data model used in standalone test scenarios.

Configuring an HTTP Node

  1. Drag an HTTP node from the node palette onto the canvas.
  2. Double-click the node (or click the gear icon) to open the config modal.
  3. Set the Method (GET, POST, PUT, DELETE, PATCH).
  4. Enter the URL — supports {{variable}} interpolation.
  5. Add Headers if needed (e.g., Content-Type: application/json).
  6. Set the Body for POST/PUT/PATCH requests.
  7. Configure Extractions to capture response data as variables.

Variable Extraction

Extractions pull data from the HTTP response and store it as workflow variables. These variables are then available to all downstream nodes via {{variableName}}.

Extraction SourceSyntaxExample
JSON body fieldJSONPath$.id → extracts the id field
Response headerHeader nameX-Request-Id
Status codeBuilt-inhttpStatus (auto-extracted)
Full bodyBuilt-inresponseBody (auto-extracted)
📘 Auto-Extracted Variables Every HTTP node automatically sets httpStatus (the status code as string), status (pass/fail), and responseBody (the full response body). You don't need to configure these — they're always available.

4. Variable Context — How {{variables}} Work

The VariableContext is the engine that resolves all {{variableName}} placeholders in URLs, headers, bodies, and other fields.

Resolution Priority

When you write {{myVar}}, the engine searches three layers (highest priority first):

  1. Extracted layer — Variables set during execution (HTTP extractions, SetVariable)
  2. Manual layer — Initial variables from the Start node or workflow settings
  3. Environment layer — Low-priority variables from the environment configuration
// Resolution example:
// Manual layer: { baseUrl: "https://api.example.com" }
// Extracted layer: { postId: "42" }

// URL: "{{baseUrl}}/posts/{{postId}}"
// Resolves to: "https://api.example.com/posts/42"

Per-Node Scoped Variables

When an HTTP node extracts a variable, it's stored in the extracted layer (global scope by default). You can also access node-specific variables using:

{{node:"Create Post".httpStatus}}   // By label
{{node:<node-id>.responseBody}}     // By ID

5. Walkthrough: The Gallery Sample

Let's examine the sample-workflow-001 gallery workflow: "Create → Extract → Verify".

Workflow Structure

Start → POST /posts → Condition: Status 201? → Delay 1s → GET /posts/{{postId}} → Condition: Valid User?

Step-by-Step Execution

  1. Start — No initial variables needed for this sample.
  2. HTTP "Create Post" — Sends POST https://jsonplaceholder.typicode.com/posts with a JSON body. Extracts postId and httpStatus from the response.
  3. Condition "Was it Created?" — Checks httpStatus == 201. If true (Yes branch), continues. If false (No branch), the remaining nodes are skipped.
  4. Delay — Waits 1000ms (simulating a real-world pause between create and verify).
  5. HTTP "Get Post Details" — Sends GET https://jsonplaceholder.typicode.com/posts/{{postId}}. The {{postId}} is replaced with the value extracted from step 2. Extracts postTitle and postUserId.
  6. Condition "Has Valid User?" — Checks postUserId == 1.

Console Log Output

During execution, the console shows:

> POST https://jsonplaceholder.typicode.com/posts
< 201 Created (245ms)
# postId = "101"
# httpStatus = "201"
* [Create Post] → pass

* [Was it Created?] condition: "201" == "201" → true (Yes branch)

* [Delay] waiting 1000ms...
* [Delay] → pass

> GET https://jsonplaceholder.typicode.com/posts/101
< 200 OK (89ms)
# postTitle = "foo"
# postUserId = "1"
* [Get Post Details] → pass

* [Has Valid User?] condition: "1" == "1" → true (Yes branch)
💡 Reading Console Prefixes > = request sent, < = response received, # = variable extracted, * = node status change, ! = error.

6. Building Your First Chain

Let's build a 3-node HTTP chain from scratch. We'll fetch a list of users, extract the first user's ID, and then fetch that user's details.

Step 1: Create the Workflow

  1. Open the Workflow Designer (sidebar → Workflows → New Workflow).
  2. Name it "User Lookup Chain".
  3. The canvas starts with a Start node already placed.

Step 2: Add the First HTTP Node

  1. Click the + button on the canvas (or drag from the node palette).
  2. Select HTTP.
  3. Connect the Start node's output to the HTTP node's input.
  4. Double-click to configure:
    • Label: Get Users
    • Method: GET
    • URL: https://jsonplaceholder.typicode.com/users
  5. Add an extraction:
    • Variable name: firstUserId
    • JSONPath: $[0].id

Step 3: Add the Second HTTP Node

  1. Add another HTTP node and connect it after "Get Users".
  2. Configure:
    • Label: Get User Details
    • Method: GET
    • URL: https://jsonplaceholder.typicode.com/users/{{firstUserId}}
  3. Add extractions:
    • userName → $.name
    • userEmail → $.email

Step 4: Add the Third HTTP Node

  1. Add a third HTTP node and connect it after "Get User Details".
  2. Configure:
    • Label: Get User Posts
    • Method: GET
    • URL: https://jsonplaceholder.typicode.com/posts?userId={{firstUserId}}

Step 5: Add the End Node and Run

  1. Add an End node and connect it after "Get User Posts".
  2. Click Run in the toolbar.
  3. Watch the nodes turn green as each step completes.
  4. Check the console for the >, <, # log lines.

7. Node State Transitions

As the workflow runs, each node transitions through visual states:

StateVisualMeaning
idleDefault lookWorkflow hasn't started yet
pendingDimmedWaiting to be executed
runningBlue pulse animationCurrently sending request / processing
passGreen borderCompleted successfully
failRed borderRequest failed or assertion failed
skippedGray, dashed borderBranch not taken (after a condition)

Click any node after execution to see its response detail — status code, response time, headers, body, and extracted variables.

8. Exercises

Exercise 1: Chain 3 HTTP Nodes

Goal: GET list → extract first ID → GET detail by ID → GET related data

  1. Create a new workflow named "Post Detail Chain".
  2. HTTP 1: GET https://jsonplaceholder.typicode.com/posts → extract firstPostId from $[0].id.
  3. HTTP 2: GET https://jsonplaceholder.typicode.com/posts/{{firstPostId}} → extract postUserId from $.userId.
  4. HTTP 3: GET https://jsonplaceholder.typicode.com/users/{{postUserId}}.
  5. Run and verify all 3 nodes turn green.

Exercise 2: Add a SetVariable Node

Goal: Use SetVariable to transform data between HTTP calls.

  1. In the workflow from Exercise 1, add a SetVariable node between HTTP 2 and HTTP 3.
  2. Add an assignment: userProfileUrl = https://jsonplaceholder.typicode.com/users/{{postUserId}}.
  3. Change HTTP 3's URL to {{userProfileUrl}}.
  4. Run and verify the result is the same as Exercise 1.

Exercise 3: Add a LogDebug Node

Goal: Inspect variables mid-flow using LogDebug.

  1. Add a LogDebug node after the SetVariable from Exercise 2.
  2. Set the message to: Post {{firstPostId}} by user {{postUserId}} — URL: {{userProfileUrl}}.
  3. Enable Snapshot Variables to log all current variables.
  4. Run and check the console output — you should see the interpolated message and a variable dump.
