1. Why Delays Matter

Real-world API interactions rarely happen back-to-back. Clients pause between requests for rate limiting, polling intervals, or natural user think time. The Delay node lets you model these pauses in your workflow.

Real-world scenario: "Rate-Limited API — Spacing Requests"

You're testing an API that enforces a rate limit of 2 requests per second. Without delays, your workflow sends requests as fast as possible and gets 429 Too Many Requests errors. Adding a 500ms delay between each call keeps you under the limit.

2. The Delay Node Data Model

The Delay node supports two modes: fixed (exact duration) and random (range).

interface DelayNodeData {
  label: string;
  delayMs: number;          // Fixed delay in milliseconds
  mode: 'fixed' | 'random'; // Delay mode
  minMs?: number;           // Random mode: minimum delay
  maxMs?: number;           // Random mode: maximum delay
}

Fixed Mode

Pauses for exactly delayMs milliseconds. The node badge displays the duration, e.g., 500ms or 2s.

// Fixed delay: wait exactly 1 second
{
  label: "Wait 1s",
  delayMs: 1000,
  mode: "fixed"
}

Random Mode

Pauses for a random duration between minMs and maxMs. Each execution picks a different value. The node badge displays the range, e.g., 200–800ms.

// Random delay: wait between 200ms and 800ms
{
  label: "Think Time",
  delayMs: 500,    // fallback if mode not set
  mode: "random",
  minMs: 200,
  maxMs: 800
}
💡 Tip Random delays make your workflows more realistic. Real users don't click at machine speed — adding randomized think time makes your API tests better simulate production traffic patterns.

3. How the Engine Handles Delays

The handleDelayNode function in graphRunnerNodeHandlers.ts is straightforward:

  1. Read the delay configuration from the node data.
  2. If mode === 'random', compute a random value: Math.random() * (maxMs - minMs) + minMs.
  3. Log the delay: * [Wait 1s] waiting 1000ms...
  4. Wait using a setTimeout promise (respecting the abort signal for cancellation).
  5. Mark the node as pass and proceed to outgoing edges.

Console Log Output

// Fixed delay
* [Wait 1s] waiting 1000ms...
* [Wait 1s] → pass

// Random delay
* [Think Time] waiting 547ms (random: 200–800ms)...
* [Think Time] → pass

Abort Handling

If the user clicks Stop during a delay, the abort signal cancels the pending timeout immediately. The node transitions to fail with an abort message.

4. Configuring a Delay Node

  1. Click the + button on the canvas or drag from the node palette.
  2. Select Delay.
  3. Connect it between two nodes where you want a pause.
  4. Double-click to open the config modal.

5. Walkthrough: Rate-Limited API Testing

Build a workflow that spaces out 3 API calls with 1-second delays to stay under a rate limit.

Start → GET /posts/1 → Delay 1s → GET /posts/2 → Delay 1s → GET /posts/3 → End

Step-by-Step

  1. Create a new workflow named "Rate-Limited Fetch".
  2. Add HTTP node: GET https://jsonplaceholder.typicode.com/posts/1, label "Get Post 1".
  3. Add Delay node: Fixed, 1000ms, label "Wait 1s".
  4. Add HTTP node: GET https://jsonplaceholder.typicode.com/posts/2, label "Get Post 2".
  5. Add another Delay node: Fixed, 1000ms, label "Wait 1s".
  6. Add HTTP node: GET https://jsonplaceholder.typicode.com/posts/3, label "Get Post 3".
  7. Add End node and connect all nodes in sequence.
  8. Run — observe that total execution time is ~2 seconds longer than without delays.

Expected Console Output

> GET https://jsonplaceholder.typicode.com/posts/1
< 200 OK (95ms)
* [Get Post 1] → pass

* [Wait 1s] waiting 1000ms...
* [Wait 1s] → pass

> GET https://jsonplaceholder.typicode.com/posts/2
< 200 OK (87ms)
* [Get Post 2] → pass

* [Wait 1s] waiting 1000ms...
* [Wait 1s] → pass

> GET https://jsonplaceholder.typicode.com/posts/3
< 200 OK (91ms)
* [Get Post 3] → pass

6. Exercises

Exercise 1: Fixed Delays Between API Calls

Goal: Space out 3 HTTP calls with 1000ms delays.

  1. Create a workflow with 3 HTTP GET nodes hitting different endpoints.
  2. Add a Delay node (Fixed, 1000ms) between each HTTP node.
  3. Run and verify total execution time is at least 2 seconds.
  4. Check the console log for the * [Delay] waiting 1000ms... lines.

Exercise 2: Random Think Time

Goal: Simulate realistic user behavior with random delays.

  1. Modify the workflow from Exercise 1 — change both Delay nodes to Random mode.
  2. Set minMs: 200, maxMs: 800.
  3. Run the workflow 3 times — observe that total execution time varies each run.
  4. Check the console for the actual delay values, e.g., waiting 547ms (random: 200–800ms).

Exercise 3: Compare With and Without Delays

Goal: Understand the timing impact of delays.

  1. Create two copies of a 3-HTTP-node workflow: one with delays, one without.
  2. Run both and compare the total execution time in the console output.
  3. The version without delays should complete in under 500ms; the version with 1s delays should take ~2.5s.
