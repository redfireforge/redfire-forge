1. The Variable System Overview

Every workflow execution has a VariableContext — a three-layer store that holds all variables and resolves {{variableName}} placeholders in URLs, headers, bodies, conditions, and log messages.

Real-world scenario: "Building a Dynamic URL from Environment Variables"

Your team tests against multiple environments (dev, staging, prod). Instead of hardcoding URLs, you set baseUrl as an initial variable and use {{baseUrl}}/api/users in every HTTP node. Switching environments is a single variable change.

Three Resolution Layers

When the engine resolves {{name}}, it searches three layers in priority order:

PriorityLayerSet ByUse Case
1 (highest)ExtractedHTTP extractions, SetVariable nodesDynamic values computed during execution
2ManualStart node inputVariables, workflow settingsConfiguration parameters, pre-set values
3 (lowest)EnvironmentEnvironment layer (environmentLayer)Shared defaults, base URLs, API keys

The first layer that contains the variable name wins. This means an extracted variable overrides a manual variable with the same name, and a manual variable overrides an environment variable.

// Layer resolution example:
// Environment layer: { baseUrl: "https://dev.api.com", timeout: "5000" }
// Manual layer:      { baseUrl: "https://staging.api.com" }
// Extracted layer:   { userId: "42" }

// {{baseUrl}}  → "https://staging.api.com"  (manual overrides environment)
// {{timeout}}  → "5000"                     (environment, no override)
// {{userId}}   → "42"                       (extracted during execution)

2. The VariableContext Class

The VariableContext class manages all variable operations during a workflow run.

class VariableContext {
  // Constructor: manual (initial) + environment layers
  constructor(
    initialVariables: Record<string, string>,
    environmentLayer?: Record<string, string>
  )

  // Core operations
  set(name: string, value: string): void     // Write to extracted layer
  get(name: string): string | undefined      // Read: extracted → manual → env
  resolve(template: string): string          // Replace all {{var}} placeholders

  // Per-node scoping
  setForNode(nodeId: string, name: string, value: string): void
  getForNode(nodeId: string, name: string): string | undefined

  // Utilities
  registerWorkflowNodes(nodes: WorkflowNode[]): void  // Maps labels → IDs
  snapshot(): Record<string, string>                   // Flat dump of all vars
  child(): VariableContext                              // Create child context
}

Key Methods Explained

  • set(name, value) — Writes to the extracted layer (highest priority). Used by HTTP extractions and SetVariable nodes.
  • get(name) — Reads from extracted → manual → environment. Returns the first match or undefined.
  • resolve(template) — Replaces all {{variableName}} tokens in a string. Handles nested references and built-in generators.
  • snapshot() — Returns a flat Record<string, string> of all variables across all layers. Used by LogDebug's "Snapshot Variables" feature.

3. Initial Variables (Start Node)

The Start node's inputVariables field lets you define variables before the workflow runs. These go into the manual layer.

// Start node configuration
{
  label: "Start",
  inputVariables: {
    "baseUrl": "https://jsonplaceholder.typicode.com",
    "userId": "1",
    "maxRetries": "3"
  }
}

How to Configure

  1. Double-click the Start node to open its config modal.
  2. In the Input Variables section, add key-value pairs.
  3. Each variable becomes available as {{variableName}} in all downstream nodes.
💡 Tip Use initial variables for values that might change between runs: base URLs, user IDs, API keys, feature flags. This makes your workflow reusable across environments without editing individual HTTP nodes.

4. The SetVariable Node

The SetVariable node lets you assign one or more variables at any point in the workflow. Each assignment has a name and an expression that supports {{variable}} interpolation.

interface SetVariableNodeData {
  label: string;
  assignments: SetVariableAssignment[];
}

interface SetVariableAssignment {
  id: string;         // Unique assignment ID
  name: string;       // Variable name to set
  expression: string; // Value — supports {{var}} interpolation
}

How the Engine Handles It

The handleSetVariableNode handler iterates over each assignment:

  1. Resolve the expression via ctx.resolve(expression) — replaces all {{var}} placeholders.
  2. Call ctx.set(name, resolvedValue) — writes to the extracted layer.
  3. Log: # variableName = "resolvedValue".

Example: Computing a Derived URL

// SetVariable configuration
assignments: [
  { id: "a1", name: "userUrl",  expression: "{{baseUrl}}/users/{{userId}}" },
  { id: "a2", name: "greeting", expression: "Hello, user #{{userId}}!" }
]

// After execution:
// userUrl  = "https://jsonplaceholder.typicode.com/users/1"
// greeting = "Hello, user #1!"
📘 Multiple Assignments A single SetVariable node can have multiple assignments. They execute in order, top to bottom. Later assignments can reference variables set by earlier assignments in the same node.

5. The LogDebug Node

The LogDebug node prints a message to the workflow console. It's your primary debugging tool for inspecting variable values during execution.

interface LogDebugNodeData {
  label: string;
  message: string;              // Supports {{var}} interpolation
  logLevel: 'info' | 'warn' | 'error' | 'debug';
  snapshotVariables: boolean;   // If true, dumps all variables
}

Log Levels

LevelConsole PrefixUse Case
infoℹGeneral information, progress messages
warn⚠Potential issues, unexpected but non-fatal values
error❌Error conditions, validation failures
debug🐛Detailed debugging info, variable dumps

Snapshot Variables

When snapshotVariables is enabled, the LogDebug node calls ctx.snapshot() and prints every variable and its current value. This is invaluable for debugging complex workflows where you need to see the full state at a specific point.

// Console output with snapshotVariables: true
🐛 [Debug Check] Variables at step 3:
  baseUrl = "https://jsonplaceholder.typicode.com"
  userId = "1"
  postId = "42"
  httpStatus = "200"
  userUrl = "https://jsonplaceholder.typicode.com/users/1"

6. Per-Node Variable Scoping

By default, variables are global — any node can read any variable. But sometimes you need to access a variable that was set by a specific node. Per-node scoping lets you do this.

Setting Per-Node Variables

// During HTTP node execution, the engine calls:
ctx.setForNode(nodeId, 'httpStatus', '200');
ctx.setForNode(nodeId, 'responseBody', '{"id": 42, ...}');

Reading Per-Node Variables

Reference a specific node's variable using the node: prefix:

// By label (the label you gave the node on the canvas):
{{node:"Create Post".httpStatus}}     // → "201"
{{node:"Get User".responseBody}}      // → '{"name": "John", ...}'

// By node ID (from the canvas):
{{node:abc123.httpStatus}}
⚠ Label-Based References When using {{node:"Label".var}}, the label must match exactly (case-sensitive). If you rename a node, update all references to its label. The engine calls registerWorkflowNodes() at startup to build the label → ID mapping.

Built-in Runtime Variables

Every HTTP node automatically sets these variables (both globally and per-node):

VariableContentExample
httpStatusHTTP status code as string"200"
statusNode pass/fail status"pass"
responseBodyFull response body as string'{"id": 42}'

8. Walkthrough: Dynamic URL with Environment Variables

Start → SetVariable → LogDebug → HTTP "Get User" → LogDebug → End

Step-by-Step

  1. Create a new workflow named "Variable Demo".
  2. Configure the Start node with initial variables:
    • baseUrl = https://jsonplaceholder.typicode.com
    • userId = 1
  3. Add a SetVariable node with assignments:
    • userUrl = {{baseUrl}}/users/{{userId}}
    • requestId = {{$uuid}}
  4. Add a LogDebug node:
    • Message: Fetching user {{userId}} from {{userUrl}} (request: {{requestId}})
    • Level: info
  5. Add an HTTP node:
    • Method: GET
    • URL: {{userUrl}}
    • Extract: userName from $.name
  6. Add another LogDebug node:
    • Message: User {{userId}} is {{userName}} (status: {{httpStatus}})
    • Enable Snapshot Variables
  7. Add End node, connect all, and run.

9. Exercises

Exercise 1: Initial Variables for Dynamic URLs

Goal: Set baseUrl as an initial variable and use it in HTTP nodes.

  1. Create a workflow with Start → HTTP → End.
  2. On the Start node, set baseUrl = https://jsonplaceholder.typicode.com.
  3. In the HTTP node, set URL to {{baseUrl}}/posts/1.
  4. Run and verify the request hits the correct URL.
  5. Change baseUrl to https://dummyjson.com and URL to {{baseUrl}}/products/1. Run again.

Exercise 2: SetVariable for Computed Values

Goal: Use SetVariable to compute derived values.

  1. Create a workflow: Start → HTTP "Get Post" → SetVariable → HTTP "Get User" → End.
  2. HTTP 1: GET {{baseUrl}}/posts/1, extract postUserId from $.userId.
  3. SetVariable: authorUrl = {{baseUrl}}/users/{{postUserId}}.
  4. HTTP 2: GET {{authorUrl}}.
  5. Run and verify both HTTP nodes pass.

Exercise 3: LogDebug for Variable Inspection

Goal: Use LogDebug to print all variables at different stages.

  1. Extend Exercise 2 by adding LogDebug nodes after each SetVariable and HTTP node.
  2. First LogDebug: After SetVariable — authorUrl = {{authorUrl}}, enable Snapshot Variables.
  3. Second LogDebug (after HTTP 2): Author name: {{userName}}, enable Snapshot Variables.
  4. Run and compare the two snapshots — notice how new variables appear as the workflow progresses.
