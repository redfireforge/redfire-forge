Conversion: Test → Parameterized Test

When dev clicks "Convert to Parameterized Test":

  1. Creates a new Parameterized Test scenario
  2. Copies: URL, method, headers, auth, params from the original test
  3. Opens the Wizard (Step 1: Path Variables) with the existing URL pre-loaded
  4. Original test is preserved (not deleted) — you keep both

The original Test remains useful for quick single-request debugging. The Parameterized Test is for regression with many inputs.

Why Sample Rows?

  • QA sees exactly what format is expected (no guessing)
  • Demonstrates edge cases: VIN with 0 offers, VIN with 3 offers, different markets
  • Shows that empty expect cells = "skip validation" (not an error)
  • Reduces back-and-forth between dev and QA
  • Sample rows are auto-populated from real API response — guaranteed correct

FValidation Modes for Parameterized Tests

The same three validation modes from the Validation tab apply to parameterized data-driven tests. Dev chooses the mode in Wizard Step 3.

Body Validation Compare the response body against expected JSON

Mode 1: No Body Validation

Only assertions (status code, response time, headers) run per row. No expected response body comparison. No expect: columns in the CSV.

Step 3 UI (No Body Validation selected)

Field selection tree is hidden. Only the assertions section is shown:

Assertions (run on every row)

STATUS = 200 TIME ≤ 500ms HEADER content-type contains json

CSV Format (No Body Validation)

path:vin,param:market
1HGCM82633A004352,US
5YJSA1E26MF123456,US
JN1TBNT30Z0000001,JP

No expect: columns. Each row only tests: Did the request succeed (status 200)? Was it fast enough? Correct content-type?

Sample Row Creation (No Body Validation)

No fetch needed — dev just enters input values (VIN, market). No expected response to capture.

Use Cases

  • Smoke testing / connectivity checks across many inputs
  • Performance/SLA testing (just checking response time per VIN)
  • Responses are too dynamic to validate body (random IDs, timestamps everywhere)

Mode 2: Full JSON Match

The entire response body is compared against an expected JSON per row. Deep recursive comparison — every field must match.

Use Cases

  • Large/complex responses — only validate what matters

  • QA-friendly — individual columns are easier to fill than full JSON blobs
  • Flexible — empty cells mean "skip" for that field on that row
