SLA Per Group — Workflow Run Specifics

Focuses on the workflow load test case: many Tests in one Scenario or across several Scenarios. Shows how SLA evaluation should work per grouping mode (Step → Iteration vs Scenario → Step).

Scenario: Workflow "E-Commerce Journey" load test — 50 VUs × 20 iterations = 1 000 executions per step. Group mode = workflowStep → iteration. Each step row shows aggregated metrics across all iterations for that step.

SLA targets are scoped by scenarioName = step display name (e.g. "Add to Cart"). The same scenarioName that the step node writes on every RequestResult.
  • Step "Add to Cart" → scenarioName: "Add to Cart" target → evaluates against that step's metrics
  • Step "Checkout" → scenarioName: "Checkout" target → evaluates against checkout metrics
  • Step "Search Product" → no target → ⚫ neutral

Key: SLA dots appear only on the Step rows. Iteration rows show ⚫ because SLA is defined at step level — it's the aggregate across all iterations of that step that's evaluated, not each individual iteration. This is correct: you want to know if "Checkout" as a whole breaches SLA, not whether iteration #7 was slow.
Same workflow, now grouped by Iteration → workflowStep. Each iteration row aggregates metrics across all steps that ran in that iteration.

Challenge: SLA targets are scoped to step names (scenarioName). An "iteration" groups results from different steps with different SLA contracts. There's no single SLA contract that applies to the whole iteration — so the iteration row shows the worst status among all steps with targets in that iteration.
Recommended display rule for iteration rows: show the worst child step SLA status (same as Option A rollup). If no child step has a target, show ⚫. This gives a quick "did this iteration have any SLA problem?" signal.

Use this to decide which option to implement. Answer the questions top to bottom.
Question Option A (rollup) Option B (scoped)
Do you need different thresholds at feature vs test level? No — all levels use the same test-level threshold rolled up Yes — each level can have its own contract
Schema / storage change required? None — deploy today Add featureGroupName + groupName to SlaTarget (backward-compat)
Editor complexity None — editor unchanged Add scope-level selector + name dropdown
Works for workflow runs (step grouping)? Yes — step row dot = step's own target status Yes — same; step targets use scenarioName as before
Works for iteration grouping? Yes — iteration dot = worst child step Yes — same rollup for iterations (no iteration-level targets needed)
What happens when a feature has no SLA targets? ⚫ if no child tests have targets; color if any child has a target ⚫ on feature row; children may still have dots
Can a feature row show 🔴 while all its test rows show 🟢? No — feature status is always worst of children Yes — feature target can be stricter or measure different metric
Implementation effort Small: ~1 utility fn + 1 column in the table Medium: schema + 2 utility fns + editor UX + column
Recommended when… You want immediate visual feedback with minimal effort. Good for 80% of use cases. You have formal SLA contracts per service area / feature, and different teams own different levels.
Recommendation: Start with Option A (rollup dots). It covers workflow runs perfectly (step row = step's SLA), covers the common test-run case (feature shows worst child), requires zero schema changes, and ships fast. Implement Option B later if users ask for feature/group-level targets explicitly — the schema change is additive and backward-compatible when you're ready.
