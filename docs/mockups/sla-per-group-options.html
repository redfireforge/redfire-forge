SLA Per Test Group — Option Comparison

Three approaches to showing SLA status at the Feature → Group → Test level. Each tab shows a fully rendered mockup so you can compare the trade-offs before implementation.

📍 Current State — no per-group SLA display
The SlaDashboard is a separate panel above the results table. It shows either aggregate checks (no scenarioName set) or per-scenario checks when scenario-scoped targets exist. The results table rows have no SLA indicator at all — you must scroll up to the SLA panel to see status.

Problem: When you're reading the results table, you have no idea which rows have SLA violations. You must scroll back up to the panel. In a long results table with 20+ tests, this is painful.
✅ Option A — Inline rollup dots (no schema change)
SLA targets stay exactly as they are today (scoped by scenarioName). A new SLA column is added to the results table. Each row shows the worst SLA status across all tests within that group — a simple rollup.
  • Feature row = worst of all its tests
  • Group row = worst of all its tests
  • Test row = its own SLA status (from SlaDashboard, same logic)
  • No SLA target → ⚫ neutral dot
No change to SlaTarget schema. No change to editor. Just a new column.

✓ Pros

  • Zero schema change — deploy immediately
  • Intuitive: feature turns red if any child fails
  • Works for both test runs and workflow runs
  • SLA panel above stays unchanged

✗ Cons

  • Can't set different thresholds per feature/group
  • Feature "inherits" child SLA — can't ignore noisy tests
  • Dot has no tooltip detail unless you hover

⚙️ Option B — Scoped targets (schema extension + richer editor)
SlaTarget gains two new optional fields: featureGroupName and groupName. You can now set different thresholds at each level of the hierarchy. The editor shows a two-part Scope column: level selector (Aggregate / Feature / Group / Test) and a name dropdown populated from the run's actual results. The SLA column in the results table shows the targets that apply to exactly that level — not a rollup.
  • A "Feature" target with featureGroupName: "Shopping Cart" evaluates all results in that feature
  • A "Group" target evaluates all results in that group
  • A "Test" target = existing scenarioName behaviour

✓ Pros

  • Full control — different p95 thresholds per level
  • Can skip SLA for noisy tests while keeping feature-level SLA
  • Clean model: each dot in the table is directly owned by a target

✗ Cons

  • More complex editor — two dropdowns per target row
  • Schema change (additive, backward-compat, but still a change)
  • More targets to maintain; easy to have overlapping/conflicting scope
